# Errata of U2 (Memory and Stack panels)

Where `docs/ARCHITECTURE.md` or a spec is silent, ambiguous or cannot be met as written for the
Memory and Stack panels, what the code in `app/src/features/memory/` and `app/src/features/stack/`
does, and why. No entry changes a declaration of `app/src/contracts/`.

## Contract

### C1. Nothing tells the other panels that the Memory panel wrote memory (3.11.2, 4.6, sim-ui §10.3)

- Says: `RunController.pokeMemory(address, value)` is "Memory panel: direct write". The original then
  calls `Hardware->updateIfNeeded(addr)`, `StackFrm->DisplayStack()` and repaints the memory window;
  10.3 adds that "the port simply repaints its Hardware panel after `pokeMemory`". Nothing says how
  the Stack panel learns of the write: `engine.writeBytes` and `engine.memory` make no host call.
- Does: after every typed byte (through `pokeMemory`) and after Copy and Fill (through
  `controller.invoke(engine => engine.writeBytes(...))`, inside the invoked function) the Memory
  panel bumps `AppState.sim.liveRevision`, whose documented meaning is "memory / hardware changed".
  The Stack panel redraws on a `liveRevision` change without re-centring (sim-ui §11.4), except while
  `sim.phase` is `running` (the original's window is frozen during a run).
- For SH8: if `pokeMemory` also bumps `liveRevision`, the panels repaint twice; that is harmless.
  The Hardware refresh after `pokeMemory` (10.3) remains SH8's (for example
  `hardware.hardwareUpdate()` inside `pokeMemory`); Copy and Fill do not refresh the Hardware panel,
  as in the original (sim-ui §10.5).
- Proposed text for 3.11.2: "`pokeMemory` writes the byte, refreshes the Hardware panel and bumps
  `liveRevision`; interface code that writes memory with `invoke(... writeBytes ...)` bumps
  `liveRevision` itself."

### C2. `viewRevision` does not say which panels the engine named (4.6, 3.12.1)

- Says: 4.6, "`repaint(what)` ... `afterEngineCall()` bumps `viewRevision`; the panels named by the
  `RepaintBit`s (Listing, Break Points, Memory, Stack) re-read their data." `AppState.sim` has only
  the one counter.
- Does: both panels treat every `viewRevision` change as their own repaint: the Memory panel
  re-reads its rows, the Stack panel runs `updateDisplay()` (re-centres). A repaint that names only
  the listing or the Break Points window (a breakpoint set from the gutter) therefore also re-centres
  a Stack panel the user had scrolled. No program can observe this.
- Proposed change (W1, SH8): carry the bits, for example `sim.repaintBits` next to `viewRevision`.

### C3. `memoryLivePaint` has no way to reach the panel (4.6)

- Says: 4.6, "`memoryLivePaint(address)` ... The panel records the row as dirty; once per frame
  `publishRevisions()` bumps `liveRevision` if a visible row is dirty." The host belongs to SH8 and
  knows neither the panel nor its visible rows; no contract carries the address.
- Does: while `Live` is checked, the Memory panel compares its visible bytes with the engine's
  memory once per display frame (`ctx.scheduler.onFrame`) and repaints if one differs - the
  "redraw visible rows that changed" that sim-ui §10.4 allows. It needs nothing from the host, and it
  works while the top row is address 0 (parity matrix 1.3.7, ~38). The panel still sets
  `SimOption.MemLive` through `controller.invoke` while `Live` is checked, as 4.6 says.

### C4. The Registers panel's double-click needs a way to set the Address field (3.11.3, sim-ui §4.4)

- Says: "double-click on an address-register field copies its text to the Memory panel's Address
  field and shows that panel." Features may not import each other (3.1).
- Does: `sim.view.memory` takes an optional argument, a number or the register field's hex text:
  `ctx.commands.run('sim.view.memory', boxText)`. The address is masked to 24 bits and rounded down
  to 16 (the Address field holds six digits). Without an argument it only shows the panel.

## Specification

### S1. `File exists! OK to replace?` is not asked by the panel (sim-ui §10.5, 3.8.5)

- Says: sim-ui §10.5, after the Save dialog, "if the file exists a box titled `Alert` asks `File
  exists! OK to replace?` (Yes / No)". 3.8.5: `FileDialogs.save` resolves with the path, "overwrite
  already confirmed".
- Does: the file dialog's own question replaces the original's; the panel does not ask a second time
  (the same rule as the editor's Save, parity matrix 1.3.3: "the overwrite question is asked by the
  port only where the platform's own dialog does not ask"). The other three messages
  (`Invalid copy range` and `Invalid memory range` titled `SIM68K`, `Invalid memory range.` titled
  `Information`) and `Error saving 68K memory to file.` (title `Information`, information icon) are
  shown as in the original. `SIM68K` is `Application->Title` (sim-ui §1.1), the title of a VCL
  `ShowMessage` box.

### S2. Beeps

- The original beeps for a refused key and before `Invalid memory range.`. The application has no
  beep service (only `TextScreenDeps.beep`, which belongs to the Output panel); the panels stay
  silent.

### S3. Where the Address field sits (2.6, sim-ui §10.1, the sketch of 2.3)

- 2.6 and sim-ui §10.1 put the field directly above the address column; the sketch of 2.3 shows
  `Address: $00[001000] From: ...` in the top strip and the column header alone on the next line.
  The kit's field with its `00` box is wider than the ten-character address column, which would push
  the header out of line with the hex columns. The panel follows the sketch: the field is the first
  control of the strip, the header line is aligned with the rows.

### S4. Rows of the Memory panel are whole: never half below and half beyond MEMSIZE

- Not an erratum, a note for testers: the top row is a multiple of 16 and so is MEMSIZE, so a row is
  either entirely valid or entirely red.

### S5. The Stack panel keeps C `int` arithmetic

- `stackAddr -= stackAddr % 2` rounds a negative `int` (a register value of $80000000 or more) up
  instead of down, and `AregAddr` is compared unmasked. The rules reproduce both (`stack/rules.ts`);
  no program can observe them.

## Notes for other packages

- U1 (Registers panel): use `ctx.commands.run('sim.view.memory', text)` for the double-click (C4).
- SH8: see C1 (Hardware refresh after `pokeMemory`) and C2.
- H1: the original's F1 contexts are `MEMORY` and `STACK`; the panels' regions are
  `data-e68-panel="memory"` and `"stack"` (the shell's), which a context-help handler can use.
