## 1. Where this package differs from ARCHITECTURE.md, and why

1. **Committed form of the `.pix` references (6.5.3, 6.2.3).** The capture program writes one `.pix`
   file per case, byte for byte as 6.5.3 specifies (`build/gdi-capture/run/pix/`). The repository
   holds them packed, one gzip file per suite: `tests/conformance/gdi/golden/<suite>.pixpack.gz`
   (format in `tests/conformance/gdi/pix.ts`: "E68R", a JSON header with each case's id and GDI's
   pen position, then the `.pix` files unchanged). 26,000 files would make the repository and every
   checkout slow; the packs are 0.85 MB in all. The pen position after each case, which 6.5.3 asks
   to be compared and the `.pix` format cannot hold, travels in the pack header. The folder is named
   `golden/` because Prettier and the repository already treat `**/golden/` as byte-exact content.

2. **Raster atlases (3.5.1 "every distinct pixel size and style Windows produces").** All of them
   would be 26 MB (Courier and Fixedsys reach 200 and 120 pixel cells, in five styles). GDI makes
   them from a few native sizes by whole-number pixel repetition (independent factors: Fixedsys
   40x90 is 8x15 times 5 and 6) and simulates the styles on the scaled glyph, by four simple rules.
   The capture checks those rules against GDI for every face, style and size and stores a cell as an
   atlas of its own only if no rule reproduces it; on Windows 11 every cell is reproduced. So
   `app/public/fonts/bitmap/` holds 25 atlases (230 KB): the native plain cells (Fixedsys 8x15;
   Courier 8x13, 9x16, 12x20, 15x25) and the four styles at each native size. `metrics.json` has a
   new section `raster` with the rules (`raster.rules`) and, for every raster face/style/plain cell,
   the native atlas, `kx`, `ky`, the underline or strike-out rows and the control bytes whose line
   has another length (`raster.cells`). **For SH3:** 3.5.1's provider rule "resample by whole-number
   repetition" is the `plain` rule; styled cells must be made with the stated style rule after the
   repetition, not by repeating a styled native atlas (bold adds one pixel after scaling, italic
   shears after scaling, underline rows scale with the cell).

3. **Outline atlases (3.5.1 "at 8-18 pt and at 24, 36, 48, 72 pt", in every style).** All of them
   are 75 MB of 8-bit coverage (Arial 72 pt alone is 13 MB). Stored: plain, bold and italic at 8, 9,
   10, 11, 12, 14, 16, 18, 24 and 36 pt (14 MB). Not stored: 48 and 72 pt (the provider resamples
   the nearest atlas, as 3.5.1 already does for every other size) and the underline and strike-out
   atlases: those are the plain glyph plus a line, and `scalable/index.json` gives the line of each
   plain atlas as `underline: [top, height]` and `strikeOut: [top, height]` in cell rows, drawn
   across the glyph's advance. Note that Windows draws the TrueType underline **below** the cell
   (Courier New 9 pt: cell rows 0-14, underline row 15), so it cannot live in a cell-high atlas
   anyway. Same rule for raster and outline faces: underline/strike-out = plain + line.
   Round 1 of the verification asked for 48/72 pt or a gate decision: kept as recorded (storing
   plain 48 and 72 pt alone would add about 10 MB). **For SH3's provider:** a request above 36 pt
   resamples the 36 pt atlas of the same face and style to the cell of `metrics.json`; underline and
   strike-out are drawn from `index.json`'s line over the plain glyph. Left to the gate (I1).
   Round 2 of the review recorded the same and proposed that the gate accept this erratum; unchanged.

4. **`metrics.json` fields beyond 6.5.3.** `faces` and `fonts` are as specified; the style keys are
   `plain`, `bold`, `italic`, `underline`, `strikeOut` (the names of `FontSpec`). Added: `about`,
   `faceKinds` (`raster` or `outline`, parallel to `faces`) and `raster` (item 2).
   `scalable/index.json` lists the outline atlases (a browser cannot list a folder).

5. **Atlas file names.** `<face>` is the face name with spaces replaced by `_` (`Courier_New-16.bin`).
   When two point sizes give the same cell height but different widths, the second file is named
   `<face>-<height>x<width>[-<style>].bin` (one case: `Courier_New-16x8-b.bin`). Providers should
   take file names from `metrics.json` / `scalable/index.json`, not build them.

6. **Underline and strike-out in metric capture (3.5.1 last bullet).** The positions come from
   `GetOutlineTextMetrics` (`otmsUnderscorePosition/Size`, `otmsStrikeoutPosition/Size`) and are in
   `tools/fonts-src/windows-outline-metrics.tsv`, which `tools/make-font-atlases.mjs` reads.

7. **`@napi-rs/canvas` is not used.** `make-font-atlases.mjs` has its own TrueType reader and
   area-coverage rasteriser (no hinting), so that the output does not depend on Skia's platform
   font back-ends; `--check` regenerates and compares, and `tests/conformance/gdi/atlases.test.ts`
   runs it on every platform of the conformance job. The dependency can be dropped at a gate.

8. **Inconsolata has no italic**; the tool slants the regular glyphs (x += 0.2 * height). Consolas
   italic is therefore a synthetic oblique.

9. **Glyphs are fitted into Windows' cell (round 1).** DejaVu Sans Mono is taller than Lucida
   Console's cell, so the accents of capitals were cut off above row 0 (É looked like E). The tool
   now fits every glyph into the cell: where there are at least 2 pixels between the cap height and
   the cell top, only the part of an overflowing glyph above the cap height is compressed into that
   room; with less room (Lucida Console at most sizes) the whole atlas is scaled vertically so that
   its tallest glyph reaches the cell top; ink below the cell is compressed towards the baseline.
   This changed 30 Lucida Console, 8 Arial and 6 Courier New atlases. `atlases.test.ts` checks that
   accented capitals differ from their base letters in every atlas.

10. **`$7F` on the fallback path (gate I1 round 2).** `windows-outline-metrics.tsv` has a last column
    `delInHighString`, and each entry of `scalable/index.json` a field of the same name: the width
    Windows gives `$7F` in a string that also has a byte of `$80` or above, measured as
    `TextWidth($80 $7F) - TextWidth($80)`. See section 2.

    2-255: the dot of a one-point rectangle, a zero-length line and a one-point ellipse (762 cases);
    for every width 13-255 a horizontal and a vertical bar and a frame, filled and unfilled; the
    vertical bar of width 206 at two lengths (974 cases). 52 KB. SH1's surface equals all 1,228
    rectangle cases; the 508 line and ellipse dots wait for SH2 like the other SH2 cases.

    `surface.test.ts` used to probe the Surface for ellipses and 21-pixel dots to decide whether to
    run SH2's comparisons; SH1's stubs pass both probes, so the comparisons ran and failed in CI.
    Now a case waits for SH2 when it has an ellipse or a line drawn with a pen 2 or more pixels wide
    (3.4 rules 4 and 6) and the file that draws it (`surface/ellipse.ts`, `surface/widepen.ts`)
    still starts its header with `// STUB written by SH1`. Waiting cases are reported as skipped tests
    named with their count and reason (2,848 today), and a summary line counts them. When SH2 replaces
    a file, its header changes and its cases are compared from then on. Wide rectangle frames are
    SH1's (3.4 rule 5) and are compared now (all equal).

13. **Another Windows (gate I1 round 2).** The first CI run of `windows-oracles` (Windows Server,
    build 10.0.26100; the references come from 10.0.26300) stopped with "no rule reproduces Courier
    italic 9x16": on that Windows four raster cells are not made by the rules of item 2. The capture
    used to throw there, before comparing anything. Now such a cell is written to `metrics.json` with
    `"ruleHolds": false` (so `metrics.json` differs and is reported like any other output), and what
    happens on a Windows other than the references' is decided by
    `tests/oracle/gdi-capture/windows-policy.ts`:
    - the committed references stay the standard: `--write` refuses on another Windows unless
      `--replace-references-from-other-windows` is given;
    - on the references' Windows every difference fails (GDI or the program changed);
    - on another Windows the differences must be exactly those recorded for it in
      `tests/oracle/gdi-capture/other-windows.json`; a new or changed one fails (that Windows
      changed). With no record every difference fails, and the run prints the record to add (also to
      the GitHub job summary) once a person has looked at the differences and accepted them.
    Reasons: a different Windows rendering differently is not evidence that the references are
    wrong, so it must not replace them; passing over the differences would hide that nothing was
    verified; and a record per Windows keeps CI's drift detection working on the runner's Windows
    too. What exactly differs on 10.0.26100 is not known here (the capture stopped at the first
    cell; no such Windows is available to this package); the next CI run lists it.

25. **6.5.3 "control bytes in task 95 - every pixel equal for the raster faces" has no single truth
    for the bytes `$01-$08 $0B $0E-$1B` (gate I3, release-candidate item 3; the architect's rule,
    outcome (2)).** The suite `text-control` was captured on two Windows: the references (Windows 11
    10.0.26300) and the `gdi-capture-run` artifact of CI run 44919519853 (GitHub's Windows Server
    10.0.26100; both 96 DPI, code page 1252, ClearType on, contrast 1200, RGB). That artifact's 252
    `text-control` captures are now committed as `golden/windows-10.0.26100/text-control.pixpack.gz`
    (28 KB; every case definition of its `cases.txt` equals `cases.ts` today, 252 of 252). Compared
    case by case (`machine-dependent.test.ts`, "the suite text-control on both Windows"):
    - **The 90 cases with a byte of `$01-$08 $0B $0E-$1B`** (Fixedsys 0, 9, 18, 30 and Courier 0,
      10, 12, 15, 19, 20, 36, all five styles): the two Windows draw **72 of 90 differently**. What
      differs is the glyph and the width of the cell the byte fills, not the pen. Fixedsys 9 `"A" b
      "B"`: 10.0.26300 fills 4 pixels for b (5 for `$02`) and paints a narrow box with ClearType
      colour fringes (on a red fill the box pixels are `$FFB6DB`, `$FFB6B6`, `$FFDBB6`, ...);
      10.0.26100 fills 6 pixels (12 for `$01`) and paints other, unsmoothed shapes (`$01` nothing,
      `$02` a hook). `spots.json` `controlBytes`: `cellRight` 20 against 22 (28 for `$01`) for every
      one of these bytes, `pen` 24 on both. The raster atlases (single bytes at the native cells,
      every style) differ in these glyphs in 22 of 25 atlases (10.0.26300's atlases hold no ink for
      the boxes, 10.0.26100's hold its shapes; Courier 8x13 plain, bold and italic are equal); the advances are equal in all 25. The pen after the text is equal in **85 of
      90**; in the 5 others (`-00089 -00103 -00113 -00114 -00124`, each with a byte of `$80` or above
      too) the two Windows are 4 to 9 pixels apart. The 18 equal pictures are cases whose fallback
      glyph is clipped or drawn over.
    - **The 162 other cases** (undefined bytes, `$0C`/"@"/`$80`, italic itemization, the zero-width
      bar): picture and pen equal on both Windows, 162 of 162. Their place in `text-control` means
      "not modelled by `text-model.ts`", not "machine-dependent"; this comparison finds no machine
      dependence in them.

    So what Windows draws for these bytes is a property of the Windows installation (which fallback
    font it links, and its ClearType rendering), not of the original program or its fonts, and no
    implementation can be "every pixel equal" to Windows for them. The port keeps its documented
    choice (a blank cell of the face's own advance; `docs/differences/SH3.md`): the reference
    machine's picture cannot be shipped exactly, because it is ClearType output whose colours depend
    on the font and fill colours and on the user's smoothing settings, and its cell widths were
    captured for Fixedsys 9 only. What holds instead, and is tested
    (`app/src/core/sim-host/text/gdi-references.test.ts`; `check-text.mjs` under Node, the browsers
    giving the Node run's pictures): the pen equals Windows in every case in which the two Windows
    agree (85 of 85), and every pixel and the pen in every case in which they draw the same picture
    and pen (16 of 16). ARCHITECTURE.md 6.5.3 has the correction note. **Not covered by the
    evidence:** the official SIM68K.exe itself was never run on Windows (these are this package's
    capture program making the VCL's GDI calls, as for every reference); only two Windows builds,
    both of the Windows 11 generation (no Windows 10); no capture with font smoothing off (that the
    setting changes the pixels follows from the colour fringes, but was not captured); Wine draws no
    Fixedsys and says nothing here.
26. **Windows' Unicode text path in the raster faces: the 162 other `text-control` cases, measured
    and captured (gate I3, release-candidate item 3, second part).** The original draws task 95 with
    `TCanvas.TextOut`, that is `ExtTextOutA(dc, x, y, 0, NULL, text, length, NULL)` with the brush
    realised (`SetBkMode(OPAQUE)`), and the text grid with the same call for one byte (trap15-b 6.7,
    `simIOu.cpp` 865-911). For a text with one of the bytes below, Windows' `ExtTextOutA` and
    `GetTextExtentPoint32A` do not draw the raster face directly: they convert the text to Unicode
    and lay it out with Uniscribe (Windows' complex-script text path, LPK / `usp10`), which cuts it
    into items by script (`ScriptItemize`), gives control characters glyphs of no width, and takes
    the characters the face has no glyph for from a fallback font (`SSA_FALLBACK` of
    `ScriptStringAnalyse`). The itemization and the font fallback are documented Uniscribe
    behaviour; which bytes send a text down the path, and what it then paints, are not documented
    and were measured with this program (about 20,000 experimental
    cases in `build/I3-item3b/exp`, then the suites below). The bytes that take a text down that
    path: the zero-width bytes `$09 $0A $0D $1C-$1F`, `$7F`, the five undefined bytes (Windows makes
    them the C1 controls U+0081 etc.) and `$86 $87 $88 $98`. What the path changes, in plain, bold,
    italic, underline and strike-out at every size the suites cover:
    - **The zero-width bar.** At 29 requested Fixedsys sizes and 52 Courier sizes (exactly
      `ZERO_WIDTH_BAR_SIZES`; independent of the byte and of plain, bold, italic; never in underline or
      strike-out) a text made only of zero-width bytes is drawn as the opaque box of a glyph of no
      width from the fallback font: 3 pixels wide from x - 1, as high as the fallback font's cell, which
      depends only on the face's cell (Fixedsys 30 → 29, 45 → 44, 60 → 59, 75 → 74, 90 → 89, 120 → 118;
      Courier 13 → 13, 16 → 15, 20 → 20, 32 → 31, 60 → 59, 75 → 74, 80 → 79, 100 → 98, 150 → 148,
      175 → 172), clipped like any box. It is drawn so **when the text has an odd number of bytes or
      two `$1F` in a row**; otherwise the first byte's cell (11,925 of 11,925 captured texts of
      zero-width bytes only agree: one to twelve bytes at nine bar sizes and two other sizes, and a
      lone `$0D` at every raster size in every style). With any other byte in the text there is no bar. The pen
      is not affected. capture.cpp measures the bar of a lone `$0D` at every raster size and style
      into `text-path.tsv`, and `run.mjs` writes it to `metrics.json` `raster.textPath.zeroWidthBar`

## 4. Contract

- `SurfaceApi.textOut(x, y, glyphs, extent, fontColor, target)` has no separate width for the opaque
  cell. GDI fills the sum of the **drawn** advances (zero-width control bytes take none) and moves
  the pen by `TextWidth`, which counts them. The tests assume the surface fills `sum(glyph.advance)`
  and moves the pen by `extent`, that the caller leaves zero-width bytes out of `glyphs`, and that a
  string of zero-width bytes only is passed as one blank glyph of one cell plus the style overhang
  (GDI fills that much then). If SH1 or SH3 read the contract differently, W1 should make it explicit.
- Not a contract defect, a limit: per-byte advances of the proportional face (Arial) are known only
  at the atlas sizes (in the atlases). At other sizes the provider can only scale them, so the pen
  after task 95 with `Lucida Sans Typerwriter` or `Terminal` at such a size may differ from Windows.
  Adding Arial's 256 advances for every size and style to `metrics.json` (about 1.2 MB) would close
  it; left for a decision.
