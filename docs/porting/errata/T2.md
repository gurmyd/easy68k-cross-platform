# Errata and notes of work package T2 (GDI capture, references, fonts)

Measured on Windows 11 build 10.0.26300, 96 DPI (the capture is DPI-unaware), ClearType on, ANSI
code page 1252, with `npm run oracle:gdi` (tests/oracle/gdi-capture). Every number below is in the
committed references and is checked by `tests/conformance/gdi/golden.test.ts`.

## 1. Where this package differs from ARCHITECTURE.md, and why

1. **Committed form of the `.pix` references (6.5.3, 6.2.3).** The capture program writes one `.pix`
   file per case, byte for byte as 6.5.3 specifies (`build/gdi-capture/run/pix/`). The repository
   holds them packed, one gzip file per suite: `tests/conformance/gdi/golden/<suite>.pixpack.gz`
   (format in `tests/conformance/gdi/pix.ts`: "E68R", a JSON header with each case's id and GDI's
   pen position, then the `.pix` files unchanged). 26,000 files would make the repository and every
   checkout slow; the packs are 0.85 MB in all. The pen position after each case, which 6.5.3 asks
   to be compared and the `.pix` format cannot hold, travels in the pack header. The folder is named
   `golden/` because Prettier and the repository already treat `**/golden/` as byte-exact content.

2. **Raster atlases (3.5.1 "every distinct pixel size and style Windows produces").** All of them
   would be 26 MB (Courier and Fixedsys reach 200 and 120 pixel cells, in five styles). GDI makes
   them from a few native sizes by whole-number pixel repetition (independent factors: Fixedsys
   40x90 is 8x15 times 5 and 6) and simulates the styles on the scaled glyph, by four simple rules.
   The capture checks those rules against GDI for every face, style and size and stores a cell as an
   atlas of its own only if no rule reproduces it; on Windows 11 every cell is reproduced. So
   `app/public/fonts/bitmap/` holds 25 atlases (230 KB): the native plain cells (Fixedsys 8x15;
   Courier 8x13, 9x16, 12x20, 15x25) and the four styles at each native size. `metrics.json` has a
   new section `raster` with the rules (`raster.rules`) and, for every raster face/style/plain cell,
   the native atlas, `kx`, `ky`, the underline or strike-out rows and the control bytes whose line
   has another length (`raster.cells`). **For SH3:** 3.5.1's provider rule "resample by whole-number
   repetition" is the `plain` rule; styled cells must be made with the stated style rule after the
   repetition, not by repeating a styled native atlas (bold adds one pixel after scaling, italic
   shears after scaling, underline rows scale with the cell).

3. **Outline atlases (3.5.1 "at 8-18 pt and at 24, 36, 48, 72 pt", in every style).** All of them
   are 75 MB of 8-bit coverage (Arial 72 pt alone is 13 MB). Stored: plain, bold and italic at 8, 9,
   10, 11, 12, 14, 16, 18, 24 and 36 pt (14 MB). Not stored: 48 and 72 pt (the provider resamples
   the nearest atlas, as 3.5.1 already does for every other size) and the underline and strike-out
   atlases: those are the plain glyph plus a line, and `scalable/index.json` gives the line of each
   plain atlas as `underline: [top, height]` and `strikeOut: [top, height]` in cell rows, drawn
   across the glyph's advance. Note that Windows draws the TrueType underline **below** the cell
   (Courier New 9 pt: cell rows 0-14, underline row 15), so it cannot live in a cell-high atlas
   anyway. Same rule for raster and outline faces: underline/strike-out = plain + line.
   Round 1 of the verification asked for 48/72 pt or a gate decision: kept as recorded (storing
   plain 48 and 72 pt alone would add about 10 MB). **For SH3's provider:** a request above 36 pt
   resamples the 36 pt atlas of the same face and style to the cell of `metrics.json`; underline and
   strike-out are drawn from `index.json`'s line over the plain glyph. Left to the gate (I1).


4. **`metrics.json` fields beyond 6.5.3.** `faces` and `fonts` are as specified; the style keys are
   `plain`, `bold`, `italic`, `underline`, `strikeOut` (the names of `FontSpec`). Added: `about`,
   `faceKinds` (`raster` or `outline`, parallel to `faces`) and `raster` (item 2).
   `scalable/index.json` lists the outline atlases (a browser cannot list a folder).

5. **Atlas file names.** `<face>` is the face name with spaces replaced by `_` (`Courier_New-16.bin`).
   When two point sizes give the same cell height but different widths, the second file is named
   `<face>-<height>x<width>[-<style>].bin` (one case: `Courier_New-16x8-b.bin`). Providers should
   take file names from `metrics.json` / `scalable/index.json`, not build them.

6. **Underline and strike-out in metric capture (3.5.1 last bullet).** The positions come from
   `GetOutlineTextMetrics` (`otmsUnderscorePosition/Size`, `otmsStrikeoutPosition/Size`) and are in
   `tools/fonts-src/windows-outline-metrics.tsv`, which `tools/make-font-atlases.mjs` reads.

7. **`@napi-rs/canvas` is not used.** `make-font-atlases.mjs` has its own TrueType reader and
   area-coverage rasteriser (no hinting), so that the output does not depend on Skia's platform
   font back-ends; `--check` regenerates and compares, and `tests/conformance/gdi/atlases.test.ts`
   runs it on every platform of the conformance job. The dependency can be dropped at a gate.

8. **Inconsolata has no italic**; the tool slants the regular glyphs (x += 0.2 * height). Consolas
   italic is therefore a synthetic oblique.

9. **Glyphs are fitted into Windows' cell (round 1).** DejaVu Sans Mono is taller than Lucida
   Console's cell, so the accents of capitals were cut off above row 0 (É looked like E). The tool
   now fits every glyph into the cell: where there are at least 2 pixels between the cap height and
   the cell top, only the part of an overflowing glyph above the cap height is compressed into that
   room; with less room (Lucida Console at most sizes) the whole atlas is scaled vertically so that
   its tallest glyph reaches the cell top; ink below the cell is compressed towards the baseline.
   This changed 30 Lucida Console, 8 Arial and 6 Courier New atlases. `atlases.test.ts` checks that
   accented capitals differ from their base letters in every atlas.

## 2. trap15-tasks-60-up.md: one disagreement, many confirmations

**Disagreement, 6.3 case B in non-Copy modes.** The spec says "Each pixel is combined once (outline
and interior do not overlap ...)". That holds for case A, but not for case B (`x1 == x2` or
`y1 == y2`, not both) at pen width 0 or 1: GDI's outline then has two coinciding sides, and the
pixels of the run are combined **twice**, except the two end pixels, which are combined once.
In Copy mode this is invisible; in XOR mode the inside of the run disappears and only its two end
pixels change (rects-00707: mode 15, `(22,23)-(69,23)` changes only pixel (22,23)). Checked for every
width-0/1 rectangle of the `rects` suite in modes 3, 6, 9, 14 and 15 (golden.test.ts, "6.3 in
non-Copy modes"). **For SH1:** the 16 `rects`, 15 `modes` and 1 `polylines` cases its surface fails
today are all this rule. Wide-pen case B in non-Copy modes was not separately analysed (SH2).

Confirmations:

- **4.6**: the 20 stock palette entries exactly as listed; index 20 and above black; only the low 16
  bits select the entry (`$01010005` = entry 5, `$0100FF05` = black); other even top bytes give
  RGB; system colours 5, 8, 15 = `$FFFFFF`, `$000000`, `$F0F0F0`, indices above 30 black. The full
  `GetSysColor` table of the capture machine (theme dependent) is `golden/spots.json` `sysColors`
  (**for SH1**: the "others as captured by T2" of 3.4 rule 1).
- **5.4**: the 16 operations with D = `$336699`, pen `$0F0FF0`, brush `$F0F00F` give exactly the
  table's formulas on lines, pixels, outlines and interiors; a raw ROP2 value v acts as
  `((v - 1) AND 15) + 1` for all v 0-255 (0 = white).
- **5.7**: Fixedsys 8x15 for 0 and 8-16 pt, 16x30 at 18 pt; Courier 10/12/15 pt = 8x13, 9x16,
  12x20; Courier New, Lucida Console and Consolas at 8-18 pt exactly as listed; `Lucida Sans
  Typerwriter` and `Terminal` are answered with Arial.
- **6.1**: all 10,000 width-1 lines of the `lines` suite equal the formula, pen position included.
- **6.2**: dot diameters 1, 3, 3, 5, 5, 7, 7, 9, 9, 11, 11, 13, 13 and pixel counts 1, 5, 9, 21, 21,
  37, 45, 61, 69, 89, 101, 129, 145 for widths 2-14; widths 0 and 1 draw one pixel.
- **6.3**: cases A and B at widths 0-12 and case C at width 1 equal the rules for every Copy-mode
  rectangle of the `rects` suite (8,000+ cases).
- **6.7**: with Fixedsys, `'A', b, 'B'` paints 16 + 4 pixels of cell for the control bytes, 5 for
  `$02`, 8 for `$0C`, 0 for `$09 $0A $0D $1C-$1F`; the pen always moves 24. The bytes drawn as a
  narrow anti-aliased box are exactly `$01 $03-$08 $0B $0E-$1B` (they come from a fallback font, so
  their pixels depend on font smoothing; the text cases with them are the machine-dependent suite
  `text-control`).

### Additions to 6.7 (task 95 strings), found while checking the text references

Corrected after the verification of round 1: the first version said that a zero-width byte stops
counting in `TextWidth` with underline or strike-out. That fitted the sampled references only; fresh
captures showed the condition is a byte of `$80` or above, in every style. The `text` suite now holds
1,881 cases (strings with zero-width bytes with and without high bytes, in every style, at several
sizes, plus 400 random strings rich in both); the old rule gives another pen position for 444 of
them. `tests/conformance/gdi/text-model.ts` reproduces all of them pixel for pixel and pen for pen,
and random probes of about 12,000 further strings against fresh captures found no difference outside
the cases listed as not modelled. The rules beyond 6.7 (also in tests/oracle/gdi-capture/README.md):

- **TextWidth:** a zero-width byte (`$09 $0A $0D $1C-$1F`) in a string of two or more bytes counts 0
  when the string contains a byte of `$80` or above, and its full advance otherwise, in every style
  (`$1C "9"` underlined moves 16 in Fixedsys 9; `$1C $AA $1D $1D` plain moves 8). Checked in Courier
  New and Lucida Console too; Consolas' `$0D` has advance 0 by itself (in
  `windows-outline-metrics.tsv`).
- the opaque cell includes the style overhang of the raster faces: +1 for bold, +`floor((h-1)/2)`
  for italic (Fixedsys 9 italic "AB" fills 23 pixels, not 16); a string of zero-width bytes only
  fills the first byte's cell plus that overhang (bold `$0A` in Fixedsys 9: 10 columns);
- with italic, the overhang is left out when two or more bytes are drawn and the string contains a
  zero-width byte (trailing ones included) or contains `$7F` and a drawn byte other than `$7F`; the
  cell is then `max(drawn advances, first advance + overhang)` (Fixedsys 72 `"A" $0D "B"`: 84);
- `$02` is a fallback-font byte like the hollow-box ones: it paints nothing but takes 5 pixels in
  Fixedsys (6.7 says so), which is not its single-byte extent (8);
- not modelled (the cases go to `text-control`, predicate `textUnmodelled()` in `cases.ts`): the
  fallback-font control bytes; the five undefined Windows-1252 bytes (alone extent 0, `$80 $81`
  measures 7 in Fixedsys); `$0C`, `@` and `$80` in strings with one of `$7F $86 $87 $88 $98` or a
  zero-width byte (drawn from a fallback font, size-dependent width: `$80` 7 pixels in Fixedsys 9, 5
  in Courier 10, 58 in Fixedsys 72); italic strings with `$86 $87 $88 $98` (overhang decided by
  script itemization: `"A" $86` loses it, `"[" $86` keeps it); and strings of zero-width bytes only
  in plain, bold or italic at the requested sizes where Windows 11 draws a thin fallback bar instead
  of the cell (`ZERO_WIDTH_BAR_SIZES`: 20 Fixedsys and 26 Courier sizes between 3 and 110 pt).
- In the outline faces GDI widens the opaque cell by the first and last glyph's ink overhang
  (1-2 pixels at 8-18 pt, up to a tenth of the cell at large sizes), so a cell is not exactly the
  advance box there. The port cannot know Windows' ink extents without capturing ABC widths; the
  outline glyphs are substitutes anyway (3.5.1). Recorded, not reproduced.

**For SH3:** `app/src/core/sim-host/text/text-screen.ts` (as of this repair) still follows the first
version (trailing-run and underline conditions). The rules above replace it.

## 3. trap15-tasks-0-59.md §12 (UNVERIFIED items 1-3): answers

1. The full table of cell sizes for the seven names, five styles and sizes 0-255 is
   `app/public/fonts/metrics.json`.
2. **Bold changes the grid of the raster faces**: Fixedsys bold is 9x15 (71 columns on 640, not 80),
   Courier bold is one pixel wider than plain at every size. Italic, underline and strike-out do not
   change the cell. For the outline faces bold usually keeps the width.
3. `Lucida Sans Typerwriter` gets Arial (15x18 at size 0, 11x15 at 9 pt). Size 0: Fixedsys 8x15,
   Courier 9x16, Courier New 10x18, Lucida Console 10x16, Consolas 9x19, Arial 15x18. New: Windows
   gives up the raster faces for large sizes and uses Arial: Fixedsys from 122 pt, Courier from
   200 pt (both reachable by task 21's size byte).

## 4. Contract

- `SurfaceApi.textOut(x, y, glyphs, extent, fontColor, target)` has no separate width for the opaque
  cell. GDI fills the sum of the **drawn** advances (zero-width control bytes take none) and moves
  the pen by `TextWidth`, which counts them. The tests assume the surface fills `sum(glyph.advance)`
  and moves the pen by `extent`, that the caller leaves zero-width bytes out of `glyphs`, and that a
  string of zero-width bytes only is passed as one blank glyph of one cell plus the style overhang
  (GDI fills that much then). If SH1 or SH3 read the contract differently, W1 should make it explicit.
- Not a contract defect, a limit: per-byte advances of the proportional face (Arial) are known only
  at the atlas sizes (in the atlases). At other sizes the provider can only scale them, so the pen
  after task 95 with `Lucida Sans Typerwriter` or `Terminal` at such a size may differ from Windows.
  Adding Arial's 256 advances for every size and style to `metrics.json` (about 1.2 MB) would close
  it; left for a decision.

## 5. Machine dependence

- Text pixels of the raster faces, the metric table, the primitives and the theme-independent
  colours do not depend on the machine's settings and are compared in CI (`windows-oracles`).
- Machine-dependent and therefore only recorded: system colours other than 5, 8, 15 (the theme),
  `text-outline-glyphs` and `text-control` (font smoothing). `run.mjs --all` compares them too.
- The CI runner (`windows-latest`, a Windows Server image) has not been compared with this machine.
  If it gives other faces or cells (for example another font substituted for `Lucida Sans
  Typerwriter`), the first CI run will fail and show the difference.
