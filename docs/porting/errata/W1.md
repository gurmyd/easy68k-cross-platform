# Errata of W1 (Contracts, base utilities and stubs)

What W1 found while copying section 3 of `docs/ARCHITECTURE.md` into `app/src/contracts/` and
building the wave-0 utilities and stubs: where the document is silent, contradicts itself, or
differs from the engine modules, what the repository does, and why. Entries under **Contract**
change or add declarations that other packages compile against.

## 1. Contract: names of the engine mirror differ from the modules' names (3.2)

- Says: 3.2, "The simulator declarations below mirror the module". The mirror's constant objects use
  other names than `engine/sim/sim68k.mjs`: `RunStatus` (module `Status`, `RUNNING`, `WAIT_INPUT` ...),
  `SimOption` (`Option`, `EXCEPTIONS` ...), `HwDevice` (`Device`), `ShiftBit` (`Shift`), `RepaintBit`
  (`Repaint`), `MapKind.Rom` (`MapKind.ROM`), `FileMode.Update` (`FileMode.UPDATE`), `Reg.OldPC`
  (`Reg.OLD_PC`).
- Does: `contracts/engine.ts` keeps the names of section 3 (other packages are written against them)
  and carries the module's numbers. `contracts/contracts.test.ts` compares every value with the module
  through an explicit rename table, so a renumbering in the engine fails a test. Nothing else differs:
  the 66 members of `Sim68k.prototype` and the 93 keys of `HOST_DEFAULTS` equal `SimEngine` and
  `SimHost` (checked by the same test, and at compile time with `satisfies Record<keyof ..., true>`);
  the keys of `DEFAULT_OPTIONS` and of a real assembly result equal `AsmOptions` and `AsmResult`.
- Not mirrored (not needed by section 3): the module's `Menu` (`ACTIVE` 0, `TRACE` 1 - section 3
  calls 1 "busy"), `Break` (breakpoint constants), `MEMORY_SIZE`, `bytesToText`, `textToBytes`;
  `asm68k.mjs`'s `loadEditorText`, `decodeCp1252`, `encodeCp1252`, `changeFileExt`, `initAssembler`.
- The module accepts `tabType` `'assembly'` / `'fixed'` as well as 0 / 1; the contract uses 0 / 1 only.
- In the module every `SimHost` method is optional (a missing one returns its `HOST_DEFAULTS` value);
  the contract requires all 93, on purpose, so that a missing part is a compile error.

## 8. Behaviour section 3 leaves open, fixed by W1

- **Vfs ordering** (3.8.1): paths that differ only in letter case share one queue; `stat` and
  `readFile` wait for the mutations requested before them (a read sees every earlier write); a failed
  mutation does not block the next.
- **`Vfs.resolve`**: lexical first ('..' as on Windows, also through a folder that does not exist),
  then each segment takes its stored spelling (exact match first). A name with a drive letter or a
  leading `\` or `/` is refused (3.8.3). The result may be a folder.
- **`Vfs.snapshot`**: breadth first, names sorted, so the files nearest the folder are taken first
  when a limit is reached. Depth: files `maxDepth` folders below the root are taken; a deeper folder is
  listed once as `too-deep`. A file over `maxFileBytes`, or one that would exceed `maxTotalBytes`, is
  `too-large`. Rejects with `not-found` / `not-directory` when the root is not a folder.
- **Backend contract** (`fs/backend-contract.ts`, also a `SyncFiles` suite, which 9.2 asks of SH6 and
  DV2 but nobody was given): `remove` of a folder removes it with its content; `remove`, `readFile`,
  `list` of a missing path reject with `not-found`; `writeFile` below a file rejects with
  `not-directory`; `writeFile` on a folder with `is-directory`; the backend keeps its own copy of the
  bytes; `list` order is free. `SyncFiles.write` on a missing file returns false (the program always
  opens or creates first).
- **Defaults** (3.10): `AppSettings` has no stated defaults; W1 uses theme `system`, empty panel and
  splitter maps (the shell's defaults apply), `editorPanes` `one`, `outputZoom` `fit`, empty
  `serialPortMap`. `EditorSettings.template` holds the shipped template with `"\n"` line breaks, as
  documents hold text (3.9.1); saved with CR LF it is the original's 420 bytes (tested against
  `reference/official-extracted/template.NEW`). `SimSettings.speed.instructionsPerSecond` is
  1,000,000, the `DEFAULT_IPS` of 4.2, written as a literal because `core/run/governor.ts` (SH8) does
  not exist yet; SH8 may import it the other way round.
- **NullSerial**: `commRead` returns -3 ("port not initialised", the device result), which the engine
  turns into result 3 for task 42 - the "tasks 41-43 return 3" of note 37. `NullNet.receivePortNet`
  returns `{ d0: 0, d1: 0 }` (0 with 0 bytes, trap15-b §12 task 107).
- **Stubs whose class signature returns a number where the host returns `number | undefined`**
  (`TextScreen.getrc`, `getCharAt`, `Surface.getXY`): the stub answers from its start-up state.
  `OutputDevice`, the actual host part, returns the engine's defaults (`undefined`).
- **Stubs that answer state-derived values, not the engine's default** (found by the wave-0
  verifier; each stub's header now says so, no behaviour changed): `TextScreen.getrc` and
  `getCharAt` (start-up state), `Surface.getXY` (the window pen of the start-up state),
  `DesktopNet` and `DesktopSerial` (the answers of `NullNet` and `NullSerial`).

## 15. `Vfs.resolve` on a mount that refuses to list some folders (defect D1, repair round)

Found by DV5's check 7 on both Mac runners (release run 44960702355; `docs/porting/errata/DV5.md`
entry D1, `docs/requests/DV5-l68-resolve.md`). In the desktop app every lookup through
`vfs.resolve` on `/disk` returned null: the walk listed every folder from the mount root down, and
the main process rightly refuses to list anything outside the granted roots (7.6), so the very
first listing (`/`, on Windows the drive) failed and the walk gave up. The `.L68` of a program was
never found (no source-level debugging in the macOS app), and neither was anything else looked up
this way (the callers are in 15.3).

### 15.1 The rule

The walk stays: it is how a name in another letter case finds the stored spelling, as the
original's Windows does and as the backend contract cases keep pinning. What changes is what a
failed listing means. Proposed text for the comment of `Vfs.resolve` in 3.8.1:

> Windows-style lookup of `name` relative to `dir`: '\' and '/' separate, `.` and `..` are applied
> lexically and `..` is allowed while it stays inside the mount. The path is walked from the
> mount's root; each segment takes its stored spelling from the listing of its folder: the exact
> one if the folder has it, otherwise the first entry that matches without regard to letter case.
> A folder the backend reports as missing (`not-found`) or as a file (`not-directory`) ends the
> walk: null. A folder whose listing fails for any other reason (the desktop app's folders above
> the granted roots, which may not be listed, 7.6; a folder the system does not let the app read)
> cannot tell spellings: its segment is kept as given and the walk goes on. A path whose last
> segment was kept that way is accepted only if `stat` then finds it. null = not found or refused.

Why this is right in every case:

| Case | What happens |
|---|---|
| The path exists exactly as given | Found, with the same result as before. On `/disk` the folders above the granted root give their segments as given (those came from a native dialog, the command line or a drop, so they are the stored spelling); from the granted root down every folder is listed. |
| Another letter case in the last segment | The program's folder is granted (it is the folder of the program), so it is listed and the stored spelling is returned, as on Windows. |
| Another letter case in a folder below the granted root | Listed, matched, stored spelling: as on Windows. |
| Another letter case in a segment above the granted root | Only a name that climbs out of the granted root and comes back down can do this (`..\DEMO\data.txt` from inside `demo`); the app's own paths have the stored spelling. On a disk that ignores letter case (macOS and Windows disks as they ship) the first folder that may be listed again is reached under the given spelling, the main process's `canonicalPath` places it inside the granted root, and the file is found; the climbed segment keeps the given spelling, not the stored one (the path works; only its text differs). On a case-sensitive disk such a name is not found, where Windows would find it: learning the stored spelling would take a listing of a folder the person did not grant, which 7.6 forbids. Recorded as a difference (below). A name that climbs out and does not come back stays refused: the next listing or the final `stat` is refused, so null, as 3.8.4 says. |
| A backend that answers case-insensitively itself | The walk still lists wherever it may, so the result is the stored spelling there; a case-insensitive `stat` is used only to confirm a last segment that could not be listed, never to choose a spelling. |
| A folder that may not be listed for another reason | Its segment is kept as given; the path is accepted when a deeper listing or the final `stat` proves it exists, null otherwise. Nothing is listed or read that the backend refuses. |
| The browser store, `/folder`, `/linked`, `/memory` | Every listing of an existing folder succeeds there, so the walk is the same walk with the same calls and the same result; no `stat` is added. Only a listing that failed with a code other than `not-found` or `not-directory` (none of these backends does that for a folder that exists) is now followed by a `stat` instead of giving null at once. |

Nothing about security changes: `resolve` asks the backend only for what it asked before (the
listings of the folders on the way) plus, in one case, a `stat` of the very path it returns, which
the caller would `stat` or read next anyway. The desktop bridge (`desktop/src/fs-ipc.ts`) keeps
refusing everything outside the granted roots; it did not change.

Difference to record (for DOC1, under 3.8): "On a case-sensitive Mac disk, a file name that leaves
the folders the app may use with `..` and comes back in another letter case is not found."
