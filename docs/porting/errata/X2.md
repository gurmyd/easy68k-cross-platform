# Errata of X2 (end-to-end simulator suite and parity map)

What X2 found while building `tests/e2e/sim/` and `tests/parity/` from ARCHITECTURE.md 6.6 and 9.6:
where the document is silent or does not fit the code, what the suites do, and why.

## 1. "The rows whose kind is `web-e2e`": the kind is set by the matrix

- Says: 9.6 X2, "a test for every simulator and EASyBIN row of 1.3 whose kind is `web-e2e`". The
  tables of 1.3 have no kind column; 6.6 says `matrix.json` gives each row its `verifiedBy` kind.
- Does: the kind of a row is the kind of the first entry of its `verifiedBy`. Every simulator and
  EASyBIN row (1.3.4 to 1.3.8 and easybin.md 21.4) is `web-e2e`, each with a test in
  `tests/e2e/sim/` (or, for two rows, X1's `tests/e2e/app/layout.spec.ts`); the unit test asserts
  both. Editor rows name X1's tests (X1 errata entry 1 offered its test titles as the ids), unit
  tests where X1 has none (rows "Editor: plain text ..." and "Message catalogue").

## 2. A fifth kind, `browser-check`, as evidence only

- Says: 6.6 lists four kinds: `web-e2e`, `desktop-e2e`, `unit`, `manual`.
- Does: `browser-check` (a `check-<name>.mjs` of the browser-checks job, which also runs in Chromium
  and WebKit on three systems) may be added to a row as further evidence, never as its first entry,
  so every row's kind is one of the four. Three rows use it.

## 3. 1.3.8 and its extension in easybin.md 21.4

- Says: 1.3.8 is to be extended by B1; B1's errata entry 4 left the complete rows in easybin.md
  21.4 for the architect or DOC1 to copy, and ARCHITECTURE.md 1.3.8 still has its seven first rows.
- Does: the matrix holds both: the seven rows of 1.3.8 (section `1.3.8`) and the twenty of easybin.md
  21.4 (section `easybin.md 21.4`). The unit test reads both documents. When 21.4 is copied into
  1.3.8, the unit test reports the changed rows; then the 1.3.8 entries are replaced by the copied
  ones and the `easybin.md 21.4` section of the test is removed.

## 4. Manual entries quote ARCHITECTURE.md 6.8

- Says: `manual` = an item of `docs/MANUAL-TEST-MAC.md` (DOC1, written in the same wave; it is not
  in this branch).
- Does: a manual entry quotes the words of its item in 6.8, which DOC1's acceptance requires the
  manual list to contain; the unit test checks them against 6.8.

## 5. Findings: tests that are expected failures until the owner repairs the feature

| Test | Owner | Defect and evidence |
|---|---|---|
| `listing.spec.ts` "the listing scrolls sideways with its heading (note 33)" | U1 | The heading strip (`.e68-listing__heading`, `overflow: hidden`) is only as wide as its own text, so its `scrollLeft` stays 0 while the rows scroll: measured `{"list":200,"heading":0}` in Chromium and WebKit. The column titles no longer stand over their columns. |
| `easybin.spec.ts` "the Address field rounds a typed address down to a multiple of 16 (easybin.md 6.1)" | B1 | Typing `003005` leaves the field showing `003005` (Chromium and WebKit). The model rounds to `003000` and the rows start there, but the rounded text equals the text before the last key, so the controlled field is not re-rendered and keeps what was typed. The original shows `003000` at once. The Memory panel's Address field (U2) does round. |

Each is `test.fail(true, '<owner>: ...')`; when repaired the test reports "expected to fail, but
passed" and the line goes, with the row's `note` in `matrix.json`.

## 6. What the suites had to learn about the application (not defects)

- The Registers panel shows the CPU at a stop only (sim-ui §4.2): during a run, and while a program
  waits for input after a Run, the fields keep the values of the last stop. Tests read registers
  after the run state says `Stopped` or `Halted`.
- The Output panel's text mirror is the text shadow array (2.11), so the echo of typed input, which
  the original draws without storing (trap15-a §3.9), is not in it, and characters written past the
  right edge with wrap off appear in the next row of the array. Text wrap is therefore tested on the
  surface's pixels.
- A memory condition of type `Write` never fires for a `MOVE` to memory: the core reads the
  destination before writing it and a condition sees the read first (`BPoint.cpp`, "either read or
  write ... not both"). It fires for a write without a read (`BSR`'s push, as U3's check uses). The
  test uses `R/W`. Engine behaviour of the original, no finding.
- Text pasted without the paste chord (the browser's own Paste) reaches the program as typed
  characters, between which the program runs; only the chord (Shift+Insert, Cmd+V on macOS) feeds
  the clipboard in one go as the original does. The paste test dispatches the chord's key-down and
  the browser's `paste` event in the page, because a headless browser's clipboard cannot be filled
  the same way in Chromium and WebKit.
- The `.L68` the assembler writes has the source's tabs already expanded (with the editor's tab size,
  `AsmEngine.assemble`'s `tabSize`), so the listing's own 8-column expansion is tested with a hand-made
  `.L68` that holds tab characters.
- Run To Cursor on a row without an address shows the original box and then does not run (note 23);
  after a halt Open and Reload stay enabled and the five run commands carry the tool-tip of note 22.
- A file dialog opened by the simulator (File > Open, Open Data, Memory > Save, task 58, Import
  /Export) starts in the folder of the loaded program, which for an unsaved document is not My
  Programs: the tests choose `Look in: My Programs` first.
- Leaving the page is checked by dispatching `beforeunload` in the page and reading whether a handler
  cancelled it: Playwright's `page.close({ runBeforeUnload: true })` behaves differently in WebKit
  (the page stayed open with no dialog event), and what a browser shows for a cancelled event is the
  browser's (6.6, "What automation cannot show").
- Full screen in a headless browser: the test accepts either outcome the design allows, entering
  full screen or the original's refusal box (2.5), and prints which happened. In gate run 44974125913
  both browsers entered full screen on all three systems.

## 7. Rows whose test covers part of the row

The kind of these rows is `web-e2e` and the main behaviour is tested; these details are not, and are
listed so that I3 can decide:

- 1.3.6 "Keyboard input, ... input prompt": the blinking `_` prompt is drawn over the presented
  image only (2.5), never into the canvas the tests read.
- 1.3.7 "68000 Stack window": the red text of bytes in the Invalid range and the mouse wheel.
- 1.3.7 "EASy68K Hardware window": the Read, ROM and Protected ranges (only Invalid is tested), the
  disabled IRQ and Reset buttons after a halt.
- 1.3.7 "Execution log and output log formats": the Rewind/Reload notes (their quirk depends on when
  the Log Output dialog was last opened, sim-ui §13.5) and the register and memory blocks of log
  types 2 and 3; the byte-exact formats are T3's conformance logs (`tests/conformance/sim/logs`).
- 1.3.5 "TRAP #15 task 24": that F1, Alt+Enter and Shift+Insert are ignored after task 24 (F6
  reaching the program and the release chord are tested).
- 1.3.6 "One surface ...": that whole programs draw the same pixels in both browsers is X3's
  (`tests/conformance/examples`, 6.5.4), written in the same wave; the matrix should name it once it
  has landed.
- 6.6 "Execute after a program that changed the memory map": the map is changed in the Hardware panel
  (an Invalid range), not by the assembler's `MEMORY` directive.
