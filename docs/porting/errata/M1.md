# Errata of M1 (floating panels, version 1.1)

Where `docs/ARCHITECTURE-PLUS.md` P9 is silent, ambiguous, or cannot be met as written, what the
code does and why. None of these entries changes what a 68000 program can observe, a file the
application writes, panel visibility, or an original menu, command or key (P1.1).

## 1. How it is built: our own windows, the library keeps only the tab (P9.2, "How it is built")

**Decision: the floating windows are drawn by `ui/dock`; FlexLayout 0.11.1's own floating windows
are not used.** The rule that decided it is the reading and Tab order ("in the order in which they
were made to float, not the order they are stacked in"); the keyboard rules decided it as well.

Evidence (the library's code, `node_modules/flexlayout-react/dist/index.js` 0.11.1, and a probe in
the real application, `c:\easy64k\build\M1-arrange\probe-library-float.mjs`, which dispatches the
library's own `Actions.popoutTab(id, 'float')`, `movePopoutToFront` and `moveFloat` on the
Simulator dock's model in Chromium):

| Rule of P9.2 | flexlayout-react 0.11.1's floating window | Probe |
|---|---|---|
| Tab and reading order: float order, not stacking | `FloatingWindowContainer` renders the windows in the order of `model.getLayouts()`, and `applyMovePopoutToFront` (a click on a window, `pointerup`) deletes the window's layout from that map and inserts it again at the end: the DOM order **is** the stacking order. The window's `zIndex` prop is never used in its style. | order `hardware, memory`; after bringing `hardware` to the front: `memory, hardware` |
| The title bar is a Tab stop with a menu (Move, Size, Dock, Close) | The header is a `div` without `tabindex`, role or keys; its drag handle is a `draggable` `div`; there is no hook to render the header ourselves. | header `tabindex` null, no focusable element in it; 80 Tab presses never reached a floating window |
| `Dock` and `x` buttons on the title bar | Neither exists (only a popout button, off); docking is by dragging the handle onto the layout. | - |
| Keyboard Move and Size (arrows 16 px, Shift 1 px, Enter, Esc) | `FloatWindow` keeps its rect in React state, set from the model only on mount and when the layout object changes, so a `moveFloat` dispatched from outside does not move the window. | after `Actions.moveFloat(id, {40, 40, 300, 200})` both windows were where they were |
| Bounds: 48 px of the title bar inside; never resized by a smaller window; at least 160 x 96 | `clampToDoc` keeps the whole rect inside the layout (`constrainFloatPanels`) or the document; `MIN_WIDTH 150`, `MIN_HEIGHT 25`; nothing runs when the window gets smaller. | - |
| A place cascaded from the last floating window | Each new window gets its tab's docked content rect. | both windows at `701, 519, 699 x 294`, one on the other |
| No `<style>` element, nothing the CSP refuses; state in the stored layout; the content not created anew | Met: inline styles only; the windows are sub-layouts of the model; tab content is portalled from the main layout, so it is not remounted. | `<style>` count unchanged; every panel mounted once |

So the library meets the last row and fails the others, and the first one cannot be fixed from
outside without moving nodes React owns.

**What is built instead** (`ui/dock/engine.ts`, section "floating windows"; `FloatChrome.tsx`;
`floating.ts`; `dock.css`):

- A floating panel's tab stays in FlexLayout's model, as a tab of a **border that is never shown**
  (`show: false`, no drops; `model.ts` `FLOAT_BORDER`), present in the model only while something
  floats. FlexLayout therefore keeps rendering the panel's content, through the same portal, into
  the same element (`.flexlayout__tab`, adopted from model to model as for every move of N1), so
  the content is the same component in the same React tree position and is never created anew
  (P9.2). The probe of our windows: every panel's mount counter stays 1 through Float and Dock.
- FlexLayout positions that element as a hidden border tab (inline `display: none` and a zero
  rect, rewritten at each of its layout passes). `dock.css` draws an element marked
  `data-e68-float` at the window's place instead, with `!important` rules (an author `!important`
  declaration wins over an inline one) that read custom properties the engine sets
  (`--e68-float-x`, `-y`, `-width`, `-height`, `-z`). React renders no `style` on that element,
  so nothing of React's is overwritten. No `<style>` element, no inline script.
- The title bar and the eight edges are drawn by `DockContent` inside the panel's own element,
  before and after the panel's content, as siblings at fixed positions, so that the content keeps
  its place in the React tree when they come and go.
- The order: the border's tabs are in float order; the dock's reading-order pass (errata N1 10)
  now puts them after every docked tab (`live.ts` `tabIdsInReadingOrder`). Stacking is a z-index
  only (`floating.ts` `zIndexOf`), so the DOM order never follows it.
- Uses of FlexLayout internals added to those of errata N1 (R1): `TabNode.isRendered()` and
  `setRendered(true)` (a panel that floats from a stored layout was never laid out, and FlexLayout
  renders a tab's content only once its container had a size; the dock marks it rendered once the
  dock itself is laid out, so that P2.2's "mounted once its dock has been shown and laid out"
  holds), and the layout controller's `redrawLayout()`.

## 2. The arrangement's type is in `state/dock.ts`, not in `ui/dock` (task of M1, P9.6)

The task asked for the type of an arrangement "in a file of `app/src/ui/dock` that
`app/src/features/layout` may import by the layer rules". No such file can exist: P2.4 and
`eslint.config.js` (`easy68k/layer-imports`) let no feature import `ui/dock` ("they reach the dock
through `state/dock.ts`"). The type `DockArrangement` (with `DockRect`, `DockFloating`,
`DEFAULT_FLOAT_SIZE`, `MIN_FLOAT_SIZE`, `FLOAT_CASCADE_STEP`) is therefore exported from
`app/src/state/dock.ts`, which features may import and which imports neither `ui/dock` nor
`flexlayout-react`.

## 3. "Inside the application window" is inside the dock (P9.2, Bounds)

A floating window lies inside its mode's dock: the workspace between the toolbar and the status
bar, which clips what lies outside it (`.e68-dock { overflow: hidden }`, today's). Its rect is
stored relative to the dock's top left corner. The bounds keep at least 48 px of the title bar
inside the dock horizontally and the whole title bar (30 px, shorter than 48) vertically. When the
window gets smaller, a window is shown moved back by that rule and never resized; its stored place
is not changed by it, so it comes back where the person put it when the window grows again. A
move or size the person makes is stored as shown.

## 4. Commands: the handlers of `app.layout.float` and `app.layout.dock` (P9.5)

A command's handler comes from a feature (main 3.12.3; `bootstrap.test.ts` requires one for every
command id). `ui/dock` is not a feature and `features/layout` is M2's. M1 exports the two handlers
as `DOCK_COMMANDS` from `state/dock.ts`; `features/layout/index.ts` spreads it into its commands
(M2, one line). Until then the tab menu's `Float` and the title bar's `Dock` call the dock
directly (the command is disabled while it has no handler), and `bootstrap.test.ts` "every command
has a handler" lists the two ids.

## 5. The narrow layout and a smaller window (P9.2 Bounds; task item f)

Decision: a floating window stays a floating window at every width. Below 1100 px the Simulator's
*default* arrangement switches to the narrow one (P3.1.3); an arrangement with a floating window
is a changed arrangement (floating is a move, P3.1.3 "What makes an arrangement changed"), and a
changed arrangement "is used at every width", so nothing switches. The windows are only moved back
by the bounds rule (entry 3). Reason: docking a window by itself when the window gets narrower would
change the person's arrangement without being asked, and the bounds already keep every window
reachable. `check-dock.mjs` (floating) shrinks the page to 900 x 560 and back.

## 6. Which panels can float; viewers

- Any panel of the Editor's and the Simulator's dock, the Output panel and the panels that cannot
  be closed included, except the last docked panel of the mode (a dock with nothing docked would
  be an empty workspace; `Float` is disabled there, `canFloat`). A stored tree must hold the
  panels that cannot be closed unless they float (`stored.ts` `readTree`).
- P9.2's "in each of the three modes" does not apply to EASyBIN: that mode has one panel and no
  dock (P3.1: "it has nothing to arrange"), so nothing floats there; `Float` and `Dock`
  (`app.layout.float`, `app.layout.dock`) are disabled in that mode (`DOCK_COMMANDS`, `inDockMode`).
- A viewer (P3.4) can float too: P9.2 says "any panel of the dock". Like its tab, its window is
  never stored (P4.2); it goes away with the viewer (its x, a mode change) and `Reset Layout`
  docks it into the Editor's group.
- A hidden panel can be made to float by `float()` (an arrangement, P9.4): it is recorded as a
  window and floats when it is shown. Nothing shows it.

## 7. A floating window's details that P9.2 leaves open

- Title bar: 30 px, the kit's dialog title bar in colours and weight; the window has a 1 px
  `--c-border-strong` border, `--r-md` corners and `--shadow-popup` (it is not modal, so the
  lighter of the kit's two shadows). In forced colours the border and the title bar's line are
  `CanvasText`.
- The title bar is one Tab stop: an element with `role="button"`, `tabindex="0"`,
  `aria-haspopup="menu"`, named by the panel's title. An explicit `tabindex`, so that Safari on a
  Mac stops there too (errata N1 29). `Dock` (a text button) and `x` are `tabindex="-1"`: they are
  in its menu. Enter and Space open the menu as Shift+F10 does (it is a menu button).
- The menu's accessible name is `Window` (`texts.ts` `FLOAT_WINDOW.menuLabel`; P9.2 gives none,
  as P3.1.4 gave none for the tab menu, whose name N1 chose).
- `Move`/`Size` from the keyboard: Size moves the right and bottom edges, as a desktop window's
  Size does after the first arrow; while either is on, the title bar is tinted
  (`--c-accent-soft`). Losing the focus ends it and keeps what it shows (as Enter).
- A press on the title bar's `Dock` or `x` that moves 4 px or more moves the window instead of
  pressing the button: a window dragged out to the left shows only the right end of its title
  bar, which is its buttons, and must still be draggable back.
- First float: 24 px right and down of its docked place, or left and up where that does not fit,
  so that it is seen to lift off; a later window is cascaded 24 px from the last floating window,
  starting again at 24, 24 where the cascade would leave the dock.
- Stacking: z-index 11 to 18 (above FlexLayout's splitters, 10; below the kit's modeless dialogs
  and menus, 20 and up). While the Output panel in a window is in full screen, that window takes
  the full screen's z-index, `calc(var(--z-modeless) - 1)`, through a `:has()` rule (P3.1.5 allows
  it for `.flexlayout__tab`). `check-dock.mjs` (floating) checks the four corners and the centre.
- Dock goes back "to the place it was docked at last" (`park.ts` `dockInto`; entry 11 says how and
  why): the arrangement it floated from, while only Float and Dock changed it since; else the place
  it was docked at as the dock understands places (the subtree it was beside, the side, its share;
  or its group and its index among the tabs), while that subtree or group exists; else ("that
  group is gone") its place in P3.1.3's default arrangement by the same rule, the default
  arrangement for the panels shown, at the dock's width now, with every panel taken out that is
  not docked now. Only where the default arrangement does not hold the panel (a viewer) or nothing
  docked is beside it there does P3.1.8's default place apply (`insertPanel`: a viewer into the
  Editor's group, a tool panel to the tool group or below Output, Files at the left edge, others at
  the right edge). Repaired after the verification of round 1 (before it, the right edge was used
  for every panel without a tool group), and again after round 2 (entry 11).
- Closing a floating panel, by its `x` or by `Close` in its title bar's menu, moves the focus as
  closing a docked panel does (P3.1.8: the selected panel of its group, the group gone: Registers
  or the Editor), also when the focus was on the title bar (the menu gives the focus back to the
  title bar before its item runs). The dock counts the title bar as part of its panel
  (`engine.ts` `focusedPanel`). Repaired after round 1: before it the focus fell to the page's
  body after `Close` from the menu.

## 8. Ways to float: dragging, and the checks of 1.0.0 that change (P9.2, P9.6)

- "Dragging a tab and dropping it where there is no docking target": inside the dock FlexLayout
  offers a place nearly everywhere, and where it refuses one (the Output panel over a group under
  160 x 120 px) a drop does nothing as in 1.0.0 (errata N1 22). So "no docking target" is outside
  the dock's layout: a tab dropped on the menus, the toolbar or the status bar floats there (moved
  into the bounds). Esc still cancels a drag.
- `check-dock.mjs`, pass `moves`, check "the tab menu lists ...": the tab menu gains `Float` before
  `Close` (P9.2), so the expected list gains it. That is the only check of 1.0.0 that changed; the
  recording `check-dock.main.json` is unchanged and was not regenerated.

## 9. What changes in the page while something floats (and only then)

While a panel floats, FlexLayout's model has the hidden border, and FlexLayout then wraps its rows
in its border container (`flexlayout__layout_border_container`, two more `div`s), which remounts
its row, group and splitter elements once (not the panels' contents, which are in another layer).
Their names, roles, slots and keys are put back by the dock's decorate pass as after every change.
With nothing floating there is no border and the page is 1.0.0's; `check-dock.mjs` (floating)
compares the dock's own elements, roles and names at the start and after Float, Dock and Reset.

A panel whose place in the order changes is moved in the DOM by React (as on every move since N1,
errata N1 10). The browser then forgets the scroll positions inside it; the dock now records them
before such a reorder and puts them back after it (`engine.ts` `ensureReadingOrder`). The check
"the Listing scrolled" fails without that (Chromium: 1500 px became 0) and passes with it.

**A known limitation: a PDF viewer shows its document from the start again after Float.** A
viewer's `iframe` (a PDF) moved in the DOM loads its document again (the same blob), as every
`iframe` does that is taken out of the page and put back; a picture's `img` keeps it (checked in
`check-dock.mjs`). Floating moves the floating panel's element to the end of the panels (its place
in the reading order), and React moves the element whose place changed, so Float moves the
viewer's own element; Dock moves the others (the docked panel goes back before them) and does not
reload the viewer. Evidence (`c:\easy64k\build\M1-arrange\probe-pdf.mjs`, a five-page PDF in the
Editor's viewer, Float, then Dock): Playwright's full Chromium (channel `chromium`, which has the
PDF viewer) fired one `load` on the frame at Float and none at Dock, and the frame's window was a
new one after Float; WebKit fired no `load` event but the frame's window was a new one after
Float, not after Dock. The PDF therefore shows its first page again, scrolled to the top, after
Float. Its page and scroll position live in the browser's own PDF viewer, which the page cannot
read, so they cannot be put back. This also held for N1's moves of a viewer. Not repaired: the
only way around it is a DOM move that keeps a frame's document (`Element.moveBefore`, not in
WebKit), under React's own children, which is not done; recorded here for `docs/differences`
(M3).

## 11. Dock puts a panel back where it was docked (P9.2), repaired after the second verification

**The defect** (verification of round 2, its major finding). Float recorded only the parked place of
P3.1.8, "next to panel N, on side S", and Dock used it whenever N was still docked, splitting N's
own group. A panel that had been a whole column or row of its own came back beside one group of
that column only: in the Editor's default arrangement `row(files, column(editor, messages))`,
Float and Dock of Files gave `column(row(files, editor), messages)`, worse than 1.0.0's hide and
show. Several floating panels docked in another order than they floated ended away from their
places (Output squeezed beside the message area after Output, Memory and Hardware floated and
docked in reverse), and a panel docked into a group of tabs became its last tab.

**What Dock does now** (`park.ts` `dockInto`; `engine.ts` `float`, `dock`):

1. **The run of Float and Dock.** The first Float from an arrangement remembers that docked tree
   (`FloatOrigin`, stored with the windows as `layout.dock.floating[mode].origin`: the tree, whether
   it was the default arrangement, and the tree the last Float or Dock stored). While the stored
   tree keeps the shape that the last Float or Dock gave it, nothing but Float and Dock changed the
   arrangement, and Dock puts the panel where it was in the remembered tree among the panels docked
   now: that tree with every other floating panel taken out (the same `removePanel` the dock uses
   for hiding). Its side, its share of the space and its index among the tabs are those it had.
   When the last panel of the run docks, that is the remembered tree itself; when the run began in
   the default arrangement and nothing else floats, nothing is stored any more and the mode shows
   its default arrangement, sized as before (`restoreDefault`, as Reset Layout does but keeping
   `layout.splits` and the remembered window rects). A move, a drop, a splitter the person drags, a
   panel shown or hidden, an arrangement of P9.4 or Reset Layout ends the run (the stored tree
   changes shape, or the engine drops the origin); a reload keeps it.
2. **The place it was docked at.** Float also records the place as the dock understands places
   everywhere else (`placeOf`, stored as `place` of the window): the subtree it was beside (its
   panels), the side and its share, or its group's tabs in their order. Outside a run, Dock puts the
   panel beside the subtree that holds exactly those panels (also when `normalizeDock` merged that
   subtree into the row or column around it: a run of children counts), or into the group that
   holds most of its old group's tabs, after the nearest tab that was before it (none there: at its
   old index, but not after the nearest one that was after it).
3. **That group gone**: its place in the default arrangement by rule 2, the default arrangement
   pruned to the panels docked now; then P3.1.8's parked place; then `insertPanel`'s default place.

The focus goes to the docked panel as before, which brings its tab to the front of its group; that
selection is not stored (as for every selected tab, P3.1.5), so the stored tree keeps the group's
front tab of the remembered tree.

**The property, as tests.** `float-engine.test.ts` (under Node): for every panel of the Editor
(Files shown and hidden) and of the Simulator (tools shown and not), in the default arrangement,
Float then Dock gives the default arrangement again (nothing stored, the tree equal with its
weights); every pair and every triple of the nine Simulator panels, floated in one order and docked
in every order (576 runs), gives the default arrangement; the same for the docked panels of the
three stored arrangements of P9.4 (written out in the test with the shapes and proportions of
`features/layout/arrangements.ts`, M2's, which the dock may not import), the stored tree equal; the
reported cases; a tab back at its index; a reload in the middle of a run; pure tests of `placeOf`,
`insertAtPlace` and `dockInto`. `check-dock.mjs`, pass `floating`, part "Dock: back where it was"
(Chromium and WebKit): the Editor's Files floated from its tab menu and docked by the title bar's
`Dock` button, every panel of both modes, every pair and triple of Simulator panels in every order,
and the three stored arrangements (each docked panel, each pair in both orders, each triple in its
order and the reverse), each compared with the arrangement before by its stored tree, its shape,
the boxes of its groups and splitters within 1 px, and the floating windows.

**Changed test of version 1.1** (M1's own, not 1.0.0's): `float-engine.test.ts` "Dock: back where
it was docked last; that group gone, to its default place" expected Memory, beside a floating
Listing, to dock below the Output panel; it now docks where it was among the panels docked now
(`column(registers, memory, messages)`), and with Listing docked again the arrangement is the one
they floated from. The test gained the cases outside a run (a move in between).

## 12. Where a window appears at its first Float (P9.8 point 2)

Float without a place (the tab menu, the double click, the strip's button, `Move Panel To...`)
gives the window, as before, the size the panel had while docked (at most three quarters of the
dock), the remembered place where the panel floated before, and otherwise the first free place of
the rule of P9.8 point 1 (`state/tiling.ts` `tileWindows`, called by `floating.ts`
`firstFloatRect`): the rightmost place first, in it the top one, over none of the floating windows
that are shown and not over the tab strip of the group the panel came from (that strip as it was
drawn before the panel left it, `engine.ts` `stripRectOf`). Only where there is no such place is
the window cascaded 24 px from the last floating window (from the top left when that would leave
the dock) and moved below the strip where it would cover it. The reviewer's case (Hardware and
Memory as tabs below the Output panel at 1366 x 768, Hardware floated) now gives Hardware 682 x 241
at the dock's top right, 0 px down; the Memory panel and its tab stay seen and clickable
(check-dock `review`). The arrangement entries without a place (`DockArrangement.floating` with no
`rect`) are placed by the same rule at `DEFAULT_FLOAT_SIZE`; `cascade` is read no more (kept in the
type so that a caller of 1.1 still compiles).

## 13. A double click, and the Float button of every strip (P9.8 point 3)

- **The double click on a tab** is the browser's own `dblclick` on a dock tab
  (`.flexlayout__tab_button`, `DockWorkspace.tsx`), so the time between the two clicks is the
  system's double-click time, not one of ours; the first click has selected the tab already, at
  once, as before. FlexLayout 0.11.1 does nothing on a double click on a tab or a strip here (its
  rename and maximize are off, P2.2), so nothing of 1.0.0 is taken away. The tabs of the Editor's
  documents are the editor's own strip, not FlexLayout's: they are not touched (check-dock `review`:
  a double click on a document's tab floats nothing). It works locked and unlocked, through the
  command `app.layout.float` with `{ panel }`.
- **The double click on a title bar** docks the window (`FloatChrome.tsx`): only when both presses
  were on the title area (not on `Dock` or `x`) and neither moved the window, so a quick drag and a
  click on a button are never taken for it.
- **The button** is the kit's `IconButton` (20 px, the tab strips' size) with a new icon `float` of
  the kit's set (`icons.svg`, `icons.ts`: a window lifted off a dashed place; `icons.test.ts`
  checks the sprite and the list agree), added to FlexLayout's buttons of every tab strip that is
  shown (`onRenderTabSet`), so it is at the strip's right end and the Tab stop after its tabs. By the
  kit's rule its tool tip is its accessible name: `Float: make this panel a window of its own`
  (`ui/dock/texts.ts` `FLOAT_BUTTON`), which begins with its name. It floats the strip's selected
  panel and is disabled where that panel cannot float (the last docked panel). With nothing
  unlocked and no tool panel shown there is no strip and so no button: the default page is 1.0.0's
  (check-dock `boxes`, `taborder`, `starts` and `scan` unchanged for it).
- **The checks of 1.0.0's Tab order that had to learn it.** Where 1.0.0 shows a strip, the button
  is an addition to that strip. In `check-dock.mjs` the walks of the passes `taborder` and `starts`
  compare with 1.0.0's recorded orders (`MAIN_TAB_ORDER`, `check-dock.main.json`); they now leave out
  exactly the stop `button|Float: make this panel a window of its own|-` after checking that each
  such stop comes right after its strip's tab (Tab) or right before it (Shift+Tab)
  (`learnFloatButtons`, one check per pass), and compare everything else with 1.0.0 as before. The
  checks that met the button, all in Chromium and WebKit: `taborder` "simulator wide, Memory shown"
  (Shift+Tab, 10 walks from the end; locked again, Shift+Tab), "simulator narrow" (Tab; Shift+Tab
  from the Output panel's key field), "simulator narrow, Memory shown" (Tab; Shift+Tab, 10 walks);
  `starts` "simulator narrow" (the walks with the window gone and back, and with the focused element
  gone beside each stop, both directions). The reading-order checks (Chromium's accessibility tree,
  `readingOrderOf`) list tabs, tab lists, regions and named separators, not buttons: they did not
  change and pass as before.

## 14. The bounds count the title area (P9.8 point 4)

`floating.ts` `boundedRect(rect, area, buttons)` keeps at least 48 px of the title area inside the
dock: the title area's right end (the window's right edge less the buttons) at least 48 px from the
dock's left edge, its left end (inside the window's 1 px border) at most 48 px from the right edge.
The buttons' width is measured on the page where the window is drawn (`engine.ts` `buttonsOf`: the
bar less the title, plus the border; fonts differ between systems), else the figures measured in
Chromium and WebKit on Windows (`TITLE_BUTTONS_WIDTH`: 80 px for `Dock` and `x`, 54 px for `Dock`
alone). The reviewer's case (a window of 662 px dragged 3000 px to the left) now leaves the title's
right 48 px in view beside the buttons (check-dock `review`: the title area's right end at 48 px,
for a window with and without `x`; pushed to the right, its first 48 px). Two checks of version 1.1's
own `floating` pass changed with the rule: "dragged out at the top left" now measures the title
area's right end (48 to 50 px) instead of the window's (48 px), and "dragged out at the bottom
right" expects the window at the dock's width less 49 px (the border) instead of 48.

## 15. Ctrl+Alt+O onto a floating window (P9.8 point 6)

`state/panels.ts` `focusNextPanel` (Ctrl+Alt+O in the Output panel, F2, Ctrl+Tab) goes to the next
panel of the cycle as before; when that panel floats and is shown, its focus request asks for the
window's title bar (`focusPanel(ctx, id, { at: 'title' })`, carried out by the shell's
`focusPanelElement`), from where Tab goes into the panel and Shift+F10 opens Move, Size, Dock. A
title bar counts as its panel for the cycle (`panelOf`), so F2 from a title bar goes on to the panel
after it. check-dock `review`: from the Output panel's key field, Ctrl+Alt+O lands on the floating
Memory window's title bar, and Tab then on the Memory panel's first field.

## 17. The room kept for the windows of Floating Tools (P9.8 point 1, the dock's part)

P9.8 point 1 needs the Output panel to keep "the left part of what was its column" while the tool
windows lie at the right of the dock. A window lies over the docked panels; the Output picture is
centred in its panel; so the picture can only stay in view if the docked panels are laid out left
of the windows. The dock therefore has a **room kept for the floating windows**: an arrangement
gives `reserve` (CSS px, `DockArrangement.reserve` in `state/dock.ts`), stored with the mode's
floating windows (`layout.dock.floating.simulator.reserve`; read only as a whole number above 0
with windows), and while a window of the mode floats and is shown the dock lays out its docked
panels left of that width (`engine.ts` `applyReserve`: the custom property `--e68-dock-reserve` and
the attribute `data-e68-reserve` on the dock, `dock.css`: a right margin on FlexLayout's main
element; the floating windows are positioned in the whole dock as before). The docked panels keep at
least 320 px. With nothing floating there is no room kept, so the page is 1.0.0's (check-dock
`boxes` unchanged; `float-engine.test.ts`: Reset Layout and docking the last window give it back).
It goes with Reset Layout, `Classic`, any other arrangement, and the last window docked. What it does
not do: a person who drags the windows away from the right edge sees the kept room empty until they
choose an arrangement or dock the windows (a known limit, not asked for by P9.8).
