The highlighter in `app/src/core/highlight` is a line-by-line port of `textS.cpp:1144-1571`,
`tokenize` (`ASSEMBLE.CPP:821-881`), `strcap`/`skipSpace` (`ASSEMBLE.CPP:233-273`), `instLookup`

corrections or additions to editor-ui §9, for DOC1 to merge.

## 1. editor-ui §9.6 step 3 and 4: a string moves `syntaxStart`

- Says: an unclosed `(` is error-styled "from `syntaxStart` ... the start of the operand field for a
  directive, but still the start of the *mnemonic* for an opcode".
- Source: the string branch sets `syntaxStart = p` at the opening quote and again behind the closing
  quote (`textS.cpp:1534, 1549`). An unclosed parenthesis after a string is therefore error-styled
  from the character behind the string: `    MOVE.B  #'A',(A0` gives `'A'` Text and `,(A0` Structure
  Error, `MOVE.B  #` Code.
- Port: as the source (test "quirk: after a string the error range starts behind the string").

## 2. editor-ui §9.4: the token buffer is contiguous, and short tokens are read past their end

- Says nothing about it.
- Source: `tokenize` copies the tokens one after the other, each ended by NUL, into `tokensS[512]`;
  `checkRelational` and the `UNLESS` test read `tokenS[n][3]`, `instLookup` reads `p[1]`, `p[2]`.
  For a token shorter than three characters that read lands in the next token:
  `    IF D0 <E >X THEN` is accepted as a structured statement (the fourth character of `<E` is the
  `>` of `>X`), `    IF D0 <E X THEN` is not.
- Port: keeps the same buffer, so these reads give the source's answers. Bytes the current line did
  not write read as NUL (the original reads whatever an earlier line left there, which is not
  reproducible; it matters only for a token of fewer than three characters at the very end of the
  buffer). An unused token (`empty`) reads as NUL in every position.

## 3. editor-ui §9.4: `''` and the buffer limit

- `''` at the start of a token writes a NUL and skips the two quotes, but the token goes on taking
  characters (they sit behind the NUL, invisible to `strcmp`). Consequence for opcodes: in
  `    MOVE.B  '' 'x` token 3 is empty, so the opcode branch takes the line for "opcode only" and the
  operand field is not scanned: the whole line is Code (§9.5 (c) "If no token follows, done" is
  decided on token `n+1` being empty, not on the text).
- `MAX_SIZE` (512) also limits the tokeniser: when the buffer is full no further token is made,
  even below `MAXT`. With the original's 255-character line buffer this cannot happen; the port
  keeps the limit for longer lines (see 6).

## 4. editor-ui §9.3 step 4: consequences of the label rule worth listing as quirks

- A run of zero length in column 0 (line starts with `#`, `(`, `Ä`, ...) is a "label": token 0 is
  the first word and the operation is token 1. `#1 junk` is entirely Macro/Other (from column 0,
  because `syntaxStart` is column 0), `ÄBC  NOP` is entirely Code.
- A column-0 label glued to its operation with `:` (`LOOP:ADD D0,D1`): `LOOP:` is Label, but the
  tokeniser makes `LOOP:ADD` token 0, so token 1 is `D0,D1` and `ADD D0,D1` is Macro/Other.
- A `;` directly after the operands is not a comment start: `    MOVE D0,D1;nocomment` is all Code
  (§9.6 says so in general; this is the case students meet).

## 5. Characters outside ASCII

- The source passes a signed `char` to the Borland ctype macros; what they return for bytes
  `$80-$FF` is not knowable from the source. The port treats every character at or above `$80`
  (and every UTF-16 code unit of a non-Windows-1252 character) as neither letter, digit nor white
  space, and `strcap` leaves it unchanged, which is what the "C" locale does for those values read
  as unsigned. No table of the highlighter contains such a character; the choice can only move
  where a label or a mnemonic ends.

## 6. editor-ui §9.3: long lines and NUL

- Lines longer than 255 characters overflow `capLine` in the original (undefined behaviour). The
  port analyses the whole line, with `MAXT` and `MAX_SIZE` applied as in the source.
- A NUL character inside a line ends the analysis there, as `c_str()` would; ranges that run "to
  the end of the line" still end at the real end of the line.

## 7. Presets: what decides "Disabled"

- editor-ui §11.2 has the preset index and `highlightDisabled` as separate stored values (lines 54
  and 57 of `settings.dat`), and the original's highlighter tests only `highlightDisabled`
  (`textS.cpp:1054`). The port does the same: highlighting is off exactly when
  `EditorSettings.highlightDisabled` is true, whatever `colorPreset` says. With `Auto` and
  `highlightDisabled` the text takes the theme's Code colour.
- `presetStyles(5)` (Auto) in `core/highlight/presets.ts` returns the Color1 values, matching 3.10
  ("the Auto preset is exported as -1 with the Color1 values"); E4 may use `presetStyles` for the
  Options dialog.

## 8. editor-ui §20.4 ("Load L68 opens `<name>.L68` in a new, uncoloured window") and ARCHITECTURE.md 2.4

- Says: list documents are "not highlighted" and open "uncoloured".
- Source: "uncoloured" can only mean without syntax colours. `TTextStuff`'s constructor sets
  `SourceText->Color = backColor` for every window (`textS.cpp:78`), and Editor Options OK sets it
  again for every MDI child (`editorOptions.cpp:148`), list windows included; their text stays in
  the RichEdit default (black). `colorHighlight` returns for `!Project.IsSource` (`textS.cpp:1056`).
- Port (repair round of gate I1): under a stored preset a list document takes the stored background
  and black text (`listColorsStyle` in `features/highlight/colors.ts`, class `e68-syntax--list`) and
  no marks; under `Auto` it keeps the theme's editor colours (docs/differences/E3.md item 3).

## 9. Gate I2: the selection was never visible

- Was: the highlighter's theme painted the background on `.cm-content` as well as on `.cm-scroller`.
  CodeMirror draws the selection in a layer behind the content (`.cm-selectionLayer`, z-index -2),
  so the opaque content covered it and no selection was ever drawn in a source document (E6's report
  and review: Find's matches were invisible).
- Does now: only `.cm-scroller` (and the editor root) carry the background; `.cm-content` is
  transparent. `check-highlight.mjs` selects blanks (a browser may recolour selected glyphs even
  without a selection background, Chromium does) and requires the pixels to change, with the focus
  and without it (HideSelection = False), under Auto in the light theme and under Color1 in the dark
  theme. The check failed on the old rule ("differs from unselected: focused false, unfocused
  false") and passes on the new one in Chromium and WebKit.

## 10. Gate I2: colour contrast of the Auto light colours (X1's a11y scan)

- X1's axe scan finds `color-contrast` (serious) on the Unknown (Macro/Other, `#808000`) and
  Structure Error (`#FF0000`) samples on `#FFFFFF` (E4's Colors tab, E5's Assembler Status rows).
- 2.8 has two rules: "text on its background at least 4.5:1" and, specifically for the editor's
  syntax colours, "With the `Auto` preset: light theme = the original defaults of editor-ui §9.2 on
  `#FFFFFF`". The specific rule decides, as fidelity to the original's look is the point of the
  light Auto palette; the dark palette was chosen for contrast. Not changed. Where an automated scan
  meets these samples it should exclude the syntax-colour spans (`[data-element]` samples and
  `.e68-syntax__*` marks) with this entry as the reason. A student who needs more contrast picks the
  dark theme or a stored preset.
