# Errata of T4 (Native twins and CPU catalogue)

Where `docs/ARCHITECTURE.md` (6.1 L1 and L7, 6.2.1, 6.2.4, the T4 entry of 9.4) or a spec could not
be followed as written, what the repository does instead, and why. No entry touches a contract.

## 1. The simulator twin is not built at `tests/oracle/native-twin/sim-twin.exe`

- Says (6.2.1): "`tests/oracle/native-twin/sim-twin.exe`: the patched simulator core with a
  headless C++ host ...".
- Found: that is a folder of tracked files; a build output there would be committed by accident
  (the `.gitignore` is frozen and does not exclude it), and 6.2.1 asks for two of them (`/O2` and
  `/Od`).
- Does: the sources are in `tests/oracle/native-twin/sim-twin/`; the programs are built into
  `build/native-twin/sim-O2/sim-twin.exe` and `build/native-twin/sim-Od/sim-twin.exe`
  (git-ignored), like every other build output.
- Proposed text: "`tests/oracle/native-twin/sim-twin/`: the sources of `sim-twin.exe` (built into
  `build/native-twin/`) ...".

## 2. There is no unpatched simulator twin

- Says (6.1 L1, 6.2.1): "the same patched sources built with MSVC ... and the unpatched sources
  built the same way"; "patched against unpatched on inputs that do not trigger the patched
  defects".
- Found: for the simulator this cannot be built. The engine's shim (`engine/sim/shim/runloop.cpp`,
  `api.cpp`) is written against the patched `runprog()` and `exec_inst()`, which return a wait code
  instead of blocking (engine/sim/PATCHES.md P04, P05, P07, P08, P25); the unpatched files call
  `Application->ProcessMessages()` in loops that only end through GUI events, and the original GUI
  forms (`SIM68Ku.cpp`, `simIOu.cpp`, ...) are not ported at all. An unpatched build would need a
  second, blocking shim - a new host, not a twin of the engine.
- Does: the simulator has the two patched twins (`/O2`, `/Od`); the assembler has all four
  (patched and unpatched, `/O2` and `/Od`). The simulator's patches are proven equivalent to the
  original by `engine/sim/check-patches.mjs` and argued one by one in PATCHES.md; the twins prove
  that no result depends on the compiler.
- Proposed text: "... and, for the assembler, the unpatched sources built the same way (the
  simulator's shim needs the patches that make it non-blocking)".

## 3. The engine's assembler twins exist only at `/Od`; the `/O2` pair is built here

- Says (6.2.1): the two assembler twins are the engine's own, built by `engine/asm/native`;
  "T4 runs them in CI and over the corpus and does not own them"; and the comparison includes
  "`/O2` against `/Od`".
- Found: `engine/asm/native/build.mjs` builds only `/Od` (into `build/asm-native/`).
- Does: `tests/oracle/native-twin/build-asm-twins.mjs` compiles the same files with the same flags
  (it reads the file lists from `engine/asm/build.mjs` and the flag list from
  `engine/asm/native/build.mjs`, and fails if either cannot be found, so the two cannot drift
  apart silently) at `/O2` and `/Od`, into `build/native-twin/asm-*/`. The engine's own build and
  its `native.test.mjs` are run as well (in CI, or with `--engine-twins`). No engine file is
  changed.

## 4. `engine/asm/native/build.mjs` finds only Visual Studio 2022

- Found: it looks for `vcvars32.bat` under the four 2022 editions only (its header mentions
  `vswhere`, but it does not use it). A runner image with a newer Visual Studio would fail.
- Does: `run.mjs` finds the compiler with `vswhere` (`msvc.mjs`) and passes it to the engine's
  script through the `VCVARS32` variable that script already honours. For the engine owner:
  using `vswhere` there too would make the script work on its own.

## 5. In CI the engine's unpatched twin is not built, so half of its native test skips

- Found: `engine/asm/native/build.mjs` takes the unpatched sources only from
  `reference/src-edit68k/Edit68Kv5.16.1`, which is not in a checkout, so in CI it builds the patched
  twin only and `engine/asm/test/native.test.mjs` skips its 95 unpatched runs.
- Does: T4's own unpatched twins are built in CI from the original archive (fetched from the
  author's repository `ProfKelly/EASy68K` at commit `dab554f0`, SHA-256 checked, unpacked into
  `build/native-twin/original/`) and compared on the same 95 runs with the same list of expected
  differences (`UNPATCHED_DIFFERS`, read from the engine's test file) and on the whole tracked
  corpus. For the engine owner: an option such as `--unpatched-src <dir>` in
  `engine/asm/native/build.mjs` would let its own test run in full in CI (run.mjs would pass
  `build/native-twin/original/Edit68Kv5.16.1`).

## 6. One single-step suite, not two

- Says (6.2.4): "The single-step suites are downloaded at test time into `build/singlestep/`
  (never committed; SingleStepTests/680x0 has no licence, m68000 is MIT)"; ground-truth section 5
  describes both.
- Does: the catalogue uses SingleStepTests/680x0 (`68000/v1`, commit `e0d5ece9`), whose JSON states
  are the 68000's architectural state and directly comparable. SingleStepTests/m68000 is a binary
  repackaging generated from MAME's 68000 core with its own conventions (RAM in words, PC = the
  next prefetch address, TAS and TRAPV not trusted, per its README); adding it would compare
  EASy68K with MAME a second time with less trustworthy data. The acceptance item says "the
  suite", and "the single-step runner covers every file of the suite" holds for all 124 files.

## 7. "The frozen baseline on every push" runs in the Windows job

- Says (6.1 L7): "on demand; the frozen baseline on every push".
- Does: `npm run oracle:twins`, which CI's job `windows-oracles` already runs on every push (its
  guard is `tests/oracle/native-twin/run.mjs`), fetches the suite in CI and checks
  `tests/conformance/cpu/baseline.json` on every run, so no change to `ci.yml` is needed for this.
  The Vitest form (`tests/conformance/cpu/baseline.test.mjs`) takes about four minutes and runs
  only with `EASY68K_SINGLESTEP=1`, so that `npm run test:conformance` stays fast for everyone else
  on a shared machine. A cache for the 200 MB download is requested (docs/requests/T4-ci.md).

## 8. "The conformance programs (simulator)" do not exist yet

- Says (6.2.1): twin against WebAssembly "for the conformance programs (simulator)".
- Found: the simulator conformance suite (`tests/conformance/sim/`) belongs to T3 of the same wave
  and has not been written.
- Does: the simulator comparison runs a standard script for **every `.X68` under `tests/`** (the
  corpus and every conformance folder) that assembles to an S-record file, plus the simulator
  engine's own test programs, the hand-written scripts of `tests/oracle/native-twin/scripts/` and
  the single-step suite. T3's programs are picked up without any change when they land.

## 9. The single-step suite needs exceptions enabled and a "neutral" step between tests

- Not in the document; recorded because it decides what the catalogue means. A real 68000 takes
  every exception, so the runner enables exceptions (EASy68K's default is off, in which case every
  exception halts with a message). Between tests the runner traces one NOP at `$000400`, because
  EASy68K's double-fault latch (`errflg`) and the static result of the previous instruction survive
  a reset (sim-core.md 3.4 step 2, 3.14) and would otherwise make an address-error test change the
  outcome of the next one.

## 10. `tests/conformance/cpu/run-singlestep.mjs` exists for oracle.yml

- Not in the document. T1's weekly workflow `.github/workflows/oracle.yml` has a job `singlestep`
  (Linux) that runs `node tests/conformance/cpu/run-singlestep.mjs` when that file exists
  (docs/porting/errata/T1.md). T4's runner was named `run-catalogue.mjs`, so the job never ran.
- Does: `run-singlestep.mjs` is the check-only entry point of `run-catalogue.mjs` (fetch and verify
  the suite, run it through the WebAssembly simulator, compare with `baseline.json`; it refuses
  `--write-baseline`; without `engine/dist` it skips, or fails with `EASY68K_REQUIRE_ENGINES=1`). The
  baseline is thereby also checked weekly on Linux, not only on Windows by `npm run oracle:twins`.

## 11. The original archive is unpacked with the System32 `tar.exe`, never a `tar` from PATH

- Found at review: `build-asm-twins.mjs` ran a bare `tar`. In Git Bash (and wherever Git for Windows
  puts its `usr\bin` first on PATH) that is GNU tar, which reads the `C:` of the archive path as a
  remote host ("Cannot connect to C: resolve failed"), so the unpatched assembler twins were not
  built and `oracle:twins` failed.
- Does: `unpackZip()` runs `%SystemRoot%\System32\tar.exe` (the bsdtar that Windows 10 and later
  ship) by its absolute path; `compare.test.mjs` unpacks a zip while a failing `tar` and Git's
  `usr\bin` come first on PATH.

## Defect reports

### D1 - TRAP #15 tasks 0 and 1 depend on a compiler flag (owner: the simulator engine)

- Found by: the native simulator twin at `/Od`, single-step suite file `TRAP.json.gz` (two tests
  in which the random D0.B is 0 or 1, D1.W is negative and A1 points at memory full of `$FF`).
- What happens: `CODE9.CPP` tasks 0/1 copy the string with `strncpy(buf, inStr, 255)`, which
  writes no NUL when the string is 255 bytes or longer; the engine's patch P24 then skips
  `buf[(short)D[1]] = '\0'` for a negative D1.W (rightly: the original writes below the buffer).
  The text printed is therefore `buf` up to the next zero byte of an uninitialised stack buffer.
  The WebAssembly build prints exactly 255 bytes only because the engine is compiled with
  `-ftrivial-auto-var-init=zero`; MSVC `/Od` prints 255 bytes followed by stack contents (`/O2`
  happened to find a zero there). engine/sim/PATCHES.md P24 states "Here the string is printed up
  to its NUL, at most 255 characters", which the source alone does not guarantee.
- Proposed fix (engine): make the documented behaviour explicit in the patch, for example
  `buf[255] = '\0';` after the `strncpy` (or `char buf[256] = {0};`), marked as part of P24, so
  that no result depends on the compiler flag. Observable effect: none for the WebAssembly build.
- Meanwhile: `compare-sim.mjs` recognises exactly this pattern (`knownDifference`, id `D1`: a
  `textOut`/`textOutCR` of 255 bytes in wasm that the twin continues) and lists it under
  "Expected differences" in the report instead of failing; every other line must still be equal.

#### What the official EASy68K v5.16.1 does (measured at the integration gate)

The original source (`reference/src-sim68k/Sim68Kv5.16.1/CODE9.CPP`, `TRAP()`) has the same
`char buf[256]` local and the same `strncpy(buf, inStr, 255)`, and for a negative D1.W it stores the
0 at `buf[(short)D[1]]`, below the buffer. So with a string of 255 bytes or more it also prints
`buf` up to the next zero byte of the host stack: `buf[255]` and what follows it are whatever the
previous C++ code left there. That is undefined behaviour, and the Wine reference confirms that the
result depends on host-stack residue:

- Probe programs (scratch, not tracked: `build/T4/d1/`) were assembled with the official
  `EDIT68K.exe` and run in the official `SIM68K.exe` under Wine with the text-output log, in the
  oracle image of `tests/oracle/wine` (`easy68k-oracle-wine`; `asm_batch.py`, then
  `sim_run.py log PROG.S68 --exec-log 0 --out-log 1 --drive run`). `LONG` is 300 bytes `'A'`, then
  `'Z'`, 0.
- `LEA LONG,A1 / MOVE.W #-1,D1 / MOVE.B #0,D0 / TRAP #15` printed 255 `A` and one byte `$C0`
  (256 characters). The same with D1.W = -256, with task 1 instead of task 0, with D1.W = `$8000`
  (the store 32768 bytes below `buf` did not crash), and after tasks 3, 8, 13 and 15 earlier in the
  program: always 255 `A` + `$C0`, in two separate runs.
- But the byte depends on the 68000 instruction executed just before the `TRAP`: after `NOP` or
  `MULU` it was `$C0`; after `MOVE.L (SP)+,D5` or after `RTS` nothing followed (255 bytes, like the
  port).
- Controls: D1.W = -1 with the 5-byte string `HELLO` printed `HELLO` (strncpy pads with zeros); D1.W
  = 300 printed exactly 255 `A` (the original writes `buf[255] = 0` itself in that branch).

So no fixed rule reproduces the original here: the extra bytes are a residue of the previous
instruction's handler in the Borland-compiled binary (and could differ again on real Windows). The
port's 255 bytes equal the original in some of the measured cases (after `RTS`, `MOVE.L (SP)+`) and
differ by one trailing `$C0` in others.

Recommendation (for the simulator engine's owner and the gate): keep the port's output (exactly
255 characters, the behaviour the original's own code documents with "terminate at char 255" and
that PATCHES.md P24 describes), make it explicit with `buf[255] = '\0';` in P24 so that it no
longer depends on `-ftrivial-auto-var-init=zero`, and record it in the engine's list of port
differences as "TRAP #15 tasks 0/1 with a negative D1.W and a string of 255 bytes or more: the
original prints up to a few more bytes of host memory after the 255th (observed: none, or one byte
`$C0`, depending on the preceding instruction); the port prints exactly 255". Imitating the `$C0`
would need an emulation of Borland stack residue per instruction handler, which nothing in the
sources defines.

### Assembler: unpatched twins differ only where a patch applies

Not a defect, recorded for completeness: on the corpus the unpatched twins differ from the
WebAssembly assembler only in the object field of lines with an error (P7, 265 runs at `/O2`, 263
at `/Od` with `--local`) and on five checklist programs of T1 that exercise patched defects on
purpose (P5, P7, P8; `UNPATCHED_CORPUS` in `compare-asm.mjs`, the same defects as
`UNPATCHED_DIFFERS` of the engine's test). The patched twins (`/O2` and `/Od`) agree with the
WebAssembly build on all 1,157 runs.
