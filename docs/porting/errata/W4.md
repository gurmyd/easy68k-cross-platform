# Errata of W4 (Engine binding)

What W4 found while binding the two engines: where `docs/ARCHITECTURE.md` or a spec is wrong,
silent or cannot be met as written, what the repository does, and why. Differences between the
engine modules and section 3.2 are not errata of the document; they are in
`docs/ENGINE-BINDING.md`, section 4. No entry changes a declaration of `app/src/contracts/`.

## 1. The oracle comparison of `smoke.X68` needs two more conditions (9.1, W4 acceptance)

- Says: "`smoke.X68` assembles to the native oracle's `.S68` byte for byte and to its `.L68` after
  masking line 3".
- Found: the `.S68` is identical (706 bytes). The `.L68` differs from the oracle's in two more
  ways, neither of them a defect:
  1. **Line 2.** The oracle is the command-line port of version 5.15.4 (toolchain §4): its line 2
     reads `Assembler used: ASy68K Assembler v5.15.04`. The engine is 5.16.1:
     `Assembler used: EASy68K Editor/Assembler v5.16.01`.
  2. **Tab expansion.** The command-line port always expands tabs as "Assembly" tabs (assembler
     §9.4.4); the application's default is Fixed, size 4. `smoke.X68` has one line with tab
     characters (source line 52), which the two settings list differently.
- Does: `app/src/engine/asm.test.ts` assembles with `tabType: Assembly`, masks lines 2 and 3, and
  requires every other of the 109 lines to be equal. It also asserts the two texts of line 2, and
  that line 3 equals the oracle's when the engine is given the oracle's time (so the date format is
  checked, not only masked). The oracle's two files are embedded in the test; they were regenerated
  with `build/oracle/asm-cli-5.15.4/bin/asy68k.exe` on 2026-11-20 and compared with the stored ones.
- Proposed text: "... and to its `.L68` after masking lines 2 and 3 (the oracle is version 5.15.4),
  with the Assembly tab type the oracle uses".

## 2. Where W4's browser tests live, and what follows (8, 7.4, 3.1)

- Says: section 8 gives W4 `app/src/engine/... *.test.ts` and nothing under `tests/`; 9.1 requires
  the fixtures, the 200 cycles and the 500 assemblies "in Chromium and in WebKit"; 7.4 gives the
  browsers to the `e2e` job only; `eslint.config.js` lets a unit test import only the runtime
  packages, `vitest`, `fake-indexeddb` and `node:*`.
- Does: `app/src/engine/browser.test.ts` is a Vitest file that builds the binding with Vite, serves
  it and drives headless Chromium and WebKit through Playwright. Three consequences:
  1. It loads `@playwright/test` and `vite` with `import(name)` from a variable, which the lint rule
     does not see. `docs/requests/W4-config.md` asks for the two names to be allowed.
  2. In the `unit` job of CI no browser is installed, so the suite is skipped there (visibly). The
     same request asks for one step in the `e2e` job, which has the browsers and `engine/dist`.
  3. `npm test` takes about 20 seconds longer on a machine with the browsers installed.
     `EASY68K_BROWSERS=none` leaves the suite out; `EASY68K_REQUIRE_BROWSERS=1` turns a missing
     browser into a failure.
- Proposed text for 9.1 (W4, outputs): "`browser.test.ts` (Vitest file that drives Playwright; run
  in the `e2e` job)".
- Since the gate after wave zero: the lint rule allows the two names for this one file, which now
  imports them plainly. A plain `npm test` skips the suite and says so; it runs with
  `EASY68K_BROWSERS=all` (or `chromium`, `webkit`) or `npm run check:engine-browsers`. In CI it
  runs in the `browser-checks` job on all three systems, not in `e2e`.

## 3. "Loads under the `app://` protocol" cannot be shown by W4 (9.1, 6.7)

- Says: W4 acceptance, "the module loads under Vite, Node and the `app://` protocol".
- Found: `app://` exists only inside Electron. The Electron shell, its protocol handler and the
  harness that starts it (`tests/desktop/dev`, Playwright's Electron support) are DV2's, in wave 1;
  the Electron binary is not installed by `npm ci` on this machine; and W4 may not start GUI
  programs here.
- Does: the binding is tested as far as the protocol is specified (7.6): the production build, at a
  sub-path, served with the handler's content types and the policy as a response header, in
  Chromium and WebKit; and with `.wasm` as `application/octet-stream`. What the handler must
  provide is in `docs/ENGINE-BINDING.md`, section 2.4. DV2's own acceptance already contains "both
  engines ... load under `app://`".
- Proposed text for 9.1 (W4): "... loads under Vite and Node, and from a server that behaves as the
  protocol handler of 7.6 is specified to (the run under `app://` itself is DV2's)".
- Since wave one: DV2's `tests/desktop/dev/protocol.spec.ts` ("both engines start under app://")
  runs both engines under `app://` in Electron, and `windows.spec.ts` checks one compilation and one
  simulator instance per window (`docs/ENGINE-BINDING.md`, sections 6 and 8).

## 4. The engine modules are loaded by URL, not imported (3.1, 3.2)

- Says: 3.1, "`engine/` imports `contracts/` and the two engine modules"; 3.2, "which loads them
  through Vite".
- Does: `loader.ts` has no `import` of an engine file. It names the six files with
  `new URL('<path>', import.meta.url)`, which Vite turns into served or copied assets, and imports
  the modules with `import(url)` at run time.
- Why: (a) `engine/dist/` is not in the repository; with an `import` of a missing file, type
  checking, the dev server and the build of the whole application would fail, and W0's erratum 3
  expects the loader to report a missing engine at run time instead; (b) `asm68k.mjs` itself
  contains a literal `import('../dist/asm68k-loader.mjs')`, so bundling it would bring the same
  failure back; (c) the files reach the browser as the engine packages built and tested them.
- Proposed text for 3.1: "`engine/` imports `contracts/`; it loads the engine modules by URL at run
  time (`loader.ts`)". The lint rule may keep allowing the import; nothing uses it.

## 5. Additions to `testing.ts` (9.1, W4 outputs)

9.1 names three helpers. The binding's own tests needed more, and they are exported because other
packages need the same things (SH3: "driven by 68000 programs through the real engine"):

| Added | Why |
|---|---|
| `assembleProgram(source, files?, options?)`, `TEST_ASM_OPTIONS`, `TEST_ASM_TIME` | A test that drives the engine with a 68000 program has to assemble it; no fixture file is needed. |
| `runProgram(engine, script?)` | The loop around `run()` with the four wait states served from plain data, so that the same script can run in a page. |
| `createMemoryFiles(initial?)` | The file tasks cannot go beyond their first `fileOpen` on a host that answers 0. |
| `TRAP15_TOUR`, `trap15TourSource()`, `runTrap15Tour()`, `TOUR_MARKS` | The program of the acceptance item "a program that calls every TRAP #15 task", with the table of host methods per task. |
| `describeCall`, `bytesOf`, `textOf`, `MemoryFiles` | Small conveniences of the above. |

`createRecordingHost(parts?)` takes the parts too (9.1 gives them to `createTestEngine` only), and
records the calls to a replaced part as well as forwarding them.

The parts are typed with `SimHostParts` of 3.3.1. Until the wave-0 gate `testing.ts` declared its own
copy, `HostParts`, because `SimHostParts` was to be declared in `core/sim-host/index.ts` (SH8) and
`engine/` may not import `core/`; the gate added `SimHostParts` to `app/src/contracts/host.ts`, and
`testing.ts` now uses it (the name `HostParts` is gone; nothing else used it).

## 6. How "every SimHost method the specs say it should" was read (9.1)

- Says: "a program that calls every TRAP #15 task reaches every `SimHost` method the specs say it
  should (recording host)".
- Does: `TRAP15_TOUR` has one entry per call (94 calls: every task of the inventory of trap15-a
  §1.2 and trap15-b §2.1, every sub-task of task 32, the three forms of task 11, both of 24, four
  of 33) with the set of host methods that call reaches according to trap15-a §4-§7 and trap15-b
  §7-§12. The test requires, per call, exactly that set: a method too many fails as well as a
  method too few. `memoryLivePaint` is left out of the sets because the program uses it as its
  marker between tasks.
- The tasks reach 80 of the 93 host methods. The other 13 (`message`, `messagesClear`, `alert`,
  `focusMain`, `autoTraceTimer`, `caption`, `memoryLivePaint`, `logWrite`, `logState`,
  `outputLogWrite`, `ioBringToFront`, `resetSounds`, `netCloseSockets`) cannot be reached by a task;
  one more test reaches them through start-up, a load, the log and the debugger, so that all 93
  imports of the `.wasm` are called through the binding, in Node and in both browsers.

## 7. Spec: a failing open is tried once per free file slot (trap15-a §7, tasks 51 and 52)

- Says: task 51 "Tries `fopen(name, "r+b")` ... Else tries `fopen(name, "rb")` ... Else ...
  `D0.W = 2`"; task 52 "`fopen(name, "w+b")` ... Failure or no free slot: `D0.W = 2`".
- Source: `openFile` and `newFile` (`SIMOPS2.CPP:68-109`) call `fopen` inside the loop over the
  eight slots and leave the loop only on success. A name that cannot be opened is therefore tried
  for every free slot: with no file open, task 52 calls `fopen` 8 times and task 51 calls it 16
  times (update, then read, per slot).
- Seen at the boundary: a recording host receives `fileOpen("OUT.TXT", 2)` eight times for one
  failing task 52, and sixteen `fileOpen` calls for one failing task 51. The results in D0 and D1
  are as the spec says.
- For SH6 (`ProgramFiles`): `fileOpen` must tolerate being asked repeatedly for the same failing
  name; anything it does on failure (a message, a log line) happens up to 16 times per task unless
  it guards against that.

## 8. The address `createNetClient` receives comes from the engine (3.3.4)

- Says: "W4's binding supplies it by reading register A2 when it forwards the call".
- Does: since the wave-0 gate the engine passes it itself (`docs/requests/W4-engine-sim.md`, item 2,
  applied): `shim/host-imports.js` gives `host.createNetClient` the 68000 address of the string,
  which is `A2 & $FFFFFF`, the address the original takes the string from
  (`&memory[A[2] & ADDRMASK]`, `CODE9.CPP:1266`), not the raw register. The binding no longer reads
  A2. A test of the binding loads A2 with `$FF002000` and expects `$002000`; the engine's own suite
  has the same check (`engine/sim/test/io.test.mjs`, task 100).
- Proposed text for 3.3.4: "the engine passes it as the third argument (`A2 & $FFFFFF`)".

## 9. The listing selection after a load (gate I1 round 3; sim-ui §6.4, §8.2)

- Defect (major, integration scenario; also errata U1.md entry 8): after a second program was
  opened over a rewound first one, `listingHighlight` named a row of the new listing that is not the
  PC (tutorial1 run and rewound, then tutorial2: row 21, `0000100A trap #15`, with PC = `00001000`).
- Cause: `OpenFile` (`SIM68Ku.cpp:289`, shim `form1.cpp`) calls `ListBox1->Items->Clear()`. In the
  VCL that is `TListBoxStrings.Clear`, which sends `LB_RESETCONTENT`; afterwards `LB_GETCURSEL`, the
  value of `ItemIndex`, is -1. The shim's `TStrings::Clear` emptied the lines but left `ItemIndex`;
  only `TListBox::Clear()` (Close) reset it. When the new program starts at the PC already shown,
  assigning the same text to the PC box runs no `regPCChange`, so no `highlight()` followed and the
  stale index survived.
- Repair: the listing's `TStrings` has a `cleared` hook that sets `ItemIndex = -1`
  (`listingItemsCleared` in `shim/form1.cpp`; recorded in `engine/sim/PATCHES.md` section 3). Now
  the selection is -1 after such a load, as in the original, and the next step selects the PC row.
- Tests: `engine/sim/test/loader.test.mjs` "opening a program over another one drops the listing
  selection ..."; `app/src/engine/sim.test.ts` "the listing selection (listingHighlight) across
  loads". Both failed on the old `engine/dist` (14 instead of -1) and pass after the rebuild.

## 12. The listing selection after a load is the original's: no row when the PC text is unchanged (gate I2)

- Reported (gate I1, carried to I2, major): in check-wave1's tour five of the ten official
  examples (tutorial2, MACRO, clockWithSound, graphicSound, mouseWindowSize) show no selected row
  after the load (engine row -1), and the check expects the PC's row.
- The original's load path (`SIM68Ku.cpp:270` `OpenFile`): `initSim()` (`STARTSIM.CPP:33`) calls
  `scrshow()`, which writes the *current* PC into the PC box and calls `highlight()`; then
  `ListBox1->Items->Clear()` drops the selection (entry 9); then the listing is loaded and
  `regPC->EditText = <address of the first listing line>`. Only that assignment can select a row
  again, through `OnChange = regPCChange` -> `highlight()` (`SIM68Ku.cpp:1186`), and `OnChange` runs
  only when the text changes. Nothing else selects a row before the first repaint. So after a load a
  row is selected exactly when the new start PC differs from the PC shown before the load; after a
  Rewind that is the previous program's start PC. tutorial1 and tutorial2 both start at `00001000`,
  so the original shows tutorial2 with no selected row.
- Measured in the official SIM68K.exe under Wine (`build/W4/probe/probe_tour.py`: the tour's
  order, each program opened with File > Open, F9, 2 s, F6, Ctrl+F2; the selection colour counted in
  the list box of a screenshot of each load). Forward: selected for tutorial1, tutorial3,
  tutorial4, fileio, clockDigital; no row for the five above. Reverse: selected for
  mouseWindowSize, MACRO, fileio, tutorial4, tutorial3; no row for graphicSound, clockWithSound,
  clockDigital, tutorial2, tutorial1. The port gives the same 20 answers (shim `form1.cpp` already
  follows the original statement for statement); no engine change.
- Test: `app/src/engine/sim.test.ts` "the ten official examples, opened one after another (forward
  | reverse), select what the original selects" (and, where a row is selected, it is the PC's).
- What follows for others: the check's expectation is wrong, not the product. check-wave1 must
  expect a selected row only where the original selects one (equivalently: the view's selected row
  equals `listingHighlight`, and is -1 when the start PC equals the PC shown before the load). The
  listing view (U1) must keep showing no selection while `listingHighlight` is -1; it does.
- Found while adding that test: `runProgram` (`testing.ts`) checked `maxInstructions` only while
  `run()` returned Running, so a program that waits on every pass of its loop (the clock examples,
  task 23) never stopped and the test worker ran out of memory. The limit is now checked after every
  status that does not end the run; test "ends with 'limit' for a program that waits on every pass of
  its loop" in `testing.test.ts`.

## 14. Tasks 53 and 54: two answers of the Borland `fread` / `fwrite` (gate I2; T3 F3, F4; SH6 E1)

- Measured by T3 in the official binary under Wine (trap15-a `a31`, `a32`): task 54 with D2 = 0 gives
  D0.W = 0 (the port gave 2); task 53 with A1 = $2000 and D2 = $FFFFFFFF, whose bounds test
  `(A1 & ADDRMASK) + D2 > MEMSIZE` wraps, gives D0.W = 0, leaves D2 at $FFFFFFFF and reads nothing
  (the port gave 2). SH6's errata E1 expected D0 = 0 and D2 = 10 from trap15-a's text; the
  measurement wins.
- Cause: the C library. Borland's `fwrite` returns the item count for an item size of 0, C99's
  returns 0; Borland's `fread` returns the requested count for that request, while here the count
  reached the host as -1 (`(int)size` in `hostFileRead`, then `Math.min(data.length, -1)` in
  `host-imports.js`).
- Repair (build level, no original file edited): `shim/prelude.h` maps `fread` / `fwrite` to
  `easy68k_fread` / `easy68k_fwrite` in `shim/hostfile.cpp`, which answer exactly those two requests
  as measured (`fwrite` with size 0 returns the count; `fread` of more than `INT_MAX` single bytes
  returns the count and reads nothing; such a count reaches `fread` only when the bounds test wraps)
  and pass everything else to the C library. `PATCHES.md` section 3.
- Tests: `engine/sim/test/io.test.mjs` "file tasks 50-59 ..." (its D2 = 0 expectation changed from 2
  to 0), `app/src/engine/trap15.test.ts` "TRAP #15 edge cases measured in the official binary". Both
  cases failed on the previous `engine/dist` (D0.W = 2) and pass after the rebuild.
- T3's suite now reports both entries of `known-differences.json` as "now equal; remove the entry";
  `docs/requests/W4-t3-known-differences.md` asks T3 to remove them.

## 16. INCLUDE names with `..` after a missing folder, or a trailing dot (gate I2; E5's review)

- E5's reviewer found that `INCLUDE 'q\..\lib.x68'` (q missing) and `INCLUDE 'lib.x68.'` give
  "Unable to access specified file" in the application, and suggested a change "in collect.ts and in
  the engine's key lookup".
- The engine needs none: `engine/asm/shim/ez_file.cpp` (`ezCanonicalPath`) already resolves `.` and
  `..` lexically and drops trailing dots and spaces of each component, as Win32 does. New test in
  `app/src/engine/asm.test.ts`, "'..' after a folder that does not exist, and a trailing dot,
  resolve as on Windows": with the files supplied, both are found. The file is missing only because
  E5's scan (`features/assemble/collect.ts`) does not supply it; that is E5's to repair.
