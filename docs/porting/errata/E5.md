What E5 found while building `features/assemble/` from `docs/ARCHITECTURE.md` 3.2, 3.8.3, 4.9, 5.3,

## 1. When Execute is enabled: 4.9 step 9 against note 20 and editor-ui §10.4

- Says: 4.9 step 9, "`Execute` is enabled when `result.executeEnabled` is true and the S-record was
  written." Note 20, last sentence: "Execute is enabled as the engine reports it
  (`AsmResult.executeEnabled`)." editor-ui §10.4 QUIRK: the original enables Execute on zero errors
  even when *Generate S-Record* is off and then runs whatever `.S68` already exists.
- Does: 4.9, the more specific text: `executeEnabled && sRecord !== null`. With *Generate S-Record*
  off the button is disabled, so a stale `.S68` from an earlier assembly is never run by mistake.
- Proposed text for note 20: "... Execute is enabled when the engine reports it
  (`AsmResult.executeEnabled`) and this assembly wrote the S-record (4.9 step 9)."

## 2. `EditorMessage.file` of the document's own rows (3.12.1)

- Says: `EditorMessage.file: VPath | null`, without saying what null means.
- Does: a row of the assembled document carries the document's path, and `null` when the document
  has never been saved (its source is assembled as `<Untitled>/untitledN.x68`, 3.8.2, but the
  document has no path). A row of an include file carries that file's VPath. The Messages panel
  shows its `File` column (1.3.3) only when a row names a file other than the document's own.
- Proposed text for 3.12.1: "`file`: the file the message belongs to; null = the document whose
  list it is, when that document has no path yet."

## 3. Which include files have their list cleared (editor-ui §10.5, DIRECTIV.CPP:709-719)

- Says: "When an `INCLUDE` starts, an already open window for that file has its message list
  cleared." The engine does not report which INCLUDEs it executed.
- Does: before the messages are routed, the lists of the open documents whose path is one of the
  INCLUDE files that the file scan of 3.8.3 found are cleared. The scan is loose on purpose (also
  inside a block that conditional assembly skips), so a list can be cleared for a file that the
  assembly did not actually include. Nothing a program can observe depends on it.

## 4. A cancelled or failed auto-save (4.9 step 1)

- Says: "a cancelled Save As cancels the assembly." `DocumentService.save` resolves to false for
  "cancelled or failed" alike.
- Does: both cancel the assembly (nothing is cleared, nothing is assembled). The original calls
  `mnuSaveClick` and assembles whatever happened.

## 5. A write failure (4.9 step 6)

- Says: "A write failure shows `File Access Error. ...` and no status dialog."
- Does: the box, then stop: no message boxes of the engine, no rows, no new summary (steps 7-9 are
  skipped). The document's list was already cleared in step 2. In the original the exception that
  leads to this box comes from writing `EASy68Ks.tmp`, before anything is assembled, so it shows no
  rows either.

## 6. An assembler that rejects (3.2, ENGINE-BINDING.md 6)

- Says: 4.9 step 5 handles `result.fatal`. `AsmEngine.assemble` also rejects: for arguments it
  refuses (a tab size outside -99..99, possible through a hand-edited `*~Tab size~` trailer) and,
  through the bootstrap's lazy binding, when the engine cannot be loaded (`EngineLoadError`).
- Does: a rejection is shown exactly like a fatal result: one row
  `The assembler stopped: <error message>`, no file, no dialog.

## 7. The snapshot retry when the snapshot adds nothing (3.8.3 step 3)

- Says: take the snapshot, add everything, "and assemble once more".
- Does: assembles once more only when the snapshot added at least one file. With the same files,
  options and time the engine gives the same result (every assembly runs in a fresh instance), so
  the second run would change nothing.

## 8. Clear Error Messages on a document that was never assembled itself (editor-ui §4.2, errata W3.md 15)

- Says: §4.2, the list "height set to 7 px". The shell applies the height rule from
  `AppState.messages` and `AppState.assemble` (`messagesPaneHeight`).
- Does: `ed.msg.clear` empties `AppState.messages[id]` and leaves `AppState.assemble[id]` alone.
  For the assembled document the shell then shows 7 px (checked in both browsers). For an include
  file's document, which received rows but has no summary of its own, the shell shows 5 px instead
  of 7. For W3: a "cleared" mark in the shell's own state would give 7 px there too; not worth a
  contract change.

## 9. Enabled states (editor-ui §2.7, 4.9 last paragraph)

- `ed.project.assemble` is enabled while a document is active and some open document is a source
  document. The original's flag is global for the frame, so an active list document can be
  assembled while a source document is open (its quirk, kept); with only list documents open it is
  disabled. While an assembly runs the command reports disabled (the toolbar button's busy state of
  4.9), and a second F9 is ignored.
- `ed.msg.clear` is enabled while the active document's list has rows. The original's list is
  disabled while it is empty, so its context menu cannot be opened then.

## 11. Two panes (2.2, note 9)

- Says: "Messages panel: under the editor of the active document ... Each document has its own
  list."
- Does: the shell has one `messages` region under the editor area (W3), and the panel shows the
  list of the active document, whichever pane it is in.

## 12. Include names with trailing dots or spaces (3.8.3, assembler §3.4.1; gate I2)

- Found: `INCLUDE 'lib.x68.'`, `INCBIN '..\Shared.\blob.bin . '` and similar names gave
  `ERROR: Unable to access specified file` when the file lay outside the program directory (inside
  it, the snapshot retry hid the problem). Win32 drops the trailing dots and spaces of every
  component of a name before it opens it, and the engine's own file layer does the same
  (`engine/asm/shim/ez_file.cpp`, `ezCanonicalPath`), but `collect.ts` passed the name to
  `Vfs.resolve` as written, so the file never reached the engine.
- Does: `collect.ts` resolves `win32Name(name)`: trailing dots and spaces of every component
  dropped, a component left empty removed, `.` and `..` kept for `Vfs.resolve`, which applies them
  lexically. Tested in `collect.test.ts` and, with the real engine, in `assemble.test.ts`.
- The review also reported `INCLUDE 'q\..\lib.x68'` (q does not exist) as unresolved. `Vfs.resolve`
  was already lexical, so `q\..` cancels out; the probe's layout (`lib.x68` in the mount root, the
  program in `p/`) makes the name `p\lib.x68`, which does not exist, so the error was right. A name
  that does reach a file through a folder that does not exist (`..\..\nothere\..\root.x68`) is now
  covered by the test above.
- Not checked against the official binary: Wine's handling of trailing dots may differ from
  Windows'; the original runs on Windows, whose rule is documented (Naming Files, Paths, and
  Namespaces) and which the engine already follows.
