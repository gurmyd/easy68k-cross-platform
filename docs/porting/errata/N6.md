# Errata of N6 (the viewer and the documents' hooks)

Where `docs/ARCHITECTURE-PLUS.md` is silent, ambiguous or does not match what N6 found, what the
code does and why. No entry changes a declaration of P4.4.

## 1. Extensions are compared in any letter case (P3.4.1)

P3.4.1 says "(any letter case)" only in the row of `.X68`, `.L68`, `.S68`; the rows of `.pdf` and
the picture extensions name them in lower case. `features/viewer/classify.ts` compares every
extension in any letter case: `REPORT.PDF` and `photo.JPG` (a camera's own spelling) are shown by
the viewer. A file the viewer takes is never one the original could use, so nothing a program can
observe changes.

## 2. The size in the strip (P3.4.2)

P3.4.2 lists "the size" in the strip without a form. `sizeText` of `features/viewer/texts.ts`
follows the figures of P3.5 (`3.4 MB`): `1 byte`, `<n> bytes` below 1,000, then `<x.y> kB` and
`<x.y> MB` with one decimal (decimal units, as P3.5's figures read).

## 3. `onWritten`'s `time` is the wall clock (P4.4, P5 N6)

P5 N6 says "`time` from the service's clock". `Clock.now()` is monotonic milliseconds of one page
(`performance.now()`), which neither another window nor a later session can compare and which is
no date to show. The document service therefore takes `clock.wallTime().getTime()` (milliseconds
since 1970, the same clock that stamps the settings across windows). `DocumentServiceDeps.clock`
is optional so that the existing tests of other packages that build a `DocumentManager` by hand
still compile; without a clock `time` is 0. `createDocumentService` always passes `ctx.clock`.

## 4. `relocate`: how the draft is rewritten, exact paths, the kind

- **The hook.** P5 N6 allows a change to `features/documents/drafts.ts` "only if `relocate` needs a
  hook to rewrite a draft". It does: the draft keeper writes a draft only when a document's
  revision changed, and `relocate` keeps the revision (acceptance). `DocumentManager` gained
  `onRelocated(listener)` (not part of the contract; `features/documents` uses it through the
  class, as it already uses `fileTime`), and `startDraftKeeper` rewrites the drafts of the moved
  documents at once under their existing keys. `relocate` awaits its listeners, so the draft names
  the new path when `relocate` resolves; a listener that throws does not make `relocate` fail.
- **A test file the entry does not list.** The drafts hook is tested in
  `app/src/features/documents/drafts-relocate.test.ts` (new, N6's), because `core/` tests should
  not drive a feature and the entry lists only `core/documents/service.test.ts` for new cases.
- **Exact paths.** `relocate(from, to)` compares paths exactly (letter case included), as `open`
  compares them (editor-ui §6.2 step 2): a document whose path is `from` or lies below `from/`
  follows. N5 passes the paths it moved, in the spelling its tree holds, which is the spelling the
  documents were opened with.
- **The kind does not change.** A document keeps `kind` (source or list) after a rename that
  changes its extension, as the contract's "text, modified state and history unchanged" reads;
  the original had no rename in place.
- **A file that cannot be stat'ed** at the new place gets the recorded time null ("not known"), so
  its next Save does not ask the question of main 3.8.6 rule 3.

## 5. A second open of the same path (P3.4.2)

P3.4.2 says both "A second open of the same path selects its tab (`selectTransient`)" and "The
bytes are read once when the viewer opens; a later change of the file is not followed (`Open`
again shows it)". Both hold: a second `show` of the same path selects the tab and, when the bytes
read now differ from the bytes shown, shows the new bytes (a new `blob:` URL; the old one is
revoked). With equal bytes nothing changes. A change of the file while the viewer is open is not
followed until the file is opened again.

## 6. When the dock refuses the tab

`wants()` asks `acceptsTransient()`; should `openTransient` then still return false (the dock
changed in between), `show` opens the file as text (`open(path, { asText: true })`), as with
`viewer` off, and keeps nothing. P3.4.2 does not name this case.

## 7. `Open as Text` and `Export`: in the strip, or under the notice, not both

P3.4.2 gives the strip `Open as Text` and `Export` for every viewer, and the notice "the buttons
`Open as Text` and `Export`". Read literally, a notice shows each button twice (in the strip and
under the notice's text), and a screen reader hears two buttons of each name in one tab (the gate's
reviewer found this). Since the gate (2026-11-22) the buttons are where the notice is: while the
notice is shown (a file that is not text, a picture that does not decode, a PDF where the browser
shows none) the strip holds the name and the size only, and the notice has `Open as Text` and
`Export`; a picture and a PDF frame have them in the strip. Every viewer therefore still offers both
commands, each once. In the desktop app `Export` is shown in neither place ("desktop app: not
shown"; the notice's own `Export` is read the same way).

## 8. The PDF line under the strip only above a frame

The line `If the PDF does not appear, ...` is shown "under the strip" of a PDF viewer. Where the
browser says it shows no PDFs, the notice replaces the frame and says the same thing more plainly,
so the line is shown only while the frame is.

## 9. `check-harness.tsx` (for the browser check only)

`features/viewer/check-harness.tsx` shows the real viewer model and panel in a stand-in for the
dock's tab, so that `check-viewer.mjs` checks the viewer itself whether or not the dock accepts
transient panels. Nothing in the application imports it (the check loads it from the development
server), so the production build does not contain it.

## 10. Chromium with its PDF viewer in the check

Playwright's default Chromium (the headless shell) has no PDF viewer and reports
`navigator.pdfViewerEnabled === false` (docs/requests/N0.md 5.1), so the viewer rightly shows the
PDF notice there. `check-viewer.mjs` therefore starts Chromium as Playwright's full Chromium in the
new headless mode (`channel: 'chromium'`, installed by `npx playwright install chromium`), which
reports `true` and draws the PDF, as Chrome and Edge do. Where that build cannot start, the check
uses the headless shell and says in a note that the PDF frame was not checked.

## 12. The viewer is asked before the "already open" step (P5 N6, P3.4.2)

P5 N6 puts the viewer's question after the read and says "the 'already open' question comes first,
as today". Taken in that order, an Open of a file that is open as text (after `Open as Text`) and
that the viewer takes first discarded the text document (asking only when it was modified) and then
showed the viewer: the document the person had open disappeared (the gate's reviewer, probe
`open('/browser/p.svg', { asText: true })` then `open('/browser/p.svg')`: `list()` empty). An Open
must never close what a person has open. So `open` now reads the file and asks the viewer before
the "already open" step: when the viewer takes the file it shows it and the text document stays
open, unchanged, with no question. A file the viewer does not take goes through the "already open"
step exactly as before (the question when modified, the document replaced in its tab); when such a
document was open, the file is read again after the question, as editor-ui §6.2 orders it, and when
none was, the bytes read for the viewer are the ones loaded (one read, as before). With `asText` or
without a viewer nothing changed. `core/documents/service.test.ts` has the four cases;
`check-viewer.mjs` (dock pass) checks it in both browsers.

## 13. The include files the assembler opens for its messages (P3.4.1)

P3.4.1 lists the opens that ask the viewer: the Files panel, `Open File...`, a drop, a start-up
argument. `features/assemble/assemble.ts` (`routeMessages`, E5's file, which no package of the
stage owns) opens an include file that error rows refer to with `deps.documents.open(path)`, so with
the viewer on an include file that the viewer takes (a picture or PDF extension, or a zero byte in
its first 8 KB) went to a viewer tab and its rows stayed under the assembled document. What the
assembler produces (the bytes of the `.L68` and `.S68`, the messages, the counts) never depended on
the viewer: it reads include and INCBIN files from the file system (`collectFiles`), not through the
document service. The repair is one argument in E5's file, `open(path, { asText: true })`, asked for
in `docs/requests/N6-include-as-text.md`; `features/viewer/callers.test.ts` lists every caller of
`DocumentService.open` in the application and proves the assembler's and the simulator's file reads
untouched (see the request for its state).

## 11. `/favicon.ico` in the browser check

Chromium's PDF viewer asks the page's origin for `/favicon.ico`, which neither the development
server nor the site has; the 404 it logs is not the application's and `check-viewer.mjs` ignores
it (only that URL).

## 14. The frame shows only the viewer's document (decision D-c, P3.4.2)

Decided by the architect, 22 November 2026 (decision D-c of the third round of the stage's gate):
the frame of the viewer never shows anything but the document the viewer gave it; when the frame
is found to show another address, the viewer puts its document back; no new text is shown for it.

The second round's review and erratum N0 11 recorded that, before a service worker controls the
page (a first visit) and in the desktop app (which has none), nothing refuses a navigation of the
PDF frame (it has no sandbox, P3.4.2, and `frame-src 'self' blob:` allows the application's own
origin): sent to the application's page, it showed a second, nested copy of the application.
Measured in this round (Playwright's Chromium and WebKit on Windows, a production build served
without a worker, `c:\easy64k\build\gate3-layout-plus\frame-probe.mjs`):

| The frame sent to | Chromium: load event, address the page reads | WebKit |
|---|---|---|
| (its own PDF, before) | the `blob:` address, `application/pdf` | `about:blank`, `text/html` (its PDF document is not readable as the blob's) |
| the application's page, `?open=` | a load event; the address, readable; the copy of the application boots in it (`.e68-shell` after about 100 ms) | the same (about 150 ms) |
| another site, a `data:` document (refused by `frame-src`) | a load event; not readable (`SecurityError`, Chromium's error page) | `about:blank`, readable |
| `about:blank` | a load event; `about:blank` | the same |

Chromium's built-in PDF viewer keeps the frame's address the `blob:` one (a fragment such as
`#page=2` may be added by it); WebKit reports `about:blank` for its own PDF document.

So `features/viewer/frame-watch.ts` decides from one reading of the frame's address: the `blob:`
address without its fragment is the viewer's own; a frame without a window decides nothing, and so
do `about:blank` and an empty address before the own address was seen there (WebKit shows its own
PDF so, and such a frame is empty; after it was seen, see decision D-j at the end of this entry); an address
the page cannot read is not the viewer's once its own document was seen there (Chromium) and decides
nothing before (a browser whose PDF viewer the page cannot read would otherwise load the document
again and again); every other readable address is not the viewer's. `ViewerPanel.tsx` (`PdfFrame`)
reads the address at each load event of the frame and every 200 ms (a slow copy of the application
fires its load event late; its address is readable as soon as it is committed). When the frame is
not the viewer's, a fresh frame with the same `blob:` source replaces it (a new element: the old
one's browsing context, and with it the nested application, ends; the tab, its strip and the
`blob:` URL stay). A guard allows at most 5 such restores in 10 seconds, so that a browser that
reports its own document in a way not foreseen here cannot loop. A picture is an `<img>`: it has no
frame that could be sent anywhere. The frame carries `data-e68-viewer-frame` (the number of
restores, for the checks); nothing a person reads changed.

Checks: `frame-watch.test.ts` (which readings count as not the viewer's, the guard);
`check-viewer.mjs`, pass `production without a worker`, and `tools/check-frame-policy.mjs`, pass
`first visit without a worker` (Chromium and WebKit): the PDF frame sent to the application's page
and to its `?open=` address shows its document again within 2 s and keeps no copy of the application
3 s later; a picture's viewer has no frame. With the worker in control, the existing refusals of
`check-frame-policy.mjs` still pass (the viewer then puts its document back after a refused load in
Chromium as well).

Not run: the desktop app (it cannot be opened with a window on this machine). Its PDF frame is
Electron's Chromium with the same code; whether Electron's PDF viewer reports the `blob:` address
as Chromium does was not measured. For the manual list (`docs/MANUAL-TEST-MAC.md`, not N6's file):
"Desktop app: open a PDF that contains a link to a web page and one to `index.html`, click each in
the viewer; the viewer must show the PDF again within two seconds, never a second copy of the
application, and the PDF must not flicker or reload by itself while you read it."

**Decision D-j (the gate's fourth round, 22 November 2026): an empty frame.** The third round's
review found that a PDF frame sent to `about:blank` stayed empty in both browsers, because
`about:blank` decided nothing. Now, once the frame's own `blob:` address was read there (Chromium),
`about:blank` (or an empty address) counts as not the viewer's when it is read at the frame's load
event or in two readings in a row; a single reading between other ones decides nothing, because a
frame that loads its document again (as a frame the dock moves does) is empty for a moment, and
putting the document back then would only load it once more. `ViewerPanel.tsx` passes `loaded` for
the reading at the load event. Before the own address was seen (WebKit, which reads `about:blank`
for its own PDF), an empty frame cannot be told from the document, so it still decides nothing:
**the gap that remains**: in WebKit (Safari) a PDF frame that a script or a link sends to
`about:blank` stays empty until the viewer's tab is opened again; nothing else is shown in it, no
script of the page runs in it, and nothing loops. Checks: `frame-watch.test.ts` (loaded, twice in a
row, a single reading, a frame without a window between, and nothing before the own address);
`check-viewer.mjs`, pass `production without a worker`: in Chromium the frame sent to `about:blank`
shows its document again within 2 s (75 ms measured) and 3 s later still; in WebKit the pass notes
the gap and checks that such a frame stays one frame, with no copy of the application and no
restore loop.

## 15. A document opened or chosen is shown in front of a viewer (P1.2; O-1 of the gate's fourth round)

`core/documents/service.ts` gains the hook `deps.shown(id)` (optional; without it nothing changes).
`activate(id)` calls it every time, also for the document that is active already (before, an
`activate` of the active document did nothing at all; it still publishes nothing then), and `reload`
calls it after a successful reload of the active document. Each call is in its own try/catch: the
dock's reaction never makes an open, a choice or a reload fail. `features/documents/index.ts`
passes `shown` as `dockOf(ctx).documentShown()` (errata N1 28: a viewer in front of the Editor gives
way to it). The start-up: when the start-up file did not open as a document (the viewer took it, or
it could not be read), the template document `startupDocument` makes then does not tell the dock
(a `WeakSet` of the windows doing that), so the start-up PDF stays in front, as P5 N6 asks
("`?open=/browser/a.pdf` at start-up shows the viewer and the Editor holds the template
document"); `check-viewer.mjs`'s dock pass now asserts that the viewer is visible then. Tests:
`core/documents/service.test.ts` (`shown`: New, Open as New Document, Open, a draft brought back;
`activate` of the active document; the "already open" question answered No; a reload of the active
document and not of another; nothing for a close, a file the viewer takes or a missing file; a
listener that throws).
