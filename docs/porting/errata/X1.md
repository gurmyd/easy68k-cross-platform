# Errata of X1 (end-to-end harness, editor and application suites)

What X1 found while building `tests/playwright.config.ts` and `tests/e2e/{fixtures,editor,app}/`
from ARCHITECTURE.md 6.6, 9.4 and editor-ui §20: where the document is silent or does not fit
the code, what the suites do, and why.

## 1. "Every editor row of 1.3 whose kind is `web-e2e`": there is no `matrix.json` yet

- Says: 9.4 X1, "a test for every editor row of 1.3 whose kind is `web-e2e`". The kind of a row is
  set in `tests/parity/matrix.json`, which is X2's (wave 3) and does not exist.
- Does: X1 chose the rows itself. Every row of 1.3.1, 1.3.2 and 1.3.3 that a browser can show has a
  test in `tests/e2e/editor/` (the file per area is named in the file's header). Rows left to other
  kinds: the desktop-only chords (Cmd+W, Cmd+Q, Cmd+, ; `desktop-e2e`), the Easter egg and dead code
  (`x`), `settings.dat` positional parsing in detail and the highlighting vectors (unit tests of E4
  and E3; the e2e suites check a sample in the real editor), what a real browser does with a
  cancelled key (manual, 6.8). X2 can take the test titles as the ids for `verifiedBy: web-e2e`.

## 2. The production build has no page object

- Says: 6.6, "against the production build served locally". The browser checks of waves 0 and 1
  read state through `window.__easy68k`, which `main.tsx` sets in development builds only.
- Does: the suites act through the interface and read what a user sees. Bytes in storage are read
  with the Files panel's Export... and written with Import... or a drop. The editor's text and
  selection are read from the CodeMirror view of the document element, found the way
  `EditorView.findFromDOM` of the pinned `@codemirror/view` finds it (`cmTile.root.view`), because tab
  characters are drawn by a widget and are not in the DOM text. If `@codemirror/view` changes that
  internal, `viewIn()` in `fixtures/test.ts` is the one place to adapt.

## 3. Port and server

- Says: W0's configuration served `npm run preview` on the fixed port 4173.
- Does: the configuration picks a free port when it is first read and passes it to the workers in
  `E2E_PORT`; `fixtures/serve.mjs` serves the build with Vite's preview API and the application's
  configuration (same headers, CSP included). `E2E_DIST` serves another build folder (this PC: a
  build in `build/X1/dist`, because `npm run build` writes `app/dist`, which others use). CI is
  unchanged: it builds, then the configuration serves `app/dist`.

## 4. Service workers are blocked except in the offline test

- Says: nothing.
- Does: `use.serviceWorkers = 'block'` for every test but `app/offline.spec.ts`: the worker
  precaches about 17 MB in every new context, which made every test pay for an install. The offline
  test allows it. Playwright's WebKit on Windows has no service workers; that test is skipped there
  only (it runs in WebKit on macOS and Linux), as DV1's check does.

## 5. One console message is expected

- The fixture fails a test whose page logged a console error. The Help panel's sandboxed frame
  without scripts (2.7) makes Chromium and WebKit log `Blocked script execution in '<help page>'
  because the document's frame is sandboxed ...` for every original help page with a script. That
  is the design, so `EXPECTED_CONSOLE` in `fixtures/test.ts` lets exactly that message through.

## 5a. The accessibility scan leaves out the help frame

- 6.6 asks for an axe scan of each mode and each dialog. axe cannot run inside the Help panel's
  frame (sandboxed without scripts, 2.7): it waits for the frame until the test times out. The
  frame's content is the original help, not the port's interface, so `app/a11y.spec.ts` excludes
  `.e68-help__frame` and scans the panel around it. Q1 (tests/a11y) may want to scan the help pages
  separately, outside the sandbox.

## 5b. Offline help in WebKit is an expected failure

- First assumed to be a defect of Playwright's WebKit for Windows only, and skipped there. CI run
  44941673365 showed the same in WebKit on ubuntu-latest and macos-latest: the application reloads
  offline, but the help page in the frame does not load (the panel keeps the fallback title
  `Introduction`; console: `Failed to load resource: WebKit encountered an internal error`).
- So `app/offline.spec.ts` now has two tests. "a reload with the network off brings the application
  back and the editor works" runs in every browser on every system, Windows WebKit included.
  "offline, Help > Help shows the introduction page" is `test.fail()` in WebKit with the reason
  "H1/DV1", and runs as an ordinary test in Chromium. Whether Safari itself has the defect is not
  shown (no Safari on the runners); the owners of the help panel (H1) and of the service worker
  (DV1) are told in X1's result. When it is repaired, the test reports "expected to fail, but
  passed": then the `test.fail` line goes.

## 5c. Printing in the tests never opens a print dialog

- The web platform prints from a hidden frame that it focuses and removes on `afterprint`, with a
  60-second fallback. Playwright's WebKit returns from that frame's `print()` without `afterprint`,
  so after Ctrl+P the invisible frame kept the keyboard focus and the chords test's next keys went
  to the frame (CI run 44941673365, all three systems). `fixtures/printing.ts` replaces `print()` in
  every child frame by one that records the document and reports `afterprint`, as a browser does
  when its dialog closes; `editor/print.spec.ts` and `app/chords.spec.ts` use it. What a real print
  dialog does is the manual table of 6.8.
- Reported to the owner of `app/src/platform/web.ts`: in a browser that never reports
  `afterprint`, the keyboard stays in the hidden frame for up to 60 seconds after printing.

## 5d. Save As and Open File wait for the document

- The file dialog closes before the save or the read is finished. `App.saveAs` waits until the
  active tab carries the new name without the Modified dot, `App.openFile` until the opened file is
  the active tab. Without it, GitHub's macOS runner sent the next command to the old document.

## 5d-bis. An extra window adds a minute to the test's time limit

- On this PC under the load of the gate (gate I2, round 1), "a file saved in one window appears in
  the other" failed 2 of 5 times in WebKit with "Test timeout of 120000ms exceeded". The trace showed
  no wait that failed: loading each window took about 40 s (Navigate 15.7 s and 10.8 s, the shell
  9.2 s and 15.7 s), single clicks 7 to 11 s, and the save finished. `App.openWindow` now adds
  `EXTRA_WINDOW_TIME` (60 s) to the test's limit for each window it opens; no expectation or action
  waits longer. With it, two-windows, drafts and fixtures passed 69 of 69 (3 repetitions, WebKit).

## 5e. Menus on the macOS key map show no access keys

- The shell's menu bar underlines no access key on macOS (1.3.2, note 14). `editor/menus.spec.ts`
  expects the original's access keys on Windows and Linux and none on macOS.

## 6. Key maps

- The page gets the key map of the system the tests run on (`navigator.platform` set by an init
  script, as E2's check does): macOS on a Mac, Windows on Windows and Linux. Playwright's device
  presets would otherwise give Chromium a Windows user agent on a Mac runner and WebKit a Mac one on
  Linux, a combination no user has (the browser's own clipboard keys follow the real system).
  `editor/shortcuts.spec.ts` runs the commands the dispatcher handles on both key maps.

## 7. Expected failures of wave-2 features

- `fixtures/pending.ts`: a test of E4, E5, E6 starts with `requirePackage()`. The package counts as
  landed when its commands are enabled with the start-up document active (`ed.options.assembler` and
  `ed.options.editor`; `ed.project.assemble`; `ed.edit.find`, `ed.edit.replace`, `ed.file.print`).
  While not, the test is `test.fail()` with the package id in the reason and stops at once. The tests
  of those features are written from editor-ui §10-§14 and 1.4 notes 2, 7, 8, 18-20, and assume the
  accessible names a user reads: dialog titles (`EASy68K Assembler Options`, `EASy68K Editor
  Options`, `Find`, `Replace`, `Assembler Status - <name>`), labels (`Find what:`, `Replace with`,
  `New Font:`, `Color Presets`), check boxes and buttons by caption, a `[data-e68-panel="messages"]`
  region in Editor mode, and for Print the web platform's hidden frame (`platform/web.ts`). Where a
  landed feature names a control differently for a good reason, the test is to follow it.
- Not settled by the documents, therefore assumed: Print with a selection prints only the selection
  (the original asks in its print dialog, which a web page cannot offer); the
  `Import/Export Settings...` dialog has buttons whose names contain `Export` and `Import`.
- Settled when the features landed (verify round 1): the tests now follow what E4, E5 and E6
  built, which agrees with the documents:
  - `Print` with a selection asks first in E6's modal `Print` dialog (All preselected, Selection),
    the port's stand-in for the range group of the original's print dialog (editor-ui §13.1 step
    1); the test chooses Selection.
  - `Import/Export Settings` (E4) has one row per file with buttons named `Import settings.dat`,
    `Export settings.dat` and so on; Export and Import go through the active file backend's Save
    and Open dialogs (titled like the buttons), not through a download or a file chooser. The
    tests save the export into My Programs and read it with the Files panel's Export...
  - `settings.dat` lines are `<value>$<name>` (editor-ui §11.4), so `Show Warnings` is the line
    `1$show warnings`, not a name line followed by a value line.
  - The .S68 file ends with an S8 record (assembler.md: always S8 with a 3-byte address), not S9.
  - Pause is enabled in every state of the simulator (sim-ui.md), so Execute's "loaded and not
    running" is shown by Run and Trace Into being enabled.
  - Replace with a selection that is not a match: note 7 settles only that the selection is not
    replaced. E6 then finds the next match and replaces it at once; the test accepts that, or a
    first press that only selects the match.
- Turned on (gate I2): E4, E5, E6 and FS2 are built and committed, so their entries in `PENDING`
  carry `landed: true`. `requirePackage()` then never marks a test as an expected failure: a
  missing feature fails the test with "<id>: <feature> has landed, but its commands are disabled in
  the page". Before this, a feature that disappeared again would have turned its tests back into
  expected failures and the run would still have been green. The mechanism stays for packages of
  later waves (`landed: false`).
- The kit's title-bar X of every dialog is a button named `Close`. `App.button(dialog, 'Close')`
  means the dialog's own Close button and leaves out `.e68-dialog__close`; `App.titleBarClose()`
  is the X.
- FS2 has no test here: the Open dialog's provider buttons are FS2's own acceptance in Chromium and
  WebKit; the editor rows only need "the Open dialog of the active file backend", which the suites
  test with the browser store.

## 8. Accessibility findings the scan allows

- Says: 6.9 item 8, no serious or critical finding of axe in any mode or dialog.
- Does: `app/a11y.spec.ts` keeps a short list `ALLOWED` (rule, a pattern on the node's HTML, the
  owner, the reason); a matching node is recorded as a test annotation, every other serious or
  critical finding fails. Two entries:
  1. `color-contrast` on text drawn in a syntax colour: the editor's `e68-syntax__*` spans (also
     the source line of the Assembler Status dialog with its error squiggle) and the element
     samples (`data-element`) of Editor Options > Colors. The colours are the original's (2.8,
     Auto preset in the light theme; the other presets and custom colours are the user's), so
     Macro/Other (olive) and Structure Error (red) on white stay below 4.5:1. Fidelity comes first
     (section 0); the owners E3, E4 and E5 may decide otherwise, and then the entry goes.
  2. `scrollable-region-focusable` on `.e68-output__viewport` (Simulator mode, SH4's Output panel):
     a defect of SH4, reported in X1's result. Delete the entry when SH4 has repaired it.
