## 5c. Printing in the tests never opens a print dialog

- The web platform prints from a hidden frame that it focuses and removes on `afterprint`, with a
  60-second fallback. Playwright's WebKit returns from that frame's `print()` without `afterprint`,
  so after Ctrl+P the invisible frame kept the keyboard focus and the chords test's next keys went
  to the frame (CI run 44941673365, all three systems). `fixtures/printing.ts` replaces `print()` in
  every child frame by one that records the document and reports `afterprint`, as a browser does
  when its dialog closes; `editor/print.spec.ts` and `app/chords.spec.ts` use it. What a real print
  dialog does is the manual table of 6.8.
- Reported to the owner of `app/src/platform/web.ts`: in a browser that never reports
  `afterprint`, the keyboard stays in the hidden frame for up to 60 seconds after printing. That
  was true when this entry was written. Since errata W3.md entry 44 (the follow-ups after
  b27ae56) the platform ends a print also by other signs once `print()` has returned: the page has
  the focus again after losing it, a pointer or key event arrives, or 1 s passes with the focus never
  lost. Such a browser now gives the focus back about 1 s after printing (measured: 1086 to 1106 ms
  in Playwright's WebKit); the 60 s fallback stays only for a page that never has the focus. The
  fixture is still needed, to read the printed document and to keep the tests free of that second.

## 12. Offline Help in WebKit: the cause (second round before I3)

The expected failure of 5b stays, now with its cause. WebKit does not send the navigation of a
frame sandboxed without `allow-scripts` to the service worker: online that frame's page comes from
the network (`fromServiceWorker` false), offline it fails with "WebKit encountered an internal
error"; the same frame with `allow-scripts`, and every frame in Chromium, is answered by the worker
(table and probe in `docs/requests/H1-help-offline-webkit.md`). The precache, the scope and the page
paths are right: `fetch()` of the page is answered offline. The rule holds online too, so it is the
engine's and not Playwright's offline switch, and real Safari is expected to show it. The repair
needs `allow-scripts` in the frame's sandbox, a change of ARCHITECTURE.md 7.6, asked of the
architect in that request; `MANUAL-TEST-MAC.md` W1 asks for Help offline in real Safari.

## 15. The launched-file test of the stability run, and offline Help in WebKit (third round before I3)

- **`app/launch.spec.ts` failed in 4 of 20 repetitions** in Chromium on ubuntu-latest (CI run of
  f17e78a, job 137108466807: three `NotReadableError`, one `NotFoundError`, all from the test's own
  `page.evaluate` at the final read), and once on this PC. Reproduced here before the repair: 5 of
  40 repetitions failed with `NotReadableError` (`--repeat-each=40 --workers=6`, production build).
- **Cause: the test, case (1) of the task.** The last step polled the file of the origin's private
  file system with `getFileHandle(...).getFile().text()` while the application's Save of that
  linked file was still running. Chromium writes a swap file and replaces the file when the
  writable stream closes; a `File` taken before the close is `NotReadableError` when read after it,
  and `getFileHandle` can meet the moment of the swap as `NotFoundError`. A probe
  (`build/H1R3/probe-opfs-race.mjs`) shows it without the application: a File taken before a
  write and read after it gives `NotReadableError`; 266 reads overlapping 200 writes gave 60
  `NotReadableError` and 6 `NotFoundError`; 200 reads made strictly after each close gave none.
  The repetitions do not share a file: each test has its own browser context and so its own
  private file system.
- **Not a product defect.** The application never keeps a `File` across its own Save
  (`LinkedBackend.readFile` and `readWhole` take the File and read it at once; `writeReal` asks
  for a new File after the close), and it never reads a linked file while its own write is open:
  the Vfs runs `stat` and `readFile` of a path after the write or append in progress on it
  (`Vfs.pending`). So a student who opens a file "From this computer...", saves and reads it again
  does not meet it.
- **Repair.** The test checks that the document is modified, presses Save, waits until the
  document is no longer modified (Save resolves after the stream's close), and only then reads the
  real file, once, requiring its bytes to be exactly the saved text and the trailer
  (`* saved back\r\n` + `TRAILER`), where it used to accept any text containing `* saved back`. It
  still proves its title: the launched file opens in Editor mode as a linked file, the status line
  hides `/linked/`, and Save writes back to the real file. Afterwards 60 of 60 repetitions passed
  (`--repeat-each=60 --workers=6`).
- **`app/offline.spec.ts`: the expected failure in WebKit is gone** (erratum H1 11). The offline
  Help test now also follows a link from one help page to another (Quick Start > Simulator I/O; not
  Credits, whose licence page refers to the original's missing `ac-archive.css`, a failed load the
  suite would report) and opens Help > Differences from EASy68K, and checks the frame's sandbox
  (`allow-scripts` in WebKit only) and that the page's head starts with the policy. It passes in
  both browsers against the production build with the network cut. Against the build of 4bd5f68
  it fails in Chromium (seen: the page has no policy); in WebKit the frame stayed empty offline there
  (entry 12, the expected failure of the second round).
