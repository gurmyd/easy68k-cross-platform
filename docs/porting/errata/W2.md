## 1. `--c-border-strong` fails the 3:1 rule of 2.8 in both themes

- Says: 2.8, `--c-border-strong` = `#9CA3AF` (light) / `#545D68` (dark), "field borders"; and,
  in the same section, "interface graphics at least 3:1, in both themes".
- Measured (WCAG 2 contrast): light `#9CA3AF` is 2.31:1 on `--c-bg`, 2.54:1 on `--c-surface`,
  2.43:1 on `--c-panel`; dark `#545D68` is 2.76:1, 2.48:1, 2.25:1. A field border is the
  visual information that identifies the field (WCAG 1.4.11), so both values break the rule.
- Does: light `#818B98` (3.14 / 3.45 / 3.31:1), dark `#6E7781` (4.06 / 3.64 / 3.30:1). Same hue
  family, the smallest change that passes on all three backgrounds.
- Checked by: `app/src/styles/contrast.test.ts` (part of `npm test`).
- Proposed text for 2.8: `--c-border-strong` | `#818B98` | `#6E7781` | field borders.

## 6. "Dialogs are `dialog` elements" (2.11) is implemented with the ARIA role

- Says: 2.11, "Dialogs are `dialog` elements with `aria-modal` where modal".
- Does: `Dialog` renders a `div` with `role="dialog"` (`role="alertdialog"` for message boxes),
  `aria-modal="true"` when modal, `aria-labelledby` its title, and its own focus trap - not the
  HTML `<dialog>` element with `showModal()`.
- Why: `showModal()` puts the dialog in the browser's top layer, above every `z-index`, which
  breaks the stacking order of 2.8 (`--z-menu` and `--z-toast` above `--z-modal`) and hides
  pop-ups (menus, lists, tool-tips) that a dialog opens. Read "dialog elements" as "elements with
  the dialog role"; the accessibility tree is the same.

## 7. MaskedField: details the specs leave open, and one rule taken from the spec over VCL

hardware §12 V1 marks the keystroke-level behaviour of the masked edits UNVERIFIED. The kit
implements (`app/src/ui/components/masked.ts`, unit-tested):

- Delete clears the position at the caret and leaves the caret where it is; Backspace clears the
  position before it and moves onto it; with a selection both clear the selection.
- A key at the end of a full field is refused (beep).
- AutoSelect as in the DFMs: the register fields select their text on focus (VCL default), SR does
  not (`AutoSelect = False`, `SIM68Ku.dfm:733`), nor do the Hardware panel's fields
  (`hardwareu.dfm:1783` and the others). This is the `autoSelect` prop; the owners pass it.
- SR Backspace: sim-ui §4.4 says Backspace "types a `0` at the caret". In the VCL, `TMaskEdit`
  also handles `VK_BACK` in its own `KeyDown` (clearing the position before the caret) before the
  `OnKeyPress` handler turns the `#8` into `'0'`; if so, the original's net effect would be "the
  position before the caret becomes `0` and the caret does not move". The VCL source is not in the
  reference tree, so the kit follows the spec. Proposed: confirm under Wine (T3) and correct
  sim-ui §4.4 or `masked.ts` (`SR_FIELD.backspace`).

## 10. Tab in an open menu of the menu bar (2.11; wave-0 gate)

- Says: 2.11, "Every command is reachable from the menu bar with the keyboard (arrow keys, Enter,
  Esc ...)"; nothing about Tab. The kit closed the menu on Tab and gave the focus back to where it
  was before the menu bar, or, with no such place, dropped it on the document body, so the next
  Tab started again at the top of the page.
- Does: Tab and Shift+Tab in an open menu close it, and the focus moves on from the menu bar in
  document order: to the first tab stop after the bar (Tab) or the last one before it
  (Shift+Tab), the place Tab and Shift+Tab from the bar's own title go. The menu bar does this by
  putting the focus on the title of the menu that was open and not cancelling the key, so the
  browser's own Tab moves on from there (no hand-made list of tab stops; the gate's first version
  had one, and it lost the focus or chose another element than the browser for hidden buttons,
  disabled fieldsets, closed `<details>`, plaintext-only contenteditables and positive
  tabindex). `Menu`'s `onClose` passes a second argument, `backward` (true for Shift+Tab), and may
  return true for 'tab' to let the key through; a context menu still cancels it.
  `MenuCloseReason` is unchanged. Escape and a choice still give the focus back to where it was
  before the bar. `check-gallery.mjs` compares both cases with Tab and Shift+Tab from the title,
  also with such unusual tab stops next to the bar, in Chromium and WebKit.

## 13. A modal dialog moves the focus on every Tab and Shift+Tab itself

- Says: 2.7 / 2.11, modal dialogs trap the focus; nothing about how. The kit cancelled Tab only
  at the two ends of the dialog's list of tab stops and left every Tab in between to the
  browser.
- Found: on GitHub's macOS runner "Tab and Shift+Tab stay inside the modal dialog" failed in
  WebKit. Safari with the system's default setting does not move Tab to a button or check box
  that has no explicit `tabindex` (Option+Tab does), so from a control in the middle the
  browser's Tab skipped the dialog's remaining controls and left the dialog; with the focus on
  the body the dialog's key handler no longer saw any key. A person using Safari could not reach
  a dialog's buttons and check boxes with Tab.
- Does: the dialog cancels every Tab and Shift+Tab (without Ctrl, Cmd or Alt) and moves the focus
  to the next or previous element of its own list (`focus.ts` `tabbables`), wrapping at the ends
  (`focus.ts` `trapStep`, which replaces `trapIndex`; unit-tested in `logic.test.ts`). Tab pressed
  while a modal dialog is open and the focus is outside it (on the body) brings the focus back
  into the top-most dialog: Tab to its first element, Shift+Tab to its last. Only the top-most
  modal dialog traps, as before. Outside modal dialogs the browser's own Tab order stays
  (`docs/differences/W2.md`).
- Does, because the dialog now moves the focus itself (found in review): its list leaves out
  controls that refuse the focus (disabled, also through a `<fieldset disabled>`, and those with
  `visibility: hidden`), and if an element of the list still refuses `focus()`, the dialog tries
  the next one in the same direction (`focus.ts` `trapOrder`), so Tab never stays in place. When
  the focused control was disabled, hidden or removed and the focus fell to the body, Tab and
  Shift+Tab go on from where that control was (its neighbours), not to the first or last element.
  A Tab pressed while an input method (IME) is composing (`isComposing`, or key code 229;
  `focus.ts` `isImeKey`) is left to the input method, as the browser would.
- Why: every control of a dialog is reachable with Tab in every browser, Safari included, as in
  the original. `check-gallery.mjs` checks that Tab from the default button visits every control
  once per round in order and Shift+Tab the reverse, that the dialog cancels every Tab key (which
  catches a dialog that leaves Tab to the browser in any browser, not only Safari), and that Tab
  and Shift+Tab after the focus was put on the body go back into the dialog. A second gallery
  dialog ("Modal dialog with hidden controls") checks that Tab passes over a hidden button and a
  disabled fieldset, goes on after a focused button was disabled or removed, and leaves a
  composing Tab alone.
- Correction (gate I1, `docs/requests/W2-dialog-focus-followups.md` item 4): as first written,
  the check for "Shift+Tab after the focused button was disabled" did not cover the case it
  named. Both browsers keep the focus on a button that disables itself, so Shift+Tab started from
  that button inside the dialog, and the branch of `moveTab` for a focus that fell to the body
  was exercised only by a reviewer's probe. The check now takes the focus away after disabling
  (blur), asserts that it is on the body, and then presses Shift+Tab; it fails when that branch
  is removed (tried in Chromium). Entry 14 lists the other follow-ups.

## 14. Modal dialogs: four follow-ups on the focus (gate I1)

From `docs/requests/W2-dialog-focus-followups.md`, found by the review of entries 12 and 13.
None of them changes the public interface.

1. **A control that hands its focus to a child.** A `tabindex="0"` container whose focus handler
   focuses a `tabindex="-1"` child was treated as refusing the focus and skipped by Tab. The dialog
   now accepts a candidate that contains the focused element (`focus.ts` `holdsFocus`), and counts
   a focused child as its container in the list (`indexHolding`), so Tab and Shift+Tab move on
   from the container instead of back into it.
2. **Focus pulled back to a control that was disabled meanwhile.** When the focus left the
   dialog, the dialog gave it back to the last control inside; a disabled or hidden control
   refused it and the focus stayed outside. Now, if the focus is not inside afterwards, it goes to
   that control's next neighbour, on through the list (`restoreOrder`), else to the first control,
   else to the box.
3. **Escape, Enter and access keys with the focus on the body.** Only Tab was handled for keys
   that reached the document outside the dialog. Escape, Enter and the access keys
   (`isDialogBodyKey`) pressed while the focus is on the body now go to the top-most modal dialog
   and act as if pressed inside it on a control that does not use them itself (Enter presses the
   default button; a letter alone works as an access key). Keys on other elements outside the
   dialog are not taken (the focus trap pulls the focus back from those).
4. **The check of entry 13**: corrected above.

Unit tests: `logic.test.ts` ("modal dialog focus follow-ups"). Browser checks in
`check-gallery.mjs`, in the dialog "Modal dialog with hidden controls", which now also has a
hand-off container ("Inner"): Tab and Shift+Tab stop at it; Shift+Tab from its child goes to the
control before it; the focus moved outside after the focused button was disabled comes back to
its next neighbour; with the focus on the body, R presses "Remove me", Enter presses OK and
Escape cancels. With the dialog code of commit a5091e2 six of these checks fail in Chromium and
WebKit; with the repair all pass.
