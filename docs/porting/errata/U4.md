# Errata of work package U4 (logging and simulator options)

Where the code of `app/src/core/sim-host/log/`, `app/src/features/log/` and
`app/src/features/sim-options/` differs from `docs/ARCHITECTURE.md`, or where the document leaves
something open that the code had to decide. Each entry: what the document says, what the code does,
and the text proposed for the document.

## Log service (3.3.5, 5.5)

### 1. `formatUsDateTime` has no home (5.3, 5.5)

- Says: 5.3, "Log headers use the same form and the same midnight rule, produced by
  `formatUsDateTime(date)` in the application (5.5)". No path, no owner.
- Does: `app/src/core/sim-host/log/format.ts` exports `formatUsDateTime(date)` (US English
  `DateTimeToStr`: `M/D/YYYY h:mm:ss AM`, the date alone at exactly midnight), `outputLogHeader`
  and `defaultLogFileNames`. Tested against the examples of sim-ui §13.4 and the headers of the nine
  logs the official binary wrote under Wine.
- Proposed text for 5.3: "... produced by `formatUsDateTime(date)` of
  `app/src/core/sim-host/log/format.ts` (U4)".

### 2. The program is held for the whole of Log Start, not only while the question is open (3.3.5, 4.4.5)

- Says: 3.3.5, "While the `Log File Options` question is open the program is held (2.7), so no
  output can fall between the click on Log Start and the first logged byte". `LogDeps` has no hold.
- Problem: `start()` also waits for the store before and after the question (`vfs.stat` for each
  file, the earlier log's last flush, the first write that creates or truncates the file). The
  dialog's hold covers none of that, and without the question (a new file) nothing holds the
  program at all: a running program's output between the click and `engine.startLog` was lost.
- Does: the Log Start command (`features/log/index.ts`, `startLogging`) calls
  `ctx.sim.controller.hold()` before `log.start()` and releases it when `start()` has resolved, as
  the original, whose `prepareLogFile` runs inside the click. Inside `start()` nothing waits
  between the plan (the answers) and `engine.startLog`. Measured: headless with the real engine and
  the question open for 0, 250 and 30,000 ms of virtual time, and in Chromium and WebKit with the
  question open for 3 s, the log holds exactly the bytes the program wrote after the click.
- Proposed text for 3.3.5, last item: "The Log Start command holds the run controller from the click
  until `start()` has resolved (the `Log File Options` question holds it too, 2.7), so no output can
  fall between the click and the first logged byte, however long the user and the store take."

### 3. The log types come from the engine, one frame after a load (3.3.5, `LogState`)

- Says: `LogState.execType`, `outputType` are "mirrors of `SimOption.ExecLogType` /
  `OutputLogType`". The engine reports no change of them, and `setLogFileNames` (called by the
  controller during a load) must enable Log Start "when a program is loaded and a log type is
  non-zero".
- Does: the service reads the four options (`ExecLogType`, `OutputLogType`, `LogMemFrom`,
  `LogMemBytes`) through `invoke` in `setLogFileNames`, `dialogShown`, `start` and
  `resetToStartup`, and keeps them itself in `applyDialog`. During a load `invoke` is queued, so
  after Open with types restored from the settings Log Start becomes enabled when the queue is
  delivered, one tick (a display frame) after the load has finished.

### 4. Cancel on the second question; a file that cannot be opened (sim-ui §13.3, note 41)

- The original asks about the execution log, opens it and writes its header, then asks about the
  output log; Cancel there returns with the execution log already open (and `startLog` then sets
  `logging` anyway).
- Does: both questions are asked before anything is written. Cancel at either leaves both files
  untouched and logging off; `engine.startLog` is not called. A file that cannot be written is
  found by the first write, after both questions: the original's `Error` box follows
  (`Can't open log file. Check log file name., Error number 0` / `Can't open log file, error 0`,
  no icon), for the execution log then the Log Output dialog, as the original. A name that is not a
  path of the port and cannot be taken relative to the program's folder (for example `C:\logs\x.txt`)
  is such a failure before any question.

### 5. Log Start with both types Disabled (sim-ui §13.6)

- The original's `startLog` sets `logging` whatever the types, enables Log Stop and leaves the
  `LOGGING` label hidden (no file was opened).
- Does: `engine.startLog` is called as in the original (the engine logs, Log Stop is enabled), and no
  file is made. The toolbar's label follows `AppState.sim.logging` (W3, SH8) and therefore shows
  `LOGGING` in this case. Nothing a program can observe; left as it is.

### 6. OK while logging does not enable Log Start (sim-ui §13.2, §13.6)

- The original's OK enables Log Start whenever a type is non-zero, also while logging, and a second
  Log Start then opens the files again over the open ones.
- Does: OK enables Log Start only while not logging (§13.6: "disabled while logging").

### 7. Log Start closes the Log Output dialog (sim-ui §13.3 step 8)

- The original's `prepareLogFile` ends with `Log->Close()`: the form is hidden and keeps the radio
  values the user may have changed without OK; the next FormShow takes them as the snapshot.
- Does: the dialog closes as with Cancel when logging starts; unconfirmed changes are dropped.

### 8. File names are paths of the port (5.5)

- Does: the names are VPaths (`/browser/work/prog_RunLog.txt`), shown and edited as such. A typed
  name that is not a VPath is taken relative to the program's folder (Windows rules,
  `resolveLexically`). The folder buttons open the port's Save dialog (`Save As`, filter
  `Text File` / `*.txt`, suggested `EASy68kELog.txt` / `EASy68kOLog.txt` in the current folder, no
  overwrite question, as the original's `TSaveDialog` defaults).

### 9. When a flush is due (3.3.5)

- Says: "A flush is due every second while logging, but never sooner than twenty times the duration
  of the previous flush."
- Does: a flush is due one second after the first byte that is not in storage yet (no timer runs
  while nothing is pending), or twenty times the duration of the previous flush if that is longer.
  Every stop of execution (the controller's `stopped()`), Log Stop (`logState(false)`) and `exit()`
  flush at once. Flushes are single-flight: one write per file at a time; a flush asked for during
  one waits and takes everything that arrived meanwhile; further requests join it.

### 10. The cost of a flush in the program's folder (3.3.5, 3.8.4) - not U4's

- Acceptance: "a 30 MB log costs the same per flush as a small one". The service hands
  `vfs.appendFile` only the new bytes (checked in every test), and the store costs the same:
  - Node, MemoryBackend: 8 KB per flush, small file 0.013 ms, 30 MB file 0.016 ms (median of 40);
  - Node, BrowserBackend on fake-indexeddb: 0.179 ms against 0.172 ms;
  - the real browser store (IndexedDB), a folder of its own, `check-log.mjs`, median of 30 flushes
    of 8 KB: Chromium 5.8 ms (small) against 5.3 ms (30 MB); WebKit 293 ms against 231 ms (WebKit's
    IndexedDB on Windows is slow for every file alike).
- Found: in the folder of the loaded program - where the log goes by default - an append of 8 KB to
  a 30 MB file costs 122 ms instead of 5 ms in Chromium (a probe of `vfs.appendFile` alone; the
  flush in `check-log.mjs`: Chromium 6.5 ms small against 246 ms for 30 MB, WebKit 376 ms against
  989 ms), because the simulator's cached view of that folder (`CachedSyncFiles`,
  `app/src/fs/sync/cached.ts`, SH6) reads the whole file again after every change made by someone
  else (`changed()` -> `refresh()` -> `vfs.readFile`). The log's appends are such changes. The
  flush governor (twenty times the previous duration) keeps this below about 5 % of the time, so
  the log still costs little; the reading is SH6's to avoid (for example, read only the appended
  part when only the size grew, or do not re-read a file the program has not opened). Reported to
  SH6 in the result of U4.

### 11. The Log panel shows this session's bytes (2.6)

- Says: "the last 200 lines of each file".
- Does: the service keeps the last 256 KiB written to each file since its Log Start (header
  included) and the panel shows the last 200 lines of that. In Append mode the earlier contents of
  the file are not read back for the panel (a 30 MB file would have to be read).

## Interface (2.6, 2.7, 1.3.4)

### 12. Nothing shows the Log panel (2.4, 2.6, 1.3.5)

- Says: 2.4, "Break Points and Log as saved (default hidden)"; 1.3.5 puts the Log panel last in the
  panel cycle. No command shows it: the View menu (`commands/tables/sim-menu.ts`, W3) has no item,
  and 1.5's list of added commands has none.
- Does: the panel is registered (`features/log`, id `log`) and works once visible; the browser
  check shows it with `showPanel(ctx, 'log')`. Request: `docs/requests/U4-log-panel-command.md`
  (a View menu item `&Log` with the id `sim.view.log`, below a separator after the original items;
  U4 then registers its handler).

### 13. The `Log File Options` question also names the file (sim-ui §13.3 step 1)

- Does: below the bold message (`Execution Log File exists!` / `Output Log File exists!`) the
  question shows the file's path in small muted text. The captions are the original's; the
  original's buttons have no access keys, nor do the port's. Escape answers Cancel.

### 14. The font dialogs (note 27; sim-ui §14.1; trap15-a §3.2)

- Does: one dialog, `sim.font`, with props `{ target: 'source' | 'output' | 'printer', font, color }`.
  - Output Window Font: the five measured fonts (Fixedsys, Courier, Courier New, Lucida Console,
    Consolas), sizes 8-18, the style list of the Windows dialog (Regular, Italic, Bold, Bold
    Italic), Strikeout, Underline and the sixteen colours. OK saves name and size
    (`SimSettings.outputFont`) and calls `TextScreen.setOptionsFont(font, color)`; style and colour
    last for the session, as in the original. `TextScreen` draws one style: with several set, the
    last of bold, italic, underline, strike-out (errata SH3.md entry 13), so Bold Italic is drawn
    italic.
  - Source Window Font: the same five fonts, sizes 8-18, no style or colour (the listing is drawn by
    CSS from `SimSettings.listingFont`, and the original saves only name and size).
  - Printer Font: any name (a text field with suggestions), sizes 1-255; OK saves it and calls
    `PrinterDevice.fontChanged()`.
  - The titles are the menu captions without the dots (`Output Window Font`); the Windows dialog's
    own title is `Font`.

### 15. Auto Trace Options and Fullscreen Options (notes 28, 29)

- Auto Trace Options: the interval field is read-only with up/down (10-1000, step 10), a saved
  value outside the range is shown clamped. OK stores both values in the settings; the simulator
  session applies them to a running simulator (features/run). Cancel changes nothing (note 28).
- Fullscreen Options: with full screen on, the original's box (title `Error`, the MessageBox with a
  NULL caption) `Please deactivate fullscreen mode before attempting to change the fullscreen
  settings.`; otherwise the dialog with its text (double spaces kept, wrapped) and the field set to
  `SimOption.FullscreenMonitor + 1`; `&Ok` is enabled for `1` only. OK sets
  `SimOption.FullscreenMonitor` through the controller; nothing is saved (the original's value never
  survives a restart). The original's `Sorry, but your system does not seem to support multiple
  monitors.` cannot arise.

### 16. Enable Exceptions and Enable Bit Field (sim-ui §14.1)

- Do: the check mark follows `SimSettings.exceptions` / `.bitField`; a click toggles the setting
  (stored at once) and sets the engine option through `controller.invoke`. The engine's own changes
  reach the settings through the session (sim-ui Q14, SH8).

## Contract

### C1. `LogServiceApi.start()` cannot say why it resolved false

- `start()` resolves false for Cancel and for a file that cannot be opened; the command must show
  the `Error` box for the second only, and needs to know which file.
- Does: `LogService` has `startFailure: { kind, fileName } | null` and `writeError: string | null`
  beyond the Api; `logStartFailure(log)` and `logWriteError(log)` in `log-service.ts` read them
  from any `LogServiceApi` (null for a service without them). Local adapter; no other package
  depends on it.
- For W1: add `readonly startFailure: { kind: 'exec' | 'output'; fileName: string } | null` (and
  optionally `readonly writeError: string | null`) to `LogServiceApi`.
