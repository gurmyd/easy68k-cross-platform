# Errata of N5 (the Files panel of the stage of additions)

Where `docs/ARCHITECTURE-PLUS.md` is silent, ambiguous or does not match the code, what N5 built and
why. No entry changes a contract.

## 1. Files N5 added that the entry of P5 does not list

- `app/src/features/files/texts.ts`: the package's texts (P5, introduction, asks for it; the entry
  of N5 does not name it).
- `app/src/features/files/MoveToDialog.tsx`: the dialog `files.moveTo`. P5 puts the dialog in
  `move.ts`; a dialog needs JSX, so the component is in its own `.tsx` file and the logic
  (`moveTargets`, `transferItems`, `refusedTarget`) stays in `move.ts`.
- `app/src/features/files/testing.ts`: test support of N5's unit tests (scripted dialogs, a fake
  DocumentService with the optional members of P4.4, a scripted HistoryService). Imported only by
  tests.
- `app/src/features/files/files-model.test.ts`: the seeded test of the last acceptance item.

## 2. `No has the focus` (P3.2.2, P3.3.4)

Until the gate, `MessageBoxRequest` (contracts/features.ts) had no way to name the default button
(`docs/requests/N5-default-button.md`). The gate's contracts engineer added the optional
`defaultButton` (a caption) and DialogHost passes it to the kit's `MessageBox`. The Delete question
of P3.2.2 and the cannot-keep question of P3.3.4 (`cannotKeepConfirm`, used by Delete, Replace and
Undo of a Copy) now pass `defaultButton: 'No'`: No has the focus and Enter answers No
(`check-files.mjs`: "in the Delete question No has the focus; Enter deletes nothing", both key
maps, both browsers).

## 3. `locations()` gains the linked root only for the Files panel

P5 says `locations` gains the linked root. `locations()` also feeds the Open and Save dialogs'
`Look in` list (FileDialog.tsx, dialogs.ts), which P3.2.5 does not change. So `locations(vfs, {
linked: true })` adds `/linked` as `Opened from this computer` (last), and `locations(vfs)` stays as
it was.

## 5. The not-enough-room message only for a large import

P3.2.6 gives the question for an import above 100 files or 10 MB, then "When the total size is
larger than the free space minus 32 MB: no question, the message". N5 reads the second as part of
the first ("no question" instead of the question): a small import is never refused by the
estimate, which is approximate (R7) and counts the application's own caches.

## 6. Move of a selection from two stores

P3.2.4: same store a move, different store a copy. A selection that holds items of two stores is
copied as a whole (each item stays where it was); a move of part of it would need two undo entries
for one command.

## 7. Items of the same name and other kind at the target

A file moved onto a folder of the same name (or a folder onto a file) is not merged or replaced:
the message (`Move`/`Copy`, `error`) `"demo" already exists.` (FS1's rename text) and that item is
skipped.

## 8. The linked files' root

- A file linked in this window (FS2's `LinkedBackend.link`) is added without a change event of the
  Vfs, so the tree lists the linked files again when a document of an unknown `/linked/...` path is
  open (the store's document list), and when the window regains the focus.
- Export of the root `Opened from this computer` exports its files as several items
  (`EASy68K export.zip`), not the internal folders.
- `Remove from List` removes `/linked/<id>` (the copy and its listings and S-records, FS2's
  `remove`), never the real file; it does not pass through `guard` (nothing of the student's is
  deleted) and has no Undo.

## 9. The strip

`Trash...` uses the icon `trash` as P3.3.3 says; FS1's `Delete` button used the same icon, so
`Delete` now shows `close` (its accessible name is unchanged). `Trash...` is disabled while
`app.files.trash` is not enabled (until N4's handler is there).

## 10. Rename and its Undo

Rename (`renameEntry`, unchanged) calls `moved(from, to)` once for the item (a rename never merges)
and `relocate(from, to)`, and pushes `Undo Rename`; it shows no toast (P3.2.4 gives a toast after a
move only). Undo Rename renames back through `renameEntry` (a change of letter case only included).
Undo of a move moves back file by file and never over anything.

## 11. What the storage line exposes for its check

The line carries `data-e68-storage-refreshes` (how many times it read the figures), so that
`check-files.mjs` measures "at most once per second" by the page's own clock.

## 12. The model test runs on `/browser` and `/disk`

`files-model.test.ts` mounts its second store at `/disk`, as N3's driver does. With a
`MemoryBackend` mounted at `/folder` (a FolderBackend without `rootHandle`), the checker reported
`(6) versions("/folder/t.X68") lists 1 of 0` after a plain save and `record` (seeds 1 to 3): the
store and the checker do not agree on the place of a `/folder` path without a root handle. A real
opened folder always has one (FS2's `FolderBackend.rootHandle`); the case is reported to N3 in the
result of N5, not worked around in N5's code.

Repair round 1 tried again with a root handle (`{ kind: 'directory', name: 'Lab' }` on the
MemoryBackend): the same report (`(6) versions("/folder/lab/t.X68") lists 1 of 0`, seeds 1, 3, 6).
The checker's `placeOf(path)` (`fs/history-model.ts`) has no root id for a `/folder` path; that is
N3's. The Files panel's own byte oracle (entry 13) does not depend on the store.

## 13. A selection that would lose a file is narrowed first (verify round 1)

P3.2.4 does not say what happens when the selection itself collides. N5 decided:

- An item inside another selected folder (after Ctrl+A) is dropped: the folder carries it
  (`outermostItems` in `bulk.ts`, used by Delete, Move and Copy). Delete counts it once.
- An item that is already in the target folder stays where it is; the others go. Only when every
  item is there is the target refused (as before).
- A second selected item whose name equals an earlier one's (letter case ignored) is not moved or
  copied: the message (`Move`/`Copy`, `error`, `OK`) `"p.X68" already exists.` (entry 7's text),
  and it stays where it is. Two same-named folders are not merged into one.
- A file that appears at the target after the command planned (and asked) is not written over: the
  same message, and it is skipped. Every overwrite still goes through `guard('replace')` only.
- Undo of a Copy always asks P3.3.4's question when guard cannot keep a copy (`Remove the copy
  anyway? This cannot be undone.`), whatever the history's state: it has no question of its own.

## 14. Rename and Undo Rename in a store that keeps letter case apart

A Linux disk (and the memory store of the tests) can hold `r.X68` beside `R.X68`. FS1's
`renameEntry` (not changed, P5) treats the exact match of the new spelling as the entry itself and
its case-only path then writes over the other file. The Files panel's Rename and Undo Rename call
`renameChecked` (`store.ts`), which refuses first with `"r.X68" already exists.`; Undo Rename names
it with `cannotMoveBackExists`. Found by the seeded model test's new byte oracle (seed 104).

## 15. No name becomes .git, and nothing is written below one (gate, verify round 2)

P1.1 rule 2 says no command of the stage writes below a folder named `.git`; P3.2 gives no text for
a command that would make one. Verify round 2 found that Rename of a folder to `.git` wrote the
student's files below a new `.git` folder, which the tree then hid. The Files panel now refuses
every way a name can become `.git` (any letter case), with texts of its own (`texts.ts`):

- **Rename and New Folder** treat the name `.git` as a name that cannot be used, as they treat an
  invalid name (title of the command, `warning`, `OK`, then the name is asked again):
  `The name ".git" cannot be used in the Files panel: a folder named .git holds a Git repository's
  own files, and the Files panel does not show it or write into it. Choose another name.` (the name
  as typed). A **file** is not renamed to `.git` either: N3's history (`core/history/places.ts`) and
  its checker take any path segment `.git` for a Git one, so a file of that name would lose its
  history's place; the seeded model test showed it (seed 13). `renameChecked` (Rename and Undo
  Rename) throws the same text, as a second line of defence.
- **Move, Copy, Delete and Undo** (of a Move, Rename or Copy) refuse an item or a target that is
  named `.git` or lies below one (the tree lists none, but a drag payload, an older undo entry or a
  caller could name one): `"<name>" belongs to a Git repository: the Files panel does not write,
  move, copy or delete anything named .git or inside a folder named .git. Use your own tools.`
  (`gitPathRefused`; the command's title, `information`, `OK`). Move and Copy also check every
  target path they planned.
- **Import** (Import Files, Import Folder, a `.zip`, files dropped into a folder) is main's command
  and is not changed (P1.1 rule 2): third round of the gate, see entry 19. Until then the items of a
  picked or zipped folder named `.git` were left out (`.git/: a folder named .git is not imported into
  the Files panel`); that is taken out again, and such a folder is imported as on main (the tree then
  hides it, as P3.2.5 says, and the history keeps nothing of it).
- **A dropped folder** named `.git` is offered to the opened-folder provider (FS2's "Open this
  folder?") as any other folder, as on main: third round of the gate, see entry 19. Until then the
  toast `A folder named .git is not opened: ...` refused it.
- **An opened folder that is itself a `.git` folder** (FS2's `Open Folder...` picker can still
  choose one; its root handle's name is `.git`): every path of that store lies below `.git`
  although no segment says so. Delete, Rename, New Folder, Move and Copy into or out of it, and
  Undo there, are refused with `The folder ".git" is the .git folder of a Git repository. The Files
  panel changes nothing in it.` (`gitStoreRefused`), and `Move To` does not list it. Import there is
  not refused (entry 19).

Tests: `git-names.test.ts` (each command of the stage and each Undo, with the Vfs's write log), the seeded model
test (`.git`, `.GIT`, `.Git` among the rename names; now and then a selection that names the
repository's `.git`; after every step a snapshot of everything below any `.git` folder must be
unchanged), and `check-files.mjs`'s opened-folder pass with the fake directory handle's write log
(Rename to `.git` and `.GIT`, New Folder `.Git`).

## 16. A move removes a source only while it is unchanged (gate, verify round 2)

P3.2.4 says a move copies, then removes. Verify round 2 found that a save by another window (or a
program's write) that lands between the copy and the removal was lost. By property 1 of P3.3.1 the
source now stays: before it removes a source, `transferItems` compares the source's modification
time, size and bytes with those it read (the bytes too, because two writes in one clock tick keep
the time); when they differ the source stays, `moved` is not called for it, Undo does not move it
back, and the message (`Move`, `information`, `OK`) says `"prog.X68" changed while it was being
moved, so it stays where it was. The copy in My Programs/b holds it as it was before the change.`
Undo of a move does the same the other way (`... changed while it was being moved back, so it
stays where it is. The copy in ... holds it as it was before the change.`, titled `Undo`). Both
copies stay: nothing is lost, and the student chooses which to keep. Tests:
`move-changed.test.ts`.

## 18. Rename keeps a file that changed during the copy (gate, second round)

The first gate's review noted (minor, pre-existing on main) that FS1's `renameEntry` copies a folder
to its new name and then removes the old folder whole: a save from another window, or a program's
write, that lands during the copy was removed with the old folder, and the renamed folder held the
bytes from before. The history kept that save as a version, so property 2 of P3.3.1 held, but the
current file no longer had a change the person had saved: property 1 (a current file changes only
as commanded) did not. P5 N5 says `renameEntry` is not changed, so the stage's Rename and Undo
Rename no longer call it for the copy: `renameChecked` moved from `store.ts` to a file of its own,
`features/files/rename.ts`, and makes the copy itself with `renameEntry`'s rules, names and order
(copy first; `"<name>" already exists.` and `"<name>" no longer exists.`; a change of letter case
through `<name>.renaming-<time>`, which `renameEntry` then finishes from that temporary name, as
before):

- After the copy, every file below the old name is compared with what was copied (modification
  time, size and bytes, as a move does, entry 16), and the folder is listed again. When a file
  changed, went or appeared, nothing is renamed: the copies are removed again (each only while it
  is still the copy written), and the error (`Rename` or `Undo`, `error`, `OK`, the name asked
  again as for `renameEntry`'s other refusals) says `The folder "lab" was not renamed:
  "lab/prog.X68" changed while it was being renamed. Rename it again to use the new name.` (for a
  file: `"prog.X68" was not renamed: it changed while it was being renamed. Rename it again to use
  the new name.`). Neither the history nor an open document moves.
- Then the old name is removed file by file, each only while it is still unchanged, and its empty
  folders after them. A file that changed in the moment between that check and its removal stays
  under the old name; the rename is made for the rest, and the message (`information`) says
  `"prog.X68" changed while its folder was being renamed, so it stays where it was. The copy in My
  Programs/work holds it as it was before the change.` For a change of letter case that case
  cannot be finished (the two spellings are one name), so the folder keeps its temporary name,
  which the message gives. Nothing is lost in either case.
- A write that fails during the copy (a full store) removes the copies made so far; `renameEntry`
  left them.
- A folder that holds `.git` is refused with P3.2.4's text here too: Rename asked that before, but
  Undo Rename did not, and a repository can appear in a renamed folder before its Undo.

The write log of the opened-folder pass of `check-files.mjs` shows the same writes and removals as
before for a rename and a change of letter case. Tests: `rename.test.ts` (9 of its 11 cases fail
with the earlier `renameChecked`, which called `renameEntry`).

**Third round of the gate: a file that is gone is moved or deleted, not changed.** The second
review found that a folder Rename running at the same time as a move out of that folder left a
duplicate: the move had copied `A/p.X68` to `B` and removed it, and the rename's removal step,
finding the source no longer "unchanged", counted it as a change and kept its copy `A2/p.X68`, so
the moved file came back in the renamed folder (nothing was lost, but the move was partly undone,
without a message). A source that is gone when its old name is to be removed was moved or deleted
by someone else (another window, a program), so its copy under the new name must not stay:

- Before anything is removed (the check after the copy), a source that is gone is a change, as it
  was: nothing is renamed, the copies go again, and the error says `The folder "lab" was not
  renamed: "lab/sub/inc.X68" changed while it was being renamed. Rename it again to use the new
  name.`
- In the moment after that check, a source that is gone has its copy removed again (only while the
  copy is still the one written: a copy someone has saved into since stays, being their save), and
  a folder of the copy that only held such files goes too when its counterpart under the old name is
  gone as well (a subfolder moved out whole). The rename is made for the rest, and the message
  (`Rename` or `Undo`, `information`, `OK`) says `"prog.X68" was moved or deleted while its folder
  was being renamed, so My Programs/work does not hold a copy of it.` (`goneAfterRenaming`). For a
  file renamed by itself nothing is renamed and the error is the one above for a file.
- A source replaced by another file of the same name is a change, as before: it stays under the old
  name, and the copy holds the one that was there (`changedAfterRenaming`).
- The same holds the other way round, found while repairing it (move.ts, undo.ts): a move whose
  source is renamed away or deleted between its copy and its removal (and Undo of a move, moving
  back) removes its copy again, with `"p.X68" was moved or deleted while it was being moved, so My
  Programs/B does not hold a copy of it.` (`... while it was being moved back, ...` for Undo;
  `goneWhileMoving`), instead of `"p.X68" changed while it was being moved, so it stays where it
  was. ...`, which was not true. A copy that replaced a file stays (the replaced file is in the
  Trash), without that message. A copy taken back is not counted as moved: no toast, no Undo, no
  `moved` of the history for it.

Each of the seven properties of P3.3.1 holds: nothing that exists is removed (only the rename's or
move's own copy, while it is unchanged), and no file comes back that someone else moved or deleted.
Tests: `rename.test.ts` (moved out during the copy, moved out after the check, a subfolder moved out
whole, deleted, deleted in a change of letter case, replaced by another file of the same name, a copy
saved into, a file renamed by itself while deleted, the review's probe with the real `transferItems`
at twelve interleavings, the messages of Rename... and Undo Rename; 8 of them fail with the second
round's `rename.ts`) and `move-changed.test.ts` (a move whose folder is renamed between copy and
removal, a deleted source beside a replace, Undo of a move).

**Fourth round of the gate.**

- *The texts (decision D-f of the architect, 22 November 2026).* The two texts the third round added,
  `goneWhileMoving` (`"<name>" was moved or deleted while it was being moved[ back], so <place> does
  not hold a copy of it.`) and `goneAfterRenaming` (`"<name>" was moved or deleted while its folder
  was being renamed, so <place> does not hold a copy of it.`), are accepted as they are: a student
  is told what happened to the file. With their siblings of the earlier rounds (`changedWhileMoving`,
  `changedWhileRenaming`, `changedAfterRenaming`) they are the texts of this entry that P3.2.4 does
  not give.
- *The moment between the last check and the removal.* The third review found that a source moved
  or deleted after the last check (`unchangedSince`) and before `vfs.remove` made that removal fail
  with a raw `no such file or folder`: a folder rename stopped half way, with the moved file in both
  places (or the deleted one back under the new name) and the other files duplicated. A removal that
  finds nothing now means what it says, a source that is gone: `removeSource` (`move.ts`) answers
  `gone` for a `not-found` and throws anything else, and the rename (`rename.ts`), the move
  (`move.ts`) and Undo of a move (`undo.ts`) then do exactly what they do for a source the check
  found gone: the copy is taken back (while it is still the one written), the student is told with
  the texts above, and the rename or move goes on with the other files. Tests: the eight cases of
  `move-changed.test.ts` "a source that goes between the last check and its removal is a source that
  is gone" (moved out and deleted; a folder rename, a file rename, a move, Undo of a move); all eight
  fail with the third round's files.
- *A known limit: the zero-width window of a replace.* A check and a removal are two operations of
  the store, and no store of the application (IndexedDB, a folder of this computer, the desktop
  app's disk) can remove a file only if it is still the one seen. So a save by another window or a
  program that replaces that same source in the instant after the check and before its removal is
  removed with it: the renamed (or moved) copy holds the bytes from before that save. The window is
  that one step (nothing of the application runs between the two but the store's own work), the
  history keeps such a save as a version when this application made it (property 2 of P3.3.1), and
  every slower interleaving is handled as above (the third review's 72 probes at the reads, writes
  and removals). Closing it would need a compare-and-remove in every backend, which the stage does
  not change (P5 N5).

## 19. An opened folder that is itself a .git folder (gate, second round)

## 25. What a Move, Undo or Rename read, and a source gone before the read (review after the fourth round)

Two minor findings of the review "safety-net-and-texts" after the fourth round, both found by the
reviewer's probe (a second window acting at every read, write and removal of a move of two files,
its Undo and a folder rename).

1. A message that was not true. A Move (and Undo of a move, and Rename's copy) took the time and
   size of a source before reading its bytes. When another window saved the file between that
   stat and the read, the bytes copied were the new ones, but the time was the old one, so the
   check before the removal (`unchangedSince`) found a different time and kept the source: the end
   state held the new bytes in both places, and the message (`changedWhileMoving`) said the copy
   "holds it as it was before the change", which it did not. The cause is the order. Now one
   function, `takeSource` (`move.ts`), reads the bytes first and then takes the time and size, and
   Move, Undo and Rename all use it. A save before the read gives bytes and a time that belong
   together, so the source counts as unchanged: it is removed, the copy holds the new bytes, and no
   duplicate is left and nothing is said. A save between the read and the stat gives a time with
   other bytes. `unchangedSince` compares the bytes as well, so the source counts as changed: it
   stays with its change, and the copy really holds the bytes from before, as the message says.
   The seven properties of P3.3.1 hold: nothing is lost, and nothing is duplicated by the command
   itself. For Rename the same save no longer refuses the rename (`changedWhileRenaming`); the
   rename is made with the new bytes.
2. The raw error of the file system as a text. A source that another window deleted or moved away
   after the plan and before the read made `readFile` fail, and its not-found text (`no such file:
   A/p.X68`) reached the dialog, or the rejection of `renameChecked`. `takeSource` gives null for a
   source that is not found, and each write loop then shows the designed text that the same case
   gets one step later (no new text):
   - Move: `goneWhileMoving` (`Move`, `information`); nothing is written for it, and the other
     files move.
   - Copy: `noLongerExists` (`Copy`, `error`, as `showError` shows a failed read). `goneWhileMoving`
     would say "moved", which is untrue for a copy.
   - Undo of a move: `goneWhileMoving` with `back` (`Undo`, `information`).
   - Rename: `noLongerExists` (thrown, as the same case throws it when the stat finds nothing). The
     folder stays as it was.

   Any other failure of the read is shown as before.

Tests: `move-changed.test.ts`, "another window acts just before or just after the bytes of a source
are taken". Save before the read and save between the read and the stat, each for Move, Undo and a
folder rename. Moved out and deleted before the read, each for Move, Copy, Undo, a folder rename
and a file rename. On the code before this entry 13 of these 16 cases fail. The 3 "between" cases
passed already, and they guard that the message stays true. The reviewer's probe
(`probe4.test.ts`, 298 cases) passes, and its log has no `no such file` and no untrue
`before the change` any more.
