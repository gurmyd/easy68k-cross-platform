# Errata of N3 (the history store)

Where `docs/ARCHITECTURE-PLUS.md` is silent, ambiguous, self-contradictory or does not match what
N3 found, what the code does and why. The seven properties of P3.3.1 win over every detailed rule
(P3.3.1, last paragraph); each decision below keeps them with the smallest mechanism, and the model
test (`app/src/fs/history-model.test.ts`) applies the same rule in its reference model.

The exported signatures of P4.4 (`createHistoryService`, `browserHistoryDeps`, `HistoryDeps`,
`createMemoryHistoryService`) are unchanged. Added beside them, for tests only:
`createHistoryStore(deps, options)` (the same store with the members of `HistoryStore`:
`globalPass`, `settled`, `close`, `windowId`, `unreadable`, `unavailableDetail`),
`createMemoryHistoryStore`, `memoryHistoryDeps`, `historyDatabaseOf`, `createFakeLocks`,
`createChannelHub` (`fs/history-memory.ts`).

## The six open cases of P7

### Open case 1: a record pushed out of its place

Case: a file is removed by a program, its record stays living; then `moved` or a Trash restore puts
another file at that place. P3.3.5 sends the old record to the Trash as `Replaced` with its newest
version as its copy, but P3.3.4's admission does not say what happens to that copy.

Decision: the copy passes Trash admission like anything else that makes the Trash half larger
(pruning the oldest items down to 0.9 x B / 2 when it would not fit). When it does not fit even
then, the record is **dropped with its versions** (`Work.pushOut` in `core/history/plans.ts`). Its
file is gone already, so property 2 is not involved (no current file is destroyed); property 4
holds because nothing above B / 2 is ever written. Model: a promised earlier version whose record
was pushed out may go when the Trash half lacked room (`explainLoss`, "pushed out without room").

### Open case 2: another window prunes a kept item between `guard`'s keep and its `act`

Case: window A keeps an item for a delete; before A's `act` runs, window B deletes something large
and its admission prunes A's item (oldest first); then A's `act` removes the file: gone without a
copy and without a question.

Decision: the keep transaction marks each record of the item `trash.pending = { window, at }`
(an addition to the record, see "records" below); the settle transaction of step 4 clears the
mark. **Pruning (admission, the global pass, the lowering when tight) never drops an item that has
an honoured mark.** A mark is honoured:

- in its own window, while that window's guard is between keep and settle (an in-memory set);
- in another window, while the marking window holds its Web Lock
  `easy68k.history.window.<windowId>` (every store requests it at creation and holds it until the
  page closes; `navigator.locks.query()` in phase 1 tells which windows are open), or when the mark
  was made after that query (a window that was open then);
- without Web Locks, for one hour after it was made (`PENDING_TTL`).

So a page closed between keep and settle leaves an item that stops being protected at once (its
lock went with the page) and is pruned in order like any other; the global pass clears marks that
protect nothing any more. Model: "a page closed between guard's keep and its act" is one of its
steps (window `close`); items with a pending mark are exempt from the oldest-first rule.

### Open case 3: stress run (c) and "down to 0.9 x B / 2"

Decision: admission prunes until the half **with the incoming change counted** is at most
0.9 x B / 2 (`Work.admit`). With five 1 MB copies per delete into a Trash half of 32 MB, every
second delete after the sixth prunes once, so 100 deletes give about 47 prunings, below the 50 the
run demands. The run's numbers are fixed to the rule as built: **120 deletes** of such folders
(`core/history/stress.test.ts`, run (c)).

### Open case 4: a living record left without versions

Case: the copy of a single-version record is not admitted when the record moves back from the
Trash (above 1 MB, or no room).

Decision: such a record is **deleted** (`Work.moveBack`): a living record always has at least one
version, as "a living record whose last version goes is deleted with it" already says for pruning.
Nothing is lost: the file was just written with those bytes. (When the copy is not admitted but
older versions remain, the record becomes living with them; when not even the record's 128 bytes
fit, it is dropped with its older versions.)

### Open case 5: `Yes` without a copy drops the records of every file `guard` saw

Decision: after `act`, only the records of the files `act` **removed or overwrote** are dropped
(`planDropLiving` with the places `guard` found gone or overwritten). For a delete, a file is taken
as removed when it no longer exists after `act`; for a replace or a restore, when `act` resolved. A
file `act` left alone (changed meanwhile) keeps its record and earlier versions.

### Open case 6: older versions of a file in the Trash can be pruned by saves

Accepted as P7 says: the copy and the item are what the Trash promises. The model follows it: a
promised `before-restore` version of a file is released from the model's promises when that file
later goes into the Trash (its record's older versions are then versions-half material of a record
in the Trash). Nothing for N4 to do unless its own review finds it surprising.

## Records and indexes (P3.3.5)

- A version stores `file` and `seq` (the store's key path `['file', 'seq']`) and `stored`, the
  stored size of its content, so that counting never reads a content.
- A record stores `lastSeq`, the highest seq it ever used: a seq is never given twice, also when
  the newest version was dropped (a copy not admitted on moving back), so that `read(path, seq)` of
  a row listed before never returns another version.
- `trash.pending` (open case 2).
- Index `byTime` has the key path `['time', 'file', 'seq']` and `byTrashed`
  `['trash.at', 'trash.item']`: total orders, so that pruning and the global pass can go on from
  where a transaction of at most 500 records stopped, and an item's records are read together.
- A `dir` record has `newestSeq` 0, `newestHash` '', `count` 0, `bytes` 128.

## Places (P4.3)

- The browser store's places are folded with `foldCase` of `core/paths/winpath.ts`, which
  **upper-cases** (`browser:/DEMO/PROG.X68`); P4.3's example shows lower case. The code follows
  `foldCase`, as P4.3's text says.
- A mount not in P4.3's table (tests mount their own) gets `<mount>:/<rel>` without folding.
- An opened folder whose backend has no `rootHandle` (a test's memory backend at `/folder`) gets a
  root found by its label; with a handle, roots are found with `isSameEntry` as P3.3.5 says.

## The thinning schedule (P3.3.4)

- Slots are aligned to multiples of their width since 1970, in UTC, so that every window computes
  the same slots.
- "Older than 60 days: dropped" wins over "the newest 10": a version older than 60 days stays only
  when it is its record's newest. (The unit list's "a version at 61 days, with and without being its
  record's newest" needs exactly this.)
- A record's newest version (for a record in the Trash, its copy) is always kept.

## Budget and the tight state (P3.3.4)

- Storage is tight below 32 MB of free space, so any quota below 32 MB is always tight, and B can
  only be below 3.2 MB (10 % of 32 MB) while nothing new is kept. Stress run (d) "B lowered from
  64 MB to 2 MB" could therefore never prune by admission after the drop; it lowers B to **3.2 MB**
  (a quota of 32 MB) instead. The unit tests that need a small B use a quota of 40 MB (B = 4 MB).
- The stress runs' numbers, fixed to the rules as built (as open case 3 asks for run (c)): with
  sources that compress as the corpus does (ratio about 3.3), 500 deletes of which 30 % are folders
  gave 23 to 26 prunings of the Trash half in runs (b) and (d), below the 50 the runs demand. The
  runs therefore delete folders (of 5 to 20 files of 2 to 46 kB) in half of the deletes, and run (d)
  lowers B after 30 % of the saves rather than in the middle, so that enough deletes follow the drop.
- A history transaction refused with `QuotaExceededError` makes the state `tight` until a global
  pass sees more than 64 MB free (or, without an estimate, until the next pass), not merely until
  the next estimate, which may lag behind (Chromium reports the disk's quota in `estimate()` even
  when the origin's quota is lowered; seen in `check-history.mjs`).
- The lowering writes `meta.notice = { armed: false, halvedAt }` before it prunes, so that a page
  closed during the lowering does not lower again at the next pass.

## guard (P3.3.4)

- Besides a path below a folder named `.git`, `guard` also rejects without calling `act` a path
  that is itself a folder named `.git`, and a folder that holds one at any depth (its files would
  be removed by `act`, against P1.1 rule 2 and property 7).
- Phase 1 reads each file between two equal stats (up to three tries), so that `seen` describes
  exactly the bytes kept; a file that keeps changing gets no copy (the question instead).
- An empty folder that is itself the path of a delete becomes a `dir` record of the item, so that
  Undo brings the folder back; the item is returned whenever one was made.
- `act` is given the `seen` of the moment the bytes were read.

## What the model test found in the store (fixed)

- **A record's spelling could be stale when it went into the Trash** (seed 519 of the full run): a
  rename whose `moved` transaction was aborted left the record's `spelling` at the old letter case;
  a later delete kept the copy, and the restore wrote the file back under the old spelling. The keep
  transaction now sets each record's `spelling` to the path `guard` read (the file's name at that
  moment), so a restore writes the file where it was.
- **A history transaction refused for the quota** made the state `tight` only until the next
  estimate, which in Chromium still reports the disk's quota (found by `check-history.mjs`); it now
  stays tight until a global pass sees room (section "Budget and the tight state").

The other sequences the full run reported were gaps of the model itself (it attached a promise to
the wrong item of two at the same path; it did not count items kept and pruned again within one
step, or exempt items a restore was taking files from), fixed in `fs/history-model.ts`.

## When a transaction fails (second round of the gate)

P4.4 does not say what a member does when its read-write transaction aborts. Before this round the
store swallowed the error and resolved, so a member that could not do its work reported that it
had: `moved` left the history at the old place while the file was at the new one (seed 7064 of the
model test, below). The rule now, member by member, from the properties of P3.3.1 (the person's
files always win; what the dialogs show can really be restored; nothing stored is unreachable):

- Every change of the history is tried up to three times, each time with a phase 1 of its own
  (`Store.change`): most aborts pass (another window's versionchange, a busy disk). It is not tried
  again after a `QuotaExceededError` (the state becomes `tight`), or when the history became
  unavailable or was closed.
- `record`, `guard` and `restoreTrash` never fail because of the history (property 3; P3.3.4): a
  version not kept is not kept, silently; `guard`'s keep that fails calls `confirm` as before; the
  transactions that only tidy up after `act` (settle the item's untouched records, drop the records
  of files `act` removed after `Yes`) leave the records as they are, which loses nothing and keeps
  every listed row readable; a file a restore wrote is restored even when its record could not
  leave the Trash (a record in the Trash whose file exists, P3.3.3).
- `moved`, `dropTrash`, `clearVersions` and `deleteAll` reject when their change could not be made,
  with `historyNotChanged(<detail>)` of `core/history/texts.ts`: `The history could not be changed
  (<detail>). Your files are not affected.` (the document gives no text; built on P3.3.7's `The
  history cannot be read (<detail>).`). What they had done stays done (`clearVersions` works in
  batches); what is listed is still there and still restorable. When the history became unavailable
  meanwhile they resolve without effect, as P4.4's table of states says for that state. The Trash
  dialog and the Port Additions dialog show the rejection (errata N4 entry 16, N7 entry 15); the
  Files panel passes a rejected `moved` by, because the move itself has happened.
- A `moved` that rejects leaves the file's records whole at the old place. Its earlier versions are
  then not listed for the file at its new place (they come back if the file returns there, or move
  with the next `moved` of that place); nothing is deleted and every row stays readable. This is the
  one case in which a version is kept but not offered with its file, and it needs three aborted
  transactions in a row.

The model applies the same rule: a promise follows a `moved` only when it resolved, and the driver
has a fault in which every read-write transaction of a step aborts (a quarter of the "transaction
aborted" steps), so that the rejections themselves are exercised.

Each failing seed was replayed against the store as it was with the model as it is now: 14 failed
there and pass with the store as it is now (defects of the store), 16 passed (gaps of the model):

- **The store (14: 2738, 2762, 4999, 5097, 7064, 10189, 11106, 12022, 12413, 13319, 16765, 19531,
  20602, 21130).** `moved` met an aborted transaction, swallowed the error and resolved: the file moved, its

  them. Repaired by the rule above (tried again, then rejected).
- **The model: a restore into the folder chosen (4: 9397, 10116, 15624, 19246).** In the folder that
  `fallback` gives, a taken name is answered with `beside` as anywhere else (`p (restored).X68`); the

- **The model: the record that holds a version (9: 2217, 4590, 9490, 14580, 15844, 16946, 17973,
  19390, 20540).** The checker accepted a promised version in *any* record in the Trash with the same

  elsewhere), and missed the file's own record where it legitimately was: in the Trash while its file
  had moved meanwhile (14580), or living where a restore wrote the file beside a taken name (4590).
  It now follows the record that held the version at the last check, wherever that record went,
  and, when that record is living elsewhere, only where a file is (otherwise seed 7064 against the
  old store would pass: a record left at an empty place hides the version from its file).
- **The model: a Replace onto the same bytes (3: 10480, 11719, 20527).** A move or copy onto a file
  with the same bytes overwrites it; `guard` must keep it (open case 5: "for a replace or a restore,

- **The model, found after the repair (4063).** A Trash restore's copy that moved back with its

  copy can fit at all is a question for the owner (it does not touch the seven properties).
- **The model, found after the repair in the memory mode (3694).** A folder delete whose `act` left
  one file: settling the item moved that file's record back, its admission pruned the versions half
  oldest first, and the model looked for an older version that had survived, finding the copies of
  the folder's other files, which the same delete had just put into the Trash half (they were no

## The typical-student figure (D4, for the owner's decision)

Stress run (a) as P5 N3 gives it (10,000 saves across 200 files over 90 simulated days in bursts,
500 deletes, 5 % of the files of 0.5 to 1 MB that do not compress, `B` = 64 MB) ends at **39.33 MB**,
above the 16 MB at which D4 makes deltas the next step. N3 did not build deltas. The run now prints
the figure's parts (read from the database at the end, after 92.7 days; ubuntu-latest and this PC
give the same figures, the run being seeded):

| | files of 0.5 to 1 MB (10 of 200) | sources (190) | records |
|---|---|---|---|
| earlier versions, 28.63 MB of `B / 2` = 32 MB | 21.98 MB (32 versions) | 6.63 MB (963 versions) | 0.02 MB |
| Trash, 10.69 MB of 32 MB (190 items) | 1.97 MB (3 copies) | 8.58 MB (1,227 copies) | 0.15 MB |

- The versions half reached its limit: admission pruned it 68 times and removed 8,178 versions. The
  Trash half never reached it (no item pruned; items leave only after 30 days).
- What is thinned first at the limit (P3.3.4): (1) the widened schedule on every living record
  (within the last day one version per 60 minutes instead of per 5; from 1 to 7 days one per 4 hours
  instead of per hour), then (2) the oldest versions of any record. At the end of the run the 780
  earlier versions of the sources are all younger than 1.3 days (606 under a day, 174 from 1 to 7
  days, none older). **What a student would notice: "the version that worked last week" is gone for
  every source**, while the ten large files hold three quarters of the half with 32 versions. A file
  deleted in the last 30 days is still in the Trash.
- The same run with the ten large files made sources like the others (a scratch variant, not
  committed; the same seed): **41.47 MB**, the versions half 31.97 MB (4,748 versions, just below
  `B / 2`, never pruned), the Trash 9.50 MB (218 items). Its 4,549 earlier versions span the whole
  schedule: 598 under a day, 1,439 from 1 to 7 days, 2,512 from 7 to 60 days (the oldest 59.7 days).
  So sources alone fill the budget in about 90 days too.

For the decision: deltas (P3.3.6: 6 to 11 times less for histories of small edits) would shrink the
sources' part, which is what fills the half in the second run, but not the large files' part in the
first (each save of those is a new file that does not compress, so a delta is the whole file). The
first run's loss of last week's versions would be avoided as well by giving versions only to files
up to a smaller size than 1 MB (the largest source of the corpus is 46 kB); that is a change of
P3.3.4's limits, also for the owner to decide.

## restoreTrash (P3.3.8, P4.4)

- A file is restored at its record's `spelling` (the path its file had when it went into the
  Trash, after any rename the history followed). With the fallback folder of an item whose store is
  not mounted, a file item goes to `<folder>/<name>` and a folder item to
  `<folder>/<folder name>/<path below it>`.
- `beside` writes `<name> (restored).<ext>`, then `(restored 2)` ... up to the first free name.
- (Gate round.) The `TrashItemInfo` of an item of an opened folder carries one more member,
  `folderName` (the roots store's `name` of its root: the folder's own name), in `trashItems()` and in
  the `info` that `restoreTrash` hands `fallback`. P3.3.8's `"prog.X68" was in the folder "Lab",
  which is not open. ...` needs it and P4.4 has no member for it; the contract member is asked for in
  `docs/requests/N4-history-ui.md` item 3. Items of other stores have no `folderName`.
- (Gate round.) The texts the store puts into the errors it throws (`read` of a version that is gone,
  `guard`'s refusals below `.git`, a Replace whose file changed) are those of
  `core/history/texts.ts` (`VERSION_NOT_KEPT`, `gitRefused`, `changedWhileReplacing`), not literals of
  `fs/history-db.ts`.
- The empty folders of the item are created after its last file, only when the restore was not
  stopped by `cancel` or a failed write (a skip or a No does not stop it).

## Texts and sizes

- `core/history/size.ts` writes sizes below 1 kB as whole bytes (`512 bytes`, `1 byte`): P3.2.6's
  "one decimal" cannot apply to bytes.
- `unreadableEntries(1)` still reads `1 entries could not be read.` as P3.3.7 gives it (erratum N0
  entry 2); N3 did not change the final texts.

## What `HistoryService` cannot tell N4 (P3.3.7)

P3.3.7's texts need the number of records that did not parse (`<n> entries could not be read.`) and
the detail of an unavailable history (`The history cannot be read (<detail>).`). The contract of
P4.4 has no member for either. The store has both (`unreadable()`, `unavailableDetail()` of
`HistoryStore`); `docs/requests/N3-history-contract.md` asks the contracts engineer for two
optional members of `HistoryService` so that N4 can read them without a cast. (Gate round: the
contract has them now.)

## The layer rule and `fake-indexeddb` (erratum N0 entry 4)

`fs/history-memory.ts` imports `fake-indexeddb` as P4.4 says. Until the allowance that
`docs/requests/N0.md` section 7 item 1 asks for exists in `eslint.config.js`, the import carries an
`eslint-disable-next-line easy68k/layer-imports` with the reason; the configuration engineer can

## `createMemoryHistoryService` sets no timers

The store schedules its global pass (10 s, then every 10 minutes) and gives an open 5 s, both on
`deps.scheduler`. `createMemoryHistoryService` turns both off (`schedulePass: false`,
`openTimeout: false`): it is what `createTestApplication` uses for every test application, and
tests that count the pending timers of their fake scheduler (`features/documents/documents.test.ts`)
would otherwise find one more. A test runs the pass by calling it (`createMemoryHistoryStore` gives
`globalPass()`). Changed with it, as P6.3 asks: `app/src/bootstrap.test.ts` (N0's) expected the
stub's state `unavailable` while the services are built; it now expects `ready`.

## The model's views of the files are Vfs's of `createVfs()`

`fs/history-model.ts` gives the commands and the history two views of the same files, to tell
which of them wrote what. They are `createVfs()` instances over backends that report each change
(`HookedBackend`), not wrappers of the Vfs, because `fs/vfs.ts` must stay the one implementation of
`Vfs` (`contracts.test.ts`). A test that mounts or unmounts a store after making the model does it
through `model.mount` and `model.unmount`.

## An opened folder that is itself a `.git` folder (the gate, 2026-11-22)

P1.1 rule 2 and P3.3.10 know a `.git` folder by a segment of the path. An opened folder (Open
Folder... or a dropped folder) whose root is itself named `.git` (any letter case) has no such
segment, although every file in it lies below `.git`; N5's report found that `guard` and the
automatic versions would then treat it as an ordinary folder. The store now asks the mounted
backend's `rootHandle.name` (`storeIsGit` in `fs/history-db.ts`): for such a store `place` is null
(nothing is recorded) and `guard` rejects every path with `gitRefused(path, 'below')` before `act`.
Test: `history-db.test.ts`, "an opened folder that is itself a .git folder" (fails without the
check: two versions recorded). The Files panel refuses its commands there already (errata N5
entry 15); FS2's folder picker still accepts such a folder (main's behaviour, unchanged).

N3's review of that change (second round of the gate): right, and not complete. `place` and `guard`
were covered; three members still knew `.git` only by a segment of the path. They now ask
`storeIsGit` too: `untracked` answers `git` for any path of such a store (the editor's note of an
untracked file), `restoreTrash` writes no file into such a store (a folder item's empty folders
included; the item's files are `left` with `gitRefused(path, 'below')`), and the folder chosen for
an item whose store is not mounted is refused there as well. Test: `history-db.test.ts`, "an opened
.git folder: untracked says git, and no Trash item is restored into it". What remains, as a known
limit: an opened folder that lies somewhere *below* a `.git` folder (Open Folder... on
