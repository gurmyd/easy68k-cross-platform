# Errata of M2 (finding the arranging and the ready-made arrangements, version 1.1)

Where `docs/ARCHITECTURE-PLUS.md` P9.3 to P9.5 is silent, ambiguous, or cannot be met as written,
and where M2 differs from its task, what the code does and why. None of these entries changes what
a 68000 program can observe, a file the application writes, the visibility of a panel, or an
original menu item, command or key (P1.1); `node tools/diff-menus.mjs --main v1.0.0` reports one
addition, the submenu `Layouts` after a separator at the end of the Simulator's View menu (in the
menu bar and in the native menu), and 330 of 330 comparisons passed.

## 1. `Arrange Panels` is a text button, drawn from a new kind of toolbar entry (P9.3)

- P9.3 names the button `Arrange Panels` and says it is a toggle with the state of `Lock Layout`
  inverted, running `app.layout.lock`. The toolbar's buttons are icon buttons whose state is the
  check state of their command, not its inverse, and the kit has no icon for arranging (the icon
  sprite is W2's). A new icon beside thirteen others would not make the arranging findable, which
  is the reason P9.3 exists; so the button shows its caption, `Arrange Panels`, as the kit's framed
  button, as high as the icon buttons (28 px), and the row keeps its height.
- `commands/tables/types.ts` gains a toolbar entry `{ type: 'toggle', id, caption, tooltip,
  inverted }`; `toolbars.ts` ends the Editor's and the Simulator's toolbar with a separator and
  that entry (`ARRANGE_BUTTON_TEXTS`); `menus.ts` `resolveToolbar` resolves it as a button with
  `pressed = !isChecked('app.layout.lock')` and the new field `text`; `ui/shell/ShellToolbar.tsx`
  draws it with the kit's `Button` (`aria-label` and caption `Arrange Panels`, `aria-pressed`, the
  tool-tip as its description through the kit's `Tooltip describes`), with the style of
  `ui/shell/toolbar-text-button.css` (pressed: as a pressed icon button). The original buttons
  keep their order and places (`tables.test.ts`, check-arrange `button`).
- Its accessible name is `Arrange Panels`; the tool-tip of P9.3 (`... (View > Lock Layout)`, in the
  Editor `... (Window > Lock Layout)`) is its description. The pressed state is `aria-pressed`
  (Chromium's accessibility tree: button "Arrange Panels", pressed).
- The toolbar stays one Tab stop (the kit's roving toolbar); the arrows reach the button, which
  is the last item before the spacer and the theme button.
- "A second window" (task item a): the lock is part of `app.layout`, which is per window (P3.1.6,
  erratum W3 16). A window opened later takes the layout stored last, so it shows the same state;
  a window already open keeps its own lock, as it keeps its own arrangement. The button of each
  window always shows that window's lock, as its menu does.

## 2. The tip is drawn by the feature, outside the shell's tree (P9.3)

- The shell has no place for a feature's notice outside a panel, and the tip belongs to no panel
  (the kit's toast has one action; the tip has two). `features/layout/ArrangeTip.tsx`
  (`watchArrangeTip`, started by the feature's `init`) therefore puts an element of its own at the
  end of the page's body while the tip is due, a polite live region (`role="status"`,
  `aria-live="polite"`, attribute `data-e68-arrange-tip`), and renders the tip into it with a React
  root of its own 100 ms later, so that the text is announced. Nothing of it exists while the tip
  is not due, so the page is 1.0.0's.
- Look: the kit's notice style (the toast's frame, its accent edge, `--shadow-popup`), at the left
  above the status bar (the toasts are at the right), at most 560 px wide; `z-index` 18 (above the
  floating windows, 11 to 18 with the later element winning a tie; below the Output panel's full
  screen, 19, and every dialog and menu). check-arrange: its box lies between the toolbar's bottom
  and the status bar's top and the page does not scroll.
- It takes no focus. When one of its buttons had the focus (the keyboard reached it), the focus
  goes back to the element that had it before, else to the Registers panel.
- "Not while a program is running or waiting for input": it is shown only while the simulator's
  phase is `idle` (not `loading`, `running`, `waitDelay`, `waitInput`, `waitHost`, `waitAlert`),
  in Simulator mode. When a program starts it goes away unanswered and comes back when the program
  stops; when the window shows another mode it goes and comes back with the Simulator.
- The setting: `AppSettings.plus.arrangeTipAnswered` (true once either button was pressed),
  `core/plus/settings.ts` `arrangeTipAnswered`, `withArrangeTipAnswered`. Like every setting but
  `app.layout` it is shared by every window of the profile at once: a tip open in another window
  goes away when it is answered in one. `withPlus` (the dialog `Port Additions...`) now keeps the
  member; it used to rebuild `plus` from the two switches. The member is not in the contracts yet:
  docs/requests/M2-plus-arrange-tip.md.
- `Arrange Panels` in the tip unlocks the layout (`setLocked(false)`, announced `Layout unlocked.`
  by the dock), then the tip closes; `Got it` closes it and keeps the lock.

## 3. The end-to-end suites and the checks do not see the tip: by the storage notice's rule, not by a pre-set profile (task item b)

The task asked to make the default of the end-to-end fixtures and of "the shared start-up helper of
the check scripts" a profile in which the tip was answered. There is no shared start-up helper: each
of the 40 check scripts (owned by as many packages) opens its own contexts. The application already
has a rule for exactly this case, the Files panel's storage notice (errata FS1 entry 28): in a
browser driven by a test (`navigator.webdriver`) it is not shown unless the page's address carries
a parameter. The tip follows the same rule: under automation it is not shown unless the address
carries `arrange-tip=1` (`ARRANGE_TIP_PARAM` in `features/layout/texts.ts`), and with it it behaves
as for a person (the setting decides). So every end-to-end test and every check of 1.0.0 sees the
window it always saw, without a change to any of them, and the tip is tested where it is the
subject (check-arrange `tip`; M3's `arrange.spec.ts` can open the application with
`app.open('?arrange-tip=1')`).

Files touched for item (b): none (`tests/e2e/fixtures` and the check scripts are unchanged). The
rule gives what the task asked of the fixtures' default (no test of 1.0.0 meets the tip) without a
profile written by each of 40 scripts, and a fixture that wants the tip opens `?arrange-tip=1`.

The desktop app's tests (repair after verify round 1). Playwright starts Electron without
`--enable-automation` (playwright-core's Electron launcher passes `--inspect=0
--remote-debugging-port=0` and the switches of its loader, none of which is that one), so
`navigator.webdriver` cannot be relied on in `tests/desktop/dev`. The desktop app started by those
tests says so itself: `EASY68K_DESKTOP_TEST_WINDOWS` makes the main process report `testMode: true`
at start-up, which the renderer has as `DesktopPlatform.testMode`. `features/layout/tip.ts`
`platformUnderTest(ctx.platform)` counts it as driven by a test, so the desktop tests see no tip
either, whatever Electron reports. A packaged app is never in test mode (security.ts), so
`tests/desktop/packaged` starts it as a person does: the tip appears there when the Simulator is
shown idle, which is its real first start; none of those tests clicks where the tip is (bottom left,
over the Messages panel). Not run: `npm run desktop:test` (M2 starts no Electron; DV2's harness
may).
