# Errata of W0 (Scaffolding)

Corrections to `docs/ARCHITECTURE.md` found while building and repairing W0 (section 8, "Corrections
to the specs"). Each entry says what the document says, what the repository does, and why. None of
them changes a contract of section 3.

## 1. TypeScript is held at 6.0.x (7.1)

- Says: 7.1, TypeScript "at the current stable release when W0 runs".
- Does: `package.json` pins `typescript` 6.0.3. On 2026-11-20 `npm view typescript dist-tags.latest`
  returns 7.0.2.
- Why: the ESLint TypeScript integration that 7.1 requires does not accept TypeScript 7 yet.
  `npm view typescript-eslint@8.73.0 peerDependencies` (the current release) gives
  `typescript: ">=4.8.4 <6.1.0"`. 6.0.3 is the newest release inside that range.
- Proposed text for 7.1: "TypeScript at the newest release that the current `typescript-eslint`
  supports (6.0.x in wave 0); it moves to 7 by a deliberate pull request once `typescript-eslint`
  accepts it."

## 2. The layer rules are a local ESLint rule, not `no-restricted-imports` (3.1, 8)

- Says: 3.1, "Dependency rules, enforced by an ESLint `no-restricted-imports` configuration written
  by W0"; section 8 and the W0 entry say the same in other words.
- Does: `eslint.config.js` defines the local rule `easy68k/layer-imports` and turns it on for
  `app/src/**`, with `no-restricted-globals` and `no-restricted-properties` for the globals and
  properties that the core layers may not touch.
- Why: `no-restricted-imports` matches import strings only. It cannot express "a file in
  `features/<x>/` may not import from `features/<y>/`" or resolve a relative path (`../../ui/...`) to
  the layer it lands in, which 3.1 requires. The local rule resolves each import to a path under
  `app/src` and checks it against the layer table. `tests/lint/import-rules.test.ts` proves that
  forbidden fixtures fail and allowed ones pass, and it runs as part of `npm run lint`.
- Proposed text for 3.1: "enforced by the local ESLint rule `easy68k/layer-imports` in
  `eslint.config.js` (with `no-restricted-globals` / `no-restricted-properties`), written by W0".

## 3. `npm run dev` warns without `engine/dist/`; it does not require it (7.2)

- Says: 7.2, `dev`: "Vite dev server for `app` (requires `engine/dist/`)".
- Does: `app/vite.config.ts` prints "engine/dist/ is missing: the engines are not built. Run
  `npm run build:engines` ..." and serves the page anyway.
- Why: in wave 0 nothing loads an engine, and the W0 acceptance (`npm run dev` serves the
  placeholder page) must pass on a fresh clone without Emscripten. From W4 on the engine loader
  reports a missing engine at run time.
- Proposed text for 7.2: "(needs `engine/dist/` to assemble or run; warns when it is missing)".

## 5. Who moves the hand-written `build/oracle` files (6.2.4, 9.1)

- Says: 6.2.4, "T1 moves the hand-written files it needs from `build/` to `tests/oracle/asm-cli/`".
  The W0 entry of 9.1 gives the same move to W0, and section 8 says `oracle/asm-cli/** W0 > T1`.
- Does: W0 made the move (`msvc-port.patch`, `run-asy68k.mjs`, `smoke-test/*.X68`; byte-identical to
  the `build/oracle` originals) and retargeted the three existing scripts that read them, because
  `build/` is git-ignored and on a fresh clone they failed with
  `Patch not found: <repo>\build\oracle\asm-cli-5.15.4\msvc-port.patch`:
  - `tools/build-asm-oracle.ps1` applies `tests/oracle/asm-cli/msvc-port.patch`;
  - `tools/build-asm-oracle-wasm.ps1` copies `tests/oracle/asm-cli/run-asy68k.mjs` next to the
    `asy68k.mjs` it builds (before, the runner had to be in `build/` already);
  - `tools/compare-asm-oracle.ps1` names `tests/oracle/asm-cli/smoke-test/smoke.X68` in its examples.
  Build outputs stay in `build/oracle/`.
- Proposed text for 6.2.4: "W0 moved the hand-written files it needs from `build/` to
  `tests/oracle/asm-cli/`; T1 owns them from then on."
