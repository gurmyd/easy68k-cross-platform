## 1. TypeScript is held at 6.0.x (7.1)

- Says: 7.1, TypeScript "at the current stable release when W0 runs".
- Does: `package.json` pins `typescript` 6.0.3. On 2026-11-20 `npm view typescript dist-tags.latest`
  returns 7.0.2.
- Why: the ESLint TypeScript integration that 7.1 requires does not accept TypeScript 7 yet.
  `npm view typescript-eslint@8.73.0 peerDependencies` (the current release) gives
  `typescript: ">=4.8.4 <6.1.0"`. 6.0.3 is the newest release inside that range.
- Proposed text for 7.1: "TypeScript at the newest release that the current `typescript-eslint`
  supports (6.0.x in wave 0); it moves to 7 by a deliberate pull request once `typescript-eslint`
  accepts it."

## 2. The layer rules are a local ESLint rule, not `no-restricted-imports` (3.1, 8)

- Says: 3.1, "Dependency rules, enforced by an ESLint `no-restricted-imports` configuration written
  by W0"; section 8 and the W0 entry say the same in other words.
- Does: `eslint.config.js` defines the local rule `easy68k/layer-imports` and turns it on for
  `app/src/**`, with `no-restricted-globals` and `no-restricted-properties` for the globals and
  properties that the core layers may not touch.
- Why: `no-restricted-imports` matches import strings only. It cannot express "a file in
  `features/<x>/` may not import from `features/<y>/`" or resolve a relative path (`../../ui/...`) to
  the layer it lands in, which 3.1 requires. The local rule resolves each import to a path under
  `app/src` and checks it against the layer table. `tests/lint/import-rules.test.ts` proves that
  forbidden fixtures fail and allowed ones pass, and it runs as part of `npm run lint`.
- Proposed text for 3.1: "enforced by the local ESLint rule `easy68k/layer-imports` in
  `eslint.config.js` (with `no-restricted-globals` / `no-restricted-properties`), written by W0".

## 11. The 20-repetition job: what its shards run, and its global limit (6.9 item 10; gate I3 round 4)

- Says: 6.9 item 10, "the end-to-end suites pass 20 times in a row (`--repeat-each=20`) on
  `ubuntu-latest` in each browser with no failure". The comment of `ci.yml`'s job `e2e-stability`
  and the documents said each test is run "twenty times in a row".
- Does: since gate I3 round 3 each browser's run is split with Playwright's `--shard` (Chromium in
  2 jobs, WebKit in 4), every shard with `--repeat-each=20`. Playwright 1.65 shards the repeated
  tests, not the files: every test of the suite runs 20 times in each browser, and those 20 runs are
  spread over the shards of its browser, 10 in each of the 2 Chromium shards and 5 in each of the 4
  WebKit shards (`npx playwright test --config tests/playwright.config.ts --list --project webkit
  --repeat-each=20 --shard=1/4`; the independent review of round 3 compared the lists: the shards of
  a browser together equal the unsharded list, 299 distinct tests per browser, 0 mismatches). So a
  test's 20 runs are not one after the other in one process; nor were they before the split (the
  workers ran them in parallel, in no fixed order, `fullyParallel: true`).
- Why it shows what item 10 asks: every test runs 20 times in each browser on `ubuntu-latest`, with
  no retry (`retries: 0`), and one failure in any of the six jobs fails the run and so the item.
  "In a row" means without a failure in between, which a failure anywhere breaks. The job's comment
  now says this; the release-candidate check can cite this entry.
- Global limit (gate I3 round 4): the Playwright command has `--global-timeout=7200000` (120 min).
  On the development PC one WebKit repetition run hung once in a worker's teardown with no test
  running (`build/gate3/item5-report.json`: the 20th repetition of a clipboard test never started;
  the worker stopped writing after the trace of the test before it), and neither the test limit of
  120 s nor Playwright ended it. On GitHub such a hang would stall the shard until the job's limit
  of 180 min, which cancels the job and uploads no report. Shown on this PC with a scratch suite
  whose fixture never finishes its teardown (`build/repairs-r4/gt`): with `--global-timeout=20000`
  Playwright printed "Timed out waiting 20s for the teardown for test suite to run" and exited 1
  after 21 s. Why 120 min: the measured unsharded times were about 76 min (Chromium) and 184 min
  (WebKit), so a shard is expected to take about 38 and 46 min; 120 min is 2.6 times the longer,
  and leaves the job about 60 min for `npm ci`, the browser, the production build and the report
  upload. `tests/lint/ci-workflow.test.ts` holds the command to it, and the limit between 2.5 times
  the longest expected shard and 135 min.
- The suite's configuration (`tests/playwright.config.ts`, X1's; read, not changed): `trace:
  'retain-on-failure'` records a trace of every test and writes it when the test's context closes
  (and deletes it when the test passed), so each of the many thousand repetitions writes a trace
  archive at exactly the moment the hang came (right after the previous test's trace). That makes
  such a hang more likely where the disk is slow or full: on this PC the disk was nearly full at the
  time, and in another run of the same tests 8 of 160 failed with `browserContext.close: ENOSPC`. It
  also costs time: the same 160 WebKit repetitions took 13.3 min with traces and 2.7 min with
  `--trace=off` (item5-report.json). On `ubuntu-latest` the disk is not near full, and the trace is
  what makes a rare failure of item 10 diagnosable, so the job keeps it; whether the stability job
  should trade the traces for that time is X1's to weigh. Nothing else in the configuration bears
  on it (`retries: 0`, `fullyParallel: true`, the default number of workers).
