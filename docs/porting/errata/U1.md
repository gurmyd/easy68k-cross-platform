## Contract

### C1. No contract for "copy an address register to the Memory panel's Address field" (3.11.3)

- Says: 3.11.3, "double-click on an address-register field copies its text to the Memory panel's
  Address field and shows that panel" (sim-ui §4.4, `regDblClick`). The Memory panel is U2's; no
  contract, store field or command carries a value from the Registers panel to it.
- Did (first version, local adapter): wrote the value to `settings.sim.memoryAddress` and called
  `showPanel(ctx, 'memory')`.
- Does (since gate I1, as U2 asked in its report): `SimMainModel.copyToMemory(box)` runs the
  command `sim.view.memory` with the register field's text (8 hex digits) as its argument. U2's
  handler sets the Memory panel's Address field by its own rules (masked to 24 bits, rounded down
  to 16) and shows the panel with the focus in that field. Tested with the real Memory feature in
  `model.test.ts` and in the browser check (real application pass).
- Proposed for W1: state in 3.11.3 / 2.6 that `sim.view.memory` takes an optional address argument
  (a number or the hex text of a register field), so that the hand-over is part of the contract.
  Taken up in gate I1: errata W1.md 11.3 (no contract member needed, the command's argument is
  enough) and 11.4 (proposed text for 3.11.3).

### C2. `AppState.sim.breakpoints` has no writer (3.12.1)

- Says: the store has `sim.breakpoints: number[]`; no section says who keeps it.
- Does: the gutter reads `engine.breakpoints()` directly (allowed: interface code reads the engine
  freely, section 0 rule 8) whenever `sim.viewRevision` moves and after its own toggles. U1 does
  not write `sim.breakpoints`, so that the field does not get two writers. SH8's session now keeps
  it (it re-reads `engine.breakpoints()` at every publish); the real-session test and the browser
  check confirm that a gutter click reaches it.

### C3. "Clear Cycles: refresh the field" (4.8)

- Says: the controller does `engine.clearCycles()` and "refresh the field". `RunSnapshot.cycles`
  is only said to be refreshed when `registersShown()` ran, which `clearCycles()` does not cause.
- Does: the panel calls `controller.clearCycles()` and then shows `0` itself, as the original's
  `ClearCyclesClick` does (`cyclesDisplay->Caption = "0"`). The next snapshot refresh shows the
  engine's count again. SH8's controller does refresh the snapshot after `clearCycles()`; the model
  takes that refresh over without the selection rule (entry 1).

## Behaviour

### 1. The selection rule of 3.11.4 and the original's `highlight()`

- Says: "After every snapshot refresh, if `snapshot.highlight` differs from the value seen at the
  previous refresh, the selection becomes the engine's row; otherwise the user's selection stays."
- Source: `highlight()` (`SIM68Ku.cpp:785-807`), called by every `scrshow()`, selects the last
  matching row whenever the PC field matches one, also when it is the same row as before; it
  leaves the selection alone only when no row matches. So in the original a row the user clicked
  is replaced by the PC row at the next stop even when the PC row did not change (a `BRA *` loop
  traced, Pause, Rewind to the same start row).
- The document contradicts itself: the fidelity table of 1.3 (row "Current instruction = selected
  row; `highlight()` rule (last match wins, stale selection, third visible row)") says "Same rule",
  and section 0 puts fidelity first. The first version of U1 followed 3.11.4's wording; the review
  of gate I1 found that a row the user clicked was kept after a trace step that left the PC on the
  same row (a `BRA *` loop, the same breakpoint hit again), unlike the original.
- Does (since gate I1): the original's rule. After every snapshot refresh that comes from a
  `scrshow()` in which the engine ran `highlight()`:
  - if the engine's row (`snapshot.highlight`) passes the original's match test - its first 8
    characters, upper-cased, equal the PC field, and it is an instruction row or the program has
    halted - it becomes the selection, also when it is the same row as before; the engine keeps its
    previous row when nothing matched, so the test tells whether `highlight()` found the PC this
    time;
  - otherwise the selection stays (stale selection);
  - either way the selection is scrolled to the third visible row if it is not on screen.
  Tested in `model.test.ts` (scripted snapshots and the session double) and in
  `real-session.test.ts` (SH8's real session and run controller).
- When the engine skipped `highlight()`: during an Auto Trace with `Disable display update`
  checked (`STARTSIM.CPP:170`). The engine's `autoTraceInProgress` is true only inside a tick, so
  the model treats "Auto Trace timer on or `autoTraceInProgress`, and the option set" as skipped.
  The one stop where that differs (a step that halts or hits a breakpoint switches the timer off
  inside the tick) is docs/differences/U1.md entry 7.
- Snapshot refreshes that are no `scrshow()`: the run controller also refreshes the snapshot for
  Clear Cycles (4.8); the original's `ClearCyclesClick` does not run `highlight()`, so the model
  takes that refresh over without the selection rule.
- Additions where the documents are silent:
  - When the listing rows are replaced (load, close, cold start: `listing.rows` is a new array),
    the selection becomes the engine's row whatever the previous value was (after Close: -1, no
    stale selection over an empty listing).
  - Go to PC, a double-click on the PC field and a typed PC (`regPCChange`) use the same match
    test on `engine.listingHighlight`; otherwise the selection stays. Either way the selection is
    scrolled into view.
- The contracts engineer left this text to U1 (errata W1.md 11.3: no declaration changes, "U1
  decides and records the text for 3.11.4"); this is that record.
- Proposed for W1: replace the sentence of 3.11.4 by "After every snapshot refresh that comes from
  a `scrshow()` with the listing display on, the engine's row becomes the selection when it matches
  the PC field (sim-ui §6.4); otherwise the selection stays."

### 2. `ListingView.refresh()` is not called for every `RepaintBit.Listing` (3.11.4, 4.6)

- Says: the comment of `refresh()` in 3.11.4: "re-read all rows (after load, close, cold start,
  RepaintBit.Listing)".
- Source: the engine reports `RepaintBit.Listing` for every `ListBox1->Repaint()`: at every
  `scrshow()` (each trace step), every breakpoint toggle. The rows themselves change only when a
  listing is loaded or the program is closed.
- Does: the Listing panel re-reads the breakpoints and redraws on `sim.viewRevision`, but does not
  re-read the rows; `refresh()` is for the run controller after a load, a close and a cold start
  (4.7 step 7, 4.7.1 step 5, 4.8 Close), as those sections say. Re-reading 100,000 rows at each
  trace step would cost tens of milliseconds per step.
- For SH8: `listing.refresh()` must run after every `engine.load()`, `engine.close()` and engine
  replacement; the panels notice the new rows by the identity of `listing.rows` (a new array per
  refresh), on the next store change or controller notification.

### 3. sim-ui §6.7: a Find that finds nothing still scrolls the selection into view

- Says: "If nothing is found, nothing happens: no message, no wrap-around, the selection is
  unchanged".
- Source: `TForm1::find` (`SIM68Ku.cpp:833-850`) runs the "make sure highlighted line is on screen"
  block after the loop whether or not a row matched; only the early `return` (search position at
  the end) skips it.
- Does: as the source (`ListingFinder.find` reports `searched`; the model then scrolls the selected
  row into view). Selection and messages are unchanged, as the spec says.

### 4. sim-ui §6.2 on short rows

- Source: `isInstruction` indexes an AnsiString at positions 9 and 11; a row that starts with `00`
  and is shorter than 11 characters would raise an exception there.
- Does: such a row is not an instruction row. No listing line the assembler writes is that short
  and starts with `00` (every line with an address carries the line-number column).

### 5. Find upper-cases ASCII letters only

- Source: `toUpper` (`SIM68Ku.cpp:810-813`) uses the C library's `toupper` on a (signed) `char`;
  bytes `$80-$FF` are negative and come back unchanged.
- Does: `upperAscii()` in `core/listing/view.ts`; `é` does not match `É` (tested).

### 6. Messages panel and the `log` role (2.11)

- Says: "The message areas (editor and simulator) are `log` live regions with polite
  announcements".
- Does: the visible list renders only the rows on screen; rows that appear while scrolling would be
  announced by a live region. So the list is a plain `list`, and a separate visually hidden
  `role="log"` region with `aria-live="polite"` receives the lines that arrive (at most three per
  update). It is hidden with the kit's `e68-sr` class (since gate I1 round 2, as the kit engineer
  asked); one extra rule keeps `white-space: pre` so that the trace lines keep their columns.

### 7. The register labels use the token monospace font

- sim-ui §2: labels Courier New bold 13 px, fields Courier New 13 px. The panel uses
  `--font-mono` (Courier New first) and `--fs-md` (13 px); the labels are bold. The listing and the
  message area use the `Source Window Font` setting (`settings.sim.listingFont`), as the original's
  list box and memo do.

### 8. Loading the same program again after Close selects no row (the original's behaviour)

- Seen with the real session (gate I1): after File > Close and an Open of the same program, the
  engine's `listingHighlight` is -1 although the PC field reads `00001000`, so no row is selected.
  The panel shows the engine's row, as it must. Ctrl+G or the first trace step selects the PC row.
- Traced in the source (gate I1, round 2): `CloseExecute` (`SIM68Ku.cpp:426`) clears the list box
  (`ItemIndex` -1) and calls `initSim()`, whose `scrshow()` runs `highlight()` over the empty list;
  `initSim()` (`STARTSIM.CPP:33-70`) resets D0-D7, A0-A6, the stacks, SR and the cycles but not
  `PC`, so the PC field keeps `00001000`. `OpenFile` then calls `initSim()` again (again over the
  empty list), loads the rows and assigns `regPC->EditText = "00001000"`: the text does not change,
  so `OnChange` (`regPCChange`, the only `highlight()` after the rows are loaded) does not run.
  Hence -1. This is the original's code path, not a port artefact; a check against the official
  binary is still welcome but no longer needed to explain it.
- A related point for the engine owner, outside U1's paths (not a U1 change): `OpenFile` empties
  the list with `ListBox1->Items->Clear()`. In the VCL that also drops the list box's selection
  (`LB_RESETCONTENT`, `ItemIndex` -1); the engine's shim (`engine/sim/shim/form1.cpp`) implements
  `TStrings::Clear` without touching `ItemIndex` (only `TListBox::Clear` resets it). Opening a
  program again WITHOUT Close while the PC field already shows its start address therefore keeps
  the old row selected in the port, where the original would most likely select nothing (observed
  in round 2: open `demo`, open `demo` again, `listingHighlight` is 6, the MOVE.L start row). The
  panel follows the engine either way, so a correction in the shim needs no change in U1.
  Filed for its owners at gate I1 round 3: `docs/requests/U1-listbox-clear-itemindex.md` (engine
  owner: the shim change; gate: the rebuild of `engine/dist`). The shim change and the rebuild
  arrived in the same round, so the test "Open of the same program again without Close" now
  expects `listingHighlight` -1 and no selected row, and passes on the rebuilt engine.
- Tested in `real-session.test.ts`: the panel follows the engine (selection = `listingHighlight`)
  and, after Close and Open, both are -1.

### 9. After a load that selects no row: Go to PC, the PC double-click and the list's top (gate I2)

- The defect carried from gate I1 ("after a program is loaded following another one, the listing
  marks no row", check-wave1's tour, five examples, all three systems) is the original's
  behaviour, read again in the source for this gate: `OpenFile` (`SIM68Ku.cpp:270-363`) calls
  `initSim()`, whose `scrshow()` (`STARTSIM.CPP:130-175`) runs `highlight()` over the OLD rows
  (it shows the PC that `initSim()` does not reset), then `ListBox1->Items->Clear()` (`ItemIndex`
  -1), loads the rows and assigns `regPC->EditText` the first row's address. The VCL's text setters
  do nothing when the text is unchanged, so `regPCChange` (the only `highlight()` after the rows
  are loaded) runs only when the PC field showed another address before. Hence:
  - a program opened while the PC field already reads its start address (the previous program
    was loaded at the same address and not run, or was reset) selects no row;
  - one opened after the previous program's PC moved selects its start row.
  Rewind (`RewindExecute`: `PC = startPC; initSim()`) runs `highlight()` through `scrshow()` over
  the loaded rows, so a reset always selects the start row. Both cases are now tests in
  `real-session.test.ts`; the panel follows the engine, as entry 8 says. The check in
  tests/integration/wave1 that requires a row after every load asks more than the original does;
  that check is the integration engineer's (the engine engineer said the same at gate I1 round 3).
- Two things the port did not do after such a load, both repaired here:
  1. **Go to PC and a double-click on the PC field selected nothing.** The original's
     `GotoPC1Click` and `regPCDblClick` call `highlight()`, which searches the loaded rows and
     selects the PC row. The port took the engine's `listingHighlight`, which is the row of the
     engine's last `highlight()` and is -1 after such a load. `SimMainModel.followPC` now searches
     the rows as `highlight()` does (the last row from index 3 whose first 8 characters,
     upper-cased, equal the PC field and that is an instruction row or the program has halted)
     whenever the engine's row does not match. Tested in `real-session.test.ts` and
     `check-sim-main.mjs` (failed before: "expected -1 to be 6").
  2. **The list kept the previous program's scroll position.** `LB_RESETCONTENT` sets the list
     box's top index to 0, so the original shows the first rows of the new listing. The Listing
     panel now scrolls to the top whenever the rows are replaced (a load, a close, a cold start),
     before a selected row is brought on screen. Tested in `check-sim-main.mjs` (the same program
     opened again with the list scrolled down: no row, scrollTop 0; then Go to PC and the next
     trace step select the PC row).
