# Errata of N4 (History and Trash dialogs, recording)

Where `docs/ARCHITECTURE-PLUS.md` is silent, ambiguous, self-contradictory or does not match what
N4 found, what the code does and why. No exported signature of P4.4 was changed:
`restoreWithQuestions(deps, items, title)` is exactly the stub's.

## 1. `No has the focus` cannot be asked of the dialog service (P3.3.4, P3.2.2)

P3.3.4 says the question `EASy68K cannot keep a copy of ... anyway? This cannot be undone.` has
`Yes`, `No`, "No has the focus". `MessageBoxRequest` (contracts, W1) has no member for the default
button, and the shell's `DialogHost` draws every message box with its first button as the default
and focused one (the kit's `MessageBox` has `defaultButton`, the host does not pass it). N4 passes
`['Yes', 'No']` in that order, as FS1's Delete does; `Yes` has the focus. Request:
`docs/requests/N4-history-ui.md` item 2.

Gate round: settled. The contract has `MessageBoxRequest.defaultButton` (the button's caption,
`docs/requests/N5-default-button.md`) and `DialogHost` passes it to the kit's `MessageBox`. Every
question of P3.3.4 that N4 asks is built by `cannotKeepBox` of `core/trash-restore/restore-flow.ts`
with `defaultButton: 'No'`, so No has the focus as P3.3.4 says.

## 2. Singular forms of the Trash's questions (P3.3.8)

P3.3.8 gives `Delete the 2 selected items for good?` and `Delete everything in the Trash for good?
(12 items, 1.4 MB)`. For one item N4 writes `Delete the selected item for good?` and `(1 item, ...)`
(`features/history/texts.ts`, `deleteForGoodQuestion`, `emptyTrashQuestion`). Every other count is
the document's text.

## 3. Texts the document does not give

- The titles of the questions of `Delete for Good`, `Empty Trash` and `Delete History and Trash`:
  the button's caption (the rule "titled with the command" of P3.3.4).
- The accessible names of the two lists (`Earlier versions`, `Items in the Trash`) and of the
  comparison (`Comparison of the selected version with the file now`).
- `<detail>` of `The history cannot be read (<detail>).` when the store gives none: `no detail is
  known`. The store gives one in every case N4 has seen (`unavailableDetail()`, errata N3).
- The folder name of an opened folder that is not open now, for `"prog.X68" was in the folder
  "Lab", which is not open. ...`: `TrashItemInfo` (P4.4) has no member for it, and the path of such
  an item (`/folder/...`) does not name the folder. N4 reads an optional `folderName` of the item,
  which the store now gives for every item of an opened folder (gate round; errata N3,
  "restoreTrash"), so the question names the folder (`Lab`). Only when the store's record of that
  folder is gone does it write `opened folder` (`UNKNOWN_FOLDER_NAME` of
  `core/trash-restore/texts.ts`). Request: item 3 (the member in the contract).
- `Was in` of a Trash row: `placeShort` of the item's folder (`My Programs/demo`, `My Programs` for
  an item at the top of the store).
- `Kept` and `When`: `Intl.DateTimeFormat` of the system's locale with year, short month, day, hour
  and minute (`21 Nov 2026, 21:42` in en-GB, `Nov 21, 2026, 09:42 PM` in en-US).

## 4. The replace question names the place with `placeShort` (P3.3.8)

P3.3.8's example reads `"demo/prog.X68" exists. ...`; `core/trash-restore/texts.ts` (N0) says
`where` is "the path as the student reads it". N4 passes `placeShort(path)` (P4.5), which gives
`My Programs/demo/prog.X68` in the browser store and `Lab/prog.X68` in an opened folder, as every
other message of the stage names a file (`displayPath` uses the same function, P3.2.5).

## 5. `RestoreFlowDeps` gained one optional member (P4.4)

`RestoreFlowDeps.vfs?` (only `stat` is used): with it the replace question names the first free
`prog (restored N).X68`, the name the store writes with `No` (errata N3, restoreTrash); without it
(a caller that passes only the four members of P4.4, as N5's Undo may) it names
`prog (restored).X68`. The function's signature and the four members are unchanged.

## 6. "asks the question of P3.3.4" and "no second question follows" for a Trash restore

The acceptance list says that in states `off`, `tight` and `unavailable` "Restore (and a Trash
`Restore` with `Yes` over a file) asks the question of P3.3.4", and also that "in states other
than `ready` the Trash restore's replace question ends with `This cannot be undone.` and no second
question follows". P3.3.4 decides it: a command whose own question promises the Trash says `This
cannot be undone.` instead, and its `confirm` then answers `Yes` without asking. So in those states
Earlier Versions' Restore (which has no question of its own) asks the question of P3.3.4, and a
Trash restore over a file asks only its replace question, whose second sentence is `This cannot be
undone.`; `No` there keeps the current file and writes the restored one beside it. The question of
P3.3.4 is asked by a Trash restore only when the history is `ready` and still cannot keep a copy of
the file to be replaced (above 20 MB, no room). The replace question's wording is remembered per
file, so a state that changes between the question and the write never asks twice.

## 7. `Cancel` in a restore of several items stops the items after it too

P3.3.8: "`Cancel` stops: files already written stay restored, and the item keeps the others." With
several items selected, `restoreWithQuestions` also leaves every later item untouched (it is one
command), which is what "stops" means for the person who pressed it.

## 8. `Open as New Document` and the document service (P3.3.8, P4.4)

`DocumentService` can make a new document only from the template (`newSource()`); no member gives a
new document a text, and a feature may not reach the document registry. Until the contract has one
(request item 1), `features/history/open-as-new.ts` makes the new untitled document with
`newSource()` and has the editor replace the template with the version's text: a view plugin,
registered through `ctx.editorExtensions` for that one document, makes one change that Undo does
not take back (`Transaction.addToHistory` false) and unregisters itself. The document is then
modified, so closing it asks whether to save it. The text is the version's text without its font
and tab trailer lines (`stripTrailer` of `core/documents/format.ts`), as opening the file shows it:
with them, the new document's first Save would write a second trailer. The comparison itself shows
the trailer lines as they are in the file, as P3.3.8 says.

Gate round: the contract now has the optional `DocumentService.newSourceWithText` (request item 1);
`openAsNewDocument` calls it whenever the document service has it, and only otherwise goes the way
described above (the member is not implemented by `core/documents/service.ts` at the time of the
gate round).

## 9. P3.3.7's count and detail are read from members P4.4 does not have

Gate round: the contract now has both as optional members of `HistoryService`; `problemsOf` reads
them through the contract, with the same fallbacks.

`<n> entries could not be read.` and `The history cannot be read (<detail>).` need the number of
records that did not parse and the detail of an unavailable history. N3's store has
`unreadable()` and `unavailableDetail()` beside `HistoryService` (errata N3;
`docs/requests/N3-history-contract.md` asks the contracts engineer for both as optional members).
`features/history/versions.ts` (`problemsOf`) reads them structurally as optional members and works
without them (count 0, the detail of entry 3).

## 10. `ed.file.history`'s `enabled` cannot see its argument (P3.6)

P3.6: enabled while "`ctx.history` exists and the path is a file outside `/memory`", the path being
the argument's or the active document's. `CommandHandler.enabled(state, ctx)` receives no argument,
and `CommandRegistry.run` runs nothing that is disabled, so the command is enabled by the active
document: a document with a path outside `/memory` (not a store's root). A caller with a path of
its own (the Files panel's context menu, N5) can therefore find the command disabled while an
untitled document is active. Such a caller may open the dialog itself by its id:
`ctx.dialogs.open('history.versions', { path })` (`VERSIONS_DIALOG_ID`, props
`VersionsDialogProps`), which is what the command does.

Gate round: settled. `CommandHandler.enabled` now receives the argument and `run` asks with it
(`docs/requests/N4-history-ui.md` item 6); the handler decides by the argument's `path` when there
is one (the menus ask without one, so they are unchanged), and
`ctx.commands.run('ed.file.history', { path })` opens the dialog whatever document is active.

## 11. The kit's DataGrid does not know the key map (P1.3)

P1.3 gives the Trash list the tree's keys: Shift+Up / Shift+Down, Ctrl+Space (macOS Option+Space),
Ctrl+A (macOS Cmd+A, Ctrl+A). The component kit has no key map (`ui/components` may not import
`commands/`), so `DataGrid` with `multiSelect` accepts both forms everywhere: Ctrl or Option/Alt +
Space, Ctrl or Cmd + A and + click. It also takes from the tree's row of P1.3, so that a selection
of rows that are not next to each other can be made with the keyboard: Ctrl+Up / Ctrl+Down (macOS
Option+Up / Option+Down) move the focused row without selecting, and Shift+Home / Shift+End extend
to the first and last row. Option+Space is recognised by its key position too (macOS reports a
no-break space as its key). Without `multiSelect` none of this exists and the grid is unchanged.

## 12. The focus when a dialog opens

The kit's `Dialog` puts the focus on the default button when nothing else asks for it, so both
dialogs open with the focus on `Close` (their default button) and Tab goes on to the list. The
order, as `check-history-ui.mjs` finds it: Earlier Versions `Close > list > Restore > Open as New
Document`; Trash `Close > list > Restore > Delete for Good > Empty Trash`; Shift+Tab the reverse.

## 13. Recording does not queue files that get no automatic versions

`record` keeps nothing for an `.L68`, `.S68`, a file above 1 MB, a binary file, a file below `.git`
or in `/memory` (P3.3.3, `untracked`). `features/history/recording.ts` asks `untracked` first and
does not queue such a file at all, so that a 20 MB binary written by Save never takes room in the
store's 16 MB queue. The bytes are copied before they are queued.

## 14. The storage-tight toast's "free space above 64 MB"

P3.3.4: a window shows the toast again "only after it has seen free space above 64 MB and a second
shortage". `HistoryService` does not report free space; `features/history/tight-notice.ts` reads
`navigator.storage.estimate()` itself whenever the history notifies a change while the state is
not `tight` and the toast has been shown (quota - usage above 64 MB re-arms it). Without an
estimate, leaving `tight` re-arms it (the store leaves `tight` only when it sees room, errata N3).

## 15. The marks at the end of a file without a final line break

The `+` and `-` marks follow `@codemirror/merge`'s chunks, which cover whole lines. Lines added
after a last line that has no line break change that last line too (it gains one), so it is marked
`-` on the left and `+` on the right, as the package's own highlighting shows it. Files saved by the
editor end with a line break (the trailer), so this is seen only with files written elsewhere.
