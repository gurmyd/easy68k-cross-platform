## 1. The goldens are a baseline of the port, not captures of the original

- Says (6.5.4): "the surface hash is committed". It does not say from where.
- Does: every hash in `tests/conformance/examples/golden/surfaces.json` comes from the port itself (its
  assembler, simulator engine and host parts, headless, under Node, real glyph atlases, virtual time). The file
  says so in its `provenance` member, a unit test checks that it does, and the README of the folder explains it.
- Why not the official binary: the official `SIM68K.exe` under Wine (T3's driver) cannot give whole-program
  pictures that mean anything for Windows. Wine has no Fixedsys font (errata/T3.md entry 1: the grid is 58 x 34,
  not 80 x 32) and its GDI draws ellipses and text its own way. What agrees with the original is covered where
  it can be: T2's GDI references (primitives, ellipses, raster atlases) and T3's flat-area checks. This suite
  proves stability and independence of browser and operating system, nothing more. Do not cite it as agreement
  with the original.

## 2. Which twenty conformance programs

- Says: "twenty conformance programs with graphics". Does: the thirteen of `trap15-b` and seven of `trap15-a`
  (`a01, a06, a07, a17, a20, a40, a46`), listed by id in `catalog.ts`. `a00, a19, a24` and `a42` were not taken:
  they end by clearing the screen, so their hash is the one of a black surface. Other `trap15-a` programs that
  print text would serve as well; seven are enough for the text grid, which `scene/x02` and the official
  examples also cover. The official examples that end black are `clockDigital` (it uses the seven-segment
  display, not the surface) and `fileio` (no output); they are kept because 6.5.4 asks for every official example.
- Four programs of this folder (`programs/x01` to `x04`) were added: lines and ellipses of every size, wide pens,
  flood fill and clipping; text in five faces and every style; the sixteen drawing modes with double buffering
  (so that `window` and `back` differ); a resized window. The T3 programs read colours of flat areas and write
  a report; these draw pictures with edges and glyphs, which is what a pixel regression is for.

## 3. "A fixed instruction count"

- Time is virtual and a run advances in frames of 16 ms, so a run cannot stop at an exact instruction: it stops
  at the first frame boundary at or after `limits.instructions` (or at the program's halt, or at
  `limits.ms` of virtual time). The count it really stopped at is in the golden, and the browser check compares
  it. Only `mouseWindowSize` (5,010,000 instructions, at 4,944 ms of virtual time) meets the instruction
  limit, before its own time limit of 6 s; the two clocks end on the time limit (10 s). All three are
  deterministic: nothing in a run reads the machine's clock. (The README and the catalog's note said
  that `mouseWindowSize` stops at six seconds; corrected in the round before gate I3.)

## 4. Finding: a finished key wait leaves the prompt overlay on the canvas

- After a program has read a line (task 2, 4 or 5; the tutorials), `surface.overlay` stays set: a blank cell
  that erases the prompt's `_` (3.5.3). The canvas therefore shows the surface with that cell painted over
  it, and "a screenshot of the canvas shows exactly the pixels of the surface" is only true if the overlay
  is counted as part of what the surface shows. The suite records `screenHash` (the image on screen with the
  overlay painted over it, as `Presenter.frame` does) next to `surfaceHash` and `shownHash`; the browser check
  compares the screenshot with `screenHash`. This is by design, not a defect; it is noted so that nobody
  "repairs" the comparison.
- Corrected in the round before gate I3 (the first text said the hashes differ for `tutorial2` to `4`, which
  the committed golden contradicts). Measured: `tutorial2` and `tutorial3` do end with the overlay set, but it
  is a blank cell painted over cells that are blank on the surface too, so `screenHash` equals `shownHash`;
  `tutorial4` ends without it. In `golden/surfaces.json`, `surfaceHash`, `shownHash` and `screenHash` are
  equal for every example except `scene/x03-modes-and-double-buffer`, where `surfaceHash` (the back buffer)
  differs from the two others (the window buffer, double buffering). No example therefore exercises an
  overlay that changes the picture end to end; that path is covered only by the unit test "screenPixels
  paints the overlay over the shown image and clips it" (`units.test.ts`).

## 5. Notes for other packages

- T3: `createWindowsGlyphs()` in `tests/conformance/sim/harness.ts` returns a provider whose `ready` promise
  `runScenario` did not await before starting the session. X3 awaits it (`runExample`). Not observed in X3's
  runs. Done by T3 in the round before gate I3: `runScenario` awaits it (docs/porting/errata/T3.md).
- Weak coverage (review of X3, wave three): `clockDigital` and `fileio` end on the same all-black surface,
  and the browser check presents the surface on a canvas of its own, not in the real Output panel. Both are
  stated in the folder's README. A check of `clockDigital`'s seven-segment state was considered and not
  added: the seven-segment display is a hardware device (SH7), whose state the conformance suite
  (`tests/conformance/sim`, hardware programs) and the Hardware panel's check already cover; this suite is
  about pixels of the surface.
- The development server's hot-reload client logs a console error ("WebSocket connection to ... failed", "Failed
  to send error to Vite server") when hot reload is off, as it is in every check. `check-examples.mjs` ignores
  exactly these messages and no others; `X3_ALL_ERRORS=1` prints everything.

## 6. Not verified

- Ubuntu and macOS. The check ran on this PC (Windows 11) in Playwright's Chromium and WebKit, where WebKit is
  the Windows build. Whether Linux and macOS give the same hashes (the surface, text and font code under `core/sim-host` calls no `Math.sqrt`, `sin`, `cos`, `pow`, `exp` or `log`,
  by a search; the engines were not audited for floating point) and whether macOS WebKit's
  screenshot of a canvas keeps colours exact (colour management) is for the CI jobs to say; the request
  `docs/requests/X3-check-examples.md` asks for them. In the round before gate I3 the configuration
  engineer added `check:examples` to the job `browser-checks` (group `simulator`, Ubuntu, macOS and
  Windows); on this PC it passed 309 of 309 in both browsers after this round's changes. Its first
  CI run on Linux and macOS is the first proof of the cross-system claim; a mismatch there is a
  finding about the engine, the host parts or the browser, not a reason to loosen the comparison.
  A real Safari's canvas is in the manual list (docs/MANUAL-TEST-MAC.md W5, W6).
