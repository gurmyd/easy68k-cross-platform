# Errata of E1 (Documents)

What E1 found while building `app/src/core/documents/` and `app/src/features/documents/` from
`docs/ARCHITECTURE.md` 3.8.6, 3.9, 5.1-5.3 and editor-ui §1, §2.7, §6, §12, §16, §19.3, §20.2:
where the document is silent, contradicts itself or disagrees with the ground truth, what the code
does, and why.

## Format

### 1. `encodeForAssembler` appends no final CR LF (3.9.2; assembler §9.4.1)

- Says: 3.9.2, "`encodeForAssembler(text)`: every line + CR LF, also the last (assembler §9.4.1)".
  Assembler §9.4.1: "The main source is what the editor control holds, saved with
  `TStrings::SaveToFile`: every line ends with CR LF, including the last."
- Ground truth: the official EDIT68K v5.16.1 under Wine (`build/ground-truth/asm/default`) received
  **no** final CR LF for the four corpus files that have neither a final line end nor a trailer
  (`site/games/invader/background.x68`, `site/games/lightsout/background.x68`,
  `site/games/lightsout/lightsout.x68`, `site/graphics/bmp_load/bmp_load.x68`), and the stress case
  `s08_no_final_newline.X68` (66 bytes in, 66 bytes received). The RichEdit's plain-text stream
  writes the text as it is.
- Does: `encodeForAssembler` writes the text with every `"\n"` as CR LF and appends nothing. With
  the trailer present the text always ends with a line break anyway (the `"\n"` that SaveFont writes
  before the trailer stays), so only files without one are affected. The assembler's output is the
  same either way (the engine adds the final LF itself).
- Verified: `corpus.test.ts` reproduces the text the official editor received (SHA-256 in
  `tests/corpus/manifest.json`) for every program of the corpus whose source is here (entry 5),
  these four included. On tracked data alone, three more sources end without a line break and were
  received without a final CR LF: `checklist/textmode-02-last-line-without-line-end-gets-one-editor-save`,
  `richedit/s08_no_final_newline.X68` and `richedit/s11_ctrl_z_end.X68`; so the correction is
  checked in CI too.
- Proposed text for 3.9.2: "`encodeForAssembler(text)`: the text with every `"\n"` written as CR LF;
  a final line break only if the text ends with one (the RichEdit's plain-text save)." and for
  assembler §9.4.1 the same correction.

### 2. Trailer lines that are too short: `Error in LoadFile()` (editor-ui §6.3 step 4)

- Says: "the characters at 1-based positions 12 and 13 up to a `~`" and similar for the other
  three; nothing about a line that ends before.
- Source: the loops are `for(i=12; str[i] != '~' && i<14; i++)` (textS.cpp:144-146, and likewise
  for Font size and Font name). The character test comes first, and C++Builder's
  `AnsiString::operator[]` checks its index (`ThrowIfOutOfRange` in `dstring.h`): reading past the
  end throws `ERangeError`. LoadFile's `catch(...)` then shows `Error in LoadFile()` and skips the
  rest of LoadFile. Lines that throw: `*~Tab size~` with zero or one character and no closing `~`
  (`*~Tab size~4`), `*~Font size~` likewise, `*~Font name~` with nothing after it.
- Does: `stripTrailer` stops at such a line, keeps it and the lines above it in the text, keeps the
  values already taken, and reports `loadError: true`; the service shows `Error in LoadFile()`
  (Information, OK) and opens the document all the same. The lines left in the text reach the
  assembler (as comments) and appear in the listing, which is why this is reproduced.
- **UNVERIFIED against the official binary.** No file of the corpus or of the oracle captures has
  such a line, so the behaviour rests on the source (`textS.cpp:142-173, 201-204`) and on
  C++Builder's `AnsiString::operator[]`, which calls `ThrowIfOutOfRange` before every access.
  `LoadedSource` has the extra field `loadError`.
- What the original's `catch(...)` also skips, and the port does not model: `SetTabsAll()`, the
  caption (`Caption = ExtractFileName(...)`), protecting the text, `Project.Modified = false` and
  `SourceText->Modified = false`, the highlighting, and turning redraw (`WM_SETREDRAW`) and the
  RichEdit event mask back on. The original is left with a window that does not repaint and may
  count as modified; the port opens the document normally (its name as caption, not modified, its
  tab stops and highlighting), which is listed in `docs/differences/E1.md`.
- The engine's `loadEditorText` (engine/asm/asm68k.mjs) is lenient here: it reads such a line as a
  trailer line and drops it. A fuzz of random trailer lines (E1's review) found thousands of such
  differences; `corpus.test.ts` finds none on real programs (`ENGINE_DIFFERENCES` is empty). The
  assembler output differs only by the comment line left in the text. If the owner prefers the
  engine's lenient reading, that is a gate decision; until then the port follows the source.
- How to settle it: add a stress file with a line `*~Tab size~4` (no closing `~`) to
  `tests/oracle/wine/asm/gen_richedit_stress.py` (T1's) and look at the text the official editor
  hands its assembler, and at its message box.

### 3. `*~Font name~` never copies the line's last character (editor-ui §6.3)

- Says: "characters from 13 up to the next `~`, any length".
- Source: `for(i=13; str[i] != '~' && i<str.Length(); i++)` (textS.cpp:164-166): position
  `Length` is never copied. With the closing `~` (every file the original writes) nothing changes;
  `*~Font name~Arial` without it gives `Aria`.
- Does: as the source. The engine's `loadEditorText` copies to the end of the line; the two agree on
  the whole corpus (`ground-truth.test.ts`).

### 4. Line ends of the ground truth

- Lone LF (339 corpus files) ends a line, as 5.1 says. A lone CR also ends a line (5.1); the only
  oracle case for it (`richedit/s05_bare_cr.X68`) is one where Wine's RichEdit differs from the
  editor model (`tests/conformance/asm/golden/REPORT.md`), so that rule rests on the document, not on
  the ground truth. `corpus.test.ts` lists s05, `s12_nul_in_comment` and `s16_utf8_bom` as the
  known Wine deviations and fails if one of them starts to match. (`s19_trailer_no_newline`, which
  the same report lists against T1's model, is reproduced by `stripTrailer`.)

### 5. The ground-truth set: `easy68k-qt` left out

- The task names 486 programs with ground truth. 301 of them are sources under
  `reference/examples/github/easy68k-qt`, a folder that must not be used, read or consulted.
  `ground-truth.test.ts` filters those manifest entries out by their path before opening anything
  and checks the remaining 185 (10 official, 41 `github/68k-assembly-learning` and
  `github/pacman-mc68000`, 134 `site/...`), all four files of entry 1 among them. The
  `richedit-stress` set had no sources on this machine then.
- Since the integration gate: the test is `corpus.test.ts` and reads the tracked
  `tests/corpus/manifest.json` (the SHA-256 of the received text of every run) and the tracked
  sources of the sets `official` (10), `github-mit` (41 with a result) and `conformance` (119 with a
  result: the checklist programs and the 24 RichEdit stress files), plus `site` (134) where it has
  been fetched: 304 programs on this machine, 170 in CI. Every one gives the official text except
  the three Wine deviations of entry 4. `build/ground-truth` is no longer read by anything of E1
  (T1's review note), and `easy68k-qt` is not in the manifest at all. The other 301 programs of the
  original set remain unchecked: their folder must not be used.

### 6. Tracked fixtures are base64 (repository rule)

- `.gitattributes` checks in everything under `app/**` with LF line ends (`text=auto eol=lf`), which
  would turn the CR LF of `.X68` fixtures into LF. The ten official examples (GPL) are therefore in
  `core/documents/fixtures/official-examples.ts` as base64, with the SHA-256 of the bytes the
  official editor sent the assembler for each. A gate may prefer a `-text` rule for
  `app/src/**/fixtures/**`; nothing depends on it.

## Behaviour

### 7. List documents keep tab type 0 and tab size 0 (editor-ui §6.3)

- `DocumentState` of a list document (`.L68`, `.S68`) has `tabType` 0 (Assembly) and `tabSize` 0,
  the zero initial values of the original's `FileInfo`, so that Save As `.X68` writes
  `*~Tab type~0~` / `*~Tab size~0~` as the original does. **E2 must not divide by `tabSize`** or loop
  on multiples of it for list documents (they are not highlighted and have no tab model in the
  original; a sensible display is tab stops every 8 columns).

### 8. The overwrite question is the file dialog's (editor-ui §6.4, §20.2)

- `FileDialogs.save` resolves with "overwrite already confirmed" (3.8.5), so the document service
  never asks `File exists! OK to overwrite?`; FS1's dialog asks it (FS1's acceptance list). The §20.2
  item "Save As onto an existing name" is FS1's test.

### 9. Titles of the message boxes

- The original's boxes come from VCL `MessageDlg`, whose title is the icon type's name: `Confirm`
  (already open, close prompt, reload, and the port's save conflict), `Error` (File Access Error,
  write failure), `Information` (`Error in LoadFile()`), `Warning` (characters without a
  Windows-1252 byte). The drafts dialog is titled `EASy68K`.

### 10. Write failure text

- The original lets the VCL report a failed `SaveToFile` (editor-ui §6.4: "the framework shows its
  standard exception message"). The port shows `Cannot create file "<path>". <reason>` (the wording
  of VCL's `EFCreateError`) and keeps the document modified.

### 11. Save As default extension

- `SaveRequest.defaultExt` is passed as `.X68` (with the dot), as W3's test of the stub uses it. The
  contract does not say whether the dot belongs to it; FS1 should accept either.
- FS1's note asks for the original's malformed `*.X68` (editor-ui §6.4). E1 keeps `.X68`: FS1's
  `normalizeDefaultExt` turns both into `.X68`, but the desktop main process (DV2,
  `desktop/src/main.ts`) appends a default extension only when it matches `^\.?[A-Za-z0-9]+$`, so
  with `*.X68` a name typed without an extension in the native Save dialog would get none. The
  result is the same for FS1's dialog and correct for the native one. If the contract is to carry
  the original's value, DV2's check must accept it first.

### 12. The UTF-8 notice is a toast

- 5.1: "the editor shows a banner: `This file looks like UTF-8. EASy68K reads it as
  Windows-1252.`". `DocumentState` has no field to carry it to the editor component, so the document
  service shows the text through `dialogs.toast` when such a file is opened or reloaded
  (`looksLikeUtf8` in `format.ts`; a UTF-8 byte-order mark counts).

### 13. Drafts: database and keys

- 3.9.4 names the IndexedDB store `drafts`. The database is `easy68k.drafts` (version 1, key path
  `key` = `<windowId>/<docId>`), separate from FS1's store so that neither has to manage the other's
  schema versions. Records hold `state` (DocumentState), `text`, the file's recorded modification
  time (so that a restored document still notices a file changed in storage) and the tab order.
- The offer runs under the Web Lock `easy68k.drafts.offer`, so two windows that start together after
  a crash cannot both offer the same drafts. Without `navigator.locks.query` nothing is offered
  (3.8.6: then every other window counts as alive).
- A draft is removed as soon as its document is no longer modified (saved, reloaded, or undone to
  the saved text) or no longer open; 3.9.4 lists save and close with Yes or No, which this covers.

## Contract

### 14. The editor component and the options need more than `DocumentService`

- `DocumentService` (contracts/documents.ts) has no way to reach the `EditorState`s of 3.9.1 and no
  way to change `insertMode`, `tabType`, `tabSize`, `fontName` or `fontSize` of an open document,
  which E2 (Insert/Replace) and E4 (Editor Options) need.
- Does (local, in core/documents, no contract change): `documentManagerOf(ctx.documents)` returns
  the `DocumentManager`; `documentRegistryOf(ctx.documents)` its `DocumentRegistry`
  (`state(id)`, `apply(id, transaction)`, `dispatch(id, ...specs)`, `subscribe(listener)` with the
  events `created`, `updated` (with the transaction), `replaced` (reload), `removed`,
  `setExtensions(source)` for the extensions of new and replaced states). `manager.update(id, patch)`
  changes the five settings. Both throw for a stub service, so tests of E2 and E4 construct a
  `DocumentManager` themselves (see `core/documents/service.test.ts`).
- For W1: add to `DocumentService` `update(id: string, patch: Partial<Pick<DocumentState,
  'insertMode' | 'tabType' | 'tabSize' | 'fontName' | 'fontSize'>>): void`, and say in 3.9.1 that the
  editor component reaches the registry through `documentRegistryOf(ctx.documents)` from
  `core/documents`.

## Gate I1

### 15. Exit asks every close prompt before anything closes (editor-ui §1.3, §6.6)

- Says: §1.3, "Closing an MDI frame first asks every MDI child `CloseQuery` ... Answering Cancel in
  any prompt aborts the exit."
- Was: `closeAll` closed each document as soon as its prompt was answered, so No for one document
  and then Cancel for another lost the first one's edits (E1's review).
- Does now: `closeAll` asks every modified document's prompt in tab order first (Yes saves at once,
  as the original saves inside `FormCloseQuery`); only when every prompt agreed are the documents
  discarded. Cancel, a cancelled Save As or a failed save stops the questions and leaves every
  document open. Tested in `service.test.ts` and, with the real dialogs, in `check-documents.mjs`.
- Not settled: the order of the prompts. The port asks in tab order (order of opening). VCL's
  `MDIChildren[]` follows `Screen.Forms`, which, as far as the VCL sources are remembered, puts the
  most recently active form first; that could not be checked here (no VCL source in `reference/`,
  and the official binary may not be run with a window on this machine). Only the order of the
  questions can differ, not their result.

### 16. `DocumentService.update` and `selection` (entry 14; H1's request)

- At gate I1 the contracts engineer added the optional members `update?(id, patch: DocumentPatch)`
  and `selection?(id): DocumentSelection | null` to `DocumentService` (contracts/documents.ts).
  `DocumentManager` has both: `update` as before (its `DocumentPatch` is now the contract's type,
  re-exported from `core/documents`), and `selection` from the main selection of the document's
  EditorState in the registry (`selected` = the selected text, `caret` = the head, in characters of
  `text(id)`). `check-documents.mjs` shows that it follows the real editor's caret and selection.
  `documentManagerOf` and `documentRegistryOf` remain for the registry itself (3.9.1).

### 17. The unload guard is asked under the name `documents` (1.3.3; W1 errata 11)

- Says: 3.13 declares `Platform.confirmBeforeUnload(needed: boolean)`, one flag for the page.
- At gate I1 the contract became `confirmBeforeUnload(needed, who?)`, one flag per party, so that
  the simulator's guard (party `simulator`, `features/run/session.ts`) and the documents' guard
  cannot switch each other off (contracts engineer and shell engineer, gate I1 round 1).
- Does now: `features/documents/index.ts` always passes `'documents'`, and gives its question back
  (`false`) when the window is disposed while a document is still modified. Tested in
  `documents.test.ts` ("unload guard"); `check-documents.mjs` still sees exactly one question.

## Gate I2

### 18. A failed Save whose reason is a whole message is shown on its own (FS2 review)

- Was: every failed write showed `Cannot create file "<path>". <reason>` (the VCL's EFCreateError,
  editor-ui §6.4). For a linked file (FS2) the path is the store's internal `/linked/<id>/prog.X68`,
  and FS2's reasons already name the file in a sentence for the user ("... has been changed by
  another program since this window last read it, so it was not saved.").
- Does: `writeError(path, reason, code?)` in `core/documents/messages.ts` shows the reason alone when
  the FsError code is `io` and the reason reads as a sentence of its own (capital or quote first,
  sentence end last, at least one space); every other failure keeps the original's prefix. The third
  parameter is optional, so other callers are unchanged. Tested in `service.test.ts`.
