## 1. "At 60 Hz" and "the 120 Hz frame source" in a browser (3.11.1, 6.9 item 9)

- Says: 3.11.1, `FrameScheduler(frameSource?)`: "frameSource replaces requestAnimationFrame in
  tests (for example a 120 Hz source)"; the task text of P1: both frame sources are simulated.
- Problem: the application does not use `core/run/clock.ts`'s `FrameScheduler`; it uses W3's
  `createFrameScheduler(source)` (`app/src/state/browser.ts`; errata SH8.md entry 16), and
  `bootstrap` gives no way to pass a source into the running page.
- Does: `check-perf.mjs` installs an init script that replaces the page's `requestAnimationFrame`
  with a timer that calls back on a grid of 1000/60 or 1000/120 ms and skips the slots the page was
  too busy for. The application's scheduler runs on it unchanged. The display's own frames
  (headless Chromium: 60 Hz) are measured too: 6.9's "at 60 Hz" on ubuntu-latest is literally the
  display, so the thresholds are judged for both the display's frames and the simulated 60 Hz
  source, and for the 120 Hz source where 6.9 names it.

## 2. Where the thresholds of 6.9 item 9 are judged

- Says: 6.9 item 9, "measured by `tests/perf/` in Chromium on `ubuntu-latest`".
- Does: the check judges the wall-clock thresholds in Chromium on Linux only (`--judge strict`
  judges them everywhere). On Windows, macOS and in WebKit it measures and prints the same figures
  with "would pass" or "would MISS", because the macOS runners deliver frames 100 ms and more
  apart and fire timers late (errata SH8.md entry 30), and a figure of the machine must not turn a
  CI job red on a system for which 6.9 sets no threshold. Everything the program observes (its own
  clock, its instruction count, its pixels, the 4096 x 4096 surface) is judged everywhere.

## 3. TaskDuration with the 120 Hz frame source (6.9 item 9)

- Says: 6.9 sets the TaskDuration threshold "at the default speed" without naming a frame rate;
  P1's acceptance asks for "the measurements of 6.9 item 9, at 60 Hz and with the 120 Hz frame
  source".
- Does: measured at both; judged at 60 Hz (display and simulated). At 120 Hz the per-frame work
  of the controller, the store and the Output panel is done twice as often, and the figure exceeds
  4.5 s on this PC (`docs/porting/speed.md`). It is printed for information. Open point for SH8 and
  SH4 (owners of the per-frame work), and for the architect: either 6.9 states that the threshold
  is for 60 Hz, or the per-frame work is reduced.

## 4. "The largest corpus file" (6.9 item 9)

- Says: "assembling the largest corpus file takes less than one second under Node".
- Found: the largest file, `tests/corpus/github/pacman-mc68000/GAME/GFX.X68` (2.4 MB), is a data
  file that `MAIN.X68` includes; the official editor was never run on it (manifest: "not tried",
  official-oracle §3.2.1), and the larger `site` files are not in the repository (not in CI).
- Does: the check assembles both `GFX.X68` on its own and `MAIN.X68` with its includes, and judges
  both. The figure is the `assemble()` call with the engine module compiled; a cold start in a new
  Node process (import, compile, assemble) is printed beside it.

## 5. Maximum speed: 200 million instructions in 10 s (6.9 item 9, 4.1, 4.5.6)

- Says: 4.5.6, "The WebAssembly core alone reaches tens of millions"; 4.1, "at `Maximum` the engine
  gets about half of each frame"; 6.9, "at `Maximum`, `engine.stepCount` advances by at least 200
  million in 10 s", that is 20 million per second on average, 40 million per second while the
  engine runs.
- Found: see `docs/porting/speed.md` - the engine alone executes far fewer than 40 million
  instructions per second on this PC, so the threshold cannot be met with half of each frame.
- Proposal (numbers in speed.md): the architect decides whether the threshold or the share at
  `Maximum` changes. Owner of `SLICE_FRAME_SHARE`, `SLICE_BUDGET_MS`, `SUBSLICE`: SH8
  (`app/src/core/run/governor.ts`). P1 changes nothing.

## 6. `DEFAULT_IPS` exists twice (4.2, 4.5.6)

- `DEFAULT_IPS` (SH8, `app/src/core/run/governor.ts`) and `DEFAULT_INSTRUCTIONS_PER_SECOND` (W1,
  `app/src/core/settings/defaults.ts`, the value stored in `SimSettings.speed`) are both 1,000,000.
  A change of the default after O-1 must change both, or `instructionsPerSecond` in a fresh
  settings document and the rate of `EASy68K-like` disagree.

## 7. O-1 and the Wine measurement

- Says: O-1, recommended default (accepted): the official `SIM68K.exe` is run on real Windows
  hardware once, "by the owner, in Windows Sandbox or a disposable virtual machine, with
  `tests/perf/calibrate.X68`. Until then `DEFAULT_IPS = 1,000,000`."
- Does: `calibrate.X68` exists and is written so that the owner needs nothing else; the steps are
  in `docs/porting/speed.md` section 5. P1 also ran it in the official program under Wine
  (`tests/oracle/wine`, one CPU per container). That figure is **not** the speed of the original on
  a Windows PC (Wine's message queue, one shared CPU, Xvfb) and does not replace the owner's
  measurement; `DEFAULT_IPS` stays 1,000,000 until the owner has measured.

## 8. An additional program: `surface.X68`

- The outputs name `calibrate.X68`, `spin.X68` and `draw.X68`; the 4096 x 4096 check needs a
  fixed program too. `tests/perf/surface.X68` (resize, clear, flood fill, read back) is P1's.

## 9. The time budget per frame does not bound one `engine.run(n)` call (4.2)

- Says: 4.2, "budget = min(SLICE_BUDGET_MS, SLICE_FRAME_SHARE * frameInterval)"; the loop checks
  `clock.now() - start < budget` before each `engine.run(n)`, `n = min(subslice(ips), floor(allowance))`;
  4.1, "A slice is bounded (half a frame, at most 8 ms); each instruction and each host call is
  bounded".
- Found: a sub-slice of 2000 instructions of a drawing program (one pass of `draw.X68` is about 70
  instructions with a clear and a repaint of 640 x 480) takes tens of milliseconds, so a single call
  overruns the frame's budget: on the loaded PC the frames while such a program ran had a 95th
  percentile of 24 to 54 ms, and at a quieter moment 17 ms at 120 Hz, where one call (p95 about 6 ms)
  is longer than the whole budget of 4.2 ms (`docs/porting/speed.md` 4.1). Each host call is
  bounded, but 2000 of them are not.
- Proposal to SH8: bound the next sub-slice by the remaining budget and the measured time per
  instruction (speed.md 4.1). `check-perf.mjs --only frames --bounded-subslice 1` shows the effect
  in the real application without changing it (an experiment: it splits each call of the controller
  into calls of 16 instructions and ends it after 1 ms; its figures are never judged).

## 10. WebKit on Windows: timers of about 15 ms

- Found: in Playwright's WebKit for Windows a timer chain asked for 8.3 ms intervals gives a median of
  15 ms, so the simulated 120 Hz source cannot be simulated there, and the rate at the default speed
  falls a few percent short whenever frames are more than 50 ms apart. Figures from WebKit on Windows
  are for information only (entry 2); macOS and Linux CI runners show WebKit's real behaviour.

## 11. `calibrate.X68` writes `result.bin`

- So that the Wine oracle's `report` recipe (`tests/oracle/wine/sim/run-report.sh`), which waits
  for `result.bin` ending in `END-OF-DUMP`, can collect its figures unchanged, the program also
  writes its three lines there. On the owner's PC it leaves that small file beside the program.
