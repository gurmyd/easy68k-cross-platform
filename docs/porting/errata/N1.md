# Errata of N1 (dock layout)

Where `docs/ARCHITECTURE-PLUS.md` is silent, ambiguous, or cannot be met as written with
flexlayout-react 0.11.1, what the code does and why. None of these entries changes what a 68000
program can observe, a file the application writes, panel visibility, or an original menu, command
or key (P1.1).

## 1. `tabSetEnableClose: true`, not `false` (P2.2)

P2.2 lists `tabSetEnableClose: false` and `tabSetEnableDeleteWhenEmpty: true`. FlexLayout 0.11.1
deletes an empty group only when the group "can be closed" (`RowNode.tidy`:
`child.isEnableDeleteWhenEmpty() && child.isEnableClose()`), so with `false` a group whose last panel
is moved away or closed stays on screen as an empty box, against P3.1.8 ("A group whose last panel is
closed disappears"). The dock sets `tabSetEnableClose: true`. What P2.2 wanted from `false` still
holds: no group shows a close button (`tabSetEnableCloseButton: false`), and `onAction` refuses
`DELETE_TABSET` of a group that holds a panel (`ui/dock/rules.ts`). `model.test.ts` has the row.

## 2. Model options P2.2 does not list (`ui/dock/model.ts` `globalAttributes`)

Added, each to keep today's look or to keep a feature P2.2 switches off from coming back through
another option: `tabEnableScrollbars: false` (each panel scrolls inside itself, as today's regions;
FlexLayout would put an extra scrolling box around it), `tabCloseType: 2` (Always: a tab's x closes
it also when the tab is not selected, as the kit's tool tabs do today), `tabEnablePin: false`,
`tabEnablePopoutIcon: false`, `tabEnableFloatIcon: false`, `tabSetEnableSingleTabStretch: false`.

## 3. `tabDragSpeed={0}` has no effect in 0.11.1 (P2.2, P3.1.8)

`LayoutController.getTabDragSpeed()` is `this._props.tabDragSpeed ? ... : .3`, so 0 means the default
of 0.3 s. Under `prefers-reduced-motion: reduce` the dock passes `0.0001` and `dock.css` sets
`transition: none !important` on FlexLayout's drop outlines (an `!important` rule wins over the inline
`transition` FlexLayout writes). `check-dock.mjs` (boxes) checks the computed transition is `0s`.

## 4. The tab strip is 29 px tall: 28 px of tabs and a 1 px border (P3.1.4)

P3.1.4 says "30 px of tabs and a 1 px border, as the kit's tool strip today". Today's tool strip
measures 28 px of tabs plus a 1 px border (the kit's `.e68-tabs--tool .e68-tabs__tab` is 28 px
tall); `SimWorkspace.tsx` subtracted 31 px (`TAB_STRIP_HEIGHT`) from the tool area, so today's tool
group was `split - 2 px` tall. The dock's strips are 29 px, and the default tool group keeps today's
arithmetic (`split - 31 + 29`, `ui/dock/sizes.ts` `LEGACY_TOOL_STRIP`), so that the Output panel is
where it was to the pixel.

## 5. The line below the Registers panel, and above the tool group while Output is collapsed

FlexLayout puts a splitter between any two groups of a column. Today there is none below the
Registers panel (a 1 px border of the region) and none above the tool tabs while the Output panel is
collapsed. The dock makes those splitters inert (no `separator` role, `tabindex=-1`,
`aria-hidden`, no pointer, drawn in `--c-border` as today's line) while the Registers group is sized
by its content and, in the default arrangement, while Output is collapsed. Box differences that
remain, all within the 1 px of the acceptance: the Registers region is 1 px shorter (its border is
now the splitter; everything below it is where it was), and with Output collapsed the tool group
starts 1 px lower.

## 6. The Output panel's strip in the narrow default (P3.1.4)

P3.1.4's rule shows a strip on a locked group only when it holds two panels, a tool panel or a
viewer. Today's narrow layout always shows the strip with the Output tab, also without tool panels.
To keep today's look, the dock shows the strip of the group that holds Output in the simulator's
narrow default arrangement (`DockEngine.stripFor`). Its tab list keeps today's accessible name
`Tool panels` there also with Output alone (`groupLabel(panels, narrowOutputStrip)` in
`ui/dock/model.ts`; the gate found the name missing; `model.test.ts` and `check-dock.mjs` (boxes,
"below 1100 px without tool panels") check it).

## 7. Unlocked, the editor's message list keeps its height below its strip (P5 N1 acceptance)

The acceptance says that unlocked each group's outer box is today's box within 1 px, except the
Registers group and the groups below it. The editor's Messages group is the other content-sized group
(P3.1.5): today it is 5, 87 or 7 px, which cannot hold a 29 px strip. The dock treats it like the
Registers group: unlocked, the group is the rule's height plus its strip, and the Editor group above
it has the rest. `check-dock.mjs` checks exactly that.

## 8. The splitters' keys and values (P2.2, P3.1.1)

FlexLayout's splitters move 10 px with the arrow keys and report `aria-valuenow` as a percentage
(`aria-valuetext` `<n>%`), where the kit's Splitter reported pixels. The dock adds the kit's other
keys to the default arrangement's splitters (today's four): Shift+arrows 50 px, Home and End the
limits, Enter and a double-click the default. Splitters of a changed arrangement have FlexLayout's
arrows only.

## 9. Splitter names "also after a move" (P5 N1 acceptance)

A move makes the arrangement changed, and P2.2 names the splitters of a changed arrangement
`Resize <panel> and <panel>`. The check therefore asserts today's names in the default arrangement,
after a tab switch, a splitter drag and a font change; after a move, the `Resize A and B` names; and
today's names again after `Reset Layout`. The names survive FlexLayout's renders (no fallback to the
plain `Resize` was needed).

## 10. Reading order: FlexLayout's internal order of the tab layer (P3.1.8)

FlexLayout 0.11.1 renders every tab's content in one flat layer, in the order the tabs were first
rendered, so after a move the DOM order of the panels no longer follows their places. The dock puts
that layer back into reading order after each change of the arrangement by setting the order
FlexLayout keeps (`LayoutController._orderedTabIds`, reached through `Model.getLayouts()` and
`ModelLayout.getController()`) and asking it to redraw: React then moves the elements, so no DOM node
is moved outside React. A focused element that the move blurred gets the focus back. These are
internals of the pinned 0.11.1 (R1); if they are missing the dock leaves the order as it is.
`check-dock.mjs` compares the DOM order with the tree in three arrangements per mode.

## 11. Chained models (no remount on rebuilds)

The dock rebuilds its model with `Model.fromJson(json, previous)` (Reset Layout, a lock change, the
narrow switch, a hidden or shown panel), which adopts the tab elements, so no panel is remounted.
FlexLayout's `Layout` keeps its components only when the new model was adopted from the one it
rendered last; when two models replace each other before React renders, the dock sets the new
model's `adoptedFromModel` (an internal field) to the rendered one. The mount counters of
`check-dock.mjs` (program) show every panel mounted once.

## 12. Roles of the groups' contents (P3.1.8)

FlexLayout's `.flexlayout__tab` is always `role=tabpanel` with `aria-labelledby` its tab button. The
dock removes both from a group shown without a strip (no tab button exists there), so the panel's
`PanelRegion` is a plain `region` as today, and puts them back when the group shows its strip. A
viewer's own element (`data-e68-panel="viewer:<n>"`) is its tab panel; the outer element then has no
role. The tool group's tab list keeps today's name `Tool panels` (set on the element; P2.2's
`name` attribute would need an action after each move).

## 13. The dialog's access keys: `P&lace:` (P3.1.4)

P3.1.4 draws the dialog with `&Panel:` and `&Place:`, two access keys on the letter P. The second is
`P&lace:` (`features/layout/texts.ts`). Tab goes from the chosen place to that place's own lists
(document order); a list keeps Enter for itself, so OK is reached with Tab or a click.

What `&Place:` collides with, exactly: the `&Panel:` list of the same dialog. Both would be Alt+P
(on the macOS key map Ctrl+Option+P, main §2.9). The kit's `Dialog` (`ui/components/Dialog.tsx`, the
access-key handler) takes the first enabled element marked `data-e68-mnemonic="p"` and does not cycle
between duplicates, so with the document's text Alt+P would always land on the Panel list and the
place's radio buttons would have no access key at all. `L` is used by nothing else in the dialog (its
other captions, `OK` and `Cancel`, carry none). The gate (round of the four engineers, 2026-11-22)
kept `P&lace:`: the text differs from the document by the position of the `&` only, and the
difference is recorded here, not silent. If the document's `&Place:` is wanted instead, the change is
the one string in `features/layout/texts.ts` and the `'l'` of `data-e68-mnemonic` in
`MoveDialog.tsx`, and the place then has no working access key.

## 14. Drop places and the Output panel's 160 x 120 px (P2.2 `setOnAllowDrop`)

FlexLayout's drop outline for a drop on a group's strip is a 3 px marker, and for a drop into the
middle of a group the group's box. The dock judges a drop into a group (middle or strip) by the
group's box and a drop beside a group or at an edge by FlexLayout's outline (the place the panel
would get). A drop before the first tab of a strip needs the tab not to start at the strip's very
edge (FlexLayout's `restrictAtStripStart`), so the strip has 1 px before its first tab.

## 15. Focus after closing a panel with the Delete key (P3.1.8)

FlexLayout's Delete on a tab moves the focus to the next tab button before it asks to delete the tab.
The dock then moves the focus into the panel of the group's selected tab (or the Editor or Registers
panel when the group is gone), as P3.1.8 says.

## 16. The Output panel's collapse button inside a tab strip

`features/output/output.css` hides the collapse button inside a `tabpanel` ("As a tab of the narrow
layout the panel cannot be collapsed"). With the dock, the Output panel is a tab panel wherever its
group shows a strip: unlocked, or moved into a group with other panels. There, as in today's narrow
layout, it cannot be collapsed; `hidePanel('output')` still collapses it and the dock draws the
expand bar in its tab (P3.1.5). Locked in the default wide arrangement nothing changes.

## 17. Transient tabs and the mode (P4.4)

P4.4 lists "a mode change" among the ways a transient tab goes away. The Editor dock closes every
viewer (running its `onClose`) when the mode leaves Editor mode. `openTransient` before the Editor
dock attaches is queued (both docks attach at start, so the queue matters only before the first
render, `?open=` and start-up arguments).

## 18. `EditorWorkspace.tsx` and `SimWorkspace.tsx` are deleted (P5 N1 Changes)

Their rules moved into `ui/dock`: the message-height rule of `EditorCenter` (`ui/dock/sizes.ts`
`editorMessagesHeight`, `EDITOR_MIN_HEIGHT`), the content-sized Registers region
(`DockWorkspace.tsx` `RegistersContent`), the Output expand bar (`OutputContent`), the narrow switch
(`DockWorkspace.tsx`, the same media query at `NARROW_WIDTH`). Nothing imported them except
`Shell.tsx`. `SplitPane.tsx` stays (the Help drawer's `useSplit` and `useElementSize`).

## 19. Splitter colour (P3.1.8)

P3.1.8 maps the splitters to `--c-border-strong` (controls, 3:1). Today's splitter line is
`--c-border`. The dock follows P3.1.8 for every splitter that is a control; the inert lines of entry 5
keep `--c-border`. The boxes are unchanged.

## 20. The View menu's panel commands have no shortcut

The acceptance item "every View menu command and its shortcut shows and focuses its panel" is checked
for the commands; `commands/tables/keys.ts` binds no chord to `sim.view.*` (F2 and Ctrl+Tab cycle the
panels, checked separately). `check-dock.mjs` prints a note.

## 21. `state/dock.ts` additions (P4.4: "N1 may add members")

`DockController.stats()` (action and mount counters for the browser check), and the exports
`attachDock`, `DockLive`, `DockAttachment`, `dockModeOf`, `lockedIn`, `withLocked`, `TransientSpec`,
`DockMoveTarget`, `DockMode`, `DockStats`. The stub's members keep their signatures. `locked()` and
`setLocked()` work without a mounted dock (they read and write `layout.dock.locked`).

## 22. A refused drop shows no preview

FlexLayout 0.11.1 keeps the last drop preview (and does not cancel the `dragover`) where the pointer
finds no place, for example over a group too small for the Output panel (P2.2 `setOnAllowDrop`). The
browser then drops nothing, but the preview of the place passed on the way stays on screen. After
FlexLayout's own `dragover` handler, the dock hides the preview of an event FlexLayout did not cancel;
FlexLayout shows it again at the next place it accepts. `check-dock.mjs` (drags) checks that no
preview is visible over the Messages group while the Output panel is dragged there, and that nothing
moves.

## 23. Esc during a drag, in the browser check

`check-dock.mjs` checks that Esc cancels a drag (nothing moves, the preview is gone). It does not
check a drag right after the Escape: Playwright's emulated drag session did not deliver the next
drag's `dragenter` after an emulated Escape, in Chromium and WebKit alike on this PC (a probe with
plain events showed `dragstart, dragleave, dragend` for the cancelled drag and a `drop` that
FlexLayout did not act on for the next one). In a real browser the next drag is a new session.

## 24. A focus request is carried out when the panel appears, not a frame later (P3.1.5)

`state/panels.ts` asks the shell to focus a panel (`focusRequest`); `Shell.tsx` (`usePanelFocus`)
does it once the panel is rendered visible. The dock renders a panel that was just put in with a
commit of its own after the request's effect, so the first try finds nothing, and the retry waited
for the next animation frame. On GitHub's macOS runners, which at times deliver frames 130 ms
apart, the panel was then on screen for a frame without the focus: `check-memory-stack.mjs` read
`null` (View > Memory) and `TEXTAREA` (View > Stack) on macOS in run 45020779731, while the same
check passed on Ubuntu and Windows and on `main` (no dock) everywhere. The request is now tried again
at once after each change of the DOM (a mutation observer, which runs before any later task can see
the panel), at each frame and at a 50 ms timer, until it succeeds or both 12 frames and one second
have passed (three seconds at most without frames). The reading-order redraw (entry 10) gives the
focus back to the element that held it last before the redraw, so a focus request that lands in
between is not undone. `check-dock.mjs` (pass `frames`) checks, with today's frames and with frames
130 ms late, that View > Memory, Stack and Log have focused their panel by the time its content is
in the page; with the earlier code 4 of its 8 checks fail in Chromium.

## 25. With Lock Layout on, the splitters and strips have today's places in the Tab and reading order (P1.2, P3.1.8)

The gate's review (second round of the stage's gate, 2026-11-22) found that with Lock Layout on, the
default, Tab did not go through the window as today: FlexLayout 0.11.1 renders the splitters and the
groups' tab strips in its layer of rows and groups and every panel's content in a second, flat layer
after it, so every splitter, and in the simulator's narrow default the Output tab, came before all
the panels' contents (Editor mode: `Resize the Files panel` and `Resize the Messages panel` before
`New Folder...`). The reading order of a screen reader was the same. Entry 10 orders only the content
layer among itself, and the box comparison could not see it.

Neither layer can be reordered without moving nodes React owns. With Lock Layout on, the dock
therefore gives each splitter that is a control, and each strip that is shown, a slot in the content
layer (`ui/dock/order.ts`, `DockSlot` in `DockWorkspace.tsx`), at today's place: a strip just before
the content of its group's selected panel, a splitter just after the content of the selected panel
of the last group before it. A slot is an empty element (1 px, clipped) with `tabindex="0"` and
`aria-owns` naming its splitter or strip, so the accessibility tree reads that element at the slot's
place. The splitter and the strip's tabs and toolbar buttons get `tabindex="-1"`; a slot that
receives the focus by Tab passes it to the element (Shift+Tab: the strip's last element); Tab and
Shift+Tab on the element put the focus on its slot and let the browser go on from there. The focus
itself is always on FlexLayout's element, which keeps its keys (the arrows, Shift+arrows, Home, End,
Enter, Delete, Shift+F10) and draws its focus ring where it is. With a strip shown while locked, the
`tabpanel` role goes on the panel's content wrapper (`data-e68-dock-content`) instead of FlexLayout's
`.flexlayout__tab`, so that the strip is read before its tab panel, not inside it (FlexLayout's tabs
then name that wrapper in `aria-controls`, `e68-dock-tabpanel-<tab id>`, and FlexLayout's own
`.flexlayout__tab` again when the strip goes or the layout is unlocked; the second round's first
draft left `aria-controls` on `.flexlayout__tab`, which then had no role, and the audit's structure
part, `the tool tabs are a tablist whose selected tab controls a tab panel`, failed on it; the
`taborder` pass of `check-dock.mjs` now checks every selected tab's `aria-controls` and label). A
viewer's tab, which named `.flexlayout__tab` (no role) since N1, now names the viewer's own element,
its tab panel, which has the same id form (`editor` pass of `check-dock.mjs`).

Unlocked, nothing of this applies: the slots go away and FlexLayout's elements are tab stops again
(the design's own order, P3.1.8).

`check-dock.mjs` (pass `taborder`) records main's Tab order (b247e17, the same in Chromium and
WebKit) in Editor, Simulator and EASyBIN mode, at 1400 and at 1000 px, with and without the Memory
panel, and compares a Tab walk from the start of the page and a Shift+Tab walk from its end with it;
on a browser that does not stop at plain buttons (Safari on a Mac) the list is filtered as Safari
would. The one addition in it is the stage's storage line of the Files panel (N5). In Chromium the
pass also compares the accessibility tree (CDP) with main's; WebKit's tree is not reachable from
Playwright, so there only the Tab order is checked. With the slots switched off, the pass fails in
Chromium on the Tab, Shift+Tab and reading-order checks of the dock's modes (it was run so: 22 of
its 48 checks failed, among them every Tab, Shift+Tab and reading-order check of Editor and
Simulator mode). A walk with Tab and with Shift+Tab over production builds of main (b247e17) and of
plus, side by side, in Chromium and WebKit, at 1400 and 1000 px, in the three modes and with the
Memory panel, gave the same sequence in 32 of 32 walks (the storage line of the Files panel set
aside). The
P3.1.8 allowance stays: inside a dock tab panel the `PanelRegion`
keeps its own region and name (main's narrow simulator has the tab panel `Output` without it).

## 26. Shift+Tab after the focused element went away: the cause is the Files panel's scroll (P1.2)

The second round's review (`layout-viewer-foundation`, its major defect) found that with Lock
Layout on, Shift+Tab from the end of the Editor window, after the focused element had been removed,
went straight to the Files tree in 7 of 10 runs in Chromium (main: 0 of 10), and that the taborder
pass of `check-dock.mjs` failed on it now and then. Its three suspects were the slots' hand-off,
the storage line's refresh and the dock's moving of nodes. None of them is the cause.

Established in this round (Playwright's Chromium and WebKit, production builds of this working copy
and of main b247e17; the probes are in `c:\easy64k\build\gate3-layout-plus`):

1. The DOM order of the tab stops, the slots, the mutations and the focus events were the same in the
   runs that went wrong and in those that did not (`probe1.mjs`); nothing was focused in between.
   The tab stop reached, the tree, and the one reached by Tab instead, the storage line, place the
   page's sequential focus navigation starting point on the Files panel's first row (`My Programs`):
   a button put just before that row is reached, one put inside the row or after the tree is not.
2. It happens only when the window had lost the focus first (the forward walk had gone past the end
   of the page) and then got it back (the walk's mark is focused): `window`'s `focus` event.
3. Replacing `Element.prototype.scrollIntoView` with a function that does nothing: 0 of 6 differ
   (with it: 5 of 6). The one caller in the application's code is the Files panel's effect "Keep the
   focused row in view" (`features/files/FilesPanel.tsx`, N5's), which runs at every render (its
   dependency, `model.selectedRow()`, is a new object each time); the stage's Files panel renders
   when the window gets the focus back (`windowFocused`, P3.3.10), main's does not. It ran 3 ms
   after the mark was removed, while nothing was focused.
4. In Chromium, `scrollIntoView` moves the sequential focus navigation starting point to the element
   scrolled to; WebKit's does not (`mini6.mjs`, no application: after a removed element at the end
   and `row.scrollIntoView()`, Shift+Tab goes to the tree instead of the last button, Tab to the
   button after the tree instead of the first).

So: the focused element goes away, the window comes back, the Files panel renders, the row is
scrolled into view, and Chromium's next Tab or Shift+Tab goes on from the Files tree. A race between
that render and the person's next key made it 7 in 10. With the focus gone and a `focus` event
given to `window` before Shift+Tab, it fails 10 times in 10 (`probe2.mjs plus chromium grid 10`
with `AFTER`); main, and WebKit, 0 in 10. The dock is not involved; main has the same effect but
nothing that renders the panel at that moment.

The repair is in N5's file: scroll only when the focused row changes, and by the tree's own
`scrollTop`, not `scrollIntoView` (`docs/requests/N1-files-row-in-view.md`, with the code). It
was tried on a copy of a production build with the effect replaced so: 20 of 20 walks as on main
(unpatched 7 of 10 differ), and the `starts` pass below 150 of 150 in both browsers.

`check-dock.mjs` now catches it every time:
- the taborder pass repeats each Shift+Tab walk from the end of the page ten times (`BACK_WALKS`)
  in every mode and width; each walk after the first starts where the one before ended (the focus
  gone from the page), as a person's next Shift+Tab would;
- a new pass, `starts`, covers the other starting points a person can reach, in both directions:
  the focused element gone at the end or the start of the page and then the window away and back
  (ten walks from the end); the focused element gone beside each stop inside a panel; a click on
  the status bar and on the menu row beside the menus; a menu and Help > About closed with Escape; a
  mode switch and back; in Editor mode (1400 and 1000 px), Simulator mode (wide and narrow) and
  EASyBIN. It compares with what main does there, recorded from main's own production build with
  `--serve <dist> --record <file>` into `app/src/ui/dock/check-dock.main.json` (two recordings of
  main gave the same file; main's figures are not all what its Tab list predicts, so the pass does
  not predict them). The one allowance: WebKit goes on from the node before an element that went
  away; before the Files tree that is main's strip, so main's Shift+Tab skips `New Folder...`, and
  here it is the selection count line of P3.2.1 (N5), so WebKit stops at `New Folder...` as Chromium
  does (that one walk, that one stop; `mini7.mjs` shows it without the application). The storage
  line (P3.2.6) is set aside in these walks, as in the taborder pass.
Until N5's change is in, the Chromium checks `Shift+Tab goes through the window as on main, 10
walks from the end` (Editor, both widths) and `the focused element gone and the window back` (Editor,
both widths) of these passes fail; every other check of them passes in both browsers (the full
check, 22 November 2026: 636 of 642, those six failing). With N5's change applied in memory by a
Vite plugin of a scratch copy of the check (`c:\easy64k\build\gate3-layout-plus\check-dock-n5fix.mjs`;
no file of N5 changed), the whole of `check-dock.mjs` passed 642 of 642 in both browsers five times
in a row, the fifth while the accessibility audit's structure part and `check-frame-policy.mjs` ran
at the same time.

## 27. FlexLayout's measuring element is hidden from assistive technology (P1.2)

FlexLayout 0.11.1 renders `.flexlayout__layout_metrics` with a child that holds the text
`FindBorderBarSize` (it measures its strips and splitters), moved off the screen by CSS only; a
screen reader read the word in every mode, and Chromium's and WebKit's accessibility trees had it
(the second round's review). The library has no option for it. The dock's decorate pass now sets
`aria-hidden="true"` on that element (`DockEngine.decorate`, `engine.ts`). The taborder pass of
`check-dock.mjs` checks in every mode and width that no text of the dock reaches the accessibility
tree but a panel's content, a tab's caption, a menu's or the dock's live status (a walk of the
dock's text nodes), and that the aria snapshot (both browsers) and Chromium's full accessibility
tree hold no `FindBorderBarSize`; on the build before the change the walk found the word twice (the
Editor's and the Simulator's dock) and the snapshot held it, in both browsers.

## 28. A document opened or chosen comes in front of a viewer (P1.2; O-1 of the gate's fourth round)

The defect: a viewer is a tab of the Editor's group (P3.4.2, `park.ts` `insertPanel`, `openTransient`).
A document opened or chosen while a viewer's tab was in front became the active document (its
document tab selected, the status bar naming it) but stayed hidden behind the viewer; nothing
brought the Editor's tab forward. The end-to-end test's long scenario failed its step 3 in every
run (both browsers, online and offline); the verifier's `repro-step3.mjs` showed it outside the
test (`{"dockTabs":["Editor","pic.png*"],"editorVisible":false}` in Chromium and WebKit, on the
build before this change).

The rule, by P1.2 ("the editor behaves as today": today the editor always shows the active
document): whenever a document is made the one a person works on, a viewer's tab in front of the
Editor's in its group gives way to the Editor's. The document service tells it (`shown`, N6's hook in
`core/documents/service.ts`, errata N6 15) for every `activate()` (also of the document that is
active already), and so for New, Open (the Files panel's double-click and Enter, `File > Open
File...`, a dropped file, a file handed over by the system, Help's examples, the start-up file),
Open as New Document, a draft brought back, the Window menu's document list, a document tab, the
assembler's include files, `Open the containing folder...`, the "already open" question answered No,
a close question that shows the document it asks about; and after a reload of the active document
(Reload File, Restore of Earlier Versions or of the Trash, a reload offered after another window
changed the file, a Move that replaced its file). Not told: a close that makes a neighbour active,
a reload of a document that is not the active one, a relocation. `features/documents/index.ts`
passes `shown` as `dockOf(ctx).documentShown()` (a new member of `DockController` and `DockLive`,
`state/dock.ts`, after entry 21), which the controller sends to the Editor dock in every mode; there
`DockEngine.documentShown` selects the Editor's tab when the selected tab of its group is a viewer,
and does nothing otherwise (no action is dispatched).

What it does not do, deliberately:
- A tool panel a person put into the Editor's group and in front of it stays in front (their own
  arrangement; bringing the Editor forward would hide the Files tree that holds the focus after a
  double-click). Only a viewer gives way.
- A viewer moved into a group of its own stays in front there.
- The keyboard focus stays where it was (the Files tree after a double-click or Enter, the element
  a menu gives it back to), as in main. Only when it was inside the viewer that is now hidden does it
  go to the editor, as for a panel that goes away (P3.1.8). It is put there once the editor shows the
  new active document: the editor takes it into its pane a render later (EditorArea's `syncPanes`),
