# Errata of T3 (simulator conformance and its Wine driver)

Where `docs/ARCHITECTURE.md` (6.1 L4, 6.2.2, 6.4, 6.8, the T3 entry of 9.4) or a spec could not be
followed as written, what the repository does instead, and why; then the findings about the
official program that the specs should take over. No entry changes a contract.

## 1. Wine has no Fixedsys: the oracle's text grid is 58 x 34, not 80 x 32

- Says (6.2.2, 6.4): self-reporting programs and headless runs are compared; trap15-a §3.2: the
  default font Fixedsys 9 has an 8 x 15 cell, grid 80 x 32.
- Found: the image (`wine32` 8.0, no bitmap fonts) has no font called `Fixedsys`; GDI under Wine
  substitutes a proportional face whose `TextWidth("W")` is 11 and `TextHeight("Xp")` 14. Measured
  with probe programs in the official program: task 22 reads row 0, column 58 as row 1, column 0
  (stride 58 = 640 / 11), task 11 to row 99 stops at row 33 (= 480 / 14 - 1), task 95 "W" moves the
  pen by 11. Courier New 10 (Liberation Mono): 12 x 15, grid 53 x 32. Installing Debian's
  `fonts-wine` (Wine's own `fixedsys.ttf`) into a derived image changed nothing (tried, not kept).
- Does: the harness runs the comparisons with Wine's cells (`WINE_CELLS` in
  `tests/conformance/sim/harness.ts`, a glyph provider with those cells and blank glyphs), so that
  the original's grid logic - wrap, scroll, stride aliasing, the last row, task 25 - is compared with
  the port's on the same grid. `runScenario({ metrics: 'windows' })` uses the application's glyph
  provider (Windows' 8 x 15, `harness.test.ts` checks 80 x 32). The cells themselves, and every text
  pixel, are layer L5 (T2, SH3), not L4. The programs read only colours of flat areas (cell
  backgrounds of spaces, insides of rectangles, ellipses and fills), never glyph or edge pixels.
- Proposed text (6.2.2, after "Simulator, self-reporting"): "Wine has no Fixedsys: under the oracle
  the default output font has an 11 x 14 cell. Programs whose results depend on the text grid are
  compared with the port running with the same cells; Windows' cells are verified by L5."

## 2. The harness runs ProgramFiles and LogService as doubles while SH6 and U4 write them

- Says (6.4): the harness "builds a `SimSession` from the real engine and the real host parts with
  `VirtualTime`, a memory file system and fake audio".
- Found: `core/sim-host/files/program-files.ts` (SH6) and `core/sim-host/log/log-service.ts` (U4)
  are stubs of the same wave (the task text forbids testing against another wave-two package's
  unfinished work). The dump of every self-reporting program goes through the file tasks, and the
  logs through the log part.
- Does: `runScenario` builds the session with `createHeadlessSession` (SH8) and every part at its
  final path except those two, which are `ConformanceFiles` and `ConformanceLog` of
  `tests/conformance/sim/doubles.ts` (a flat folder in memory with C-stream semantics and no
  buffering; both logs in memory). `EASY68K_CONFORMANCE_PARTS=final` (or `parts: 'final'`) uses the
  classes at the final paths; gate I2 should run the suite that way once SH6 and U4 are in. With the
  doubles, results of the file-task programs (`trap15-a/a27`-`a37`, `windows-confirm`) test the
  engine's side of the file tasks and the doubles, not SH6.
- Repair (verify round 1): in the first version the `final` mode could never return `result.bin` or
  a log (it read them from the doubles, which that mode does not build, and gave ProgramFiles a new
  empty view on every `viewFor` call). Now the program's folder is one `MemorySyncFiles` seeded with
  the folder's files and shared by every `viewFor` call (`createFolderView`); the outcome's files are
  read back from it, `result.bin`'s end marker is checked there, and the two logs are read from the
  vfs (`<program>_RunLog.txt`, `<program>_OutLog.txt`, sim-ui §13.1) after `log.flush()`. Bytes the
  real ProgramFiles still holds in an unclosed stream's buffer are not in the outcome, as they are not
  in the official program's file when the oracle kills it. `harness.test.ts` runs a report and a log
  program in both modes and compares them; on 2026-11-21 the whole comparison in `final` mode gave
  the same result as with the doubles (no difference beyond the five listed).
- Gate I2: SH6 and U4 are committed, so `final` is now the default, as 6.4 says;
  `EASY68K_CONFORMANCE_PARTS=doubles` (or `parts: 'doubles'`) selects the doubles, which stay to
  cross-check the real parts. The doubles' `fileKey` no longer drops a folder from a name: a name
  with a folder in it (`nofolder\x.bin`) names a folder that does not exist and fails, as in the
  original and the real ProgramFiles (review of T3, round 2; `trap15-a/a54-files-missing-folder`,
  `harness.test.ts` runs it in both modes).

## 3. The simulator driver is mounted, not copied into the image

- Says (T1's sim README): "a script that T3 adds or renames needs one more name on that `COPY`
  line" of the Dockerfile (owned by T1).
- Does: `regenerate.mjs` mounts `tests/oracle/wine/sim` read-only at `/mnt/sim-driver` and runs
  `sim_corpus.sh` / `sim_batch.py` from there; `sim_batch.py` imports `asm_batch.py` and `xwin.py`
  from the image. No rebuild for a driver change, and the image checks of T1's runs stay valid.
  `sim_run.py` is unchanged. `sim_proofs.sh` (obsolete: its programs moved into the suite) is
  deleted at gate I2, after T1's Dockerfile stopped copying it (docs/requests/T3-oracle-image.md).
- A `--file` run with `--out DIR` keeps its work folder in `DIR/.work-<run>`, so that a caller who
  must keep scratch output in a folder of its own can (review of T3, round 2;
  `fileWorkDirectory` in `regenerate.mjs`).

## 4. run-report.sh waits for an end marker, not for result.bin "to stop growing"

- Says (6.2.2): "wait for `result.bin` to stop growing, kill the process".
- Does: the program ends its file with the line `END-OF-DUMP` and closes it (task 56 flushes); the
  driver waits for that line (`sim_run.py`, official-oracle.md 5.1). "Stops growing" cannot be told
  apart from a program that is still computing, and the C library writes the file in 512-byte
  pieces (3.8.4), so the file can stop growing for a while before it is complete.
- `run-report.sh` and `run-log.sh` take an `.S68` as 6.2.2 says, and also an `.X68` (assembled by the
  official editor first). `run-log.sh <file> <type>` takes `1`, `2`, `3`, `N+out` or `out`.

## 5. Goldens: one folder per suite, execution logs gzipped, a manifest

- Says (6.2.2): "Outputs for redistributable inputs are committed under `tests/conformance/*/golden/`."
- Does: `tests/conformance/sim/golden/<suite>/<program>.result.bin`, `.OutLog.txt`, and
  `.log<N>[o].RunLog.txt.gz` (an execution log of type 2 is about 350 bytes per instruction);
  `golden/manifest.json` holds the hashes (masked header dates and listing date) and the status of
  every run, `golden/REPORT.md` the runs without a result. A golden is rewritten only when its
  masked content changed. The official `.S68` is not stored: its SHA-256 is, and the comparison
  checks that the port's assembler produces the same bytes for every program.

## 6. dumplib.X68 moved and extended; the result file is result.bin

- `tests/oracle/wine/sim/dumplib.X68` is now `tests/conformance/sim/dumplib.X68` (included as
  `..\dumplib.X68`, so that T4's twins, which assemble every `.X68` under `tests/` in its folder,
  find it). `DMP_OPEN` takes no name any more and always creates `result.bin` (6.2.2's name); new
  routines `DMP_VAL`, `DMP_CLRC`, `DMP_CYC`, `DMP_POS`, `DMP_ROW` (task 22). The proof programs of
  official-oracle.md 5.1/5.2 moved into the suite unchanged apart from that
  (`instructions/p1`-`p5`, `logs/l01`-`l05`).

## 7. Panel actions "at instruction counts"

- Says (6.4): "a scenario (keys to type at each `WaitInput`, panel actions at instruction counts,
  time to advance)".
- Does: `ScheduledAction` has `atInstruction` (checked after every frame of virtual time, so the
  action comes at the first frame boundary at or after that count), `atMs` (virtual time) and
  `whenIdle`. Exact instruction boundaries need Trace Into, which a scenario can script
  (`{ kind: 'traceInto' }`). The checklist tests use `atMs`.

## 8. Speed of the official runs, and the size of the log set

- official-oracle.md section 7 measured about 7 s per self-reporting run. With one CPU per container
  (the task's limit of six CPUs for six containers) and dumps of 50 to 200 lines, a run takes 10 to
  50 s plus about 15 s to assemble; the whole suite about an hour with six containers.
- 6.9 item 2 asks for "at least 20 execution logs totalling at least 100,000 instructions" for
  version 1.0.0 (the acceptance of T3 asks for 20 logs). The suite has 27 execution-log runs with
  47,664 instructions in all (`golden/REPORT.md`). The official Auto Trace ran at 8 to 12
  instructions per second in a one-CPU container (official-oracle.md 5.2 measured 61-72 without the
  CPU limit), so the 18,183-instruction log took half an hour; reaching 100,000 needs more programs in
  `logs/` and about two more container-hours, or fewer containers with more CPUs each.

## 9. Checklist items without a golden are tested headless against the specs

- Says (6.4): one test per item of sim-ui §19 and hardware §13.
- Does: items that need a person at the original (panel clicks, Trace Into, typed keys, Rewind) or a
  memory map have no golden from the Wine oracle; `tests/conformance/sim/checklist.test.ts` runs them
  in the harness with scripted panel actions and checks what the specs dictate. Hardware §13: items
  4, 7, 11, 12, 15, 20-23, 25, 26, 27 (both halves), 31, 32, 33; sim-ui §19: Q3 (a program reaching
  address 0 pauses with no message), Q10 (Rewind keeps memory and forgets an open file without
  closing it; with the real ProgramFiles), Q24 (the Rewind note reaches the output log only after the
  Log Output dialog was shown; scenario option `logDialogShown`). The other items are covered by
  goldens (`hardware/h01`-`h09`, `quirks/`, `logs/l14`, `l15`) or need the interface (L5, the e2e
  package). All of these pass on 2026-11-21; none disagrees with its spec.

## Findings about the official program

### F1 - T4's D1: tasks 0 and 1 with a negative D1.W print exactly 255 characters here

`trap15-a/a05-task0-negative-count` (output log and report): a 300-byte string printed with task 1,
D1.W = -1 after `NOP`; task 0 with D1.W = $8000 after `MULU`; with $FF00 after `RTS`; with -1 after
`MOVE.L (SP)+,D5`; and the 5-byte `HELLO` with -1 after `NOP`. The official program printed exactly
255 `A` in all four long cases and `HELLO` in the short one, in the output log and in the text array
(task 22). T4's measurement (docs/porting/errata/T4.md, D1) saw one extra byte `$C0` after `NOP` and
`MULU`; here, with other code before the TRAP (the dump routines), none. So the bytes after the
255th are residue of the host stack that depends on what the Borland code did before, as T4
concluded, and the port's 255 characters equal the original in every case measured by T3. The
recommendation of T4 stands (make P24's `buf[255] = '\0'` explicit, record the difference).

Gate I2: `trap15-a/a55-task0-negative-count-first` repeats T4's probe as a suite program (the TRAP
#15 calls come first, with no dump routine before them), with the output log as its golden. The
official program printed 255 `A` and the byte `$C0` after `NOP` and after `MULU`, and exactly 255
`A` after `MOVE.L (SP)+` and after `RTS`: T4's measurement, reproduced. The engine's P24 now ends
the string at character 255 explicitly, so the port prints 255 every time; the difference is listed
as accepted (owner: the engine) in `known-differences.json`.

### F2 - stdio-buffer under Wine: 512-byte buffer, large writes go through, reads are buffered

`tests/conformance/windows-confirm/stdio-buffer.X68`, run with `run-report.sh` in the oracle
(`windows-confirm/stdio-buffer.wine.result.bin`). The C library is the Borland run-time linked into
`SIM68K.exe`, so these are the original's rules (only the file system below is Wine's):

- written bytes become visible to a second stream in blocks of 512: nothing after 1 to 512 bytes,
  512 after the 513th byte, 1024 after the 1025th, ... (the buffer is written when it is full and
  another byte comes); after `task 56` all 2,100;
- a large write is not cut into blocks: 10 buffered bytes followed by one write of 1,000 make all
  1,010 visible at once, and one write of 5,000 on a fresh stream makes all 5,000 visible;
- a reading stream keeps what it read: after reading 10 bytes of a 100-byte file it has buffered the
  whole file, and bytes another stream changed and closed meanwhile are not seen without a seek.

ARCHITECTURE.md 3.8.4 assumed BUFSIZ 512 (confirmed), "commits whole multiples" (true for small
writes; a write of 512 bytes or more goes out whole, with what was buffered) and "does not buffer
reads" (the original does). For SH6 (ProgramFiles) and the owner of 3.8.4. To be confirmed on Windows
with the same program (6.8), though nothing in it depends on Wine but the file system.

### F3 - task 54 with D2 = 0 gives D0.W = 0

`trap15-a/a31-files-zero-length`: the original reports success for a zero-length write; the port
reports 2 (C99 `fwrite` returns 0 for a zero item size). trap15-a §7 task 54 asked for exactly this
measurement and for a special case in the port. Owner: the simulator engine (`SIMOPS2.CPP`
`writeFile`). Task 53 with D2 = 0 gives 2 in both. **Repaired by the engine at gate I2**
(`engine/sim/shim/hostfile.cpp`, PATCHES.md section 3; docs/requests/W4-t3-known-differences.md):
a31 now equals the golden and its entry is removed from `known-differences.json`.

### F4 - task 53 with a byte count that wraps the bounds test reports success and reads nothing

`trap15-a/a32-files-bounds`: A1 = $2000, D2 = $FFFFFFFF on a 10-byte file. The original gives
D0.W = 0 and leaves D2 at $FFFFFFFF (the Borland `fread` returned the requested count) and stores
nothing at $2000; the port gives D0.W = 2. trap15-a §7 task 53 expected "a normal success with D2 =
bytes read"; that is not what happens. Owner: the simulator engine (`CODE9.CPP` case 53 /
`readFile`). The A1 = $FFFFF0, D2 = $20 case (D0.W = 2, nothing read) agrees. **Repaired by the
engine at gate I2** (same patch as F3): a32 now equals the golden; its entry is removed.

### F5 - task 40 with CID 16 gives D0.W = 1

`trap15-a/a47-serial-without-port`: the CID check (`> 15` gives 1) is in `TsimIO::initComm`, so the
port's host part must make it; `NullSerial.initComm` (`core/sim-host/serial/null.ts`, owner W1)
returns 2 for every CID. The other results agree (CID 0 with a missing port: 2; tasks 41-43 on an
unopened CID: 3). `DesktopSerial` should make the same check. **Repaired by W1 at gate I2**
(`NullSerial.initComm` gives 1 for a CID above 15): a47 now equals the golden; its entry is
removed. Whether `DesktopSerial` (DV4) checks the CID too is not covered by the suite (the harness
runs the null device).

### F6 - drawing modes 18-23 under Wine leave the copy mode

`trap15-b/b06-modes-above-15`: under Wine every mode 18-23 draws the red pen unchanged, where
trap15-b §5.4 / V8 (from the binary's table) expects white for mode 20 and the inverse of the pen for
mode 22. Wine's `SetROP2` refuses values outside 1-16 and keeps the previous mode; whether Windows
does the same with the values the table yields is open (V8). Listed with owner SH1 (surface, the
ROP2 table of trap15-b §5.4) and marked unconfirmed (`unconfirmed` in `known-differences.json`): if
`b06` run on Windows (tests/conformance/windows-confirm) draws as Wine does, SH1 changes modes 18-23;
if Windows follows trap15-b's table, the difference is Wine's and the golden is replaced by the
Windows result. The port keeps trap15-b's table until then. (The first version assigned it to an
owner "oracle", which names no package that would act; that owner no longer exists, and
`conformance.test.ts` accepts only the engine and host packages as owners.)

### F7 - a stream that mixes reads and writes without a seek between them (review of T3, round 2)

C leaves a read right after a write on the same stream (or a write right after a read) undefined
without an `fseek` between them; the Borland run-time in `SIM68K.exe` does something definite, and
a student's program can observe it. Measured with three suite programs (goldens from the oracle at
gate I2; the reviewer's probes v1, v4 and v5 gave the same):

- `trap15-a/a51-files-read-after-write`: write `ABCDE`, then read 4 without a seek: the original
  gives D0.W = 0, D2 = 4 (bytes of its buffer), and after the close the file holds one byte, `A`.
  The port gives D0.W = 1 (end of file) and the file holds `ABCDE`.
- `trap15-a/a52-files-write-after-read`: write `ABCDE`, seek to 1, read 2 (`BC`), write `X`: the
  original reports success but the file is still `ABCDE` after the close; the port's is `ABCXE`.
- `trap15-a/a53-files-past-end-then-read`: write `ABCDE`, seek to 25, write `X`, read 4: the
  original's read gives 0 (port: 1), its close gives 2 (port: 0), a new stream reads `ABCDE` only
  (port: 26 bytes, the gap as zeros and `X`), and task 57 on the file then fails with 2 (port: 0).

ARCHITECTURE.md 3.8.4 says pending bytes are committed "before a read through the same stream",
which is not what the original does. Owner SH6 (ProgramFiles) and the owner of 3.8.4; listed in
`known-differences.json`, marked unconfirmed until the three run on Windows (6.8; only the file
system under the C library is Wine's).

### F8 - names, devices and the edges of the 512-byte buffer (SH6's questions, gate I2)

Answers to "What T3 is asked to confirm" in docs/porting/errata/SH6.md, from suite programs with
goldens of the official program under Wine:

- Item 1, `trap15-a/a59-files-buffer-edges`: 300 + 300 bytes leave 300 visible (as SH6 chose);
  511 + 1 leave nothing, one byte more makes 512 visible; one write of 513 makes 513 visible; **one
  write of exactly 512 on an empty buffer leaves nothing visible** (it fills the buffer and waits for
  the next byte). The port shows 512: a difference, owner SH6. The rule that fits every
  measurement: a write that fits into what is left of the buffer is copied into it, even when it
  fills it exactly; one that does not fit writes the buffer first and then goes out whole when it is
  512 bytes or more (else into the buffer).
- Item 2, `trap15-a/a56-files-same-file-twice`: two task 51 on one file each get a slot with their
  own position (`A`, then `AB` from the start); task 52 on the file while both are open succeeds
  (slot 3), and a 1-byte write and close through it succeed; the first stream then reads `BCD` from
  its position 1. The port agrees byte for byte.
- Item 7, `trap15-a/a57-files-odd-names`: `DATA.TXT.` and `data.txt ` open `data.txt`; `d?ta.txt`
  and `d*.txt` give 2 for tasks 51, 52 (D1 = $FFFFFFFF) and 59. The port agrees.
- Item 8, `trap15-a/a58-files-devices`: on `NUL`, tasks 52, 54, 56, 59 and 51 succeed as in the
  port, but a read gives end of file (D0.W = 1) where the port reads back the 3 bytes it stored in
  an ordinary file. Owner SH6; unconfirmed (Wine's null device) until run on Windows. `CON` was not
  measured (it would wait for a console that the oracle does not have).
- `trap15-a/a54-files-missing-folder` (review of T3, round 2): `nofolder\x.bin` and
  `nofolder/x.bin` fail with 2 for tasks 52, 51 (D1 = $FFFFFFFF), 59 and 57. The port agrees, with
  the real ProgramFiles and with the doubles. (The doubles now also drop trailing periods and
  spaces and refuse `?` and `*`, for a57; programs whose result shows the C library's buffers are
  skipped in the doubles mode, `NOT_MODELLED_BY_DOUBLES` in `doubles.ts`.)
- Items 3, 4 and 5 (Rewind with a file left open, the run-time's stream table running out, the
  order in which forgotten streams are written at exit) need the Rewind button or the end of the
  simulator, which the oracle's two recipes (official-oracle.md 5.1, 5.2) do not drive; not
  measured. Item 9 (the printer's page geometry) needs a printer in the container; not measured.

### Results in numbers

(160 self-reporting programs, 27 execution logs with 47,664 instructions, 17 output logs). The port
(harness with the two doubles and Wine's cells): 208 artifacts compared, 203 equal, 5 different, all
five assigned in `tests/conformance/sim/known-differences.json` (F3, F4, F5, F6, and the accepted `%`
difference of sim-ui Q23). Every `.S68` the port's assembler makes equals the official assembler's.

Gate I2 (2026-11-21): nine programs added (`trap15-a/a51`-`a59`, F1, F7, F8) and run in the oracle
(`regenerate.mjs --only trap15-a/a5`, 10 of 10 runs with a result). The port with the real parts

all eight assigned: SH6 five (a51, a52, a53, a58, a59), the engine two accepted ones (l14, a55),
SH1 one (b06). F3, F4 and F5 are repaired and their entries removed. The whole list as data, with
every differing line: `EASY68K_SIM_REPORT_JSON=<file>` (the gate's copy:
`build/gate2/T3-mismatches.json`).
