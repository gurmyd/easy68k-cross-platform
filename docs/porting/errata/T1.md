"Corrections to the specs"). Each entry says what the document says, what the repository does, and
why. Entries 9 to 12 and 17 are findings about the official program that the specs (and E1) should take over.

## 2. Where goldens are, and when only a hash is kept (6.2.2)

- Says: "Outputs for redistributable inputs are committed under `tests/conformance/*/golden/`.
  Outputs for inputs that may not be redistributed are kept in `build/golden-local/`; only their
  SHA-256 (after masking) is committed, in the corpus manifest."
- Does: as said, with two additions.
  1. An output larger than 512 KiB is not committed either; the manifest marks the run
     `golden: false` and holds the hashes, and the comparison for it is by hash. Today that is
     `github/pacman-mc68000/GAME/MAIN.X68` only: its two listings are 4.4 MB and 5.5 MB and its
     S-records 1.3 MB each (it includes the 2.4 MB `GFX.X68`), 12.5 MB together, against 3.3 MB for
     all other 585 golden files.
  2. The manifest holds the hashes of **every** run, also of those whose files are committed, so
     that one rule ("the canonical output has this hash") covers all sets.
- Proposed text: add "An output above 512 KiB is kept like a non-redistributable one: its hash in
  the manifest, the file in `build/golden-local/`."

## 3. The date line is compared, not masked, wherever the official listing is in the repository (6.1 L2)

- Says: L2, "`.S68` and `.L68` (date line masked) are byte-identical".
- Does: the comparison gives the assembler the time printed in the official listing, so the whole
  `.L68` is compared byte for byte, the `Created On:` line and its format included. The date line
  is masked only in the hashes of the manifest (they must not change with every regeneration) and
  therefore for the runs that are kept as hashes only.

## 4. What "masking" an undefined symbol means (6.1, official-oracle §3.5 and §4 item 2)

- Says: "Tests must mask object code on lines that carry an `Undefined symbol` error."
- Found on the corpus: three things differ in such a program, and they need three rules
  (`tests/conformance/asm/compare.ts`):
  1. the object-code field (columns 11 to 32: the original prints address and code as one field of
     32 characters and the line number after it, LISTING.CPP:129, 159-161) of the statement. The
     original prints the message directly above the **last** listing line of the statement: with
     "Constants Expanded" that is the last continuation line, and the lines above the message up to
     the source line belong to the statement too (`pacman-mc68000/GAME/STATES.X68`, expand options);
  2. in the symbol table, the value of an entry whose name cannot be a label: the original creates
     such an entry (`,D0`) from a failed operand and leaves its value uninitialised (one program of
     the `site` set);
  3. in the S-records, the bytes of exactly those statements (`undefinedSymbolRanges`): a
     statement's bytes run from the address of its listing line to the address of the next listing
     line (which covers code the listing does not show, such as an unexpanded macro body or `...`),
     or, when no line follows or the next is lower (`ORG` backwards), as many bytes as its
     object-code field shows. Those data bytes and the checksum of a record holding one are masked;
     type, length and address of every record and every other byte are compared. (The first
     version masked all data of every record of such a program, so a fault of the S-record writer
     alone went unnoticed in 122 runs; T1 review, gate I1. The manifest was rehashed with
     `regenerate.mjs --rehash`, which needs no Docker: every one of the 561 stored runs still
     equals the port.)
- With these rules every run of the permitted corpus is equal (entry 6); without rule 2 and the
  continuation-line part of rule 1 three runs were left unexplained.

## 5. "Unconfirmed" applies to the editor model, not to the assembler comparison (6.2.2)

- Says: files with bytes >= $80, long lines, lone LF or CR, tabs or Ctrl-Z are flagged
  `richedit-sensitive`; "until [a sample is confirmed on Windows] a mismatch on a flagged file is
  reported as 'unconfirmed', not as a failure."
- Does: the manifest carries the flag (142 of the 186 example programs have it: every LF-only file
  and every file with a tab). A mismatch on such a file is nevertheless a **failure**, because the
  comparison does not depend on the RichEdit path: the oracle captures the text the official
  editor handed to its assembler, the manifest stores its SHA-256, and the test assembles exactly
  that text. What is unconfirmed is whether Windows' RichEdit hands over the same text as Wine's.
  That concerns four synthetic inputs, where Wine's text differs from the model (NUL byte, UTF-8
  byte-order mark, bare CR at the end of the file, trailer without final newline; official-oracle
  §3.4): the manifest marks them `receivedFile`, the captured text is committed beside their
  goldens, and `golden/REPORT.md` lists them. For every other program the captured text equals the
  model.
- Proposed text: "... until then the text the editor model produces for such a file is
  'unconfirmed' where it differs from the text captured under Wine; the assembler comparison uses
  the captured text and is exact."

## 8. L3, the command-line port (6.1, 6.2.4, 7.4)

- Says: L3 "`asy68k.exe`, the v5.15.4 command-line port built natively ... Same output except the
  documented 5.16 changes ... Windows CI ... T1"; `ci.yml` runs `node tests/oracle/asm-cli/run.mjs`
  when the file exists. `compare_cli.py` of the old oracle compared the command-line port with the
  official outputs.
- Does: `tests/oracle/asm-cli/run.mjs` builds `asy68k.exe` (`tools/build-asm-oracle.ps1`) and
  compares it with the **port's** assembler on the tracked example sets, both option sets, the same
  text (the editor's load; the command-line port has no editor) and Assembly tabs (the only tab
  type the command-line port lists with). `classify.ts` accepts a difference only when the source
  contains the construct that causes it (assembler §8.2, §8.3; official-oracle §3.5); anything else
  fails the run. `compare_cli.py` was not carried over: with L2 in place the official program is
  compared with the port directly, and the command-line port is only the second opinion L3 asks
  for. Result on 2026-11-21: 104 runs, 71 identical, 33 with documented differences (28 undefined
  symbols, 4 lines with INCLUDE that the command-line port does not upper-case, 1 lower-case
  generated label), 0 unexplained.
  In CI (windows-oracles, run 44913261966 of commit 8611609, the sources cloned at the pinned
  commit; the split between the two classes moved with the engine and masking changes since):
  104 runs, 67 identical, 37 with documented differences (32 undefined symbols, 4 INCLUDE lines,
  1 generated label), 0 unexplained.
- Two things the document does not say: the sources of the command-line port are not in the
  repository (`reference/` is git-ignored), so `run.mjs` clones
  `github.com/rayarachelian/EASy68K-asm` at `7102f270282266d6c9d29b80ff5a98182c3cedff` when they are
  missing (CI); and `GFX.X68` (2.4 MB), which the official editor cannot load under Wine, is
  covered here: the command-line port and the port agree on it.

## 9. assembler §9.3.8: a macro line that expands beyond 255 characters crashes the official program

- Says: assembler §9.3.8 describes the overflow as a hazard for the port; `engine/asm/PATCHES.md`
  P8 gives it a defined result.
- Found: the official `EDIT68K.exe` v5.16.1 **crashes** on the program
  `tests/conformance/asm/checklist/programs/macro-10-*/prog.X68`: Wine reports a stack overflow at
  address `0x2c312c31` (the text `1,1,` of the expanded line: a return address was overwritten) and
  the process exits. No listing exists, so the item "a body line that expands beyond 255 characters"
  has no golden; the port's defined result cannot be checked against the original.

## 10. assembler §9.3.4: a valid printf conversion in a macro body line

- Says: assembler §9.3.4 (hazard), engine README "UNVERIFIED against the real EASy68K.EXE: `%`
  that forms a valid printf conversion in a macro body line".
- Found (official program under Wine, `checklist/macro-09-*`): with `DC.B '%d%s%%'` as a body line,
  the expansion **ends at that line**: neither the line nor the `ENDM` line appears in the listing,
  no code is emitted for it, no error is reported, and the assembly goes on after the macro call.
  `AND.B #%00001111,D0 ; 50% done` (no valid conversion) expands normally. The port expands the
  `DC.B` line literally. Listed in `tests/conformance/asm/known-differences.json` for the engine's
  owner.

## 11. assembler §9.3.9: a SET line that only pass 2 reaches

- Found (`checklist/dir-11-*`): `IFNE FWD` / `S SET 5` / `DC.B S` / ... / `ENDC` / `FWD EQU 1`. The
  official program assembles `DC.B S` to `05` with **no error**; the port reports `Undefined
  symbol` and emits `00`. Listed in `known-differences.json` for the engine's owner (`PATCHES.md`
  P14).

## 12. assembler §9.3.6: a terminator with nothing open

- Found (`checklist/stc-03-*`): `ENDI` with an empty stack gives, in the official program,
  `Undefined symbol` and a listed label line `_020C002A` (a value read from the empty stack); a
  following `IF D0 <EQ> #1` without THEN then assembles to `6600 0008` with only the `THEN
  expected` warning. The port reports `Invalid syntax` for the `ENDI` and an additional
  `Undefined symbol` (`BNE _00000000`) for the `IF`: 6 errors instead of 5. The label value of the
  original is not reproducible, but the messages and the count are. Listed in
  `known-differences.json` for the engine's owner.

## 13. Checklist item "recursion to the limit" has no golden (6.4, assembler §3.9)

- The official program crashes on a macro that calls itself without end (stack overflow,
  official-oracle §3.2), so the item is proved against the original only by a recursion that ends
  by a condition (`checklist/macro-12-*`); the unbounded program (`macro-13-*`) is kept, and the
  report names it.

## 14. `oracle.yml` (7.4)

- Says: "build the Wine container (layer cache) ... open a pull request if any changed"; 7.4 caches:
  "Docker layers (buildx, GitHub cache)"; "Workflows have `permissions: contents: read` by default;
  only `pages.yml` and the `publish` job ask for more."
- Does:
  - the image is cached as one file (`docker save` / `docker load`) with `actions/cache`, keyed by
    the hash of the Dockerfile and the scripts it copies. This needs no action beyond the ones
    `ci.yml` already pins; buildx with the GitHub cache would add two third-party actions;
  - the job that runs Docker, Wine and the downloaded official programs has a read-only token. A
    second job, `propose`, has `contents: write` and `pull-requests: write`; it receives the changed
    goldens as an artifact, accepts only paths under `tests/corpus/manifest.json` and
    `tests/conformance/`, and opens the pull request with the `gh` command. So `oracle.yml` is a
    third workflow that asks for more than read access, in one job;
  - a pull request opened with the workflow's token does not start `ci.yml` by itself (GitHub's
    rule); its text says to close and reopen it;
  - the simulator regeneration (`npm run oracle:wine:sim`, T3) and the single-step job (T4) are
    written with guards and are skipped until `tests/oracle/wine/sim/regenerate.mjs` and
    `tests/conformance/cpu/run-singlestep.mjs` exist;
  - screenshots of failed runs are not uploaded: they can show text of the `site` set.

## 16. An unexpected window fails the run; the help-viewer boxes are the one exception (6.2.2, official-oracle §4 item 7)

- Says: 6.2.2, the script "fails loudly on any unexpected window"; official-oracle §4 item 7, keep
  what a crashed run wrote.
- Was (until gate I1): `asm_batch.py` pressed Return (or `n` on a `Confirm` box) on any other window
  and went on to record the run as `ok`; `regenerate.mjs` only added a note.
- Does: besides the editor and its `Assembler Status` dialog, any window fails the run
  (`window_verdict`, `check_windows`): it is recorded with a screenshot, the editor is killed, and
  the manifest records `status: "failed"` with the window's title and the phase of the run in
  `reason`. `regenerate.mjs` (`failureOf`) also refuses a record that lists a dismissed window, so an
  older driver cannot pass, and it exits 1 when a run that had a result has none now. The driver
  tests its own rule (`asm_batch.py --self-test`, run by `regenerate.mjs` before every regeneration).
- The one exception: the editor's help-viewer `ShowMessage` boxes (mainS.cpp:123, 149, 154 at
  start-up, 807 at exit; caption `EASy68K`, the application title) are dismissed and recorded as a
  note, at most as many per phase as the source can show. They depend on the help system of the
  machine, not on the program assembled. No run of the corpus has shown one under Wine. Their
  caption is the only thing the driver can read, so another `ShowMessage` box at start-up would pass
  as one of them; its screenshot and the note in the manifest still show it.
- A failed run whose editor had finished assembling (the status dialog was up) keeps the `.L68` and
  `.S68` it wrote, as `<label>.failed.L68` / `.S68`, and the manifest marks the run `outputsKept`; the
  comparison test compares them like goldens. Today that is `richedit/s03_long_line_4000.X68`: the
  `Access violation at address 00479971 in module 'EDIT68K.exe'` box (caption `EASy68K`) above the
  status dialog, after 14 errors and 1 warning; the port's output equals the kept files.
