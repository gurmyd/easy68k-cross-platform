## Keyboard (2.9)

### 1. Text-editing chords are left to the focused text field (2.9.1 step 3)

- Says: 2.9.1 step 3, "A command of the current mode bound to the chord and enabled: run it,
  `preventDefault()`", for every chord of the table. The table binds Ctrl/Cmd+Z, X, C, V, A,
  Shift+Cmd+Z and Shift+Insert to the six Edit commands.
- Elsewhere: 1.4 note 45 ("Paste from the menu ... has no key event to ride on ... The keyboard
  chords and the desktop app are not affected"), 7.6 ("Text editing with Cmd+X, C, V, A and Z works
  ... through menu items with the matching roles"), and the DV2 acceptance "Cmd+C and Cmd+V work
  in the Memory panel's Address field". A browser performs cut, copy and paste only on the key's
  own event; a cancelled Ctrl+V cannot paste without the clipboard permission prompt of note 45.
- Does: while a text input, a textarea or editable content (the editor) has the focus, the
  dispatcher leaves the chords of `ed.edit.undo`, `redo`, `cut`, `copy`, `paste` and `selectAll`
  that contain no Alt to that element (`commands/keymap.ts`, `TEXT_EDITING_COMMANDS` in
  `commands/tables/keys.ts`). With the focus anywhere else the chord runs the command as step 3
  says. The Alt forms (Ctrl+Alt+Z, Ctrl+Option+Z) are commands everywhere.
- Consequence for E2: the editor component binds undo, redo and select-all in its own CodeMirror
  key map (to the same functions as the command handlers); cut, copy and paste arrive as the
  browser's clipboard events.
- Proposed text for 2.9.1: add after step 4, "The platform's text-editing chords (Ctrl/Cmd+Z, X,
  C, V, A, Shift+Cmd+Z, Shift+Insert) are left to a focused text field or editor."

### 2. The chords of 2.9.3 are cancelled in every mode, bound or not (2.9.1 against 2.9.3)

- Says: 2.9.1 cancels an event only for a command of the current mode (steps 3 and 4). 2.9.3
  says of "F5, F6, F7, F10, Ctrl+O/S/P/F/G/R": "the dispatcher calls `preventDefault()`". F5 is
  bound to no command in any mode, Ctrl+S to none in Simulator mode, Ctrl+G to none in Editor mode.
- Does: 2.9.3 wins. `GUARDED_CHORDS` (`commands/tables/keys.ts`) are cancelled in every mode,
  also while a modal dialog or a menu is open, whether or not a command is bound; nothing is run
  and the event still reaches the focused element. Reloading the page on F5 would throw away the
  simulator's state. On macOS the Cmd forms of O, S, P, F and G are guarded too; Cmd+R is not
  (2.9.3: "interception is not dependable").
- Proposed text for 2.9.1: a step "A chord of the list of 2.9.3: `preventDefault()`, in every mode
  and also in steps 1 and 5."

### 3. Ctrl+F2..F5 on macOS, and Ctrl+F4 in the Output panel (1.3.4, 2.9.3, 2.9.4)

- Says: 1.3.4 gives macOS only `Shift+F2`, `Shift+F3`, `Shift+F4`, `Shift+F5` for Rewind, Reload,
  Log Start and Log Stop. 2.9.4 rule 2 takes "Ctrl+F2, Ctrl+F3, Ctrl+F9, Ctrl+F4, Ctrl+F5" in the
  Output panel on every platform, and rule K3 calls the Shift form "an alternative". 2.9.3 makes
  Ctrl+F4 desktop-only for "Windows, Linux browsers", where it closes the tab. For macOS it has
  another row: Ctrl+F2 .. Ctrl+F8 are system shortcuts "unless the user has switched them off".
- Does:
  - **macOS**: the lists of the four commands hold both forms, the Shift form first (it is the one
    shown). A user who has switched the system's Ctrl+F<n> shortcuts off gets the original keys.
    This includes Ctrl+F4, in a browser as well as in the desktop app: no browser on macOS uses
    that key, so the first row of 2.9.3 does not apply there.
  - **Windows and Linux**: outside the Output panel Ctrl+F4 acts in the desktop app only, as 2.9.3
    decides; a browser shows and uses Shift+F4.
  - **The Output panel, every platform**: rule 2 takes each of the original's chords whenever its
    key-down arrives, in a browser and in the desktop app. `outputPanelKeyAction()` does not look
    at `desktopOnly`. Most browsers on Windows and Linux never deliver Ctrl+F4 to a page; one that
    does gets Log Start, and the key-down is not posted to the program. The original's I/O window
    never receives this key while key commands are enabled, so a program must not either
    (section 0 rule 1).
- Contract: `CommandSpec.keys.desktopOnly` is one list for both key maps and cannot say "on
  Windows and Linux only". W3 keeps the contract's shape and names the platform in a second list,
  `DESKTOP_ONLY_ON_WINDOWS_AND_LINUX` (`commands/tables/keys.ts`, today `Ctrl+F4` alone). The
  dispatcher and the menus ask `chordsOn(id, os, desktop)` (`commands/specs.ts`; also
  `isDesktopOnly(id, chord, os)`); nothing reads `keys.desktopOnly` directly.
- For W1: say in `contracts/commands.ts` that `desktopOnly` is read through `chordsOn`, or split
  the field by key map (`desktopOnly?: { win?: string[]; mac?: string[] }`).
- Done at the wave-0 gate: the comment on `CommandSpec.keys` says that `win`, `mac` and
  `desktopOnly` are read through `chordsOn` and `isDesktopOnly`; the field keeps its shape.
- Proposed text: 1.3.4, macOS column of Rewind, Reload, Log Start and Log Stop: "Shift+F<n>,
  Ctrl+F<n>". 2.9.3, first row, decision: "Log Start = Shift+F4; outside the Output panel
  Ctrl+F4 only in the desktop app; in the Output panel a Ctrl+F4 that arrives is Log Start
  (2.9.4)".

### 4. After task 24, F1 and the panel cycle are ignored too (1.3.5, sim-ui §3.5)

- Says: `CommandSpec.suppressedByTask24` marks "one of the eleven of sim-ui §3.5". The row
  "TRAP #15 task 24" of 1.3.5 and sim-ui §3.5 also ignore F1 and Ctrl+Tab on the main window.
- Does: `ALSO_IGNORED_AFTER_TASK_24` = `sim.help.context`, `sim.panel.next`. While
  `AppState.sim.keyCommands` is false their chords, like those of the eleven, are cancelled and do
  nothing in Simulator mode; menus show no shortcut for them. The commands still run from the
  mouse, as in the original.

### 5. The three chords of the Output panel act only there (2.9.1 against 2.9.4)

- Says: the table binds Alt+Enter, Shift+Insert / Cmd+V and Ctrl+Alt+O to `sim.output.fullscreen`,
  `sim.output.paste` and `sim.output.releaseKeyboard`; by 2.9.1 step 3 they would act in every
  panel of Simulator mode.
- Does: the dispatcher never acts on them (`OUTPUT_PANEL_COMMANDS`); the original handles them in
  the I/O window's own key handler. The Output panel (SH4) acts on them through
  `outputPanelKeyAction()` (`commands/output-keys.ts`), which implements rules 1 to 4 of 2.9.4 from
  the chord table so that the rules of 1.3 are applied in one place.

### 6. "The Output panel has the keyboard" needs a marker (2.9.1 step 2, 2.10)

- Does: the element that takes keys for the program carries `data-e68-keys="program"` (SH4: the
  hidden textarea). While it or an element inside it is the event target, the dispatcher does
  nothing at all. Other controls of the Output panel (zoom, the full-screen button) are ordinary
  controls.

### 7. Menus: no command while the focus is in a menu; Alt+letter (1.3.2, note 14)

- Does: while the event target is inside the menu bar or an open menu, no command runs (letters
  and arrows are the menu's, as on Windows; guarded chords are still cancelled). `Alt+<letter>`
  that no command uses opens the menu with that access key on Windows and Linux, unless the focus
  is in a dialog, whose own access keys come first. macOS: nothing (no access keys).

### 8. F1 belongs to two Editor commands (1.3.2)

- Says: "F1 in the editor" = `ed.help.context`, "F1 on the frame" = `ed.help.help`.
- Does: both are bound to F1. The dispatcher runs the first ENABLED command in the order of the
  key table (context, then help). H1's handler of `ed.help.context` therefore reports itself
  enabled only while the editor has the focus. The Help menu shows no shortcut next to `Help`, as
  the original's menu shows none (`NOT_SHOWN_IN_MENUS`).

### 9. "Recorded" key and code pairs (2.9.2)

- Says: "The unit tests of the table use key and code pairs recorded from real keyboards".
- Does: `commands/key-fixtures.ts` holds the pairs (macOS Option layer including dead keys, Windows
  AltGr, QWERTZ, AZERTY, Russian, Greek, the numeric keypad). **None of them was captured on a
  keyboard.** This package had no access to the keyboards, and an automated browser types through
  its own US table, not through a keyboard layout, so it cannot record them either. What stands
  behind each list:
  - **Windows lists** (US, German, French, Russian, Greek): the characters in `key` were compared
    with the layout tables that Windows 11 itself uses (`KBDUS.DLL`, `KBDGR.DLL`, `KBDFR.DLL`,
    `KBDRU.DLL`, `KBDHE.DLL` in `System32`), read through each file's `KbdLayerDescriptor` export
    without installing or activating a layout (a one-off script, not in the repository): all 23
    values checked agree (the unshifted, Shift and AltGr characters of the positions the fixtures
    use, and the positions where a layout has no AltGr character). Not confirmed by this: the
    `code` names, and the rule that a browser reports the unmodified character in `key` while
    Ctrl is held (Ctrl + the S position of a Russian layout is `ы`). Both are from the UI Events
    specifications.
  - **macOS lists** (Option layer, dead keys, Russian) and the **keypad list**: from the UI Events
    specifications and the published layouts only.
- Still to do, by a person with the keyboards: `docs/requests/W3-key-recording.md` has a recorder
  for the browser console and the presses per keyboard, for the manual list of 6.8. W3 replaces
  the fixtures with what comes back.
- AltGr chords follow the key's position, as 2.9.1 says; on layouts whose AltGr layer has letters
  on Z, C, U or O (Polish) the Editor's Ctrl+Alt chords win over the character, as accelerators
  do in the original on Windows.

### 21. Keys of the numeric keypad (2.9.1)

- Says: "function keys, digits and punctuation from `KeyboardEvent.code`"; nothing about the
  numeric keypad, whose `code` names a position without a fixed meaning.
- Does: while NumLock is off the keypad's keys are Insert, Delete, Home, End, PageUp, PageDown and
  the arrows, and the event says which in `key` (`key: 'Insert'`, `code: 'Numpad0'`). `keyNameOf()`
  (`commands/chords.ts`) names such a press by `key`, so Insert and Shift+Insert from the keypad
  are the chords of the table: on many laptops that is the only Insert key. Windows reports both
  places as the same virtual key (`VK_INSERT`), which is what a Windows program's shortcuts go
  by. The keypad's Enter is Enter. With NumLock on the keypad types digits and operators; these
  form no chord (on Windows a shortcut on `1` is not a shortcut on `Num 1`).
- Proposed text for 2.9.1: a fourth item, "a key of the numeric keypad from `key` when that names
  a navigation key (NumLock off); keypad digits and operators form no chord".

## Shell and services (2.1-2.4, 3.12)

- Says: the factory is `createSimSession(ctx)`; 3.1 forbids `features/<x>/` to import
  `app/src/engine/` and `app/src/fs/`. The session (`features/run/session.ts`, SH8) needs
  `createSimEngine` / `releaseSimEngine` (4.7.1) and `CachedSyncFiles` (`ProgramFilesDeps.viewFor`,

- Does: the bootstrap calls `createSimSession(ctx, env)` with `env: SimSessionEnv`
  (`app/src/state/services.ts`):
  `{ engines: { create(host): Promise<SimEngine>; release(engine): void };
     createCachedSyncFiles(deps: CachedSyncFilesDeps): SyncFiles }`.
  `main.tsx` fills it from `app/src/engine/index.ts` and `app/src/fs/sync/cached.ts`. The stub of
  `features/run/index.ts` has this signature. The disk view of the desktop app is
  `ctx.platform.syncFiles` and needs nothing here.
- For W1: move `SimEngineFactory`, `SimSessionEnv` and `ServiceFactories` into
  `contracts/features.ts`.
- Done at the wave-0 gate: the three are declared in `contracts/features.ts`;
  `state/services.ts` re-exports them (errata W1.md, entry 10).
- Proposed text for 3.12.3: "the factory of `features/run` is `createSimSession(ctx, env)`, with
  `env: SimSessionEnv` of `contracts/features.ts`".

### 11. Parts delivered later are picked up by name (3.12.3, 3.8.1, 3.13)

- Says: "vfs (+ backends)" is created by the bootstrap, and the platform is "chosen at start by
  the presence of `window.easy68kDesktop`". `fs/browser-backend.ts` (FS1) and `platform/desktop.ts`
  (DV2) do not exist in wave 0 and have no W1 stub; 9.3 says "I1 edits no wiring".
- Does: `main.tsx` looks for them with `import.meta.glob` and calls a function with a fixed name:
  - `app/src/platform/desktop.ts`: `export function createDesktopPlatform(): Platform | Promise<Platform>`;
  - `app/src/fs/<name>-backend.ts`: `export function createStartupBackends(platform: Platform):
    FileSystemBackend[] | Promise<FileSystemBackend[]>` (optional; every backend returned is
    mounted before the features start). `platform.disk` is mounted by the bootstrap itself.
  Until a backend with the mount `browser` exists, a `MemoryBackend` stands at `/browser` so that
  the paths of 3.8.2 work; its files are gone when the page closes.
- Proposed text for 3.12.3 (`docs/requests/W3-layer-rule.md` item 3): "`main.tsx` chooses the
  platform (`createDesktopPlatform()` of `platform/desktop.ts` when `window.easy68kDesktop`
  exists, otherwise the web platform) and mounts whatever `createStartupBackends(platform)` of
  each `fs/*-backend.ts` returns; the bootstrap mounts `platform.disk`. Both happen before the
  features start."
- Not solved here: a feature that must construct a backend at run time (FS2: the opened folder)
  cannot import `app/src/fs/` under the lint rule of 3.1. See `docs/requests/W3-layer-rule.md`.

### 12. Clock and scheduler of the context (3.11.1, 3.12.3)

- Says: `AppContext.clock` and `.scheduler` exist from the start; `RealClock` and `FrameScheduler`
  are SH8's (`core/run/clock.ts`), without a W1 stub.
- Does: `app/src/state/browser.ts` has `createRealClock()` and `createFrameScheduler()` (frames,

### 13. Contract: state of the shell that `AppState` does not hold (3.12.1, 2.3, 1.4 note 4)

- Says: `AppState` has no place for the tool tab in front, a collapsed Output panel, a pending
  focus request or "Exit has run" (note 4: "shows an empty workspace with the text `You can close
  this tab.`").
- Does: a second small store, `ShellState` (`app/src/state/shell.ts`), tied to the context.
  Features use the functions of `app/src/state/panels.ts` (`showPanel`, `hidePanel`, `focusPanel`,
  `focusNextPanel`, `panelVisible`) and `showExitScreen(ctx)`.
- The Output panel's collapsed state is not persisted: it is always visible at start (2.4).

### 14. Regions that are not panels of 2.4: `editor`, `easybin`, `status`

- Says: `PanelSpec` is the only way a feature puts a component into the shell (3.1: the shell may
  not import `ui/editor`, which does not exist in wave 0 anyway), and 2.4 lists eleven panel ids.
- Does: three more ids are regions of the shell: `editor` (the editor area of 2.2, owner E2),
  `easybin` (the EASyBIN workspace, owner B1) and `status` (the status bar of a mode; SH8 for the
  simulator). A PanelSpec with the id `help` serves every mode (2.1). `messages` exists once per
  mode (E5 in Editor mode, U1 in Simulator mode); the pair (mode, id) identifies a panel. Until a
  feature fills it, a region shows its title, and the status bar shows what the store knows.

### 15. The height rule of the editor's message list is in the shell (2.2)

- Does: the shell owns the separator above the Messages panel, so it applies editor-ui §7.3
  itself from `AppState.messages` and `AppState.assemble` (5 px, at least 87 px, 7 px;
  `messagesPaneHeight()` in `state/layout.ts`). E5's panel only fills the region.

### 16. Per-window layout in a shared settings document (3.8.6 rule 2, 3.10)

- Says: `update()` re-reads the stored document; "the panel layout of a window that is already
  open stays as it is".
- Does: `SettingsService` keeps `app.layout` per window. An event from another window replaces
  everything except the layout; `update()` applies a change to the stored document with this
  window's layout laid over it, and writes the layout back only if the change touched it. A window
  that starts takes the layout stored last. Everything else in the document (the theme included) is
  shared at once.
- `core/` may not touch `localStorage`: the service takes a `SettingsStorage` (read, write,
  onExternalChange); `state/browser.ts` implements it on `localStorage` and the `storage` event.

### 17. `DialogService.open` with an unknown id rejects (3.12.4)

- Does: `open(id, ...)` for an id no feature registered rejects with an error naming the id.
  A dialog component draws itself with the kit's `Dialog` and must pass the same `modal` value it
  was opened with. Dialogs must be opened through `ctx.dialogs`: only those block commands and
  hold the controller.

### 18. The native menu is described completely by the page (7.6, 3.13)

- Says: 7.6 lists what the native menu bar contains; `NativeMenuItem` can carry roles.
- Does: `buildNativeMenu()` (`commands/native-menu.ts`) builds the whole bar and the bootstrap
  hands it to `Platform.setNativeMenu` whenever it changes: the application menu (About, Settings...
  in Editor mode, New Window, Services, Hide, Quit = the mode's Exit command), the mode's menus,
  a standard Edit menu of role items in Simulator and EASyBIN mode, Window, Help.
  - Menu-level roles used: `appMenu`, `editMenu`, `window`, `help`; item roles: `about` is NOT
    used (About and Quit are command items so that the port's dialogs and close prompts run),
    `services`, `hide`, `hideOthers`, `unhide`, `undo`, `redo`, `cut`, `copy`, `paste`,
    `selectAll`, `minimize`, `zoom`.
  - `accelerator` is the chord in the normal form of `commands/chords.ts` (`Cmd+O`,
    `Shift+Cmd+S`, `Ctrl+Alt+Z`, `Ctrl+Shift+.`); DV2 translates it to Electron's spelling.
  - The Editor has a Window menu of its own; the system's `minimize` and `zoom` join it after a
    separator instead of a second menu called Window.

### 22. The page's assembler is the real engine, loaded on first use (3.12.3)

### 23. Stored settings this version cannot use (3.10)

- Says: "Unknown keys are kept; missing keys take defaults; a version field allows migration."
  Nothing about a known key with a value that is not one of the contract's.
- Does: such a value is treated as missing and the default takes its place: a value of another
  type than the default, and, for the eight settings whose type is a fixed list of values
  (`tabType`, `colorPreset`, `execLogType`, `outputLogType`, `speed.mode`, `theme`,
  `editorPanes`, `outputZoom`), a value that is not on the list. The lists are `SETTING_CHOICES`
  in `core/settings/service.ts`. They are needed because the type of the default cannot decide
  for these: `outputZoom` is `'fit' | 1 | 2`, so a stored `2` differs in type from the default
  `'fit'` and is right, and a theme `'blue'` has the type of the default and is wrong.
  `service.test.ts` holds the table against `contracts/settings.ts` at compile time: a setting of
  this kind, or one of its values, that is missing from the table fails `npm run typecheck`.
- Not checked: the entries of the free-keyed tables `layout.panels`, `layout.splits` and
  `serialPortMap`. They are kept as stored, and their readers (`state/layout.ts`) take the
  default for an entry they cannot use.
- Proposed text for 3.10: after "missing keys take defaults", "a stored value that the contract
  does not allow for its key is treated as missing".

### 24. Ctrl+Alt+letter follows the key's label on Windows and Linux (2.9.1; wave-0 gate)

- Says: 2.9.1, third item of the chord rules: "a letter from `KeyboardEvent.code` (`KeyA` ..
  `KeyZ`) when `altKey` is set or when `key` is not an ASCII letter (rule K6: Option on macOS and
  AltGr on Windows change `key`; Cyrillic and Greek layouts have no ASCII letters). Such chords
  follow the key's position." Rule K6 of 1.3 says the same of every chord with Alt.
- Elsewhere: rule K1, "Windows and Linux use the original keys". The original's accelerators
  (Redo Ctrl+Alt+Z, Comment Ctrl+Alt+C, Uncomment Ctrl+Alt+U) are Windows virtual keys, and a
  virtual key follows the label of the key in the active layout. By position, a German user's
  Redo was Ctrl+Alt + the key labelled Y, and a French user's Ctrl+Alt + the key labelled W.
- Does: the words "when `altKey` is set" now apply to the macOS key map only. On the Windows and
  Linux key map a chord with Alt held takes its letter from `key` when `key` is a single ASCII

### 26. Two windows that write settings at about the same time (3.8.6 rule 2, 3.10)

- Says: 3.8.6 rule 2, "`SettingsService.update()` reads the stored document again, applies the
  change to that, and writes it, all in one synchronous step, so two windows never overwrite each
  other's fields. A `storage` event from another window replaces the in-memory copy". 3.10 says
  the same.
- Found: that is not enough. A browser does not promise that one page reads another page's
  `localStorage` write at once: WebKit and Chromium keep a copy of the storage in each page's
  process and bring it up to date later, by a message that the page handles between tasks; the
  `storage` event comes with it or apart from it. A window can therefore read the document, apply
  its change and write the whole document while another window's newer change has not reached
  its copy, and that change is gone from the store. Measured on a slow machine with a probe of
  two plain pages doing the same read-change-write, 200 rounds in WebKit: in 1 round page B did
  not see page A's write, in 4 page A did not see page B's, although the `setItem` had returned
  and a whole round trip through Playwright had passed, and those 5 rounds lost a setting; on the real application, the shell check's sequence lost A's font size
  in 39 of 100 rounds in WebKit (none in Chromium), and in none when one more round trip to page
  B was put between A's write and B's: it depends on timing alone. When page B is busy while A
  writes, B reads the old text afterwards in both browsers (Chromium 19 of 20, WebKit 18 of 18);
  a window that is busy assembling or running a program is in that state. This is what made the
  shell check's "settings survive two pages writing in turn" fail now and then in WebKit on CI.
  A Web Lock does not help: it orders the writers but does not bring a page's copy up to date.
- Does: every setting the port changes carries a stamp, `[milliseconds, writer]`, in a table
  `stamps` at the top of the stored document, keyed by the setting's path
  (`"editor.fontSize"`; a `.` or `~` inside a key is written `~1` or `~0`). The panel layout
  `app.layout` is one setting, as before. `update()` stamps the settings its change touched with
  a time later than every stamp the window has seen (`Date.now`, given by the storage of
  `state/browser.ts`, because `core/` has no clock of its own here). Every document a window sees,
  read from its copy or handed over by a `storage` event, is merged with what the window knows,
  setting by setting: the later stamp wins; a setting without a stamp, or with the same stamp on
  both sides, comes from the document seen. A window that finds a document from another window
  lacking one of its own newer settings writes the merged document back ~~at once~~ (superseded by
  entry 27: after a pause of 10 to 50 ms, and only if no window has put it back meanwhile). The event's
  `newValue` is used, not `getItem`, which may still return the older text: `SettingsStorage`'s
  `onExternalChange` listener now receives that text (`undefined` when a storage cannot tell; the
  service then reads), and `SettingsStorage` has an optional `now()`.
- Result: changes to different settings from different windows are never lost, whatever the
  timing, as long as one window that knows the change stays open until another window's write
  reaches it (the window that wrote from an old copy repairs its own write when the other
  window's write reaches it, even after that other window has closed). Two changes to the same
  setting end with the same value in every window and in the store: the one with the later stamp,
  which is the later change by the computer's clock, and always the later one when the second
  window had already seen the first change. A window that opens while another's write is still on
  its way, and writes before it arrives, can still lose that write if the other window closes at
  once; the browser offers no way to wait for it.
- Stored format: the key `easy68k.settings.v1` and the shape of the settings are unchanged; the
  document gains the top-level key `stamps` (entry 27: now always written). A document without
  it (every document written so far) loads as before: its settings have no stamps until they are
  changed; one that is written while windows are open is entry 27. A version of the port from before this change keeps `stamps` as
  an unknown key and writes it back unchanged; its own changes then win over the stamps of the
  same settings when the two meet. `stamps` never appears in `SettingsService.get()`.
- Check: `service.test.ts` drives several services on a storage whose writes reach other windows
  only when the test delivers them (the failing interleaving of the shell check, one setting
  changed twice, a window that closes, the layout, 300 random interleavings of three windows).
  `check-shell.mjs` repeats the in-turn sequence ten times and waits until both pages store and
  show every value; it then blocks page B while page A writes, so that B certainly writes from an
  old copy (the check counts the rounds in which the page clocks show that B read after A's write
  and saw the old value; ~~and wants two~~ superseded by entry 27: it reports how often that
  happened and passes with a note when the browser never let B read an old copy), and requires
  that nothing is lost and, for one setting
  changed by both, that B's later value ends in both pages. The old service fails these rounds
  in both browsers every time.
- Proposed text for 3.8.6 rule 2: "**Settings.** A page may read another page's `localStorage`
  write late, so re-reading before a write is not enough. Each changed setting carries a stamp
  (time, window) in the document's `stamps` table; every document a window reads or receives with
  a `storage` event (its `newValue`) is merged with what the window knows, setting by setting, the
  later stamp winning, and a window whose newer setting is missing from another window's write
  writes the merged document again, after a short pause and only if no other window has done so
  meanwhile. A document without a `stamps` table was written by something other than the port and
  replaces what the windows know; windows that take it in agree on the earliest time one of them
  took it in as its stamp (entries 27 and 28). Subscribers are notified; the `editor` and `sim`
  settings then take effect at once, while the panel layout of a window that is already open stays
  as it is."
- Proposed text for 3.10, replacing its last sentence: "`update()` reads the stored document
  again, applies the change and writes it; because a page may read another page's write late,
  each changed setting carries a stamp in the document's `stamps` table and every document a
  window reads or receives with a `storage` event is merged with what it knows, setting by
  setting, the later stamp winning (3.8.6 rule 2), so several windows share one set of settings
  without overwriting each other. A document without a `stamps` table (written by an older version
  or another tool) replaces the settings, and a setting missing from another window's write is put

### 27. Settings documents without stamps, and putting a setting back once (3.8.6 rule 2, 3.10; follows entry 26)

- Says: as entry 26 quotes; the design knows no stamps. Entry 26 as first made: a document
  without a `stamps` table loads as before, and a window whose newer setting is missing from
  another window's write writes the merged document back at once.
- Found, by review of entry 26: (1) a document without stamps that something other than the
  port writes while windows are open (the developer tools, an outside tool, a future import that
  writes the key) was silently undone: every window merged it with its own stamped settings,
  which won over a setting without a stamp, and wrote them back; before entry 26 such a write
  replaced the settings. (2) With several windows that all knew a setting another window's
  stale write lacked, each wrote it back, and each write-back sent an event to every other window:
  four pages making 48 parallel updates caused 395 writes (967 KB) in Chromium and 609 (1.49 MB)
  in WebKit, against 48 (about 98 KB) before entry 26. Nothing was lost, and it settled.
- Does: (1) the port now always writes the `stamps` table, `{}` before any change, so a stored
  JSON object without one was written by something else. When a window receives such a document
  by a `storage` event, or reads one in `update()` that it has not taken in before, it replaces
  what the window knows, as every write did before entry 26, and the settings it changed are
  stamped then, by that window, so that they count as newer than what any window knew: the page
  whose own storage was written gets no event and hears of it only through another window's next
  write, and a window that has not heard of it yet may still write the older values. A document
  without stamps that the window has already taken in (the one it found at start) and that its
  copy of the storage still shows is merged as before, so it cannot undo a newer write. A stored
  text that is not JSON is still merged (the windows keep their settings). (2) A window puts a
  missing setting back after a short pause, 10 to 50 ms and different in each window
  (`SettingsStorage.defer`, optional, given by `state/browser.ts`; without it the write-back is
  made at once, as before), and only if the newest document it knows to be stored still lacks
  something: of several windows that would repair the same write, the first writes and the others
  normally hear of it before their pause ends. An `update()` in the window writes at once and
  cancels the waiting write-back; a page being hidden (`pagehide`) or a service being disposed
  makes it at once.
- Result: an outside document without stamps reaches every window, as before entry 26. Where a
  window changes a setting while such a document is still on its way to it, the outside
  document's value for that setting wins in the end (it is stamped when it arrives); before entry
  26 the outcome of that case depended on the order of writes too. An older version of the port
  that never saw a `stamps` table writes documents without one, and they now replace the settings
  of the open windows, as before entry 26; an older version that read a document with stamps keeps
  the table. The guarantee of entry 26 now needs the window that knows a missing setting to stay
  open for the pause after it hears of the stale write, or to be hidden or closed normally (which
  runs the pause's task at once). Fewer write-backs with several windows; with one writer there
  are none, as before.
- Check: `service.test.ts` (an outside document reaches every window, also the page in which it
  was written, and is not undone by a window that has not heard of it; an old document still in a
  window's copy does not undo a newer write; the table is written empty; of three windows that
  could repair a stale write only the first writes; a disposed window and an `update()` make the
  waiting write-back at once). The random test of three windows now takes the expected values from
  the order of its own updates, the clock moving on before each, not from the stamps the service
  writes. `services.test.ts` tests `defer` (pause, `pagehide`, cancel). `check-shell.mjs` writes a
  document without stamps into page A's storage and requires both pages to show and store it after
  page B's next update. Its out-of-date-copy rounds no longer fail when the browser never lets page
  B read an old copy (pages that share one copy of the storage would): they then pass with a note
  that the race was not produced; what must hold is that nothing is lost. They try at most four

### 28. A document without stamps counts from the first window that took it in (3.8.6 rule 2; follows entry 27)

- Found, by review of entry 27 (`docs/requests/W3-settings-followups.md`, item 1): each window
  stamped an outside document (one without a `stamps` table) with the time at which IT received
  it. A window that received it late held a later stamp than a change a person had made meanwhile
  in a window that already had it, and its write-back restored the outside value. The reviewer's
  case: the outside document sets the font size to 21 at 2000; window B receives it at 2010; the
  person sets 30 in B at 2020; window A receives the outside document at 2030 and then B's write;
  every window and the store ended with 21.
- Does: the stamps a window gives an outside document name as writer `outside:` followed by a
  32-bit FNV-1a hash of the document's text (`outsideWriter()`), the same in every window, and the
  window also keeps that stamp in the stamp table under `~outside` (`OUTSIDE_MARK`; no path of a
  real setting can be written so, because a `~` in a key is written `~0` or `~1`). The mark goes
  out with every write of that window, also after the settings the document changed have been
  changed again. Whenever two stamp tables meet (`mergeStamped`), every stamp of an outside writer
  is first moved back to the earliest time either table holds for that writer
  (`alignOutsideStamps()`). So every window that took the document in ends with the time of the
  first window that took it in, which is never later than a change made after it in a window that
  had it. In the reviewer's case A first stamps 21 at 2030, and B's write, which carries the mark
  at 2010, moves that back to 2010; B's 30 at 2020 wins in both windows and in the store.
- Limits (as first made; entry 31 replaces the single mark by one mark per outside write and tells two writes of one text apart): one mark per window, the last outside document it took in. Of two outside documents
  written within a moment of each other, a window that takes in the older one late may learn its
  earlier time only from per-setting stamps that still name it. A change made in a window that had
  not yet received the outside document, after the document was written, can still lose to it;
  nobody can tell which came first in that case.
- Check: `service.test.ts`, the reviewer's case as written; the same with the late window being
  the page in which the document was written (it reads it from its own copy); three windows, where
  the third learns the earlier time only from the mark because B changed the setting again; and

### 33. One rule for documents without stamps, whenever a window opened (3.8.6 rule 2; gate I1 round 3; replaces the counting of entry 31)

- Found, by the independent review of gate I1 round 2 (major; probe
  `build/review-I1r2-shared-parts/probe/settings-probe.test.ts`, test 1): window A is open; at 2000
  an outside writer stores X (font size 21); window B opens now and finds X in its first read; at
  3000 A sets 30; at 4000 X is written again. Result `{a: 21, b: 30, store: 21}` after every write
  had arrived. B had never counted the X it found at start, so it named the second write as the
  first (`outside:<hash>`), the name under which A's write had already told it the time 2000, and
  kept its 30 from 3000. Entries 28 and 31 had grown case by case; this entry states the rule
  first and derives the code from it.
- **The rule.** An *outside document* is a stored JSON object without a `stamps` table: the port
  always writes the table, so only something else writes one (a tool, the developer tools, a
  version of the port from before stamps). Each such write is one event in the shared history,
  and every window gives it the same stamp: the writer `outside:<hash of its text>#<n>`, where n
  counts the writes of that text (the first is named without `#1`), and the time at which the
  first window took it in, never later than any change a window made after it had it. A window
  *takes in* a write exactly once, the first time it sees a document that differs from the last
  document it saw, wrote, or took in: in its first read when it opens, in a `storage` event, or,
  for a write made in its own page, which raises no event there, in its own copy when it reads
  before an update. An event whose text is the last one the window saw is not a new write. When it
  takes in an outside write, the window stamps every setting that write changed with
  `[now, writer]` and records the mark `~outside/<writer>` with the same stamp; a window that
  opens on an outside document records only the mark, since it has nothing older to replace. n is
  one more than the highest number the window knows for that text, and it knows a number from its
  own take-ins and from the writer of every stamp and mark in every stamped document it reads or
  receives. This gives every window the same n because a browser delivers the `storage` events of
  a page in the order of the writes, and changes the page's copy with the event (HTML, "Web
  storage", the broadcast of a change is a task on one task source): a stamp that reaches a window
  inside another window's document was written after the outside write it names, so the window
  has either taken that write in already or opened after it, and in both cases counts it. Times
  then agree as in entry 28: whenever two stamp tables meet, every stamp of one outside writer moves
  back to the earliest time either holds for it (`alignOutsideStamps`), and the marks travel with
  every write, so every window ends with the earliest take-in time. Since n is new to the window
  that takes the write in, it knows no stamp of that writer yet: its stamp is later than all it
  knows, and the outside document replaces every setting of the window, as the store does; the
  time moves back only when another window's stamps of the same write meet it.
- Checked on paper against every case of the three reviews (A, B, C windows; X the outside text;
  h its hash):
  1. Round 1, the reviewer's case (X at 2000; B takes it in at 2010 and sets 30 at 2020; A takes X

  2. Round 1, the late window is the page whose developer tools wrote X: A reads X from its own

  3. Round 1, three windows, C learns the time only from the mark: C takes X in late as `h`, B's
     write carries the mark: as case 1. Holds.
  4. Round 2, X written twice, A hears the second write first, B writes before hearing it: both
     count `h` from the first write, so both name the second `h#2`; B's later take-in moves to A's
     time through the mark. 21 everywhere. Holds. The same with B hearing A's write-back: under the
     order of delivery B hears the restore first; holds.
  5. Round 2, developer tools write X twice in one page: the second read shows X again after the
     window's own write, a different last document, so it is taken in as `h#2`. Holds.
  6. Round 2, the random interleavings: no case outside the rule; checked by running.
  7. Round 3, this review: B's first read is X, a take-in, so B counts `h` and records its mark; A's
     write at 3000 names `h` too (no change of count); the second X is `h#2` in both windows, at

  8. Round 3's own question, a window that opens after the second write of X and finds X itself: it
     counts X as `h` (it cannot know better), records only a mark, and stamps no setting; the first
     stamped document it receives carries `h` and `h#2` and raises its count to 2, so a third write
     is `h#3` as in every other window. Its wrong mark `h` is later than the true one and moves back
     to it, and it stamped no setting with it, so nothing changes. If the third write reaches it
     before any stamped document, it names it `h#2`; it takes the whole document, as the store
     holds it; its stamps later align down to the time of the true `h#2` and lose to the other
     windows' `h#3`, which carry the same values or later changes: the windows still agree. Holds
     for agreement.
  10. A window opens while another window, which has not yet received the latest outside write,
     has already written over it: the new window never sees that write, and a change it makes can
     lose to it in the windows that take it in late. This is entry 28's limit (a change made after

  9. Round 2's "window that hears another window before the outside document" (a test of entry 31

     reading of a stamp from another window. A page cannot tell the two apart.
