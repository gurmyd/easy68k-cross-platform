# Errata of M3 (tests and documents, version 1.1)

Where `docs/ARCHITECTURE-PLUS.md` P9 (and the task of M3) could not be followed exactly as written,
or where the code differs from it, and what M3 did. None of these entries changes the application.

## 1. A finding, repaired since: `Dock` did not put the Output panel back where it was docked (M1)

Status: seen in Chromium and WebKit on a production build of the tree as it was at 20:22 on
25 November; the same tests pass on every build made from 20:35 on (the files of `ui/dock` changed
in between). The tests stay, so that it cannot come back unseen. What was seen:

P9.2: "`Dock` (the panel goes back to the place it was docked at last; if that group is gone, to its
place in the default arrangement of P3.1.3)". The end-to-end test keeps that rule as written:
`tests/e2e/plus/arrange.spec.ts`, "Dock puts the Output panel back where it was docked: the whole
right column", and the last step of "a program that draws and waits for a key ...".

Smallest reproduction (Chromium and WebKit, production build, a fresh profile, 1400 by 900):
Simulator mode, `View > Lock Layout` (unchecked, so that the Output panel shows its tab), right click
on the tab `Output`, `Float`, then the window's `Dock`. Expected: the Output panel takes the whole
right column again (top 94, bottom 878, left 701 in that window). Seen: the Output panel is docked
beside the Messages panel at the bottom (top about 779), and the Listing takes the full width above
both. The Hardware panel, floated from the tool group and docked, does go back into the tool group
(that test passes), so the parked place of a panel that was alone in its column is what goes wrong
(erratum M1 entry 7 describes the rule: "next to which panel, on which side").

The two tests were not weakened for it.

## 2. `tools/check-guide-strings.mjs` also reads the toolbar table

The caption `Arrange Panels` and its two tool tips (P9.3) are constants of
`app/src/commands/tables/toolbars.ts` (`ARRANGE_BUTTON_TEXTS`, M2), not of a `texts.ts`: the toolbar
table is in `commands`, which may not import a feature. `features/layout/texts.ts` refers to them by
name, which the tool does not follow for a quote as a whole. The tool's `sourceFiles` therefore lists
`commands/tables/toolbars.ts` beside `commands/specs.ts`; the STAGE_TEXTS list is unchanged (its test
counts the `texts.ts` files). Without it, the guide's **Arrange Panels** failed the check.

## 3. Section 1.6 of the main document still names `N0.md` to `N8.md`

The task limits the edit of `docs/ARCHITECTURE.md` to rows of section 1.5. Section 1.6 says that the
differences of the stage of additions are in `docs/differences/N0.md` to `N8.md`; version 1.1 adds
`M1.md` and `M2.md`, which `tools/make-differences.mjs` now merges after N8. The sentence of 1.6 was
left as it is; the architect may add "and, for version 1.1, `M1.md` and `M2.md`".

## 4. The rows of section 1.5 and of the parity matrix

Two rows, one per kind of new command: `Float`, `Dock` (`app.layout.float`, `app.layout.dock`) and
`Layouts` > the four entries (`sim.view.layout.*`). The toolbar's `Arrange Panels` runs
`app.layout.lock` ("no new command", P9.3) and has no row of its own; the end-to-end test
"the toolbar's Arrange Panels is Lock Layout inverted ..." covers it, and the matrix need not name
it (the matrix's rule of untracked tests applies to `tests/e2e/sim` only).

## 5. The tip in a browser driven by a test

M2 made the tip appear in a driven browser (`navigator.webdriver`) only when the address carries
`?arrange-tip=1` (errata M2), so that no test of 1.0.0 meets it. The tip tests therefore open the
application, every reload and the second window with that query (`openWithTip`,
`ARRANGE_TIP_QUERY` in `tests/e2e/fixtures/plus.ts`); a reload without it would show no tip to the
driven browser alone and prove nothing about "never again after a reload".

## 8. A reload made at once after the start interrupts the simulator engine's fetch (WebKit)

In the first stability run (`--repeat-each=5`, WebKit), the three tip tests failed once each with
the page's console error `Simulator: The simulator engine could not be created: EngineLoadError:
... Importing a module script failed.` (or `Load failed.`): they navigated to `?arrange-tip=1`
right after the fixture had opened the application, while its simulator engine was still being
fetched. That is the test's doing, not the application's (a person does not reload within that
moment). The suite's reloads now go through `reopen` (`tests/e2e/fixtures/plus.ts`), which waits
for `simEngineLoaded` before it navigates: the browser's record of what the page fetched (Resource
Timing) names the simulator engine's three files (`sim68k*.mjs`, `sim68k-loader*.mjs`,
`sim68k*.wasm`) with their responses complete, and, in Simulator mode, the status bar's run state is
no longer `Loading` (the application's own signal that the start is over). Editor mode draws no
state of the simulator's start, hence the files. (Round 1 waited for Playwright's `networkidle`,
which is a quiet time of 500 ms, not a state; the verifier found that.) Other suites of 1.0.0 that
reload at once may meet the same in WebKit; none of them was changed.

## 10. A test of 1.0.0 changed: the View menu of the Simulator gains `Layouts` (P9.4, P9.5)

`tests/e2e/sim/menus.spec.ts`, "menu bar > View: the original's items in order, with this key map's
shortcuts, then the port's additions": its table `ADDED` names the port's additions of each menu
after the original's items. P9.4 adds the submenu `Layouts` to the Simulator's View menu, after
`Reset Layout` and a separator (M2, `commands/tables/sim-menu.ts`), so the test failed in both
browsers (found by M3's verifier, round 1; neither M2 nor M3 had changed it). The table now ends
`..., 'Reset Layout', 'Layouts'` and `AFTER_SEPARATOR` gains `Layouts: 'Reset Layout'`, so that the
separator before it is checked as those of the other additions are. A submenu is enabled in a
browser, which the test's enabled check expects of every addition but `Serial Ports...`. This is the
only test of 1.0.0 that M3 changed; it changes only because P9 changes what it tests.

## 11. Dragging a tab onto the toolbar floats its panel, also in WebKit

The verifier of round 1 saw no window after dragging the Hardware panel's tab onto the toolbar in
WebKit and could not confirm the guide's sentence "a tab dropped outside the panels (on the menus,
the toolbar or the status bar) makes its panel float there". Not reproduced: `check-dock.mjs --only
floating` passes "unlocked, a tab dropped on the toolbar (no docking target) floats" in Chromium and
WebKit, and the new end-to-end test "unlocked, a tab dragged onto the toolbar makes its panel float
there" (`arrange.spec.ts`) passes in both (three runs each). Both drag as a hand does: a small move
first, then on to the toolbar in steps; how the verifier's probe dragged is not known. The test also
checks "there": the window's left edge is 24 px left of where
the tab was let go and its top is the dock's top (moved into the bounds, errata M1 entry 8).

## 12. The scroll-backs of the Hardware panel taken out; the window's left edge required (CI run 45809923850)

`tests/e2e/plus/arrange.spec.ts` scrolled the Hardware panel back to its left edge before measuring
what is seen, in the tests "Floating Tools at 1366 by 768" and "P9.10 point 2", and not in the step
"Floating Tools" of "View > Layouts: each of the four arrangements ...", which failed on Ubuntu
(97.6 % of the displays seen). The cause was in the product (errata M1 entry 19: the window carried
the sideways offset the panel had in the narrow column of Side by Side, and WebKit's reveal of a
focused field's caret). The test no longer scrolls anything: a helper `hardwareSideways` reads the
panel's sideways offset after three frames, and the three places require it to be 0 before they
measure. Against a build without the repair this fails on Windows too (3 px in the step, 15 px in
WebKit at 1366 by 768); with it, the whole of `tests/e2e/plus` passes on Windows and in a Linux
container. No test of 1.0.0 changed.

The second and the third run on GitHub (45825817588, 45836792509) each failed the test "Floating
Tools at 1366 by 768" in WebKit on Ubuntu with an offset of 30, in the plain run and now and then in
the shards that repeat every test twenty times. The helper read the offset after three frames, a
frame being an animation frame or 100 ms without one. The trace of a failed test shows that the
helper took 313 ms: no animation frame came, the runner's browser did not update the screen for
about 0.85 s after the layout was applied, and what puts the window back waited for a screen update
(errata M1 entry 19, "Why a rule and not a time"): the read fell in between. `hardwareSideways` now
returns the offset once the page is at rest (the same
through ten screen updates in a row, at most 5 s): what stays on the screen. A window that stayed
scrolled, as before the repair, fails it on every machine. The test also makes the late focus
happen everywhere: the page gives the focus to a field the window cuts at its right, with no
action of a person; the panel reveals it at once; at rest the offset must be 0; after Shift+Tab and
Tab it must be more than 0 (a person's key ends the hold, the field is revealed).
