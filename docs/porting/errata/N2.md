# Errata of N2 (editor split and document tabs)

Where `docs/ARCHITECTURE-PLUS.md` (P3.1.4, P3.1.7, P5 N2) is silent or does not match what N2 found,
what the code does and why. No entry changes a text, a command, a key or anything a 68000 program
can observe.

## 1. Where the split commands reach the panes (`features/editor`)

- Says: P5 N2 puts the three commands "as functions on `PaneModel` and the layout setting" in
  `ui/editor/split.ts`, their handlers in `features/editor/index.ts` and `commands.ts`. It does not
  list `features/editor/editor-api.ts` (the `EditorActions` interface) or `ui/editor/session.ts`.
- Does: neither of those two files changed. `split.ts` has the pure rule (`splitEditor`), the
  enabled rule (`splitEnabled`), `runSplit` on a `PaneModel` and the setting, and
  `splitActionsOf(ctx)`, which reaches the window's `PaneModel` through `editorSession(ctx)` and
  writes `AppSettings.layout.editorPanes` itself. `editorCommands(editorFor, splitFor?)` takes the
  split operations as a second, optional parameter (absent: the three commands are disabled, so the
  existing tests that pass a fake `EditorActions` are unchanged); `features/editor/index.ts` passes
  `splitActionsOf` (the layer rule lets `features/editor/` import `ui/editor/`).
- `Split Editor Right` from one pane is `tilePanes` and the layout `vertical`, exactly as E2's
  `setLayout('vertical')`; the setting is written once, only when it changes.

## 2. A split from two panes may leave a pane empty

P3.1.4: with two panes, Split moves the active document to the other pane. When every other
document is in that other pane already (for example two documents after `Split Editor Right`, then
`Split Editor Down`), the pane the document left is empty and shows E2's text `No document in this
pane. New and Open put a document here after a click into it.` This is what the rule says; N2 does
not add a rule of its own. `Close Split` (Cascade) gathers everything again.

## 3. `Earlier Versions...` and E2's `Move to the Other Pane`

P3.6 puts `Earlier Versions...` at the "end of the editor's context menu below a separator"; P5 N2
puts it in `EDITOR_CONTEXT_MENU` below a separator after `Reload File`. E2's own addition `Move to
the Other &Pane` (docs/differences/E2.md) is appended after that list while two panes are shown, so
with two panes `Earlier Versions...` is the last item of `EDITOR_CONTEXT_MENU` but not of the menu.
N2 followed P5 N2 and did not move E2's item. The item runs `ed.file.history` without an argument
(the active document, P3.6); it is disabled until N4's handler exists.

## 4. Dragging: what the data carries, and browsers that drop custom types

- `Tabs`' `drag` property is exactly P5 N2's (exported as the type `TabsDrag` from `Tabs.tsx`;
  `ui/components/index.ts`, W2's, is not in N2's list, so it is not re-exported there; users write
  `TabsProps['drag']`). Without it, nothing is `draggable` and the strip handles no drag event.
- The data of a document tab is `{"window": <token>, "id": <document id>}` (JSON) under
  `application/x-e68-document`: document ids are per window, so a tab dragged from a second
  application window must not move a document of this one. The editor also keeps, per window, the
  document whose tab is being dragged (set at `dragstart`); a pane accepts a drop only while that is
  set and the document is in the other pane, so its own pane and a drag from elsewhere (a file,
  another window) show no drop place.
- Found: Playwright's WebKit on Windows keeps only `text/plain`, `text/uri-list` and `text/html`
  of a drag's data (`getData` of a custom type returns `''` and `types` does not list it). `Tabs`
  therefore remembers the drag its own page started (type and data) and uses it when the browser
  dropped the type; `text/plain` is deliberately not set, because a drop of text into a document's
  editor would insert it. Safari itself is untried (no Mac here).
- A drop moves the document (`moveToOtherPane`, through `moveToPane`, which changes nothing when
  the document is in the target pane already, so a drop that reaches the strip and the pane around
  it moves once). Like the tab menu's `Move to the Other Pane`, it does not change the active
  document.

## 5. Playwright's WebKit loses the first press after a drag (checks only)

In Playwright's WebKit on Windows the first mouse press after an HTML drag dispatches no
`pointerdown`. The menu bar opens on `pointerdown`, and the kit's "last pressed control"
(`focus.ts`, used to give the focus back after a dialog opened by a click in Safari) is set on it.
`check-editor.mjs` and `check-gallery.mjs` therefore press once on a place that is not a control
after each drag (the window's status bar; the gallery example's panel text). Nothing in the
application works around it; whether Safari behaves so is untried.

## 6. Where the tool-tip function is tested

P5 N2 gives N2 one new file and its tests (`ui/editor/split.ts`). The tab's tool-tip
(`documentTabTitle`, with `placeLabelsOf`) is in `EditorPane.tsx`, where the tab is drawn, and is
tested in `split.test.ts`, with the context menu list, rather than in a new test file N2 does not
own. A document without a path keeps its name as tool-tip, as before.

## 8. `TabsDrag.positional` (P5 N2 lists `type`, `data`, `onDropAt`)

The gate's reviewer found that the strip marked the tab under a drag ("the dropped tab goes here"),
while the editor ignores that place: a dropped document takes its place in the other pane by the
order of opening, as `Move to the Other Pane` does, so that the Window menu's list and the panes
agree. `TabsDrag` gains one optional member, `positional` (default true, as the gallery's example
uses it): `false` makes the strip take a drop as a whole, outline the strip, mark no tab and call
`onDropAt(null, data)`. `EditorPane.tsx` passes `positional: false`. `check-editor.mjs` checks that
while a tab is dragged over a tab of the other pane the strip is outlined and no tab is marked.

## 9. The strip's memory of a page's drag is cleared wherever the drag ends

`Tabs.tsx` keeps the drag this page started (for browsers that drop custom types from the drag
data, entry 4). It was cleared by the strip's own `drop` and the tab's `dragend` only; a drop on the
other pane's body (EditorArea's) unmounts the dragged tab, whose `dragend` then never runs, so the
drag stayed remembered. The tab now registers, at `dragstart`, capturing `drop` and `dragend`
listeners on the window that forget the drag once the event has been handled (and remove
themselves). `currentTabDrag()` reads it; `check-editor.mjs` checks it is null after a drop on a
pane's body.
