## 2. Contract: the editor cannot reach a document's EditorState (3.9.1)

Status: resolved in gate I1 (errata/W1.md 11.2 and 11.3). The proposed `DocumentEditorAccess` was
declined; 3.9.1 now says the editor reaches the registry with `documentRegistryOf(ctx.documents)` of
`core/documents`, and the contract has `DocumentService.update?(id, patch)`. Since round 2,
`document-link.ts` does exactly that: when `ctx.documents` is E1's `DocumentManager` it works on
`documentRegistryOf(ctx.documents)` and sets Insert/Replace with `ctx.documents.update?.(id, {
insertMode })`; any other service (the wave-0 stub, test doubles) gets the local states of case 3
below. The run-time probing of `ctx.documents.editor` and `.registry` is gone. The text below is the
history.

- Says: 3.9.1, "One `EditorState` per document lives in `core/documents/registry.ts`; the editor
  component (E2) attaches a view to it." `DocumentService` (contracts/documents.ts) has only
  `text(id): string`: no way to read the state, to store the editor's transactions into it (so that
  Save, Assemble and drafts see the edits), to hear that Reload replaced it, or to set the
  per-document `insertMode`.
- Does: `ui/editor/document-link.ts`, a local adapter, which tries three things in order:
  1. the object proposed below, as `ctx.documents.editor`;
  2. a registry of the shape E1's wave-1 `DocumentManager` exposes (`ctx.documents.registry` with
     `state(id)`, `apply(id, tr)`, `subscribe(listener)` with `updated` / `replaced` events, and
     `ctx.documents.update(id, { insertMode })`), adapted to the same object. Nothing is imported
     from `core/documents/`; the shape is checked at run time. With it, the text lives only in E1's
     registry and Save, Assemble and drafts read what the editor wrote (seen working in the browser
     check against the tree of this wave);
  3. otherwise (the wave-0 stub) the link keeps the states itself, created from `text(id)`, with its
     own Modified (the text compared with the text it started from) and Insert/Replace; the editor
     then works fully, but no other service sees its edits.
  An outside change (an `updated` event for a transaction the editor did not make, e.g. E1's
  `setExtensions`, or `replaced` on Reload) is followed by the view; if the new state has lost the
  editor's compartment, the view adds it again.
- Proposed for `contracts/documents.ts` (E1 implements it; E2 already uses it when present):

  ```ts
  export interface DocumentEditorAccess {
    getState(id: string): EditorState;                    // the document's state (3.9.1)
    apply(id: string, tr: Transaction): void;             // store tr.state, bump revision, set modified
    subscribe(id: string, listener: () => void): () => void;   // the state was replaced elsewhere (Reload)
    setInsertMode(id: string, insertMode: boolean): void; // DocumentState.insertMode
  }
  export interface DocumentService { ...; readonly editor?: DocumentEditorAccess; }
  ```

  `EditorState` and `Transaction` would need structural stand-ins in the contracts, as `Extension`
  has (errata W1.md entry 2), or the access object could live in `core/documents/` with only its
  presence in the contract. Rules E2 relies on: `apply` is called with every transaction of the view,
  in order, including reconfigurations (no text change); E1 must not call the `subscribe` listeners
  for transactions that came through `apply`. The editor adds its configuration to a state it gets
  (one compartment, `editorCompartment` in `ui/editor/extensions.ts`), so E1 should not add
  `history()` itself; a second copy would be harmless (same extension object).

## 3. Undo granularity: 20.3 against note 5

- Says: editor-ui §20.3, "Undo reverses single typed characters one at a time". Note 5 and the row
  "Undo/redo, unlimited" of 1.3.3: "Standard editor history (grouped typing, redo cleared by a new
  edit, saved state tracked)".
- Does: note 5. Typing is grouped by CodeMirror's history (500 ms); Paste, Cut, a Tab press,
  Comment, Uncomment, Indent, Outdent and the auto-indent fill are single steps each
  (`isolateHistory`), Redo is Ctrl+Alt+Z (and Ctrl+Z / Shift+Cmd+Z in the editor). The transaction
  tests of `editing.test.ts` check grouping instead of "one at a time".

## 4. Shift+Tab (note 12) in detail

- Says: note 12, "Shift+Tab deletes the blanks before the caret back to the previous stop".
  Silent about Real Tabs on (editor-ui §8.2: UNVERIFIED, probably a tab character), about tab
  characters before the caret, and about a selection.
- Does: the same rule with Real Tabs on and off. Only blanks (U+0020) are deleted, never a tab
  character or text; the previous stop is that of the document's model (Assembly 44 > 20 > 12 > 0,
  multiples of the fixed size beyond 44). With a selection the caret is its end and the selection is
  dropped, as for Tab. One undo step.

## 5. Tab key details the documents leave open

- The column Tab works from is the TRUE visual column (tabs before the caret expanded with the
  document's stops), the column the status bar now shows (19.3, note 17). The original used its
  status-bar value, which counted tab characters and used the global tab size (§7.2 quirks a, b).
  The difference shows only on lines that already contain tab characters.
- Fixed tabs with a tab size that is not a positive integer (possible only through a hand-edited
  trailer): Tab inserts nothing, as in the original (§8.2); tab characters are displayed with
  size 8 (§8.3). Assembly tabs beyond 44 use the same fallback 8 for their stops.
- "With a selection the blanks go in at the selection's end" (2.4): the end is the larger offset,
  whichever way the selection was made.

## 6. Menus re-read "enabled" only when the store changes (3.12.2)

Status: the store update described here is now the stated rule of the contract (errata/W1.md 11.2,
`CommandHandler.enabled`); `CommandRegistry.invalidate()` was declined. Nothing to change in E2.

- Says: `CommandHandler.enabled(state, ctx)`; the shell resolves menus and toolbars in a store
  selector (W3's `use-commands.ts`). Undo, Redo, Cut and Copy depend on the editor's history and
  selection, and Indent/Outdent/Insert on the editor's focus; none of these is in `AppState`.
- Does: the editor session announces a change of any of them (undo possible, redo possible,
  selection empty, focused document) with `ctx.store.setState(s => ({ ...s }))`, a new state object
  with the same contents, at most once per change of these facts. Selectors re-run; nothing else
  changes. A text field's own selection (the Find box) is not tracked: while a field is the target,
  Cut and Copy count as enabled and do nothing on an empty selection.
- For W3/W1: a `CommandRegistry.invalidate()` (or a revision counter in `AppState`) would say this
  without a dummy update.

## 7. Comment / Indent: the selection afterwards

- Says: note 6, "act on the caret line when nothing is selected; undo is correct. Otherwise
  editor-ui §8.5 exactly"; §8.5: "the selection starts at the same character offset as before and
  its length is adjusted by the number of characters added or removed".
- Does: with a selection exactly that (anchor = old start, head = start + old length +- n). Without

## 8. Two panes: which document goes where (2.2, note 9)

- Says: "With `Tile Horizontally` or `Tile Vertically` the area holds two such stacks; a new
  document opens in the active pane." Silent about what the second pane shows when it is created.
- Does: each document is in exactly one pane. When tiling from one pane with two or more documents,
  the active document moves to the second pane and the first pane shows the document opened last
  of the others; with one document the second pane is empty and says so ("No document in this pane.
  New and Open put a document here after a click into it."). A click into a pane makes it the
  active pane. `Cascade` shows every document as a tab of one pane again (pane membership is kept
  for the next Tile). The tab context menu offers `Move to the Other &Pane` while two panes are
  shown (an addition, docs/differences/E2.md). The size of the two panes can be dragged; it is not
  stored (`AppSettings.layout.splits` has no key for it).
- Window commands: Cascade, Tile Horizontally and Tile Vertically are enabled while a document is
  open (the VCL window actions are enabled while a child window exists); their handlers also answer
  `checked` with the current layout, which a menu shows only if W3 makes them check items.

## 10. The editor's key map

- Undo (Ctrl/Cmd+Z), Redo (Shift+Cmd+Z, Ctrl+Shift+Z) and Select All are bound in CodeMirror's key
  map (errata W3.md entry 1). Ctrl+Y, which a stock CodeMirror binds to Redo on Windows, is not bound:
  the original has no such key.
- Esc followed by Tab moves the focus out of the editor (CodeMirror's tab focus mode), so that
  keyboard users are not trapped by WantTabs; Esc has no other meaning in the original editor.
- Enter with any modifiers (every combination of Ctrl, Alt, Meta and Shift) inserts a plain line
  break followed by the auto indent (§5.2 rule 11). Alt+Enter is Simulator mode's Full Screen; in
  Editor mode it reaches the editor.
- Ctrl/Cmd+X and Ctrl/Cmd+C with no selection do nothing: CodeMirror would cut or copy the whole
  caret line, which the original edit control never does (the Edit menu disables both without a
  selection, §2.2 rows 3-4). A `cut` / `copy` handler cancels the event when every range is empty.
- The status-bar position is the end of the selection (`range.to`, §7.2; VCL's `CaretPos` reads
  `EM_EXGETSEL`'s `cpMax`), whichever direction the selection was made in, the same position the
  Tab key works from.
- Ctrl+Backspace, Ctrl+Delete, Ctrl+E and the Ctrl+Shift keys that the original swallows work as in
  a standard editor (note 13). Ctrl+Insert does not flip the Insert/Replace indicator (19.3).

## 13. macOS: Ctrl+Z, A, X, C and V in the editor (rule K2)

- Says: rule K2 (1.3), "On macOS every `Ctrl+letter` shortcut works with Cmd or Ctrl"; the key
  table (`commands/tables/keys.ts`) gives Undo, Cut, Copy, Paste and Select All the chords Cmd+Z, X,
  C, V, A and Ctrl+Z, X, C, V, A on macOS. The dispatcher leaves every one of these to the focused
  editor (TEXT_EDITING_COMMANDS, errata/W3.md entry 1), where "the editor component binds undo,
  redo and select-all in its own key map" and the browser does cut, copy and paste.
- Found: the browser of a Mac acts on the Cmd forms only. Ctrl+C and Ctrl+X do nothing there,
  Ctrl+V pages down, Ctrl+A moves to the start of the paragraph, and CodeMirror's `Mod-z` / `Mod-a`
  are Cmd on a Mac. So on macOS the Ctrl forms of K2 did nothing in the editor (or moved the caret).
  The browser check did not see this: it pretended to be Windows on every system and pressed Ctrl.
  On the macOS runner of CI it failed for that reason ("Ctrl+C and Ctrl+X with a selection copy and
  cut it", clipboard empty) - a Windows key map on a Mac is a combination no user has, and the
  check would equally have passed an editor that does not copy with a Mac's own keys.
- Does: the editor's key map binds Ctrl-z (undo), Ctrl-a (select all), Ctrl-x, Ctrl-c (cut and copy
  through `execCommand`, which the browser allows during the key press, with the Clipboard API as
  fallback) and Ctrl-v (as Paste from the menu, note 45: natively in the desktop app; in a browser
  the page asks for the clipboard and, when refused, shows `Press Cmd+V to paste`), on macOS only
  (CodeMirror's `mac` field; elsewhere Ctrl is the platform's own key). Without a selection Ctrl+X
  and Ctrl+C do nothing, as in entry 10. The unit test reads the chord table, so a Ctrl chord added
  there for a text-editing command fails the test until the editor binds it.
- The browser check now gives the page the key map of the system it runs on (macOS on a Mac,
  Windows elsewhere), reads every chord it presses from the application's chord table
  (`chordsOn()` in the page) and presses every chord the table gives a command: on a Mac Cmd+C and
  Ctrl+C, Cmd+/ and Ctrl+Option+C, Cmd+Z and Ctrl+Z, Ctrl+Shift+I for Insert/Replace, and so on;
  keyboard paste with each paste chord in Chromium with clipboard permission. `--keys mac|windows`
  overrides the choice for diagnosis; native clipboard keys of the other system then fail by design.
- Outside the editor the same holds for plain text fields (a dialog's input, the Find box): the
  dispatcher leaves Ctrl+X/C/V/A/Z to them and a Mac's browser does not treat the Ctrl forms as
  editing keys. That is the dispatcher's part (W3), reported to the shell engineer.

- Status (gate I1, round 3): proven on the macOS runner. CI run 44919519853 (commit c4d3dfa),
  browser-checks (macos-latest, interface), Editor check: "140 of 140 checks passed" with the macOS
  key map, among them Cmd+C/X and Ctrl+C/X copy and cut, Cmd+A and Ctrl+A, Cmd+Z and Ctrl+Z,
  Cmd+V and Ctrl+V keyboard paste (Chromium) and the toast "Press Cmd+V to paste", in Chromium and
  WebKit. Ubuntu and Windows: 122 of 122. Round 3 also made a clipboard key without the clipboard
  functions count as handled (it does nothing), so that Ctrl+V can never fall through to
  standardKeymap's emacs-style page down on a Mac (review of round 2, minor defect).

## 15. Gate I2 round 1: a selection made by code survives `focusPanel(ctx, 'editor')`

- Found (E6's report and review): `focusPanel` called `element.focus()` on CodeMirror's content
  element. The browser then restored its own earlier DOM caret, CodeMirror read it back as a
  `select` transaction, and a selection made just before (Find's match, a jump to a message's line)
  was undone. E6 worked around it with a 400 ms guard in `features/find/model.ts`.
- Does: W3's `state/panels.ts` now sends `PANEL_FOCUS_EVENT` (cancelable) to the element first;
  `DocumentEditor.tsx` cancels it and calls `view.focus()`, which writes the state's selection into
  the page. `check-editor.mjs` ("focusPanel('editor') keeps a selection made while the focus was
  elsewhere") selects [6, 11] with the focus on the toolbar, calls `focusPanel`, and requires
  [6, 11] with the focus in the editor. E6 can drop its guard (and with it the review's defect that
  an arrow key within 0.4 s of a match is undone).

## 16. The caret jumped to the start after a dialog on a slow machine (2.10; X1's macOS failure)

- Found: X1's test "Undo reverses typing, a paste and a comment ..." failed once on GitHub's macOS
  runner in Chromium, and DOC1 saw it fail in a Debian container with `" PASTEDbase"` where
  `"base PASTED"` was expected. The question was whether a paste can arrive as two undo steps. It
  cannot: the paste landed at the start of the line. After Save As the dialog service gives the
  focus back to the content element with `element.focus()`; Chromium first moves the page's
  selection to the start of that element, and CodeMirror undoes that move only when the
  `selectionchange` arrives within 200 ms of the focus (`@codemirror/view` 6.43,
  `DOMObserver.readSelectionRange`, `lastFocusTime > Date.now() - 200`). On a slow machine it
  arrives later and the caret went to line 1: a student who saved with Save As and went on typing
  or pasted would have written at the top of the file. Reproduced on this PC with the CPU slowed 12
  to 26 times through the DevTools protocol: 7 of 8 runs; never at normal speed (12 of 12 runs).
- Does: `focus-caret.ts` (in `baseExtensions`): on a focus of the content element that no pointer
  press gave (none within the last second), the view dispatches its own selection at once, inside
  the focus event; the update writes it to the page before the browser's `selectionchange` is
  read, and CodeMirror then sees no change. A click still places the caret. With the repair 8 of 8
  slowed runs keep the caret. Entry 15 repaired the same effect for `focusPanel` only; this covers
  every way the focus comes back (dialogs, Tab).
- Tested: `tests/e2e/editor/editing.spec.ts`, "after Save As on a slow machine the caret stays where
  it was" (Chromium, CPU slowed 16 times; X1's), and `focus-caret.test.ts` for the pointer rule.
