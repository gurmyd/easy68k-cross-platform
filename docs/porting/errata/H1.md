### 9. The panel attaches nothing to the page frame

- Says: 2.7: the pages are shown in a sandboxed frame "(no scripts)"; nothing about links or keys
  inside it.
- Found: the frame is a separate document, so the application's key dispatcher does not see its
  keys, and WebKit (Safari) refuses to run an event listener on the document of a frame that has no
  scripts: it logs "Blocked script execution ... the document's frame is sandboxed" for every event.
  Chromium runs such listeners. To behave the same in every browser the panel attaches nothing to the
  frame's document.
- Does: the frame is `sandbox="allow-same-origin allow-popups allow-popups-to-escape-sandbox"`.
  `allow-same-origin` lets the panel read the frame's address and title when it has loaded;
  `allow-popups` lets a link with `target="_blank"` open a new tab, which is how the original's links to
  the web already work. A link to another page navigates the frame by itself; the controller notices
  the load (`noteLoaded`) and records the page as a new history entry, so Back and Forward work.
  Consequences: Escape pressed while the page itself has the focus does not close the drawer (it does
  from the toolbar, the tree and the filter); Ctrl+C copies text from the page as the browser does; the
  browser's own Back button moves the frame back like any in-page navigation.

### 10. Four links get `target="_blank"`

- Says: "keep their content byte for byte except for what the entry tells you to rewrite".
- Found: three web addresses (`excode.htm`, `quickStart.htm`, the GPL page) and the link to the Quick
  Reference PDF have no `target`; the original's other web links (`main.htm`, `credits.htm`, ...) do. A
  PDF or another site cannot be shown in the sandboxed frame, so the import adds `target="_blank"` to
  these four anchors (and to any anchor of that kind that has none). The count is in
  `manifest.json` (`blankTargetsAdded: 4`); a test checks that every such link has a target.
- Desktop (DV2): a link with `target="_blank"` asks Electron for a new window. The main process must
  answer it with `setWindowOpenHandler`: send `http:` and `https:` addresses to the system's browser
  (`shell.openExternal`, allow-listed as `platform.openExternal` is) and deny everything else; a
  PDF is a file of the app and is shown by the `help` window or handed to the system.

### 11. Help offline in WebKit: `allow-scripts` there, and no script in any help page (third round before I3)

- Says: ARCHITECTURE.md 7.6 and 2.7: the help pages are shown in a frame sandboxed without scripts
  (entry 9). 6.9 item 7: the offline test passes.
- Found (second round, `docs/requests/H1-help-offline-webkit.md`): WebKit hands the navigation of a
  frame sandboxed without `allow-scripts` to no service worker; online the page comes from the
  network, offline the frame stays empty ("WebKit encountered an internal error"). With
  `allow-scripts`, and in Chromium with any sandbox, the worker answers. The architect took option 1
  of the request, with limits a to e; all are done:
- **a. Only where it is needed.** `core/help/engine.ts`: `engineOf(navigator.vendor)` is the
  application's one engine rule (moved from `features/files/storage-notice.ts`, which re-exports
  it, so the Files panel's storage notice and the Help frame use the same function; core, because
  both features may import core and neither the other, 3.1), and
  `helpFrameSandbox({ platform, engine, controlled })` gives
  `allow-same-origin allow-scripts allow-popups allow-popups-to-escape-sandbox` only for the web app
  in WebKit while a service worker controls the page, and
  `allow-same-origin allow-popups allow-popups-to-escape-sandbox`, exactly as before, everywhere
  else (Chromium, the desktop app, and WebKit without a controlling worker: a first visit, which
  loads the frame from the network as it always did). "Controlled" is a further narrowing of
  "where the engine is WebKit": only then can Help be offline, and only then does the worker's rule
  of c keep the rest of the site out of the frame, so there is no state in which the frame may run
  scripts and the rule does not hold. `HelpPanel.tsx` decides it once, when the frame is created.
- **b. No script runs in a help page.** `tools/import-help.mjs` writes
  `<meta http-equiv="Content-Security-Policy" content="script-src 'none'">` (`HELP_PAGE_POLICY`) as
  the first element of the head of every page it imports, the generated Differences page included
  (`insertPolicy`: right after `<head>`; in the two pages without a head tag, `excode.htm` and
  `Quick Reference.htm`, first in the document, where the parser opens the head). After its own
  changes it refuses a page that holds a script element, an inline event handler attribute, a
  `javascript:` address (character references read, also inside a style), a refresh, or an address
  with another scheme than a web or mail address (`pageRefusals`): it stops with exit code 1 and
  `import-help: <file>: refused, the page holds ...`. The tree was regenerated: compared byte for
  byte with the tree of 4bd5f68, each of the 161 pages differs by exactly that element (and its line
  end), the 80 other files are identical, and `README.txt` gains one bullet that says so. The test
  that runs in CI is H1's unit test `core/help/imported.test.ts` (part of `npm test`): for every
  `.htm` and `.html` below `app/public/help`, from the folder's own listing, the policy is the
  first element of the head (only the doctype, comments, white space and the html and head tags may
  come before it), it is there once, and the page holds no script element, no event handler
  attribute and no `javascript:`; and `pageRefusals` finds nothing in any page.
  `core/help/import.test.ts` tests `insertPolicy`, `pageRefusals` and `addressKind` and runs the
  script on a scratch source with a bad page (exit 1, the file named).
- **c. The frame can show nothing but Help.** The service worker answers a navigation whose
  destination is a frame only below `help/` and every other one with an error (DV1 erratum 15).
  `import-help.mjs` refuses a page with a link (any `href`, `src`, `background`, `action` and
  the like) to an address of the site outside the help folder: `..` above the folder, a
  root-relative `/...` or `\\...` (`addressKind` 'outside'); links to other sites stay as they are
  (they have `target="_blank"`, entry 10). None of the original's pages has one. Proved in both
  browsers by `check-pwa.mjs` (a help page with links to the application's `index.html` and to
  `../../?open=...`, clicked in the Help frame of a controlled page: the application is not loaded in
  the frame; a link to another help page still works) and, as evidence, by a probe with the rule
  cut out of the worker, in which WebKit ran the whole application inside the Help frame.
  The frame's `onLoad` now also survives an error page, whose document is not of this origin
  (reading its address threw a `SecurityError` into the console before).
- **d. The expected failure is gone.** `tests/e2e/app/offline.spec.ts` (X1 erratum 15) passes in
  both browsers against the production build with the network cut: the introduction page, a link
  from Quick Start to Simulator I/O, and Help > Differences from EASy68K.
- **e.** One correction note under ARCHITECTURE.md 7.6; the request's status line; MANUAL-TEST-MAC
  W1 asks for Help, its links and the Differences page with Wi-Fi off in Safari itself (Playwright's
  WebKit is not Safari); the known limitation "Help does not work offline in WebKit" is removed from
  part 5 of DIFFERENCES.md, which is written in that file itself (not from a fragment).
- What remains: a same-origin page that does not carry the policy can still be reached by the
  frame only where no worker answers (then the frame has no `allow-scripts`, a).

### 12. The import reads tags as the HTML tokenizer does, and refuses more (round 4 before I3)

- Defects (independent review of the third round, `build/gate3/round3-result.json`, review.defects
  1 and 2): `pageRefusals` and `imported.test.ts` looked for an event handler with
  `/\son[a-z]+\s*=/i`, which needs white space before the name, so `<img src="x.gif"/onerror=...>`,
  `<body/onload=...>` and `<a href="x.htm"onclick=...>` were imported (each is a real handler:
  checked in Chromium and WebKit, `build/repairs-r4/forms.mjs`); and `addressKind` resolved
  `..%2Findex.html` as a file of the help folder, which a server that decodes `%2F` serves as the
  application's page (the service worker's half: DV1 entry 16).
- `tools/import-help.mjs`:
  - `readTag` reads a tag as the tokenizer's states do: a name ends at white space, `/`, `>` or `=`;
    a new attribute name starts after white space, after a `/` and right after a closing quote;
    quoted values run to the same quote (a `>` in them ends nothing), unquoted ones to white space or
    `>`. `tagsOf` reads one tag from every `<` followed by a letter (or `/` and a letter) wherever
    it stands, in comments and in style text too, because a browser ends a comment at `--!>` as
    well and reads no comment in a style element: every tag a browser reads is among them. As written
    in the task, `<img src=x.gif/onerror=...>` (unquoted) is one `src` value for a browser, not a
    handler; it is refused all the same (`HANDLER_ANYWHERE`: `on...=` after white space, a slash or
    a quote anywhere in a tag), since the import cannot tell what a page meant.
  - Refused now as well, each with a test in `import.test.ts`: the elements `script`, `svg`,
    `math`, `iframe`, `frame`, `frameset`, `object`, `embed`, `applet`, `portal`, `fencedframe`,
    `form`, `isindex`; a `srcdoc` attribute; a `base` element other than `<base target="_self">`
    (eight pages of the original have exactly that, which keeps links in the frame); a `meta`
    whose `http-equiv` is not `content-type`, `content-language` or `content-security-policy`
    (refresh above all, character references read); `javascript:` and `vbscript:` anywhere in a
    tag after character references (numeric ones, and named ones such as `&Tab;`, `&NewLine;`,
    `&colon;`) and tabs and line ends are read; in an address attribute (`href`, `src`, `srcset`,
    `action`, `formaction`, `data`, `ping`, `xlink:href`, ... `ADDRESS_ATTRIBUTES`) a scheme that is
    not a web or mail address (`data:`, `blob:`, `file:` in any letter case), a named character
    reference outside the short list the import reads, an escaped slash, backslash, dot or percent
    sign (`%2F`, `%5C`, `%2E`, `%25`, either case) or an escape that does not decode, and an address
    of the site outside the help folder read both as written and as a server decodes it (`&sol;`,
    `&period;` included); a link (`a`, `area`) to another site without `target="_blank"`, which would
    open the site in the frame.
  - The regenerated tree is byte for byte the committed one (242 files compared, 0 differ; the
    original's pages hold none of these forms).
- `imported.test.ts` checks the committed tree a second way: from every `<`, the tag up to the first
  `>` and up to the first `>` outside quotes, with `on...=` after white space, a slash or a quote;
  no `script`, `iframe`, `object`, `embed`, `svg`, `math`, `form`, `frame`, `applet` or `srcdoc`;
  `base` only as `<base target="_self">`; no refresh.
- Not refused: what a style sheet says. A `url(javascript:...)` in a style element runs nothing in
  today's browsers, and the import does not parse CSS; `javascript:` in a `style` attribute is refused
  with the rest of the tag.

## Contract

### C1. The editor's selection and caret are not in the contracts

- F1 in the editor needs the selected text and the text around the caret (editor-ui §15.3).
  `DocumentService` gives the document's text but not the selection or the caret, and the
  editor component's API is E2's. H1 reads the browser's own selection inside the region
  `data-e68-panel="editor"` (`features/help/editor-context.ts`): the selected text, or the line
  that holds the caret (`.cm-line` for CodeMirror). That works for CodeMirror 6 and for any
  contenteditable; it does not see a selection in a document that is not rendered.
- Wanted from W1/E2: a way to ask the active editor for `{ selected, text, caret }`, for example
  `DocumentService.selection(id)`. H1 would then replace the adapter's `readEditorWordContext`;
  nothing else changes. Filed as `docs/requests/H1-editor-selection.md`.

### C2. A feature cannot learn the port's version or its repository

- The About boxes show the version and link to the repository (1.4 note 11, O-14: not hard-coded).
  `buildInfo` is in `app/src/build-info.ts`, which a feature may not import (3.1), and `AppContext`
  has no field for it.
- H1 reads the version from the window title that the shell builds ("... - unofficial port
  <version>", `windowTitle` in `bootstrap.ts`; `portVersionFromTitle`) and falls back to the
  repository `gurmyd/easy68k-cross-platform` (until 2026-11-21 `gurmyd/easy68k-mac`; `DEFAULT_REPOSITORY` in `core/help/about.ts`), the address the
  task statement gives. Filed as `docs/requests/H1-build-info.md`.

### C3. There is no folder chooser in `FileDialogs`

- 5.8, desktop: "asks for a folder, copies them there and shows the open dialog in it". `FileDialogs`
  has `open` and `save` for files.
- H1 asks with `save` (title "Copy the Examples to (folder name)") and treats the name typed as the
  folder to create, then calls `open` with `startDir` set to it. A request for a real folder
  chooser (a `chooseFolder` member, DV2 and FS1) is `docs/requests/H1-folder-chooser.md`.

### C4. A modal dialog blocks the commands that would open help from it

- editor-ui §15.2: F1 and the Help button in the two option dialogs open `options.htm`.
  `CommandRegistry.run` does nothing while a modal dialog is open (3.12.2), and a feature may not
  import another feature's function.
- H1's `ed.help.help` and `sim.help.help` accept the page as their argument
  (`run('ed.help.help', 'options.htm')`), which works from a modeless dialog or from outside one. For
  a modal Options dialog E4 needs a way past the block; filed as `docs/requests/H1-help-from-dialogs.md`.
