Differences from EASy68K

This port is meant to behave like EASy68K v5.16.1 for Windows (the "original") in everything a 68000 program can notice: what a source file assembles to, the listing and S-record files, what an instruction does, the cycle counts, the TRAP #15 tasks, the pixels a program draws and the log files. The assembler and the simulator are the original's own C++ code, compiled for the browser.

Some things could not stay the same, because a web page or a Mac is not Windows, and some defects of the original's windows and dialogs were fixed on purpose. This page lists every such difference and why it exists. You can also open it from the application: Help > Differences from EASy68K.

What could change the results of a program

Most differences below concern only the editor and the simulator's windows. These are the ones a program can notice. If your program or your course depends on one of them, read its note.

  • Speed. The simulator runs about 1,000,000 instructions per second on every computer (the original ran as fast as the PC allowed, roughly 0.3 to 3 million). A delay made of a counting loop therefore takes the same time everywhere. Options > Execution Speed... changes it. Delays made with TRAP #15 task 23 take exactly 10 ms per unit. (Part SH8 below.)
  • When keys and mouse clicks arrive. A key press or a click reaches the program between groups of at most 2000 instructions, not after every single instruction. (Part SH8.)
  • Key codes on keyboards that are not US English. TRAP #15 task 19 reports the key by its position on a US keyboard: on a French keyboard the key labelled A reports $51 (Q). Typed characters (tasks 2, 4, 5, 18) are not affected. (Part SH4.)
  • Characters. A character that Windows-1252 does not have (Greek, Cyrillic, emoji) is not delivered at all; the original delivered ?. On a Mac, Option+key types the Mac character, and pasting into a running program is Cmd+V instead of Shift+Insert. (Part SH4.)
  • One key is taken from programs: Ctrl+Alt+O (Ctrl+Option+O on a Mac) always moves the keyboard out of the Output panel, so that nobody can be trapped there (note 44).
  • Files. A program reaches only the files in its own folder and the folders it was given, not the whole disk. In a browser those files are kept by the browser (My Programs) or in a folder you opened; the file name task 58 returns looks like /browser/demo/data.txt instead of C:\.... (Note 46, parts SH6, FS2 and DV2.)
  • Serial port and network (TRAP #15 tasks 40-43 and 100-107) work only in the Mac app. In a browser they return the original's "not available" results (note 37).
  • The Output window is at most 4096 x 4096 pixels (part SH1), and Windows' system colours are those of a default Windows 11 desktop (parts SH1 and SH3).
  • Text in the outline fonts (Courier New, Lucida Console, Consolas) has the original's sizes and positions but not quite its pixels (part SH3). The default font, Fixedsys, is exact.
  • Execution logs: a listing line that contains % is written as it is (the original printed garbage there), and the date in the header is always in the US format (part U4, note 42).

1. Changes decided in the design

Copied from section 1.4 of docs/ARCHITECTURE.md. The note numbers are the ones the rest of this document and the specifications refer to ("note 12").

  1. File dialogs depend on the file backend (3.8): the browser store has its own dialog; the File System Access backend and the desktop app use system dialogs. Filters and default extensions are the original's. A name typed without an extension gets .X68 when the first filter is selected (editor-ui §6.4 recommendation).
  2. Printing goes through the system print dialog (browser or macOS). Printer Setup... opens the same dialog, because web pages cannot open a separate printer set-up. Page content rules are kept.
  3. Close saves the document that is closing (the original saves the active one) and a cancelled Save As cancels the close. GUI defect, editor-ui §19.3.
  4. Exit. Desktop app: quits after the close prompts. Web: runs the close prompts, saves settings, stops logs and shows an empty workspace with the text You can close this tab.; a page cannot close its own tab.
  5. Undo/redo uses the editor component's history instead of the original's one-record-per-keystroke stacks with their defects (stale redo, overtype not recorded, corrupting comment undo). Nothing a program can observe depends on it.
  6. Comment / uncomment / indent / outdent act on the caret line when nothing is selected; undo is correct. Otherwise editor-ui §8.5 exactly (column 0 only, one character per command).
  7. Find starts at the caret when nothing is selected (the original restarts from the top of the document). End of document reached. and the restart from the top after it are kept. Replace does not replace a selection that is not a match; an empty replacement does not skip a character.
  8. Option dialogs: Cancel restores everything; the Editor Options size box shows the document's real size; the modified flag is not touched by OK; F1 and Help open options.htm (the evident intent) instead of the introduction page.
  9. MDI becomes tabs. Cascade, Tile Horizontally and Tile Vertically choose between one pane and two panes. Arrange and Minimize All act on minimised child windows, which do not exist in a tabbed interface; the items stay in the menu, disabled, so that the menu matches hand-outs.
  10. Help is the original HTML, shown in a Help panel (web) or a help window (desktop). Entry points that the original sends to the introduction page by mistake (SIM_BASIC, SIM_OPTIONS, MEMORY in the memory window, EDIT_OPTIONS) open the page they were meant to open (sim-ui §16.1).
  11. About boxes keep the original texts and add the port's name, version, repository link and the statement that the port is unofficial. Check compares with the port's latest GitHub release. The B-M-W Easter egg needs a picture of unknown origin from the binary form file and is dropped. F1 in the simulator's About box does nothing.
  12. Tab key with Assembly tabs at column 12, 20 or beyond 43: the original inserts nothing; the port advances to the next stop (12 > 20 > 44 > next multiple of the fixed tab size). Shift+Tab deletes the blanks before the caret back to the previous stop (the original treats it as Tab). This changes what is typed, never how a file is assembled or listed.
  13. Swallowed keys. The original blocks Ctrl+Backspace, Ctrl+Delete, Ctrl+E and every Ctrl+Shift combination to work around its edit control. The port lets the standard editing keys work.
  14. Menu mnemonics work where the browser delivers Alt+letter. F10 never opens a menu (it is Auto Trace).
  15. untitledN numbers do not skip.
  16. Line numbers and inline markers are additions. Line numbers can be switched off (View setting in Editor Options, General).
  17. Status bar: the fixed 64-underscore ruler has no meaning without a fixed window width.
  18. Messages: the assembled document keeps its identity while include files are opened for their messages (the original lets the include file steal the active window, so later messages, the dialog title and Execute refer to the include file).
  19. Highlighting has no 400 ms delay and is not limited to visible lines. The Auto preset follows the light or dark theme and is the default; choosing any original preset or colour behaves as in the original in both themes.
  20. Execute gives the program a simulator in start-up state, as the original does by starting a new simulator process: the window's simulator is shut down the way SIM68K exits and started again (4.7.1), then the file is loaded like a command-line file. Nothing of an earlier program is left - no memory-map range, output size, pen position, breakpoint or open port. The original leaves the earlier simulator windows open; the port has one simulator per window, so if a program is running or waiting there, the Caution question of sim-ui §8.4 is asked first (not when it is stopped or halted; O-16). A second window keeps the old one (note 43). Execute is enabled when the engine reports it (AsmResult.executeEnabled) and this assembly wrote the S-record (4.9 step 9; erratum E5 1).
  21. Settings files next to the executable cannot exist in a web page or a signed app bundle. Positions and sizes of Windows windows ($main top and its neighbours, the simulator's window lines) and the $maximized edit flag have no meaning in a tabbed single window; they are ignored on import and written with the original's defaults on export.
  22. Open and Reload stay enabled after a halt and while a program runs (the original disables Open after a halt until Pause or Rewind). While a program is running, Open asks the Caution question first. Run, Run To Cursor, Auto Trace, Step Over and Trace Into keep the original's disabled state after a halt; their tool-tip then reads Program halted. Rewind or Reload to run it again.
  23. Run To Cursor runs only when a valid instruction row is selected; after either error box the original runs anyway (sim-ui Q5).
  24. Pause during Auto Trace always re-enables the run commands (sim-ui Q9).
  25. Log Start cannot use Ctrl+F4 in a browser on Windows or Linux (it closes the tab).
  26. EASyBIN is a mode of the same application, not a separate process.
  27. Font dialogs are the port's own. The Output Window Font list is limited to the fixed-pitch fonts of the measured metric table (3.5.1: Fixedsys, Courier, Courier New, Lucida Console, Consolas), because the text grid depends on those measurements. Colour and style choices behave as in trap15-a §3.2.
  28. Auto Trace Options: the saved interval is applied at start-up (sim-ui Q16).
  29. Fullscreen Options: a web page and a single-window app cannot place the output on a chosen monitor. The dialog is kept with its text; it accepts only 1. The original resets the choice on every load anyway and never restores it from the settings file.
  30. Ctrl+Tab is reserved by browsers. F2 replaces it, except in the Output panel, where F2 belongs to the program and Ctrl+Alt+O moves on (note 44). The desktop app also has Ctrl+Tab itself.
  31. Registers that changed since the previous stop are shown in the accent colour (added; can be switched off). Values and refresh moments are the original's.
  32. Cycle counter shows the full 64-bit value. The original formats it with a 32-bit conversion (sim-ui Q18, unverified on the binary); Overflow above 2^48-1 is kept.
  33. Horizontal scrolling of the listing is ordinary scrolling.
  34. Simulator status bar is used for run state; the original's is always empty.
  35. Output panel cannot be closed, only collapsed, so "showing the window" always succeeds.
  36. Full screen in a browser needs a user gesture. When a program asks for it (task 33, D1.L = 2) without one, the Output panel shows Press any key or click to enter full screen and enters on the next key or click; task 33 results are unaffected. In Safari and Firefox the Esc key leaves full screen and does not reach the program; in Chromium browsers and in the desktop app it reaches the program, as in the original (2.5).
  37. Serial and network in the browser: task 40 returns 2, tasks 41-43 return 3; tasks 100 and 101 return $276B0002, 102 and 106 $276D0001, 103 and 107 return 0 with 0 bytes, 104 and 105 $276D0001 (trap15-a §6, trap15-b §12.4 option 1).
  38. Memory live update fixes the unsigned-wrap defect at address 0 (sim-ui §10.4).
  39. Open clears PC breakpoints only when a file was chosen (sim-ui Q12).
  40. Advanced breakpoints: the editor defects of sim-ui §12.2 are fixed (slot mix-ups on Clear and edit, five-character Backspace, draggable rows, editable lists, stale indexes: deleting a condition renumbers the references in existing expressions and removes expressions that used it, after a confirmation). Count is read as decimal. The evaluation rules, including count 0, A7 = user stack pointer, last-read/last-write matching and the parenthesis conversion, are the original's because the engine evaluates them and they decide where a program stops.
  41. Log Start after Cancel or a failed open leaves logging off (the original writes through a null file, sim-ui Q22).
  42. Log contents are the original's, including the stale-snapshot rule for the Rewind/Reload notes (sim-ui Q24). One exception: a listing row is written literally, not used as a printf format (sim-ui Q23, sim-core §11.7); rows containing % differ from the original's undefined output.
  43. Several simulators. The original is two programs that can each be started any number of times. The port is one window holding one editor and one simulator, and any number of such windows (browser tabs, New Window in the desktop app); they share settings and the browser store safely (3.8.6). Two simulators that talk to each other over the network are two windows of the desktop app.
  44. Keys in the Output panel. The program receives every key the original's I/O window receives (2.9.4). The port takes exactly one chord away from programs: Ctrl+Alt+O, which moves the keyboard out of the Output panel in every state, so that a keyboard-only user is not trapped after task 24. The chords the port added elsewhere (F2, F4, Shift+F<n>) are not active there.
  45. Paste from the menu, toolbar or context menu in a browser has no key event to ride on and must ask the browser for the clipboard: Chromium asks for permission once, Safari shows a small Paste confirmation each time. If the browser refuses, a toast says Press Ctrl+V to paste (Cmd+V on macOS). The keyboard chords and the desktop app are not affected.
  46. Files of a 68000 program. Names are matched as on Windows (either slash, any letter case). A name with a drive letter, and a name that leaves what the program may reach (3.8.4), does not resolve; the program gets the original's result for a missing file. The path task 58 returns is the port's own (/browser/demo/data.txt, or a real path in the desktop app), not a Windows path. Written data becomes visible when the original's C library would have written it (3.8.4).

Differences from the original introduced by FS1

(docs/differences/FS1.md)

None of these changes what a student's program can observe.

  • Dropped files are copied before they are opened (browser). The original opens a dropped file where it lies. A browser gives the page the file's bytes but no path it can keep, so the port copies it into My Programs/Imported/ and opens the copy; saving writes the copy. Use Export... to take it out again. The desktop app opens a dropped file where it lies, as the original does, and shows the Open dialog in a dropped folder.
  • Names that differ only in letter case are one name in every store. As on Windows, Rename... refuses a name that exists in another spelling, and Import... and dropped files replace (after the question) the file that is already there under another spelling, keeping its spelling, instead of adding a second spelling beside it.
  • A dropped .S68 brings its listing along. The original loads only the first dropped file. The port still loads only that one, but also copies a dropped .L68 with the same base name into the same folder, so that the simulator finds the listing beside the program instead of showing the nine explanatory lines.
  • A dropped .S68 in Simulator mode may ask one more question (browser). As in the original, The current debug environment will be lost, click OK to continue. (Caution) comes first when a program is loaded, and Cancel leaves everything as it was. After OK the port copies the file into My Programs/Imported/ before loading it; if an earlier copy with other contents is already there, "My Programs/Imported/<name>" already exists with other contents. Replace it with the new file? (title Drop) is asked then. The desktop app loads a dropped .S68 where it lies and asks only Caution, as the original does.
  • The port's own Open and Save dialogs (browser). They list the browser store ("My Programs") and an opened folder instead of the disk, offer From this computer... (and Open folder... where the browser can), and say in a short note where files are kept. Names are checked against Windows' rules (no \ / : * ? " < > |, no reserved device names, no trailing space or period) so that exported files work on Windows. Only one file can be chosen from the list; several files can be brought in at once with From this computer... where the opener asks for several.
  • The Files panel (an addition, 1.5): the browser store as a tree with New Folder..., Import..., Export..., Rename... and Delete. Delete and Import ask before removing or replacing anything.
  • A browser storage that is slow to answer does not hold up the start. After three seconds the application is shown and the Files panel says that My Programs is still opening; what is opened or saved meanwhile waits for the storage (at most 20 s, after which the session keeps files in memory and says so).
  • A full or blocked browser storage is reported. The original writes to the disk and shows the run-time library's error. The port says in plain words that the file was not saved and that nothing saved before is lost, or that the browser keeps no files at all (some private windows).

Differences from the original introduced by E1 (Documents)

(docs/differences/E1.md)

None of these changes what a program assembles to, its listing or its S-record.

  • Close saves the document that is closing, and a cancelled or failed save (cancelled Save As, a refused write, Cancel at the Windows-1252 question, No at the save-conflict question) cancels the close and an Exit (1.4 note 3). The original saves the active document and closes anyway.
  • untitledN numbers increase by one per new document; the original also counts opened and reloaded files (1.4 note 15).
  • Enabled state is computed from the active document: Save, Save As and Close File need an open document (also a list document, which is editable); Reload File needs a document with a name. The original keeps frame-wide flags that ignore the active document (editor-ui §2.7, §19.3).
  • Open allows several files to be chosen at once and starts in the folder of the active document; each file is opened in turn as the original opens one.
  • Saving a file changed in storage since it was loaded or saved asks '<name>' has been changed outside this window. Save anyway? (3.8.6). The original overwrites.
  • Characters without a Windows-1252 byte (typed or pasted) are asked about once per document: This file contains N characters that EASy68K cannot store. They will be saved as "?". (3.9.3).
  • Local drafts of modified documents and the offer Unsaved changes from your last session were found for <names>. with Restore and Discard (3.9.4).
  • Unload guard: the browser's "leave site?" prompt while a document is modified.
  • Exit on the web ends with an empty workspace and You can close this tab. (1.4 note 4).
  • UTF-8 notice: a file that is valid UTF-8 with multi-byte sequences opens as its Windows-1252 bytes, as in the original, with the notice This file looks like UTF-8. EASy68K reads it as Windows-1252. (5.1).
  • Write failure shows Cannot create file "<path>". <reason>; the original shows the VCL's exception message.
  • Reopening an already open file replaces it in its own tab (the original closes the window and opens a new one at the end).
  • A trailer line too short to read (*~Tab size~4 without its closing ~, erratum 2): both show Error in LoadFile() and keep the line in the text. The original's window is then left half set up (no repaint, no caption, no tab stops, possibly modified); the port opens the document normally. Derived from the source, not checked against the binary.

Differences from the original introduced by SH5 (sound)

(docs/differences/SH5.md)

What a 68000 program observes through TRAP #15 tasks 70-77 is the original's (trap15-b §11 and §13): every D0 result, the cases in which D0 is not written, the standard player's busy flag, currentWave, the sticky looping of a DirectX slot and what a reset keeps. The differences below are in what is heard, or in cases the original leaves undefined.

  • The standard player's busy time comes from the WAV header. The original asks Windows whether a sound is still playing; the port computes start + duration from the file's fmt and data chunks (parseWav), so a program's wait loop ends on time even when the browser plays nothing (audio locked before the first click, a suspended context, a sound that cannot be decoded). Windows' own buffering makes its busy time a little longer than the sound; the port's is the sound's exact length.
  • A file that exists but is not a WAVE file counts as a sound of length 0 for tasks 70 and 72/76: D0.W = 1 and the player is free at once (on Windows PlaySound may play the default system sound instead; trap15-b V14, unverified). Nothing is heard.
  • The DirectX player (tasks 73, 74, 75, 77) accepts RIFF WAVE files only. MIDI and DirectMusic segment files, which DirectMusic also loads, give '<name>' Error loading and D0.W = 0 (ARCHITECTURE.md 3.7). A WAVE file whose codec the browser cannot decode loads (D0.W = 1) and is silent.
  • One decoded sound per DirectX slot. DirectMusic's loader cache may make two slots loaded from one file the same object, and may keep a slot's looping across a reload and a reset (trap15-b §11.4, V6, unverified). The port keeps each slot separate; looping stays set for a slot until the slot is loaded again or the simulator is reset, the recommended port behaviour.
  • Task 74 over a slot whose sound plays. The original releases the old segment without stopping it; the port lets the old sound play on too, and stops a sound left looping that way at the next simulator reset (in the original it is unspecified whether it ever stops).
  • Task 73 sounds stop at a cold start (a new simulator), because the original's process has ended by then; a reset (Rewind, opening a program) does not stop them, as in the original.
  • A sound that had to wait is heard in step with the program. A sound asked for while audio is locked or suspended starts, once audio runs, where it would be by then; a sound whose time is over by then is not played at all, and a loop joins at the right place. Uncompressed WAVE files (every official sound) never wait for a decoder; a compressed one (ADPCM, mu-law ...) may wait for the browser's decoder, and a wait of less than 0.2 s starts it from its beginning. If the standard player's next sound starts while such a late sound still plays, the late one is cut off at that moment: the original's one voice never sounds two sounds at once.
  • At most 64 sounds at once. A program that starts more overlapping sounds than that (task 75 in a tight loop) is not heard beyond the 64th; the results in D0 are unchanged.
  • Unlocking. Browsers start audio only after the person has clicked or pressed a key: every run command, every key in the Output panel and any click or key in the window once a sound is waiting unlocks it. Until then programs run as usual and are silent.

Differences recorded by T3 (simulator conformance)

(docs/differences/T3.md)

What the port does differently from the official EASy68K v5.16.1 simulator where a student could notice it, found or settled by the conformance suite (tests/conformance/sim). The per-mismatch list with evidence is tests/conformance/sim/MISMATCHES.md; the owners are in tests/conformance/sim/known-differences.json.

R-16: the execution-log lookup that runs past the last listing row

  • Original (sim-core §8.3): lineToLog() starts its binary search with botIndex = Count, so Strings[Count] can be read; the VCL then throws EListError, exec_inst catches it, and the instruction whose opcode was fetched is not executed.
  • Port: the engine keeps the same code (engine/sim/shim/form1.cpp); its TStrings::Strings[] (shim/vcl/vcl.h) throws EStringListError for an index at or past Count, which the same catch (...) of exec_inst receives. By construction the outcome is the original's.
  • Not reached by any program of the suite: the last rows of a listing are the symbol table and the error count, whose first eight characters sort after every address in the locale order the engine imitates (digits before letters), so the search turns down before it reaches Count. No golden can show the case; it stays a statement about the code.

Text in execution logs with %

  • Original: a listing row is the format string of fprintf (sim-ui §19 Q23), so %d, %s and the like print whatever the stack holds.
  • Port: the row is written literally (engine/sim/PATCHES.md, 11.7).
  • Evidence: logs/l14-percent-in-listing (see MISMATCHES.md for what the official program wrote).

Tasks 0 and 1 with a negative count on a string longer than 255 characters

  • Original (trap15-a §12 item 8; T4's report D1): with D1.W negative the text is copied with strncpy into a 256-byte buffer without a terminating NUL, so after the 255th character the output can carry whatever the host stack holds. trap15-a/a55-task0-negative-count-first printed 255 characters and the byte $C0 after NOP and MULU, and exactly 255 after MOVE.L (SP)+ and RTS; with other host calls before it (trap15-a/a05) always exactly 255.
  • Port: always exactly 255 characters (the engine's P24 ends the buffer at character 255).
  • Nothing a program can rely on: the extra byte is residue that depends on the Borland code that ran before. Accepted (owner: the engine; known-differences.json).

Differences introduced by DV3 (macOS packaging and release)

(docs/differences/DV3.md)

Nothing in this package changes what a student's program can observe. The differences are in how the macOS app reaches a user and how it starts the first time, compared with the Windows original, which is a set of .exe files that Windows starts without any of this.

1. The first start of the downloaded Mac app (section 11)

The Mac app is signed ad hoc: it carries a valid signature that proves the files are unchanged since the build, but no Apple Developer ID, and it is not notarised by Apple (ARCHITECTURE.md 7.6, section 11). macOS marks every file downloaded with a web browser as "quarantined", and Gatekeeper refuses to open a quarantined app that Apple has not notarised. This is the text the README and every release note carry (desktop/scripts/release.mjs copies the part between the two marks into the release notes):

The Mac app is not notarised by Apple (the project has no paid Apple developer account), so macOS blocks it the first time. This happens once; after that EASy68K opens like any other app. If you cannot or do not want to do this (for example on a Mac managed by your school, where these settings may be locked), use the web version instead: it does the same in Safari or Chrome and needs no installation.

The Mac app needs macOS 13 (Ventura) or later.

Install. Download the .dmg for your Mac (arm64 for Apple silicon, M1 and later; x64 for Intel; Apple menu > About This Mac tells you which), open it and drag EASy68K into Applications. (Or download the .zip, which macOS unpacks into EASy68K.app, and move that into Applications.)

What you will see. When you open EASy68K for the first time, macOS shows a message instead of starting it. On macOS 15 (Sequoia) and later it reads "“EASy68K” Not Opened. Apple could not verify “EASy68K” is free of malware that may harm your Mac or compromise your privacy.", with the buttons Done and Move to Trash; older versions say "“EASy68K” cannot be opened because the developer cannot be verified." Some versions instead say that "“EASy68K” is damaged and can't be opened". The app is not damaged: this is how macOS words the same block for an app that is not notarised. Click Done (or Cancel), never Move to Trash.

Way 1: System Settings (for the "Not Opened" or "developer cannot be verified" message)

  1. Open System Settings (Apple menu > System Settings) and choose Privacy & Security in the sidebar.
  2. Scroll down to the Security section. It shows "“EASy68K” was blocked to protect your Mac." (The line appears for about an hour after you tried to open the app; if it is gone, try to open EASy68K once more.)
  3. Click Open Anyway and confirm with your password or Touch ID.
  4. Open EASy68K again. macOS asks a last time; click Open Anyway (or Open).

On macOS 14 (Sonoma) and earlier you can instead Control-click (or right-click) EASy68K in Applications, choose Open from the menu and then click Open in the message.

Way 2: Terminal (works for every message, including "is damaged")

  1. Open Terminal (Applications > Utilities > Terminal).
  2. Paste this line and press Return. It removes the quarantine mark from the app, and asks for nothing:
xattr -dr com.apple.quarantine /Applications/EASy68K.app
  1. Open EASy68K as usual.

If you put the app somewhere else than Applications, use its path in the command instead (you can type xattr -dr com.apple.quarantine and then drag the app onto the Terminal window).

Not yet seen on a Mac by this package: the wording of the messages above is taken from Apple's documentation and from reports of other ad-hoc signed apps, and the exact dialog on each macOS version is an item of the manual test (ARCHITECTURE.md 6.8, docs/MANUAL-TEST-MAC.md, owner DOC1: "First launch of the downloaded app: the Gatekeeper dialogs and the documented way through them"). Whoever runs it corrects this section, and the README, with what the screen says.

What GitHub's macOS runners have shown (release.yml runs 44938987022 and 44939698734, both architectures, through desktop/scripts/check-downloads.mjs): the app inside the .zip (unpacked with ditto) and inside the .dmg passes codesign --verify --deep --strict and is byte for byte the bundle the packaged checks tested (same CDHash); the .dmg holds the Applications link; the minimum is macOS 13.0. With the quarantine mark a browser sets, Gatekeeper's assessment (spctl --assess --type execute) rejects the app, and syspolicy_check distribution reports "Notary Ticket Missing". So the block described above does happen, and it is the not-notarised block, not a broken signature. A runner cannot show the dialog itself; its exact wording stays an item of the manual test.

2. Two downloads instead of one

The original is one Windows installer. The port's Mac app comes as two builds, Apple silicon (arm64) and Intel (x64), each as a .dmg and a .zip (1.1). There is no universal build: each download carries only the code of its processor, including serialport's native module, which is reduced to that processor (desktop/scripts/after-pack.mjs).

3. Version and the About box

The app's version (Finder's Get Info, CFBundleShortVersionString) is the port's own version from the root package.json (7.5), not 5.16.1. What a program or a file can observe keeps the original's values (1.2).

4. No automatic updates

As 7.6 says, the app has no updater. A new version is downloaded from the releases page; the About box's update check only says whether one exists (7.5).

Differences from the original introduced by B1 (EASyBIN)

(docs/differences/B1.md)

None of these changes a byte that EASyBIN loads into memory or writes into a file: Open S-Record, Open Binary, Save S-Record, Save Binary, Copy and Fill give the original's results, quirks included (docs/porting/easybin.md 19), checked against the original's own functions compiled natively.

  • A mode, not a program. EASyBIN is the third mode of the application (ARCHITECTURE.md 1.4 note 26). Its memory image lives as long as the window and is kept when the mode is switched. Simulator View > EASyBIN switches to the mode instead of starting EASyBIN.EXE.
  • Exit ends the whole application, as Exit does in Editor and Simulator mode: the editor's save questions come first. The original ended only EASyBIN, without a question.
  • The window title is EASyBIN's caption (EASyBIN v2.5.0, or the path of the opened file), as in the original, followed by the port's - unofficial port <version> like every title of the port.
  • File dialogs are the port's (ARCHITECTURE.md 3.8.5). Their Open dialog does not return a name that does not exist, so error: cannot open file ... and Error openning ... appear only when a chosen file cannot be read. Paths are the port's (/browser/...), also in messages and the caption.
  • Dropped files are read directly in a browser (nothing is copied into the browser store); the caption shows the file's name without a folder.
  • Help opens easybin.htm in the Help panel. The start-up messages about help.chm and HTML Help do not exist. F1 in the About box opens the credits page in the Help panel behind the box (the original opened it in the separate help window).
  • About EASyBIN keeps the original's texts and adds the port's name, version and the statement that it is unofficial.
  • Beep is a short quiet tone (no system sound in a browser).
  • The memory area can also be reached with Tab; when it gets the focus the cursor is put on a cell (column 10) if it was not on one. The cursor is shown while the area has the focus, and it does not blink with reduced motion (2.11).
  • The tab order follows the layout; the original's went to Length before First Address and to Size and Copy before From and To.
  • The $7F character of the ASCII column is drawn as □ (Courier New has no glyph there; a browser would draw nothing and shift the column).
  • Colours of the bytes follow the theme: file 0 = text colour, file 1 = olive, file 2 = the success green, file 3 = the accent blue, out of range = muted text, past the end = the error colour (the original: black, olive, green, blue, gray, red on white).
  • Keys typed into the memory area are Windows-1252 characters; a character outside that code page is refused with a beep. On macOS, Cmd+key is left to the menus and the browser; Ctrl+letter types the control character as on Windows.
  • The mouse wheel: one row per notch as in the original; touchpad deltas add up to rows, and a change of direction starts afresh.
  • Copy downwards past the end of memory stops with Invalid copy range and keeps what it copied, as the original does; the port also shows those bytes at once (the original did not repaint).
  • The Open S-Record... and Save Binary... buttons in the two groups have these names as tool-tips and accessible names; the original's glyph buttons have no hint.

4. Not yet confirmed against the original

The behaviour of the original was worked out from its source code and checked by running the official EASy68K v5.16.1 under Wine. Some details cannot be settled that way; the specifications mark them UNVERIFIED and the port does what the specification recommends. Until they are confirmed on real Windows (decision O-2 in docs/ARCHITECTURE.md, section 10.2), they are listed here as not yet confirmed:

  • the open items of docs/porting/trap15-tasks-0-59.md section 12 (TRAP #15 tasks 0 to 59), among them whether the font of task 21 survives Rewind and Reload (part SH3 above);
  • the open items of docs/porting/trap15-tasks-60-up.md section 15 (drawing, sound, keyboard and mouse), among them how Windows draws ellipses (R-2), the flood fill's drawing mode (part SH1) and what DirectMusic does with two slots loaded from one file (part SH5);
  • docs/porting/hardware.md section 12 (the hardware window), docs/porting/sim-core.md section 13 (the simulator core), docs/porting/assembler.md section 12 (the assembler), docs/porting/editor-ui.md section 22 item 12 and the rows of the quirk register in docs/porting/sim-ui.md section 19 that are marked UNVERIFIED;

  • the cases the conformance suite records as unconfirmed in tests/conformance/sim/known-differences.json, with the evidence in tests/conformance/sim/MISMATCHES.md.
