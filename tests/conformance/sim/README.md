# Simulator conformance suite

The port's simulator against the official `SIM68K.exe` v5.16.1 (layer L4 of `docs/ARCHITECTURE.md`
6.1, the checklists of 6.4). Owner: work package T3.

Every program here is run twice: in the official simulator under Wine
(`tests/oracle/wine/sim`, `npm run oracle:wine:sim`), which writes the goldens, and in the port by
the headless harness (`harness.ts`), and the two results are compared byte for byte.

```sh
npx vitest run --config tests/conformance/sim/vitest.config.ts            # all (part of npm run test:conformance)
EASY68K_SIM_ONLY=trap15-a npx vitest run --config tests/conformance/sim/vitest.config.ts
EASY68K_SIM_REPORT=1 npx vitest run --config tests/conformance/sim/vitest.config.ts   # also MISMATCHES.md
npx prettier --write tests/conformance/sim/MISMATCHES.md                   # then format it (format:check)
EASY68K_CONFORMANCE_PARTS=final npx ...      # ProgramFiles and LogService at their final paths (gate I2)
node tests/conformance/sim/generate-instructions.mjs                      # rewrite instructions/g-*.X68
```

## Programs

| Folder          | What                                                                                                                                                                                                                              | Recipes          |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| `instructions/` | every instruction group of sim-core 3.16: `g-*` generated by `generate-instructions.mjs` (random operands and edge values, random condition codes, cycle count per case), `p*` the first proof programs of official-oracle.md 5.1 | report           |
| `exceptions/`   | the catalogue of sim-core 3.9 with exceptions enabled: frames, stacked PCs, cycles, quirks                                                                                                                                        | report           |
| `trap15-a/`     | the items of trap15-a §13 that a program can check by itself: text output and the text array (task 22), the cursor, tasks 3, 15, 17, 20, 30-33, the file tasks, the memory map, serial without a port, T4's defect D1             | report, outlog   |
| `trap15-b/`     | trap15-b §15 V1-V9 and §5-§7 where Wine's GDI draws what Windows draws: flat areas, raster operations, pens, pen positions                                                                                                        | report           |
| `hardware/`     | hardware §13 items a program can check: device bytes, task 32, auto interrupts, masks, STOP                                                                                                                                       | report           |
| `quirks/`       | the "affects program results" quirks of sim-ui §19 and sim-core that a program can observe                                                                                                                                        | report           |
| `logs/`         | execution logs of all three types, with and without the output log                                                                                                                                                                | log:N, log:N+out |

A program's first comment block names what it checks (`* @item`), how it runs (`* @recipe`,
`* @switches`, `* @files`, `* @timeout`) and, as a hint, who would own a difference (`* @owner`);
`programs.ts` reads it. A self-reporting program writes `result.bin` with the routines of
`dumplib.X68` (registers, memory, cycles, the text cursor, task 22 rows, values) and ends it with
`END-OF-DUMP`.

## Files

| File                                  | What                                                                                            |
| ------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `programs.ts`                         | the program list and headers, golden names, manifest types, masking (also used by the oracle)   |
| `harness.ts`                          | the headless harness of 6.4: `assembleConformance`, `runScenario`                               |
| `doubles.ts`                          | ProgramFiles and LogService doubles while SH6 and U4 are being written                          |

| `programs.test.ts`, `harness.test.ts` | the programs and the harness themselves                                                         |
| `checklist.test.ts`                   | checklist items without a golden (panel clicks, Trace Into, keys, Rewind, memory map), headless |
| `known-differences.json`              | every accepted mismatch with its owner and cause                                                |
| `MISMATCHES.md`                       | the last report of mismatches (generated)                                                       |
| `golden/`                             | the official results (generated by the oracle; see its README)                                  |

## Rules

- A mismatch is a finding. It is reported with its evidence and assigned to an owner in
  `known-differences.json`; the golden is never adjusted. A listed difference that disappears
  fails the test until its entry is removed.
- The harness starts a program as the oracle does: a load with the origin `commandLine` and the
  switches `/r`, `/e`, `/b` (sim-ui §8.1); a log is started with the log part's `start()`, then Run or
  Auto Trace (10 ms, display update off).
- An owner is the engine or a host package (`OWNERS` in `compare.ts`): the party that acts. A
  defect of the harness is repaired, not listed. A result seen only under Wine is listed with the
  package that acts if Windows agrees, and marked `unconfirmed` with what would confirm it.
- With `EASY68K_CONFORMANCE_PARTS=final` (or `parts: 'final'`) the program's folder is one in-memory
  view shared by the real ProgramFiles, and the logs are the files the real LogService writes beside
  the program; the outcome reads both back.
- Text-grid programs run with Wine's cells (see `harness.ts`); with `metrics: 'windows'` the
  harness uses the application's glyph provider instead.
